- [x] **2.4. Внешних CDN больше нет** ✅ 28.09. Хостов оказалось не три, как
      значилось в плане, а пять: кроме Tailwind, Font Awesome и jQuery админки
      тянули DataTables (`cdn.datatables.net`), SortableJS и Select2
      (`cdn.jsdelivr.net`). Четыре положены локально из npm; пятый, Tailwind,
      закрыт сборкой — по решению владельца.

      **Почему Tailwind нельзя было просто «положить рядом».** `cdn.tailwindcss.com`
      отдаёт не стили, а компилятор: он разбирал разметку заново в браузере
      каждого посетителя на каждой загрузке. Теперь css собирается заранее
      (`npm run build:css` → `public_html/assets/css/app.css`, 118 КБ) и лежит в
      репозитории. **На сервере node не нужен** — приезжает готовый файл; это и
      делает сборку приемлемой для PHP-проекта.

      **Риск, из-за которого пункт стоял:** Tailwind видит только имена классов,
      написанные целиком, — склейки вида `'bg-' . $color` в сборку не попадают и
      стиль исчезает молча. Поэтому риск не «оценён», а закрыт проверкой:
      `.tools/tailwind_classes_lint.py` вытаскивает из всех `class="…"` (включая
      литералы внутри PHP-тернарников) **1 407** утилит и требует найти каждую в
      собранном css. Сейчас нет ни одной пропажи. 17 исключений внесены поимённо
      с объяснением: 8 — это Bootstrap из вьюх `*_bootstrap_5_3.php`, 3 — имена,
      которых в Tailwind нет вовсе (`focus:shadow-outline` из v1, `animate-ring`,
      `order` без значения), 6 — утилиты v4 в проекте на v3 (см. следующий пункт).

      Второй страж — в CI: css пересобирается и сверяется с репозиторием, как
      реестр модулей. Правка вьюхи без пересборки не проедет.

      **Шестой хост нашёлся уже после**: `security.php` в `nj599_account`
      рисовал QR для двухфакторной аутентификации картинкой с
      `api.qrserver.com` — то есть отправлял секрет TOTP в адресе запроса на
      чужой сервер и в его логи. Теперь QR рисуется в браузере той же локальной
      библиотекой, которой с самого начала пользуется `nj530`.

      Попутно: четыре инлайновых `tailwind.config` в разных шаблонах (они уже
      разошлись — у `nj601/finish.php` конфига не было вовсе) заменены одним
      `tailwind.config.js` с объединением настроек.

**Результат этапа:** −10 зависимостей, −496 КБ из публичного корня, −3 внешних хоста,
минус один мёртвый модуль. Поведение не меняется ни в одном месте.

## Этап 3. Пятый контракт: модуль объявляет себя сам — 3–5 дней. Главный этап

Это то, ради чего всё остальное. Приём уже изобретён в проекте: манифест
`config/nj_module.php` инвертировал зависимость для **меню**. Применяем его к **данным**.

Расширяем манифест секциями, каждая из которых убивает один чужой реестр:

```php
// application/modules/njXXX_slug/config/nj_module.php
'worker'    => ['channels' => [...]],  // → убирает channels_ui из конфига nj120
'reconcile' => [...],                  // → убирает 35 SQL из конфига nj120
'schedule'  => [...],                  // → убирает расписания из конфига nj603
'cleanup'   => [...],                  // → убирает 32 таблицы из nj100_cleanup
'recent'    => [...],                  // → убирает 14 SQL из Dashboard.php
'health'    => [...],                  // → убирает 10 таблиц из Errors.php
'search'    => [...],                  // → убирает 9 SQL из Search.php
```

Порядок — по убыванию опасности:

- [x] **3.1. `reconcile` + `worker.channels`** ✅ 28.09: 27 каналов в манифесты 24 модулей, конфиг nj120 со 183 строк до 38.
- [x] **3.2. `schedule`** ✅ 28.09: 14 расписаний, конфиг nj603 со 158 строк до 36.
- [x] **3.3. `cleanup` + `health`** ✅ 28.09: 11 чисток (конфиг nj100 со 112 строк до 27) и 10 источников «хвоста ошибок».
- [x] **3.4. `recent` + `search`** ✅ 28.09: 6 источников ленты из Dashboard и 9 источников
      глобального поиска из nj100_search (199 строк сервиса → 154). Перенос SQL доказан
      механически: запросы пересобраны из манифестов и побайтово сличены с прежними —
      9 из 9 совпали и для вошедшего пользователя, и для анонима.
- [x] **3.5. Сборщик реестра с кэшем** ✅ 28.09: `Manifest::all()` собирает 66 манифестов
      один раз и кладёт в `Kohana::cache` на час, `Manifest::reset()` инвалидирует
      (закрывает п. 4.5 вчерашнего анализа про отсутствие кэша). Попутно найдена
      мина: выкладка **не чистила** `application/cache`, поэтому новый модуль,
      изменённое расписание или снятый с раздачи источник поиска подхватывались
      бы только через час. `bin/deploy.sh` теперь чистит кэш сразу после
      обновления кода.

**Результат этапа (достигнут 28.09):** чужих файлов при добавлении модуля — с 7 до 1;
осталась одна строка в `application/bootstrap.php`. Правило «модуль
владеет своими таблицами» становится исполнимым, а не благопожелательным. Удаление
модуля = удаление одной папки. `AGENTS.md` §11 («производные данные — по реестру»)
распространяется с одного `nj115` на всю платформу.

## Этап 7. Развилка, которую надо пройти владельцу

Не инженерная задача, но от неё зависят приоритеты всего продуктового бэклога.
В одном монолите живут два бизнеса с противоположной экономикой:

| | Хаб утилит | LLM-конвейер B2B |
|---|---|---|
| Состав | 16 сервисов с `auth=FALSE` | профиль, досье, письма, лиды, отрасль, вакансии, радар |
| Себестоимость запроса | ноль | рубли за прогон (21 канал) |
| Источник спроса | поисковый длинный хвост | продажи, нужен аккаунт |

Они мешают друг другу: витрина из 60 бесплатных игрушек размывает доверие, нужное для
B2B, а трафик за UUID-генератором не конвертируется в досье на контрагента. Решение —
не «какой флагман собрать», а **какая модель основная**, и вторую ей подчинить
(утилиты как воронка с явным мостом, либо B2B на отдельный вход). Детали — §5,
суждение 5 в `OPINION-2026-09-28.md`.
