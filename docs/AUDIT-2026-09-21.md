## 1. Резюме

Платформа **архитектурно здорова**: 28 модулей `njXXX_*` в едином стиле
(init+Service+views+миграции+манифест+README/AGENTS), одна очередь (nj120),
питон-воркеры для всего тяжёлого, MCP-хаб, ACL config-driven, публичный UI — русский.
Размеры модулей скромные (140–350 КБ), vendor-библиотек всего 3 (mermaid, qrcode, three),
JS — инлайн по правилу «1 HTTP-запрос».

Серия инцидентов 21.09 вскрыла **системную дыру процесса**: контракт миграций
не проверялся ничем (broken файлы падали фаталом на проде слоями). Контракт
теперь описан в AGENTS.md §2.4 + добавлены grep-проверки в чек-лист перед пушем.

## 2. Архитектура (как есть)

```
Браузер ──HTTP──▶ Kohana (application/)
                   ├─ nj110_catalog  — меню/чипы/карточки из манифестов
                   ├─ nj100_search   — шапка-поиск (ILIKE по 6 таблицам) + /search/api
                   ├─ nj599_account  — TOTP 2FA, сессии, журнал входов, «выйти везде»
                   │                   (enforcement kick-сессий в Erp100_Base::before)
                   ├─ nj120_jobs     — очередь (PG) + /tasks (свод задач)
                   ├─ nj597_notif.   — колокольчик (опрос 45с) + письма symfony/mailer
                   └─ Service_NjXXX  — бизнес-логика, свои таблицы nj_<id>_*
                        │ push(channel)
                        ▼
                   nj_120_jobs (PostgreSQL) ──poll──▶ python-воркеры (workers/)
                        ├── LLM (OpenRouter/Toolforge, env-провайдеры)
                        ├── DDG-поиск + webread-конвейер (Markdown, без сырого HTML)
                        ├── локальный OpenSCAD (рендер nj570)
                        └── DOCX/PDF/XLSX (python-библиотеки)
                        │ callback NJxxx_*_API_BASE + WORKER_SITE_TOKEN
                        ▼
                   таблицы nj_<id>_* → UI (карточки, статусы, колокольчик)

MCP: nj160_mcp — единый хаб ИИ-агентов; инструменты модулей — config/mcp.php
Миграции: /migrate_pg (+ API) или bin/deploy.sh --migrate (пинок из /update/kick)
Деплой: владелец запускает сам; ветка прода задаётся на сервере (DEPLOY_BRANCH)
```

Сильные стороны: модульная изоляция (чужие таблицы/view не читаются), события и
очередь вместо прямых связей, анонимы через куку `ubid`/`Visitor::uid()`,
самоотчёт об ошибках в API (json `{error}` с файл:строка), идемпотентные DDL.

## 5. Тех долг и решения (по приоритетам)

### P1 — сейчас (часть закрыта этим аудитом)
- ✅ **env-гигиена**: в `.env.example` добавлен `OPENROUTER_PROXY` (используется кодом!);
  в `workers/.env.example` — `LLM_PROVIDER`, `NJ590_FETCH_TIMEOUT`, `NJ590_MAX_PAGE_BYTES`,
  `NJ580_DOCTOR_PKG`. Помечены комментарии: `MAIL_USERNAME/MAIL_PASSWORD` — легаси,
  `ADMIN_*/APP_*` — только docker.
- ✅ **README-дыры**: nj100_search, nj100_platform (README), nj593 (AGENTS) — созданы.
- ⚠️ **Ветка прода зафиксировать явно**: `DEPLOY_BRANCH=<ветка>` в
  `/etc/default/n2j-deploy` (имя ветки в репозиторий не коммитим).
  Риск при неверной ветке: случайно задеплоить откат всего.
  *(Закрыто 28.09.2026: дефолта в скрипте больше нет — см. AGENT-LESSONS «ветка деплоя».)*

### P2 — скоро (решения владельца)
1. **Yandex OAuth — мёртвый узел**: модуль не зарегистрирован в `Kohana::modules()`,
   ссылок на `/oauth/yandex/*` в UI нет, роуты не грузятся. Развилка:
   а) включить — добавить в bootstrap + кнопку на /auth/login (хук after_login уже готов);
   б) архивировать — убрать модуль и `YANDEX_OAUTH_CLIENT_ID` из .env.example.
2. **Composer-диета** — в PHP-коде (`application/`) не найдено ни одного использования:
   `guzzlehttp/guzzle`, `phpoffice/phpspreadsheet`, `phpoffice/phpword`, `dompdf/dompdf`,
   `monolog/monolog`, `nesbot/carbon`, `php-mqtt/client`, `php-amqplib/php-amqplib`,
   `league/commonmark`. (DOCX/PDF/XLSX делает python; почта — symfony/mailer; .env — phpdotenv.)
   Перед удалением — контрольный grep по динамическим загрузкам, затем `composer remove`.
3. **Легаси — ВЕРДИКТ владельца (21.09): «оставлял не просто так» — ретиремент ОТМЕНЁН.**
   Переоценка после разбора:
   - `erp208_events` — **АКТИВНО ИСПОЛЬЗУЕТСЯ**: `Service_Erp208_EventBus` (publish/listen,
     журнал событий в БД, прокси в erp217 по target_user_id) назначен ЕДИНСТВЕННОЙ
     событийной шиной платформы; nj120 публикует job_done/job_failed через неё
     (раньше — мёртвый Kohana Event::fire «в пустоту»);
   - `erp217_notification_center` — живёт как прокси-получатель шины (механика
     подписок/шаблонов доступна); nj597 остаётся активным «колокольчиком»;
   - `erp118_links`, `erp212_file_storage`, `erp218_module_manager` — заморожены ДО
     потребности, не удалять;
   - `modules/email` (SwiftMailer) — по-прежнему НЕ использовать (правило «почта —
     только symfony/mailer»); из живого кода вызовы убраны 21.09 (регистрация/сброс).
   - `PostgreSQL_PDO` — не зарегистрирован; уточнить у владельца перед удалением.
4. **pg_trgm под ILIKE-поиск**: nj100 ищет по 6 таблицам `ILIKE '%q%'` — при росте
   данных добавить GIN-индексы (`pg_trgm`) отдельными миграциями. Пока объёмы малы — не горит.
5. **Дублирование DDL** «ensure_tables() == миграция» — правило рабочее (nj597/598/599 совпадают);
   соблюдать при любых изменениях схемы.

### P3 — идеи на потом
- **Полностраничный /search**: сейчас поиск — только дропдаун в шапке; страница с фильтрами
  по типам («мои материалы / база знаний / организации / вакансии») напрашивается.
- **doctor-скрипт nj598** (по образцу nj580_doctor.py / mail_doctor.php).
- **Наблюдаемость**: Kohana::$log пишется в файлы без просмотра в админке — простой
  хвост ошибок в /nj100/admin сократил бы цикл «прод-ошибка → лог → фикс».
- ~~nj600 «Аккумулятор предпочтений»~~ — **ПОСТРОЕН 21.09** (`nj600_prefs`): пассивный
  серверный сбор (хук в Base::before + фразы nj100), `nj_600_events` с TTL-очисткой
  (21 дн. по умолчанию, env NJ600_RAW_TTL_DAYS) + компактная `nj_600_profile`
  (JSONB-счётчики с капами, не растёт), /nj600/admin (KPI+очистка), /prefs/api/profile,
  MCP: nj600_platform_top / nj600_profile_by_key. Следующий шаг — «Детектор намерений»
  (LLM поверх Service_Nj600_Prefs::profile()).

## 7. Гигиена ФС и БД

- Корень репо аккуратен: `application/ modules/ system/ public_html/ workers/ bin/ docs/ docker/ tests/`;
  `modules/`+`system/` — фреймворк Konine, не редактируются.
- Документация не дублируется: AGENTS.md (правила) → docs/ (гайды) → README (старт).
- Миграции: 18 модулей с таблицами имеют по 1–3 миграции, имя класса = имя файла,
  DDL идемпотентен. Служебная `migrations_pg` — учёт применений.
- Максимальный размер модуля ~350 КБ (легаси erp217/212/218 — кандидаты на ретиремент,
  после чего топ тяжелых станут nj-модули ~140–250 КБ).
