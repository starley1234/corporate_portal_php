# Портал PRX: карта системы и следующий шаг

**Решение: развиваем модульный монолит.** PHP, PostgreSQL и Python-воркеры уже
разделяют интерактивную и фоновую работу. Не нужно выделять сервисы по сети,
менять фреймворк или вводить новые слои ради единообразия.

| Задача | Куда идти |
|---|---|
| Страница сотрудника | `public_html/index.php` → `application/bootstrap.php` → контроллер модуля → сервис → PHP view |
| Операция над записью | Контроллер получает `Prx_Actor`; политика модуля проверяет доступ к объекту, сервис выполняет операцию над данными владельца |
| Запрос внешней системы | `/api/v1/...` → ключ и scope в `prx150` → сервис владельца; не сессия сотрудника |
| Тяжёлая операция | Сервис ставит задачу в `prx120`; Python-воркер обрабатывает её, PHP-модуль владеет бизнес-результатом |
| Общие возможности | `Storage::` для файлов, `Event::publish()` для событий, манифест модуля для обнаружения возможностей порталом |

Данные и миграции принадлежат модулю. Если нужно текущее состояние чужой
записи, используем публичный сервис владельца, не его таблицы. Событие
сообщает о произошедшем, а очередь выполняет отложенную работу. Обработчик
HTTP не должен ждать OCR/LLM, если операция уже спроектирована как фоновая.

## Что показала сверка

- Список подключённых модулей определяется `application/config/modules.php`
  и дополнительным блоком в `application/bootstrap.php`. Каталог и дорожная
  карта не доказывают наличие работающего маршрута.
- В checkout `prx390`–`prx393` подключены как стенд, `prx394` отсутствует.
  Карта показывала отсутствующий модуль и исторические события как часть
  действующего потока. Это исправлено в YAML и сгенерированной странице
  `/architecture`. Подключение в коде не означает готовности к production.
- Для нового модуля уже есть шаблон, правила и CI. Следующий пробел для
  принятия решений — подтверждённый сквозной сценарий, а не ещё одна схема.

## Порядок работы

1. **Подтвердить базу на PHP 8.4 и чистой PostgreSQL.** Прогнать CI и
   зафиксировать результат в журнале проверок. Состояние production не
   выводить из статических проверок или наличия модуля в bootstrap.
2. **Проверить один сквозной поток:** синтетический PDF → приём → очередь →
   текст → карточка → ИИ-предложение. Критерии: пользователь без доступа не
   читает документ; сбой воркера виден; повтор обработки не плодит карточки;
   предложение не меняет карточку без явного принятия.
3. **Рефакторить по результатам.** Чинить нарушенную границу у владельца
   данных и добавлять тест. Сохранять публичные фасады и URL; не переносить
   модули массово. Карта должна меняться вместе с границей в коде.
