# Архитектура PRX

## Решение

**Модульный монолит + PostgreSQL + Python-воркеры.** Один репозиторий и
согласованный релиз; PHP и воркеры — отдельные процессы. Не микросервисы.
PHP обслуживает HTTP и бизнес-операции, Python выполняет длительные задания.
Новые брокеры, фреймворки и универсальные слои без конкретной задачи не нужны.

```text
Браузер / корпоративная система
            ↓
Controller → Service → PostgreSQL
                ├── Storage → приватные файлы
                ├── Event → локальные необязательные подписчики
                └── JobQueue → Python handler → OCR / LLM / embeddings
```

## Где что находится

| Путь | Ответственность |
|---|---|
| `application/config/modules.php` | Базовый список модулей и порядок миграций; стендовый блок — в bootstrap |
| `application/classes/` | Общие контракты: actor, policy, SQL, CSRF, события, файлы |
| `application/modules/prxNNN_slug/` | Вертикальный модуль: HTTP, бизнес-логика, схема, UI, тестируемые контракты |
| `workers/prx_workers/handlers/` | Обработчики очереди по модулям-владельцам |
| `workers/prx_workers/` | Общий runtime: очередь, heartbeat, retry, cancel, usage |
| `services/` | Отдельные внешние процессы, например OCR-шлюз |
| `system/`, `modules/` | Исторический фреймворк Konine/Kohana и его библиотеки |
| `tests/`, `workers/tests/` | Проверки поведения; `tests/Contracts/` запускаются без БД |
| `docs/architecture/model/` | Машиночитаемая карта и ADR, не второй реестр подключения |

## Один модуль — один владелец данных

- **Controller:** метод HTTP, входные данные, аутентификация, вызов сервиса, ответ.
- **Service:** бизнес-операция, объектные права, транзакционная граница.
- **Policy:** правила доступа к записи; скрытая кнопка не является проверкой прав.
- **Миграции:** только своя схема. Чужие таблицы напрямую не читать.
- **View:** только отображение переданных данных, без SQL и бизнес-операций.
- **Манифест `config/prx_module.php`:** меню, scope, поиск, каналы и обслуживание.
  Манифест описывает возможности, но не выдаёт права и не запускает cron.

Между модулями используются публичный Service, `Storage::`, `Event::publish()`,
очередь и HMVC-виджеты. Внутренние классы и ORM-модели не являются контрактом.
Общий код выделяется при реальном повторении, а не заранее.

## Три канала доступа

| Канал | Аутентификация | Изменение состояния |
|---|---|---|
| UI, включая AJAX | Сессия → `Prx_Actor` → ACL + объектная policy | POST + CSRF |
| Внешний API | `Controller_Prx150_Machine`: ключ + scope → `Prx150_Principal` | Явный метод HTTP, без сессии |
| Worker API | Обязательный worker-токен; для результата PDF — ещё номер попытки | Проверка токена до операции |

`Prx_PostGuard` не считает наличие заголовка доказательством аутентификации.
Сессионный контроллер по умолчанию требует CSRF. Машинный endpoint явно
объявляет канал и сам обязательно проверяет credentials. Вебхуки с собственной
подписью перечислены отдельно в `application/config/post_guard.php`.
Фасад файлов не заменяет проверку доступа к бизнес-объекту.

## Транзакции и асинхронность

1. **Обязательная синхронная операция:** публичный Service, ошибка возвращается
   вызывающему. Один слой владеет транзакцией; выбранное соединение общее для
   всех её записей. `Prx_Db::transaction($operation, $db)` проверяет begin/commit
   и запрещает вложенный вызов helper на том же соединении. Не оборачивать его
   в ручной begin и не делать commit внутри callback.
2. **Длительная обязательная работа:** очередь `prx120_jobs`. Изменение данных
   и постановка задания должны быть в одной PostgreSQL-транзакции на одном
   соединении (пример — `Service_Prx395_Extraction`). Повторы возможны:
   обработчик обязан быть идемпотентным. БД и файловая система не атомарны —
   нужны компенсационная очистка и периодическая уборка.
3. **Необязательная реакция:** `Event::publish()`. Подписчики синхронные,
   ошибки изолированы, гарантии доставки нет. Событие не является очередью
   и не должно быть единственным способом продолжить обязательный процесс.

Отдельный универсальный event outbox пока не реализован. Если понадобится
надёжная рассылка доменных событий нескольким потребителям, требуется отдельный
ADR и transactional outbox, а не изменение смысла существующего `Event`.
PG- и HTTP-режимы очереди существуют параллельно: их полная эквивалентность
при гонках пока не доказана. Правила эксплуатации — [WORKERS](WORKERS.md).

## Границы и исключения

- Старый документооборот `prx390`–`prx393` подключён явным блоком в
  `application/bootstrap.php`. Для отключения закомментировать четыре строки;
  отдельного env-флага нет.
- `prx395` — асинхронный PDF API. `prx450` — синхронный OCR-шлюз: допустим
  только с ограниченными таймаутами и параллелизмом на целевой инфраструктуре.
- `prx560` — технический RAG-кэш, не хранилище HR/корпоративных документов.
  Semantic API не обеспечивает готовый ACL-aware retrieval.
- В legacy-сервисах ещё встречаются массивы actor, SQL с ручным quoting и
  singleton. При изменении операции приводить её к общим контрактам, не
  создавать третий вариант. Массовое переименование не является целью.

## Вход для разработчика и агента

1. Прочитать корневой `AGENTS.md`, затем `AGENTS.md` нужного модуля.
2. Для новой операции использовать [FOUNDATION](FOUNDATION.md),
   для нового модуля — [MODULE_GUIDE](MODULE_GUIDE.md).
3. Проверить `make check`, `make env-check`, `make test-contracts`,
   `make lint`, `bash bin/test`, Python- и JS-тесты. CI — `.github/workflows/ci.yml`.
4. Карта системы: `/architecture`, `/architecture/data.json`,
   [модель и сборка](architecture/README.md). Проверенные результаты и
   ограничения среды — [VALIDATION](VALIDATION.md).
