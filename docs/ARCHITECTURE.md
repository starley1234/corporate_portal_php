## 1. Принцип: микромодульный монолит

Не микросервисы (отдельные процессы/деплои) и не классический монолит (всё
вперемешку), а третий путь:

* **один деплой, одна БД, один фронт** — эксплуатационно дёшево;
* **модули изолированы как сервисы**: свои таблицы (префикс `nj_<id>_`),
  свой Service-слой, свои точки входа (HTTP/HMVC), свои миграции;
* **связи — через контракты** (§3): сервис-вызов и очередь как несущие,
  шина событий как журнал. Чужие таблицы напрямую читают только агрегаторы,
  и это записанное исключение, а не лазейка (см. «Поперечное чтение» ниже).

**Что эта изоляция даёт, а чего — нет.** Даёт **удаляемость**: модуль можно
выключить, переписать или снести поодиночке. НЕ даёт выносимости в отдельный
сервис: замер 28.09.2026 — циклы в графе зависимостей и 74 связанных модуля из
77, а модуль внутри цикла не выносится в принципе. Обещание «позже выносится
почти без переписывания» убрано как невыполнимое: за него платили церемонией в
каждом модуле, а получить было нельзя (docs/OPINION-2026-09-28.md, §1, §5).

### Правила владения данными

| Правило | Смысл |
|---|---|
| Таблица принадлежит ровно одному модулю | кто создал — тот и меняет схему |
| Префикс `nj_<id>_` | видно владельца в любом SQL/дампе/админке |
| Чтение — через Service-метод владельца | владелец контролирует контракт |
| Ссылочная целостность — только внутри модуля | FK на чужие `id` — по соглашению, без FK-констрейнтов (иначе вынос модуля ломается) |
| Схема БД общая (`public`) | раздельные схемы — только по явному решению (см. `DB_DEFAULT_SCHEMA`) |

## 2. Реестр модулей (актуальное состояние)

**Пространства имён:**
* `njXXX_*` — модули этого проекта. Все новые модули — только с этим префиксом
  (таблицы `nj_<id>_<имя>`, классы `Service_Nj<id>_*`, события `nj<id>.*`).
* `erpXXX_*` — legacy-наработки, общие с другим ERP-проектом. Заморожены:
  не развиваем, не переименовываем, новые сущности в них не добавляем.
* Общие таблицы ядра без префикса (`users`, `roles`, `sessions`, `llm_*`,
  `migrations_pg`) принадлежат платформе, а не модулям.

Диапазоны номеров (соглашение, едино для nj и erp, помогает не путаться):

| Диапазон | Уровень | Примеры |
|---|---|---|
| 100–199 | Ядро/платформа: то, без чего не работают остальные | 100, 111, 118, 120 |
| 200–299 | Инфраструктурные сервисы платформы | 208, 212, 217, 218 |
| 300–399 | Организационные домены (HR, CRM, задачи...) | свободно |
| 400–499 | Бизнес-модули (склад, продажи, биллинг...) | свободно |
| 500+ | Продуктовые/прикладные модули (онлайн-сервисы N2J) | свободно |
| llm, email, ... | служебные модули без номера (общая инфраструктура) | вне реестра |

## 3. Коммуникации модулей

```
            ┌──────────────────────────────────────────────┐
            │                 HTTP (nginx)                 │
            └───────┬───────────────────────┬──────────────┘
                    │                       │
             Controller (HTTP/API)     HMVC-виджеты
                    │                       │
                    ▼                       ▼
              Service_ErpXXX_*  ◄──►  Service_ErpYYY_*   (контракты)
                    │                       │
                    ├──► Event::fire(...) ──┤            (шина erp208)
                    │                       │
                    └──► Service_Nj120_JobQueue::push   (асинхронно)
                                  │
                                  ▼
                        PostgreSQL: nj_120_jobs
                                  │  LISTEN/NOTIFY + poll
                                  ▼
                     Python-воркеры (workers/, отдельный сервер)
                      ├── LLM-эндпоинт (Toolforge/OpenRouter)
                      ├── Embedding-эндпоинт (EMBEDDING_API_URL)
                      └── колбэки в PHP API / события в шину
```

Контрактов **три**, и они неравноправны — ниже честные роли, а не список
пожеланий (числа — замер по коду 28.09.2026):

1. **Service-вызов** — несущий. 1 705 обращений. Синхронно, в рамках запроса.
   Если сомневаетесь, каким контрактом связать модули, — этим.
2. **Очередь** (`nj120`) — несущая для всего долгого. 38 постановок. HTTP-запрос
   только создаёт задачу, ответ мгновенный.
3. **Шина событий** (`erp208`) — **журнал аудита и мост к уведомлениям**, а не
   средство развязки: 41 публикация, но всего 3 имени события (`nj120.job_done`,
   `nj120.job_failed`, `nj601.invoice_paid`) и 2 подписчика, заведённых
   миграцией-мостом `nj120 → nj597`. Публиковать событие полезно (остаётся след);
   **рассчитывать, что кто-то его слушает, — нельзя**. Нужна реакция — вызовите
   сервис или поставьте задачу.

**HMVC больше не контракт.** `Request::factory('erpXXX/widget/...')` осталось в
4 местах на весь проект; как способ связи он мёртв. Новый код на нём не пишем.

### Поперечное чтение (агрегаторы)

Правило «модуль не читает чужие таблицы» имеет одно записанное исключение:
**агрегаторы** — дашборд, глобальный поиск, хвост ошибок, чистки, дайджест.
Они читают по 10–28 чужих таблиц, потому что вертикальные контракты (A зовёт B)
не покрывают вопрос «покажи последнее по всем модулям». Это была признанная
дыра в модели, а не расхлябанность, и закрыта она **пятым контрактом**.

### Пятый контракт: модуль объявляет себя сам

Модуль описывает свои реестровые записи в собственном `config/nj_module.php`,
а собирает их `Manifest` (`application/classes/Manifest.php`): каналы очереди
и условия дожима (`worker.channels`), расписание пинков (`schedule`), чистку
своих таблиц (`cleanup`), источник «хвоста ошибок» (`health`), строку ленты
«последнее» (`recent`) и свой источник глобального поиска (`search`).
Подробности и правила — в `AGENTS.md` §3.

28.09.2026 так переехали все шесть реестров: 27 каналов из конфига `nj120`,
14 расписаний из `nj603`, 11 чисток из `nj100`, 10 источников ошибок,
6 источников ленты и 9 источников поиска — прямо из кода агрегаторов. Ядро
очереди больше не знает схем двух десятков чужих модулей, а новый модуль
попадает во все витрины платформы, ничего чужого не правя.

Осталась одна точка регистрации — строка в `application/bootstrap.php`.
Больше, чтобы завести модуль, трогать чужие файлы не нужно.

## 4. Асинхронный контур (детально: docs/WORKERS.md)

* Очередь — **таблица PostgreSQL** (`nj_120_jobs`): транзакционно вместе с
  бизнес-данными, ничего лишнего в инфраструктуре, `FOR UPDATE SKIP LOCKED` —
  конкурентное разгребание несколькими воркерами.
* Пробуждение воркеров — `pg_notify('nj120_jobs', ...)` + опрос как fallback.
* Python-воркеры (`workers/`, asyncio) умеют работать **двумя способами**:
  напрямую с PG (asyncpg) или по **HTTP-API** модуля (`/nj120/api/*`, токен
  `WORKER_API_TOKEN`) — на случай, когда воркеры на другом сервере без доступа
  к БД.
* Результаты — обратно: HTTP-колбэк, обновление задачи, событие в шину
  (`nj120.job_done`), по которому PHP-модули узнают о результате.

## 5. LLM и эмбеддинги

* Весь PHP-код работает с LLM через фасад `Llm::` (модуль `llm`): провайдеры,
  модели `provider::model`, vision, `extract` (JSON), tool-calling, логи запросов.
* Конфиг: `application/config/llm.php`. **Эмбеддинг-сервер настроен отдельно** —
  у него собственный эндпоинт (`EMBEDDING_API_URL`), ключ, модель, размерность;
  в конфиге — секция `embedding` и провайдер `embedding_server`.
* Тяжёлая работа с LLM (индексация, агенты, батчи) — через очередь в воркерах;
  PHP только ставит задачи и читает результаты.
* Для семантического поиска в БД — расширение `pgvector` (уже в docker-образе
  PostgreSQL); хранилище векторов — отдельный модуль (см. дорожную карту).

## 6. Развёртывание

| Окружение | Как | Что где |
|---|---|---|
| Локальная разработка | `bash bin/restore-env.sh --serve` или `make up` | всё в docker либо нативно |
| Прод (монолит) | docker compose / nginx + php-fpm | `public_html` — docroot, воркеры рядом или на соседней машине |
| Сервер воркеров | `workers/` (docker/worker/Dockerfile) | доступ к PG портом **или** к PHP через `WORKER_API_TOKEN` |

Миграции накатываются из основного приложения (`bin/console db:migrate`) —
сервер воркеров схему не меняет никогда.

### Как читать этот документ дешевле

Раздел §2 (реестр модулей, ~25 КБ) целиком нужен редко: модуль описан в своём
`AGENTS.md`, а карточку собирает `python3 .tools/context_pack.py pack <модуль>`
(≤ 8 КБ). Индекс разделов — в начале файла; один раздел отдаёт
`python3 .tools/context_pack.py section "<заголовок>" --path docs/ARCHITECTURE.md`.
Протокол помодульной работы с бюджетом токенов — `docs/CONTEXT.md`.

### Анти-цели (осознанно не делаем)

* Микросервисы «на всякий случай» — пока один деплой дешевле. И тем более не
  платим за «готовность к распилу»: она недостижима (см. §1), а цена реальна.
* Отказ от Kohana в один шаг — миграция постепенная, через Service-слой
  (сервисы не зависят от Kohana-специфики сильнее, чем от Database/Config).
* Общие таблицы «на всех» — источник спагетти; всегда префикс + владелец.
