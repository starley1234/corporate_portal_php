# Архитектура PRX

## Слои и философия

Один deploy, одна PostgreSQL и каскадная файловая система Konine/Kohana.
Основная цель — ИИ-пайплайны с API для корпоративных систем.
Модуль — вертикальный срез: схема, Service, HTTP, UI, тесты и манифест.
Бизнес-логика находится в сервисах, а не в контроллерах/представлениях.
Новые сервисы не создают свои Auth, очереди, LLM-клиенты или уведомления.

```
Browser → PHP/HMVC → application/config/modules.php
                   ├─ Auth + роли/ACL + сессии/2FA
                   ├─ Manifest → каталог / меню / поиск / health / cleanup
                   ├─ Service_PrxXXX_* → своя схема PostgreSQL
                   ├─ Event → prx208 EventBus → подписчики
                   ├─ prx597 → in-app / outbox → каналы доставки
                   └─ prx120 → PostgreSQL queue → prx_workers (PG или HTTP)
                                                    ├─ LLM
                                                    └─ embeddings → prx115
```

## Сохранённые платформенные и активные бизнес-модули

| Модуль | Ответственность |
|---|---|
| `PostgreSQL`, `PostgreSQL_PDO` | Драйверы PostgreSQL (PDO — альтернативный, не подключён одновременно) |

| `prx110_catalog` | Каталог, меню, чипы, палитра и видимость модулей |
| `prx111_migrations` | Реестр и выполнение миграций по подключённым модулям |
| `prx115_semantic` | Индексация, векторный/гибридный поиск, кэш запросов |
| `prx120_jobs` | Очередь, task UI, мониторинг, heartbeat и бюджеты |
| `prx208_events` | Шина событий, подписчики и журнал |
| `prx212_file_storage` | Файлы, приватное хранение, ссылки/разрешения |
| `prx218_module_manager` | Инвентаризация и метаданные жизненного цикла |
| `prx300_employee` | Организации, площадки, подразделения, профиль сотрудника, внешние ID, сопоставление Auth↔сотрудник и delta-импорт HR-данных |

| `prx150_api_hub` | Ключи внешних потребителей, scope, лимиты и журнал использования API |

| `prx595_useradmin` | Управление пользователями и ролями |
| `prx597_notifications` | Уведомления, шаблоны, предпочтения каналов и outbox |

Фреймворковые Auth/ORM/DB/cache/minion и другие зависимости лежат отдельно
в `modules/`. При совпадающем ID 100 разные суффиксы — историческое ядро;
новый scaffold не допускает повторного ID.

## Пять контрактов

1. **Публичный Service:** синхронный вызов бизнес-операции. Policy и проверка
   объекта внутри сервиса, не только в контроллере.
2. **Событие:** именованное `prxXXX.entity.action`, стабильный payload с ID,
   а не приватной моделью ORM. Нужную идемпотентность обеспечивает подписчик.
3. **HMVC:** готовый HTML-виджет, не прямой include чужой view.
4. **Очередь:** длительная работа с таймаутом, повтором и отменой; `usage.py`
   сохраняет ресурсный учёт даже при ошибке. Секреты не передавать в payload.
5. **Манифест:** `config/prx_module.php`. Агрегаторы читают `Manifest`, а не
   знают списки чужих модулей. Владелец определяет SQL recent/search/cleanup,
   подписи каналов и ссылки. Метаданные не заменяют проверку HTTP/Service ACL.

Старый `docflow` (`prx390`–`prx393`) выключен по умолчанию и
[включается для тестирования](QUICK-CHECK.md) одним блоком в `application/bootstrap.php`.
Черновики `prx394` остаются в архиве. Новый [документный API](integrations/document-extractions.md)
и проверка `/prx395_document_extract` от них не зависят.

`application/config/modules.php` — источник истины подключения и порядка
миграций. Менеджер модулей управляет метаданными; не считайте запись в его БД
автоматическим подключением PHP-модуля. События подключены до очереди,
уведомления после неё. Миграции запускаются явно через CLI/deploy.

## Фундамент платформы

Пять классов, на которых строится каждый новый модуль (подробно —
`docs/FOUNDATION.md`):

| класс | роль |
|---|---|
| `Prx_Actor` | серверный контекст «кто действует»: user_id, роли, оргконтекст |
| `Prx_Policy` | объектные правила доступа к записи (RBAC + оргконтекст) |
| `Prx_Db` | SQL с именованными параметрами и `transaction()` |
| `Prx_Event` | единая публикация доменных событий `prxNNN.<entity>.<action>` |
| `Prx_PostGuard` | глобальная CSRF-проверка небезопасных методов |

Контракт доступа: контроллер получает actor (`$this->actor()`) и требует
право (`->require('prxNNN.view')`), сервис проверяет объект через политику.
Массивы прав из контроллера в сервис не передаются.

Контракт страницы — page-kit: `partials/page_header`, `filters`, `empty_state`,
`pagination`, `flash`. Каркас нового модуля генерирует scaffold v2
(`make new-module`), Gates — `make check`.

## Документация архитектуры

`docs/architecture/model/*.yaml` — источник истины для схем, слоёв, модулей и ADR.
`make architecture` проверяет модель (`check --strict`) и собирает
`docs/architecture/dist/architecture.html` + `.json`. Модуль `prx101_architecture`
отдаёт страницу после входа (право `prx101.view`) и JSON по
`/architecture/data.json`; сборка не требует Node на production, потому что
`dist/` коммитится. Подробности и формат вкладок — `docs/architecture/README.md`; движок — `docs/architecture/engine`.

## Границы безопасности

`login` — право входа, не должность. В prx300 оно открывает только собственный
профиль и справочник после активной связи аккаунта с сотрудником; сервис
ограничивает коллег его организацией и allowlist рабочих полей. RBAC +
object policy + оргконтекст должны проверяться перед доступом к данным,
файлам, поисковой выдаче и LLM-контексту. Для API различать 401 (нет сессии)
и 403 (недостаточно прав); worker API — отдельный секрет.

Общий `prx560` — техническая память, не корпоративная wiki и не HR-хранилище.
Сейчас он не зарегистрирован в глобальном поиске и доступен через admin UI.
Существующий semantic API — инфраструктурный механизм, **не готовая система
разграничения корпоративных документов**. Проектирование ACL-aware retrieval,
организационных политик, аудита, анонимных каналов и retention — обязательная
часть реализации соответствующих бизнес-сервисов.

## Эксплуатация

Логи — `application/logs/prx-site.log`, `workers/logs/prx-worker.log`.
Runtime/секреты не в Git. Статика локальная, CSS собирается при разработке.
Обслуживание — `bin/console portal:maintain` по таймеру, см. WORKERS.md.
Изоляцию production-сети, мониторинг, резервное копирование и восстановление
надо проверить на целевой инфраструктуре до запуска пользователей.
