# ProcessHub (nj670) — процессы, факт и аудит

Сервис `/process`: онтологическая модель бизнес-процессов, схемы BPMN «План
(To-Be)» и «Факт (As-Is)», AI-аудит разрывов, выгрузка регламента DOCX/PDF по
ГОСТ Р 7.0.97-2016 с матрицей RACI и карта организации целиком. Онтологию можно
наполнять не только вручную: документ, скан или выгрузка разбираются моделью
на роли, системы, артефакты и черновики процессов. Модуль самостоятельный: свои
таблицы `nj_670_*`, свои маршруты, свой воркерский канал. Ядро платформы не
меняется.

## Кому что доступно

| Что | Право |
|---|---|
| Просмотр своих процессов, холст, факт, аудит, отчёты | владелец процесса (или vip/admin) |
| Создание процесса, синтез схемы, загрузка журнала, аудит, отчёт | `nj670.start` (vip/admin) |
| Справочник онтологии и настройки пространства | `nj670.start` в своём пространстве |
| Админ-страница `/process/admin` | `nj670.admin` (admin) |

Анонимным отдаётся `401`/страница входа. Мутации принимают только POST с CSRF,
JSON-холст — `POST /process/api/<action>` с тем же токеном из разметки
редактора (`csrf":"…"`).

## Быстрый старт

Название процесса можно не заполнять: если поле пустое, имя берётся из первой
осмысленной строки текста (нумерация списка отбрасывается), из имени файла —
у загруженного PDF/скана, иначе «Процесс от 19.10.2026». Обязательно только
поле «Текст регламента» (или файл источника).

```bash
bin/console db:migrate
bin/console processhub:seed-demo --scenario=procurement   # дефис допустим
bin/console processhub:seed-demo --scenario=procurement --fresh=1
```

`--user=admin@n2j.ru` задаёт владельца (по умолчанию первый подходящий
пользователь). Команда идемпотентна: без `--fresh` возвращает уже созданный
процесс, с `--fresh` пересобирает его. После загрузки печатается код процесса
(`procdemo23`, если свободен) и ссылка на стенд. То же самое делает кнопка
«Загрузить демо» на `/process/demo`.

Демо-сценарий «Закупка ТМЦ» фиксирован по числам — их можно называть на
презентации без оговорок:

| Показатель | План (To-Be) | Факт (As-Is) |
|---|---|---|
| Шагов (без start/end) | 5 | 9 |
| Календарный срок | 3 раб. дн. (1 440 мин) | 14 раб. дн. (6 720 мин) |
| Стоимость | 23 525 ₽ | 137 387,50 ₽ |
| Особенности | 1С:ERP, Диадок, авто-проверка контрагента | Telegram вместо Диадока, обход юриста 35 %, СБ 7,5 раб. дн., «ручное выбивание счёта» |

Предзаполненный аудит: 6 находок, 18 400 ₽ потерь на процедуру, критический
риск. Простой СБ — 3 600 мин, то есть 53,6 % срока. Юрист обойдён в 14 из 40
кейсов (35 %), Telegram — 40 из 40.

## Возможности модуля

1. **Синтез схемы из источника** — `/process/create`: текст регламента,
   `.txt/.md`, PDF, скан/фото, аудио. Файл ложится в `storage/nj670/sources`,
   воркер (`nj670.synthesize`) достаёт текст (PDF-слой, vision, ASR), размечает
   шаги, роли, системы и артефакты по справочнику компании, строит шлюзы и
   раскладку по дорожкам. Без воркера текст разбирается правилами
   (`allow_rule_fallback`), результат помечается `rules-engine`.
2. **Process Mining Lite** — `/process/<code>/fact`: CSV/XLSX с колонками
   `Case_ID, Activity, Timestamp, Resource` (русские синонимы поддерживаются).
   Считаются частота переходов, медианы, паузы; рёбра факта получают
   `weight` (толщина) и `avg_minutes` (цвет: ≥ 480 мин — красный, ≥ 120 —
   янтарный). XLSX читается и на хосте без `ext/zip`: собственный разбор
   zip-контейнера (`Mining::_zip_entry`).
3. **AI-диф и аудит** — `/process/<code>/audit`: полупрозрачное наложение
   «план ↔ факт», семантическое сопоставление, находки `shadow_it`,
   `missing_control`, `bypass`, `extra_step`, `bottleneck`, `sla` с оценкой
   потерь. Без модели работает `Diff::run_fast` (правила по словарю и
   ставкам ролей).
4. **Холст** — `/process/<code>/editor`: палитра BPMN (пулы/дорожки,
   пользовательские и автоматические задачи, XOR/AND, таймер), перетаскивание,
   добавление и удаление, Copilot по выбранному узлу. Раскладка своя
   (Sugiyama-подобная), без X6/dagre и CDN; ручные координаты сохраняются при
   пересборке (`Synthesis::merge_copilot`). Рядом — живая проверка схемы:
   старт/конец, недостижимые шаги и тупики, задачи без роли, шлюзы без
   ветвления и XOR без условий; клик по замечанию подсвечивает шаг.
   Кнопка «на весь экран» (или `F`,
   `?full=1`) разворачивает холст на всё окно; схема выгружается в BPMN 2.0 XML
   по `/process/<code>/bpmn?kind=plan|fact` и в PlantUML
   (`/process/<code>/plantuml?kind=plan|fact`) для Confluence.
   Схему можно **импортировать** обратно: в `/process/create` приложите
   `.bpmn/.xml` — дорожки, роли, шлюзы, условия и `bpmndi`-координаты станут
   план-версией «на рассмотрении» (`bpmn-import`), `callActivity` сохранит ссылку
   на процесс компании, а `textAnnotation` + `association` превратятся в
   комментарии шага. Обратный экспорт тоже пишет аннотации, поэтому круг
   «ProcessHub → Storm → ProcessHub» не теряет замечания ревьюера. **Подпроцессы** задаются в инспекторе («Вызывает
   процесс»): на холсте рисуется двойная рамка, двойной клик открывает
   дочернюю схему; иерархия `parent_id` видна на карте и в паспорте.
   **Оверлеи аудита** (`!` риск, `✓` контроль, `?` вопрос, `i` идея) и
   **комментарий ревьюера** ставятся на шаг в инспекторе, видны на холсте и
   попадают в регламент разделом «Комментарии ревьюера». Кнопка **▶**
   прогоняет «шустрый токен» по схеме от старта до конца — для демонстрации
   маршрута на защите регламента; токен живёт в координатах графа, поэтому
   панорама и масштаб его не отрывают.
5. **Онтология из документа** — `/process/ontology`: текст от 40 символов или
   файл (PDF, фото, аудио). Воркер `nj670.ontology` отдаёт предложение:
   роли, системы, артефакты, события, метрики, правила, подразделения и
   черновики процессов. Совпадения по коду помечаются «уже есть» и не
   дублируются; ничего не создаётся до кнопки «Принять выбранное». Лимиты —
   120 сущностей, 10 процессов, 30 шагов; квота 20 разборов в сутки.
   Текстовый `.txt/.md` читается на сайте, остальное — воркером (OCR/ASR).
6. **Карта организации** — `/process/map`: процессы по подразделениям,
   владельцы, системы, артефакты, матрица «процесс × система», пробелы
   (без владельца, без плана/факта/аудита, системы и роли вне процессов) и
   подсказки («самый большой разрыв план/факт»). Всё — из сохранённых версий и
   справочника, без отдельного ночного пересчёта. Иерархия процессов —
   дерево родителей/детей, вызовы `callActivity` — отдельный блок.
   Реестр `/process` фильтруется по тексту (название, код, описание,
   подразделение, владелец), подразделению, владельцу и состоянию
   («нет факта», «без владельца», «с аудитом»).
7. **Регламент** — `/process/<code>/report`: титульный лист с «УТВЕРЖДАЮ»,
   лист согласования, таблица шагов `№ | Роль | Вход | Действие | Система |
   Выход | SLA`, векторно-табличный маршрут по дорожкам, авто-матрица RACI,
   раздел аудита и «Комментарии ревьюера» по оверлеям шагов. DOCX собирается
   собственным ZIP-писателем, PDF — через `Service_Nj634_Txt2pdf` (DejaVu).
   Оба файла доступны по `/process/r/<id>/{docx,pdf}`.
8. **Паспорт процесса** — `/process/<code>/passport`: одна страница для
   собственника и аудитора. Архитектурный срез (роли/системы/артефакты с
   частотой в плане и факте), покрытие шагов ролями и системами, теневые
   места и оверлеи, таблица шагов, RACI, последний аудит, комментарии,
   родитель/дети/вызовы, версии и готовые DOCX/PDF. Данные считаются из
   актуальных версий — отдельной синхронизации нет.

9. **«Что если»** — `/process/<code>/simulate`: поток заявок в месяц, рабочие
   дни и численность ролей. Считаются загрузка роли (спрос / ёмкость),
   очередь M/M/1, срок с очередью, максимальная пропускная способность и
   «сколько людей нужно» для 80 % загрузки. Это оценка ёмкости, а не
   покадровая DES: работы ролей складываются, параллельные ветки не
   разводятся, шаги без роли видны отдельным предупреждением. Ставки ролей
   дают месячный ФОТ. Переключатель «план/факт» показывает, где факт требует
   больше людей.

### Сравнение версий

`/process/<code>/versions` — семантический diff двух редакций: шаги
сопоставляются по `step_id`, поэтому переименование не выглядит как
«удалили и создали». Показываются добавленные/удалённые/изменённые шаги с
полями (название, тип, роль, система, работа, ожидание, вход/выход), новые и
пропавшие связи, изменение срока и ожидания. `Compare::compare()` не зависит
от БД и покрыт unit-тестами.

## Оформление

«Золотая середина»: спокойный деловой стиль с одним акцентом (индиго) и
цветом как носителем смысла. Индиго-700 — первичные кнопки и холст,
индиго-600 — ссылки и иконки заголовков. Тонированные плитки KPI и статусы
дают иерархию без пестроты: процессы — индиго, аудиты — бирюза, регламенты —
зелёный, потери — розовый; «План» всегда индиго, «Факт» — бирюзовый, на
холсте и в регламенте одинаково. На холсте приглушённые заливки типов узлов
различают старт/конец, авто-, ручные задачи, шлюзы и таймеры; связи, петли и
ожидания читаются на проекторе. Легенда оверлеев и палитра серверных
миниатюр совпадают с холстом.

## Модель данных

| Таблица | Что хранит |
|---|---|
| `nj_670_workspaces` | пространство компании: название, валюта, ставки |
| `nj_670_entities` | онтология: `class_type` (`role`, `system`, `artifact`, `event`, `metric`, `rule`, `department`), `code`, `name`, `attributes` JSONB |
| `nj_670_processes` | процесс: код, владелец-роль, иерархия `parent_id`, указатели `plan_version_id`/`fact_version_id` |
| `nj_670_versions` | версия: `kind` (`plan`/`fact`), `version_tag`, `status`, `graph_topology` JSONB, итоги `total_duration_minutes`/`total_cost_rub` |
| `nj_670_nodes` / `nj_670_edges` | плоский индекс для запросов; источник истины — `graph_topology` |
| `nj_670_imports` | загруженные журналы: имя, размер, статистика разбора |
| `nj_670_audits` | аудит: статус, `risk_level`, `total_impact_rub`, `findings` JSONB |
| `nj_670_reports` | отчёт: версия, аудит, статус, размеры файлов, ошибка |
| `nj_670_events` | журнал действий для ленты/аудита |
| `nj_670_ontology_jobs` | разбор документа: источник, статус `queued/running/done/error`, предложение модели `result` JSONB, `accepted_at`; чистится через 90 дней |

Контракт графа: `{lanes, nodes[{id,step_id,type,title,lane,role_code,
system_code,input_code,output_code,duration_minutes,wait_time_minutes,x,y,w,h,
properties}], edges[{id,from,to,type,condition,weight,avg_minutes}], meta{…}}`.
Коды узлов — латиница; подписи ролей/систем — в онтологии.

В `properties` узла допустимы (белый список `Graph::_clean_props`):
`description`, `condition`, `role_label`, `system_label`, `shadow`, `problem`,
`control`, `severity`, `sla_minutes`, `process_code`/`process_title` (вызов
подпроцесса), `bpmn`/`bpmn_x`/`bpmn_y` (импорт), `comment`, `overlay`
(`risk|control|question|idea`), `overlay_by`, `overlay_at`. Неизвестный оверлей
отбрасывается при нормализации — холст не умеет его рисовать.

## Жизненный цикл версий

`queued → draft → in_review → active → archived`, ошибка — `error`.

* Воркер присылает схему: факт сразу становится `active`, план — `in_review`,
  но указатель процесса уже смотрит на новую версию (`point_to`), поэтому
  черновик видно на холсте.
* Утверждение — `POST /process/<code>/approve` (право `nj670.start`, CSRF):
  версия становится `active`, прежняя активная уходит в `archived`.
  Кнопка «Утвердить план» показывается владельцу для плана в `in_review`.
* Неактивированные версии не теряются: переключение «План/Факт» берёт
  указатели процесса, история — в `/process/<code>/report` и БД.

## Воркер и деградация

Каналы: `nj670.synthesize`, `nj670.mine`, `nj670.diff`, `nj670.export`,
`nj670.ontology`.
Сайт кладёт задачу в `nj_120_jobs` и отдаёт контекст через `/process/w/*`
(строгий `WORKER_API_TOKEN`). Переменные воркера: `NJ670_API_BASE`
(иначе `NJ120_API_BASE`, иначе корень из `NJ120_API_URL`), `NJ670_SITE_TOKEN`
(иначе `WORKER_SITE_TOKEN` / `WORKER_API_TOKEN`), `NJ670_MODEL`,
`NJ670_LIGHT_MODEL`, `NJ670_ASR_*`.

### Пульс присутствия

Воркер раз в минуту шлёт `POST /process/w/ping` (`NJ670_PING=0` — выключить,
`NJ670_PING_INTERVAL` — период). Сайт хранит последний пульс в
`nj_670_events` (`kind = worker_ping`) и считает воркер живым, если пульс
свежее окна `NJ670_WORKER_PRESENCE_MINUTES` (по умолчанию 5 минут).

Зачем: раньше признаком жизни был только heartbeat **взятой задачи**. У
простаивающего воркера задач нет — сайт считал его выключенным и на создание
процесса отвечал «воркер не в сети», хотя воркер работал. Теперь у пульса есть
приоритет, а heartbeat задач остался запасным признаком для старых воркеров
(окно 60 минут). Он же спасает, когда собственный пульс уже устарел, а задача
жива — например, воркер упал сразу после старта, но успел взять работу.
Диагностика: `bin/console processhub:doctor` и блок
«Воркер» на `/process/admin`; ручное переопределение —
`NJ670_WORKER_FORCE_ONLINE=1`.

### Проверка вёрстки без сервера

```bash
cd /tmp/phpwasm && node phpwasm_stand.mjs .tools/nj670_views_stand.php
```

### Миниатюры схем

Превью на страницах аудита, факта и паспорта — тот же серверный SVG
(`Service_Nj670_Graph::svg`), поэтому стрелки там подчиняются тем же правилам,
что на холсте: вход в ближнюю грань, обход встречного блока, дуга для
самопетли. Форма путей закреплена стендом:

```bash
cd /tmp/phpwasm && node phpwasm_stand.mjs .tools/nj670_graph_stand.php
```

### Как UI показывает работу

Полос прогресса в модуле нет (правило интерфейса). Вместо них:

* общий partial `views/670/_job.php` — полоса «Воркер: этап», секундомер
  `м:сс` и три пульсирующие точки. Стоит на страницах факта, аудита,
  регламента, версий и паспорта. Сама опрашивает `POST /process/api/status`
  раз в 5 секунд, обновляет этап на месте и перезагружает страницу, когда
  задача завершилась (не больше трёх перезагрузок подряд). Запрос идёт с
  `jobs_only: true` — только задачи и статус воркера, без графа и метрик;
* на холсте — тот же индикатор в панели под схемой, а `jobs[].stages`
  попадают в `title` (цепочка этапов через «→»);
* в реестре — баннер: «Воркер не отвечает» (amber) или «обрабатывает N
  задач» с точками (indigo); пропадает, когда очередь пуста;
* кнопка «Собрать схему» на `/process/create` блокируется и показывает
  «Собираю схему…» — запрос не выглядит мгновенным.

Этапы приходят из журнала задач (`nj_120_job_events.event = 'progress'`),
их пишет `ctx.progress()` воркера: «читаю документ», «размечаю шаги»,
«раскладываю дорожки».

Если воркер офлайн:

* синтез текста идёт правилами (`rules-engine`), создание процесса работает;
* загрузка журнала считается на сайте (`Mining::analyze`), факт сохраняется;
* аудит — `Diff::run_fast`, отчёт — `Report::build_local`;
* Copilot и бинарные источники (PDF без текстового слоя, фото, аудио)
  возвращают понятную ошибку — «нужен воркер» / «нужен провайдер».

Проверить связку: `cd workers && python -m pytest tests/test_nj670_processhub.py`
(13 тестов каналов без сети).

## API и MCP: заполнить модуль агентом

Один персональный ключ (`n2jmcp_…`, создаётся в настройках MCP) работает и
для MCP-хаба, и для JSON API — сессия и CSRF не нужны. Владелец ключа
получает своё рабочее пространство; запись дополнительно требует права
`nj670.start` (vip/admin).

```bash
# 1. Создать процесс из текста (схема соберётся воркером или правилами)
curl -s https://n2j.ru/process/api/create \
  -H 'Authorization: Bearer n2jmcp_…' -H 'Content-Type: application/json' \
  -d '{"title":"Закупка ТМЦ","text":"Снабженец формирует заявку в 1С.\nРуководитель согласует заявку.\nЮрист проверяет договор.\nБухгалтер оплачивает счёт."}'

# 2. Прочитать, что собралось (код из ответа)
curl -s 'https://n2j.ru/process/api/status?code=prc1a2b3c4d' \
  -H 'Authorization: Bearer n2jmcp_…'

# 3. Перерисовать схему вручную (новая версия; version_id — правка текущей)
curl -s https://n2j.ru/process/api/graph \
  -H 'Authorization: Bearer n2jmcp_…' -H 'Content-Type: application/json' \
  -d '{"code":"prc1a2b3c4d","kind":"plan","nodes":[{"id":"start","type":"start","title":"Старт"},{"id":"a","type":"user_task","title":"Проверить заявку","role_code":"lawyer","duration_minutes":60},{"id":"end","type":"end","title":"Конец"}],"edges":[{"from":"start","to":"a"},{"from":"a","to":"end"}]}'

# 4. Дополнить справочник (upsert по коду — без дублей)
curl -s https://n2j.ru/process/api/ontology_save \
  -H 'Authorization: Bearer n2jmcp_…' -H 'Content-Type: application/json' \
  -d '{"kind":"role","name":"Юрист","code":"lawyer","rate_per_hour":2500}'
```

MCP (JSON-RPC `POST /mcp/api/rpc`, тот же ключ):

| Инструмент | Что делает |
|---|---|
| `nj670_processes` | список процессов с кодами и статусами |
| `nj670_process` | процесс + граф плана и факта + метрики |
| `nj670_create` | создать процесс и собрать схему из текста |
| `nj670_save_graph` | сохранить граф новой версией (или правкой) |
| `nj670_ontology` / `nj670_ontology_upsert` | справочник: чтение и upsert |
| `nj670_status` | задачи воркера (этап, секундомер), аудит, отчёты |
| `nj670_synthesize` | поставить сборку из текста в очередь |

Сценарий агента: `nj670_create` → `nj670_status` → при необходимости
`nj670_save_graph` и `nj670_ontology_upsert`. Коды ролей/систем берутся из
`nj670_ontology`; в шагах они указываются как `role_code` / `system_code`.

## Ограничения песочницы

* Нет `ext/zip` и GD: DOCX собирается своим ZIP-писателем, XLSX-журнал —
  своим чтением контейнера; в локальном DOCX вместо картинки схемы печатается
  табличный маршрут по дорожкам. Воркерский путь добавляет растровую схему
  (`_diagram_png`).
* Нет провайдера LLM/OCR: проверены контракты `/process/w/*` и правила-фолбэки,
  живые вызовы модели в песочнице не выполняются.
* CDN запрещены, X6/dagre не подключены — холст и SVG рисуются своим кодом.
  Панорамирование считается от экранной точки захвата, поэтому не зависит от
  частоты перерисовки кадров; проверка — `npm run test:nj670:canvas`.
* Колесо масштабирует от курсора без Ctrl, Shift+колесо сдвигает по
  горизонтали, Ctrl/Cmd+колесо — pinch тачпада. Стрелки выбирают грани по
  положению цели и обходят третий блок, а не идут сквозь него.
