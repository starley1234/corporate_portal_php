# Большие PDF по частям: запуск и контракт API v1

`prx396` разбирает большой PDF на части через очередь `prx120` (канал
`pdf.chunks`) и возвращает сплошной текст. В отличие от
[prx395](document-extractions.md) здесь нет потолка «файл целиком в ответе»:
документ режется на куски по `PRX396_CHUNK_PAGES` страниц, каждая часть
обрабатывается и сохраняется отдельно, а результат отдаётся сквозной
выгрузкой. Ошибки видны владельцу по коду, а не «что-то пошло не так».

**Нужно только проверить в браузере?** Страница модуля — `/prx396_pdf_chunks`.
Здесь — настройки и контракт для интеграторов.

**Что выбрать.** До ~20 страниц и до 10 МиБ — `prx395` (проще, ответ целиком).
Крупные сканы и книги, где важны возобновление после сбоя и предсказуемый
лимит текста, — `prx396`. Синхронный разбор без хранения — `prx450`
([document-ocr.md](document-ocr.md)).

## 1. Развёртывание

1. На стороне PHP выполните `bin/console db:migrate` (нужны `prx_396_*`).
   Машинный доступ выдаёт `prx150`: в `/prx150_api_hub` создайте ключ с правом
   `prx396.extract` и скопируйте его — второй раз он не показывается.
   `WORKER_API_TOKEN` — отдельный секрет, он должен совпадать на PHP и Python.
2. На Python включите канал `pdf.chunks` в `WORKER_CHANNELS` (для пилота —
   `WORKER_CHANNELS=echo,pdf.chunks`). Не используйте одно имя `WORKER_NAME`
   для нескольких одновременно работающих процессов: очередь использует его
   для восстановления задач после рестарта.
3. Подключение к очереди и OCR — те же правила, что у prx395: `pg` по
   умолчанию (DSN из `DB_DEFAULT_*`), `WORKER_QUEUE_MODE=http` без доступа к
   БД; `OCR_PROVIDER=tesseract` (нужны `pdftoppm` и `tesseract` с `rus+eng`)
   или `OCR_PROVIDER=remote` с `OCR_SERVICE_URL` до `/parse`. Подробности —
   в [document-extractions.md](document-extractions.md) §1.
4. Нативный запуск: `python3 -m pip install -r workers/requirements.txt`,
   затем `cd workers && python3 -m prx_workers`. Приоритет окружения:
   процесс > `workers/.env` > корневой `.env`.

Настройте `upload_max_filesize` и `post_max_size` не ниже
`PRX396_MAX_PDF_BYTES` с запасом на multipart; для ответа `POST .../part`
прокси не должен резать тела крупнее `6 × PRX396_MAX_TEXT_BYTES` (потолок
согласован с формулой prx395). Не пишите заголовки авторизации и тела
запросов в access-логи.

### Лимиты в окружении

Задавайте `PRX396_*` в корневом `.env`; значения по умолчанию и диапазоны —
в `.env.example` и в
`application/modules/prx396_pdf_chunks/config/prx396_pdf_chunks.php`.
При некорректном значении используется дефолт. После изменения перезапустите
PHP и воркер.

| Ключ | Дефолт | Смысл |
|---|---|---|
| `PRX396_MAX_PDF_BYTES` | 100 МиБ | размер исходного PDF |
| `PRX396_MAX_PAGES` | 500 | страниц в документе |
| `PRX396_CHUNK_PAGES` | 10 | страниц в части (прогресс и возобновление) |
| `PRX396_MAX_TEXT_BYTES` | 50 МиБ | суммарный текст результата |
| `PRX396_TTL_HOURS` (алиас `PRX396_RESULT_TTL_HOURS`) | 72 | срок хранения с постановки |
| `PRX396_TASK_TIMEOUT_SEC` / `PRX396_MAX_ATTEMPTS` | 1800 / 3 | таймаут и попытки задачи |
| `PRX396_PDF_MEMORY_MB` | 512 | RLIMIT_AS изолированного pypdf (проба, нарезка) |
| `PRX396_PROBE_TIMEOUT_SEC` | 60 | таймаут того же подпроцесса |

**Снимок лимитов.** При постановке PHP кладёт копию лимитов в полезную
нагрузку задачи и в `config_snapshot` партии: воркер обрабатывает по
значениям на момент постановки, а не по тому, что сейчас в `.env`. Таймаут,
попытки и срок хранения действуют для новых заданий; уже записанные партии
не пересчитываются. Не задавайте разные лимиты в PHP и `workers/.env`:
более строгая сторона отклонит файл или результат.

## 2. Проверка воркера

`/prx120/monitor` → **«Проверить воркер»** (или `bin/console prx120:probe
--wait=30`) подтверждает, что Python забирает задачи. Для канала `pdf.chunks`
карточка `/prx120/task/<id>` показывает стадии: `plan`, `download_pdf`,
`validate_pdf`, `extract_part` (с номером части и диапазоном страниц),
`store_part`, `complete`. Проба страниц и нарезка части выполняются в
изолированном подпроцессе с лимитом памяти и таймаутом — падение подпроцесса
не роняет воркер и повторяется очередью.

Служебный Worker API (`/prx396_pdf_chunks/worker/...`, заголовок
`X-Worker-Token`) — внутренний контур PHP ↔ Python, потребителям он не нужен.

## 3. API

```bash
# PRX_URL и PRX_API_KEY задаёт клиент, а не репозиторий.
curl --fail-with-body "$PRX_URL/api/v1/pdf-chunks" \
  -H "Authorization: Bearer $PRX_API_KEY" \
  -H 'Idempotency-Key: erp-scan-77-v1' \
  -F 'file=@book.pdf;type=application/pdf'
# 202 Accepted
# {"batch_id":42,"status_url":"/api/v1/pdf-chunks/42","result_url":"/api/v1/pdf-chunks/42/result"}

curl --fail-with-body "$PRX_URL/api/v1/pdf-chunks/42" \
  -H "Authorization: Bearer $PRX_API_KEY"

curl --fail-with-body "$PRX_URL/api/v1/pdf-chunks/42/result" \
  -H "Authorization: Bearer $PRX_API_KEY" -o book.txt
```

- `Idempotency-Key` — 1–128 знаков из `A–Z a–z 0–9 . _ : -`. Те же байты и
  тот же ключ возвращают тот же `batch_id`; другой файл с тем же ключом —
  `409 idempotency_conflict`; истёкший ключ — `409 idempotency_key_expired`.
- Опрашивайте `status_url` каждые 1–3 с. `GET` возвращает `status`
  (`queued`, `running`, `succeeded`, `failed`, `canceled`), `attempt`,
  `parts_done`/`parts_total`, `next_part`, `pages_total`, `expires_at`.
  `failed` в очереди — финал: попытки исчерпаны или ошибка не лечится
  повтором, в ответе есть `error.code`. `worker_lost` — воркер умер посреди
  обработки (стоит поставить тот же файл с новым `Idempotency-Key`),
  `worker_crash_loop` — воркер падает именно на этом файле (повтор не поможет).
  `canceled` — только ручная отмена администратором.
- `GET .../result` доступен при `succeeded` и отдаёт `text/plain` по частям
  (spool-чтение, не «весь текст в JSON»); до готовности —
  `409 result_not_ready`.
- Ошибки HTTP: `401` нет/неверный ключ, `403` нет scope `prx396.extract`,
  `404` чужое/истёкшее задание, `409` конфликт/lease, `413` размер или
  `result_too_large`, `415` не PDF, `429` лимит ключа **или исчерпанный
  бюджет токенов** (`budget_exceeded` — владелец уже потратил дневной/месячный
  лимит на другие задачи; PDF не расходует токены, отказ приходит только при
  уже исчерпанном бюджете), `503` инфраструктура. Ответ —
  `{"error":{"code":"…","details":{…}}}`.
- Коды фоновой задачи. **Терминальные** (валидный PDF не лечится повтором):
  `invalid_pdf`, `encrypted_pdf`, `page_limit`, `no_text`, `result_too_large`,
  `ocr_config`, `ocr_unavailable`, `file_unavailable`, `lease_lost`,
  контрактные `invalid_part`/`invalid_plan`/`invalid_attempt` и другие 4xx от
  `/part`. **Повторяемые** (сеть, таймаут OCR): `worker_endpoint_unavailable`,
  `ocr_timeout`, `batch_incomplete` — ретраятся до `PRX396_MAX_ATTEMPTS`.

## 4. Возобновление после сбоя

Части хранятся в `prx_396_parts` со статусом; после таймаута, рестарта
воркера или потери ответа задача продолжается с первой несохранённой части
(`plan` возвращает список, воркер шлёт только `pending`/`failed`). Повторная
отправка уже сохранённой части идемпотентна: PHP отвечает тем же `part_ack`
и не перезаписывает файл. Потерян ответ на `/part` лечится повтором всей
задачи — дубликатов в результате нет. Lease привязан к номеру попытки:
устаревшая попытка получает `409 lease_lost` и не пишет поверх чужой работы.

## 5. Хранение и очистка

Исходник и части текста закрыты в `prx212`; в записи очереди и мониторе —
квитанция, не текст. Срок — `PRX396_TTL_HOURS` (72 ч с постановки). После
истечения API скрывает артефакты; физическое удаление — команда:

```bash
bin/console prx396:purge
# по cron каждые 5–15 минут под сервисным пользователем PHP, с flock
```

Команда возвращает число удалённых записей, сирот и ошибок; ненулевой код
требует внимания. Не используйте «Очистить все записи» в мониторе как чистку
документов: очередь потеряет статус до истечения TTL.
