# prx597 — как модулю попасть в центр уведомлений

Вынесено из `application/modules/prx597_notifications/AGENTS.md` 16.11.2026:
памятка модуля должна читаться одним экраном. Это контракт интеграции, а не
история; код не менялся.

## Как модулю попасть в центр уведомлений

Три шага. Без первого события нет в реестре — `emit()` его не доставит.

### 1. Объявить событие в манифесте

`application/modules/<ваш_модуль>/config/prx_module.php`:

```php
'notify' => [
    'events' => [
        'mymodule.order.paid' => [
            'title'        => 'Заказ оплачен',
            'description'  => 'Клиент оплатил заказ — деньги пришли',
            'category'     => 'billing',      // system|billing|jobs|content|security|social
            'icon'         => 'fas fa-sack-dollar',
            'channels'     => 'in_app,email', // через запятую
            'roles'        => 'login',        // login|manager|admin, через запятую
            'ability'      => 'mymodule.view',// пусто — доступно по ролям
            'digest'       => TRUE,           // FALSE — только немедленно, без сводки
            'placeholders' => 'order_no,amount,pay_url',
        ],
    ],
],
```

Декларация подхватывается сама: `Registry::sync_manifests()` читает все
манифесты (не чаще раза в час) и сливает их с ручными правками админа —
ручное не затирается, если `source = 'manual'`.

Склейка в сводку — **по умолчанию включена**: уведомление не превращается в
спам само по себе. Не склеивают только срочные события, и это пишут явно
(`'digest' => FALSE`): ошибки сборки, безопасность, деньги. Склейка работает,
когда человек выбрал режим (умолчание — раз в сутки, `digest.default`), и
касается только внешних каналов: в колокольчике событие видно сразу.

Приоритет — одна шкала на все механизмы: **меньше значит важнее**
(`1` критично, `5` обычное, `9` фоновое). До 16.10.2026 тихие часы и склейка
читали число наоборот, поэтому `1` была и критичной, и почти неважной сразу.
Конфиг: `priority.quiet_skip = 1` (что не ждёт утра), `priority.digest_from = 5`
(что можно копить).

События, которые модули заводили сами (`source = 'runtime'`), до 16.10.2026
не умели копиться в сводку — режим «раз в сутки» у человека ничего не менял.
Разовая правка `Registry::apply_digest_default_once()` (зовётся из
`Notify::ensure_tables()`, закрывается отметкой `registry.digest_default`)
включает им склейку и не трогает строки манифестов, события, заведённые
человеком, и всё, что он уже правил руками.

### 2. Позвать emit() в момент события

```php
Service_Prx597_Notify::emit('mymodule.order.paid', [
    'order_no' => $order->id,
    'amount'   => number_format($order->sum, 0, '.', ' '),
    'pay_url'  => '/orders/'.$order->id,
], [
    'user_id'  => (int) $order->user_id,          // кому; 0/нет — по roles/ability
    'priority' => 3,                              // 1..10, МЕНЬШЕ — важнее
    'href'     => '/orders/'.$order->id,          // куда ведёт клик
    'dedup'    => 'order-'.$order->id,            // не слать то же самое дважды
]);
```

`emit()` ничего не шлёт синхронно: пишет строку в ленту (`prx_597_inbox`/
`prx_597_notifications`) и ставит задания в очередь `prx_597_outbox`. Доставка
— отдельным проходом `Engine::run()` (HTTP `/prx597/api/outbox` по расписанию
раз в 5 минут, с токеном воркера).

Легаси-сигнатура `Notify::notify($user_id, $kind, $title, $body)` работает и
дальше: тип события выводится через `kind_event()`, код вида
`prx597.legacy.<kind>`.

### 3. Не изобретать доставку

Никаких своих `mail()`, своих таблиц уведомлений и своего «ещё одного»
колокольчика. Каналы, шаблоны, лимиты, тихие часы, привязку мессенджеров и
архив пользователь настраивает один раз — на `/prx597?tab=settings`.
