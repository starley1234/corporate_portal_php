# Внешний API: ключи, права и использование

`prx150_api_hub` — единственная точка, где внешняя система получает доступ.
Модуль не отдаёт бизнес-данных: он проверяет ключ, scope и лимит, пишет
использование и показывает это администратору. Сервис-модули только объявляют
свои права и наследуют машинный базовый контроллер.

Зачем так: у каждого сервиса свой ключ и своя проверка — это 10 модулей ×
свой auth, свои лимиты и свой журнал. Здесь одна модель и один контракт ошибок.

## Модель — три сущности

| сущность | таблица | что хранит |
|---|---|---|
| Ключ | `prx_150_api_clients` | имя, SHA-256 ключа, префикс, scopes, лимит/мин, срок, статус, организация, последний запрос |
| Использование | `prx_150_api_usage` | ключ, scope, метод, путь, статус, время, объём, HMAC-хеш IP |
| Scope | `api_scopes` в манифесте модуля | `prxNNN.<action>` → название, описание, лимит по умолчанию |

Центрального списка сервисов нет: владелец модуля сам объявляет права.
Ключу можно выдать любое подмножество; `*` — только для внутренних задач.

Организация у ключа необязательна (`organization_id` NULL): внешний ключ может
быть общим для платформы. FK на `prx_300_organizations` нет — модуль не читает
чужие таблицы; при выдаче ключа существование проверяет публичный сервис
`prx300`, а без подключённого `prx300` допустим только NULL.

## Путь запроса

```
потребитель
  │  Authorization: Bearer prx_…
  ▼
Controller_Prx150_Machine::respond()
  ├─ 401 нет/неизвестный ключ
  ├─ 403 нет scope / отозван / истёк
  ├─ 429 превышен лимит
  ├─ действие модуля (Service)
  └─ finally: INSERT usage + X-Request-Id
```

Сессия, cookies и CSRF в машинном API не участвуют. `Prx_PostGuard` пропускает
запрос с заголовком `Authorization`, поэтому CSRF-токен внешнему потребителю
не нужен.

## Как выдать ключ

1. Откройте `/prx150_api_hub`, вкладка «Ключи».
2. Укажите потребителя, лимит (запросов в минуту), срок и права. Организацию
   можно не выбирать: тогда ключ действует вне оргконтекста.
3. Создайте ключ и сразу скопируйте: полный ключ показывается один раз,
   в базе — только хеш.
4. Выдайте потребителю: адрес платформы, ключ и документацию сервиса
   (`/prx150_api_hub/docs`).

Отзыв — необратим; для замены создайте новый ключ. Отозванный ключ сразу
получает `403 key_revoked`, независимо от кэшей потребителя.

## Как подключить новый сервис

1. В манифесте модуля объявите права:

   ```php
   'api' => ['/api/v1/document-ocr/parse'],
   'api_scopes' => [
       'prx450.parse' => [
           'title' => 'Распознавание документов',
           'rate_limit' => 60,
       ],
   ],
   ```

   Префикс scope обязан совпадать с ID модуля — чужое право заявить нельзя.

2. Машинный контроллер наследует `Controller_Prx150_Machine` и задаёт scope:

   ```php
   class Controller_Prx450_Api extends Controller_Prx150_Machine
   {
       protected const SCOPE = 'prx450.parse';

       public function action_parse(): void
       {
           $this->respond(function () {
               // ... Service ...
               $this->_json_response($result, 200);
           });
       }
   }
   ```

3. Маршрут — `/api/v1/<service>/…`; страница модуля — `/prxNNN_slug`.
   `respond()` сам проверит ключ, scope, лимит и запишет использование.

## Идемпотентность

Создающие операции принимают заголовок `Idempotency-Key`
(`[A-Za-z0-9._:-]{1,128}`). Ключ живёт `PRX_IDEMPOTENCY_TTL_HOURS` (по
умолчанию 24) в разрезе scope и владельца — то есть ключа `prx150`.

| ситуация | ответ |
|---|---|
| новый ключ | операция выполняется, результат запоминается |
| тот же ключ, то же тело (`sha256`) | сохранённый результат, без повтора |
| тот же ключ, другое тело | `409 idempotency_conflict` |
| истёк TTL | `409 idempotency_key_expired` |

Реализация — `Prx_Idempotency` (`docs/FOUNDATION.md`): advisory-lock в
PostgreSQL, поэтому работает при любом числе PHP-процессов. Тело не
хранится, только хеш; для файлов это `sha256` файла.

## Контракт ошибок

Всегда JSON, всегда с кодом:

```json
{"error":{"code":"rate_limited","details":{"retry_after":60,"limit_per_min":60,"scope":"prx450.parse"}}}
```

| HTTP | код | когда |
|---|---|---|
| 401 | `unauthorized` | нет заголовка, неверный формат, неизвестный ключ |
| 403 | `forbidden` | нет нужного scope |
| 403 | `key_revoked` / `key_expired` | ключ отозван или истёк |
| 429 | `rate_limited` | превышен лимит запросов в минуту |
| 503 | `service_unavailable` | внутренний сбой; повторить позже |

Внутренние пути, токены, тексты документов и HTML ошибок шлюза в ответ
не попадают.

## Правила

- **Один потребитель — один ключ.** Не выдавайте один ключ «всем» и не
  переиспользуйте ID после ротации.
- **Минимальные права.** Ключу — только нужные scope; `*` — только внутренним
  задачам.
- **Ключ — не пользователь.** Машинный API не использует сессию, роли и ACL
  сотрудников. Права ключа — отдельная граница.
- **Журнал — не биллинг.** Лимит мягкий (по журналу за минуту), один
  параллельный запрос может пройти сверх; для точного биллинга нужен отдельный
  счётчик.
- **IP — только HMAC-хеш.** Без `PRX150_IP_HASH_KEY` не сохраняем вовсе.
- **Не логируем секреты и документы.** В журнале — путь без query, статус,
  время и объём.

## Проверка

```bash
# 401 без ключа
curl -i -X POST https://portal.example/api/v1/document-ocr/parse -F file=@doc.pdf

# 200 с ключом
curl -s https://portal.example/api/v1/document-ocr/parse \
  -H "Authorization: Bearer $PRX_API_KEY" -F file=@doc.pdf
```

Администратору: `/prx150_api_hub/usage` — фильтры по ключу, scope, статусу и
периоду; `/prx150_api_hub/docs` — контракт для потребителя.
