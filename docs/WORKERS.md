# Очередь и эксплуатационные задачи PRX

## Процесс воркера

`workers/prx_workers` — общий runtime: claim, heartbeat, progress,
complete/fail, retry/backoff, отмена, watchdog, graceful shutdown и usage.
Режим `pg` использует asyncpg и LISTEN/NOTIFY; `http` обращается к сайту
через `/prx120/api/*` с `X-Worker-Token`.

```bash
python3 -m pip install -r workers/requirements.txt
cd workers && python3 -m prx_workers
```

На одном сервере используются `APP_URL`, `DB_DEFAULT_*` и `WORKER_API_TOKEN`
из корневого `.env`. `workers/.env` и переменные systemd могут их переопределить.
Даже `pg`-воркер обращается к PHP по HTTP. `python -m prx_workers --check-site`
проверяет адрес и токен без постановки задач. Подробности — в
[инструкции для systemd](systemd-сервис.md). В браузере — относительные URL.

| Канал | Что делает |
|---|---|
| `echo` | Живая проверка PHP → Python → PHP (`prx120:probe` / монитор) |
| `document.extract` | Извлекает текст из PDF, возвращает квитанцию после записи в prx395 |
| `llm.summarize` | LLM-запрос из payload, возвращает текст |
| `embeddings.index` | Возвращает sample векторов для инфраструктурных задач |
| `semantic.index` | Индексирует тексты коллекции prx115 через PG или HTTP |

Секреты и адреса моделей — окружение, не payload. Общие клиенты `llm.py`,
реестр провайдеров `providers.py`, сторожа `watchdogs.py`, watchdog
`llmwatch.py`, ресурсный учёт `usage.py`, webread не дублировать.
Новый канал добавляется явно в HANDLERS и в `config/prx_module.php` владельца.
Для HTTP-доставки semantic.index нужны `PRX115_API_BASE`, `PRX115_SITE_TOKEN`
(или `WORKER_SITE_TOKEN`). В PG-режиме индексация пишет в БД напрямую.

### Распознавание документов

`doc.normalize` и `doc.analyze` включаются только на тестовом стенде с
`PRX_DOCFLOW_ENABLED = TRUE` в `application/bootstrap.php`; `doc.draft` выключен. [Быстрая проверка в UI](QUICK-CHECK.md).

Канал `document.extract` поддерживает локальный `tesseract` и `remote` для
`/parse` с ответом `content`. Запускается только отдельным Python-процессом;
даже при PG-очереди доступ к сайту нужен для выдачи PDF и приёмки результата.
Инструкция запуска, проверка через `echo` и диагностика стадий:
[PDF → текст](integrations/document-extractions.md).

## Обслуживание и уведомления

Старый прикладной планировщик удалён. Новый платформенный CLI:

```bash
bin/console portal:maintain
```

Один проход: reconcile/requeue stale, сбор результатов задач в уведомления,
outbox, дайджесты и poll мессенджеров (если настроены). Ошибка завершает команду
ненулевым кодом — оператор должен отслеживать его. Части доставки используют
свои блокировки; дополнительно исключайте параллельный запуск всей команды.
Пример cron от пользователя приложения (пути адаптировать):

```cron
* * * * * cd /srv/portal && flock -n /srv/portal/application/cache/maintain.lock bin/console portal:maintain >> /srv/portal/application/logs/maintenance.log 2>&1
```

Альтернатива — HTTP `/prx120/api/maintain` и `/prx597/api/outbox` с
`X-Worker-Token`. Не кладите токен в URL/cron-логи. Секции `schedule` манифестов
сами по себе ничего не запускают. Docker worker не запускает PHP maintenance;
таймер нужен отдельно.

По умолчанию email выключен, мессенджеры не привязаны и внешние токены пусты.
Для email: `composer install`, `EMAIL_DSN`, `EMAIL_FROM`,
`PRX597_EMAIL_ENABLED=1`; настройте разрешённые каналы/шаблоны в админке.
Перед production проверьте SMTP, idempotency, retry и dead letter на тестовых
получателях. Не посылайте кадровые данные через внешние каналы по умолчанию.

## Приоритеты обзора Python (17.11.2026)

Это рекомендации, а не описание уже внесённых исправлений:

1. **Высокий — граница сети `webread.py`.** `fetch_sync()` проверяет только
   исходный hostname, после чего `curl_cffi` и `httpx` автоматически следуют
   редиректам и разрешают имя заново. Это допускает переход на внутренний
   адрес и DNS rebinding, если недоверенный URL передан в `fetch`. Проверка
   также принимает диапазон `100.64.0.0/10`, который `ipaddress` не считает
   глобальным. Текущие семь зарегистрированных обработчиков напрямую `webread`
   не вызывают; риск относится к его использованию с недоверенными адресами.
   До исправления не открывать такой путь без ограничений исходящего трафика.
   Нужны ручная проверка каждого redirect и схемы, запрет всех неглобальных и
   внутренних CIDR, проверка/фиксация фактического IP соединения (включая
   IPv6 и режимы proxy) и ограничение числа переходов. Тесты должны покрывать
   redirect на loopback/link-local/CGNAT, цепочки, смену DNS и прокси.
2. **Высокий — лимит загрузки.** `WEBREAD_MAX_PAGE_BYTES` сейчас проверяется
   после получения и декодирования всего `r.text`: он не ограничивает сетевую
   нагрузку и память. Нужен потоковый лимит, в том числе после распаковки,
   с закрытием ответа при превышении; возвращать фактический конечный URL.
3. **Средний — конфигурация и повторяемость.** `Config.validate()` проверяет
   режим и адреса, но принимает отрицательные и неконечные значения
   интервалов (например `NaN`). Проверять положительные конечные таймауты,
   согласованность интервалов и размеры при старте; покрыть ошибочные env
   тестами. Уточнить поддерживаемый синтаксис собственного `.env`-парсера и
   рассмотреть фиксируемые зависимости и отдельные optional extras.
4. **Средний — последующее разбиение runtime.** `base.py` объединяет жизненный
   цикл, планирование, heartbeat и остановку; `queue.py` содержит оба транспорта
   и SQL. Небольшими шагами выделить эти обязанности за существующими
   интерфейсами и расширить общие контрактные тесты PG/HTTP: claim, heartbeat,
   complete/fail, retry, отмена, потеря владения и graceful shutdown.
   Существующие тесты очереди и watchdog сохранять; смену поведения отделять
   от механического рефакторинга.

## Проверки

```bash
python3 -m pip install -r workers/requirements-dev.txt
PYTHONPATH=workers python3 -m pytest workers/tests -q
```

Mock LLM и embeddings — в `workers/mock`. Они предназначены для разработки,
не показывают реальное качество RAG и не заменяют проверку прав на документы.
