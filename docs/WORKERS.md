## Процесс воркера

`workers/prx_workers` — общий runtime: claim, heartbeat, progress,
complete/fail, retry/backoff, отмена, watchdog, graceful shutdown и usage.
Режим `pg` использует asyncpg и LISTEN/NOTIFY; `http` обращается к сайту
через `/prx120/api/*` с `X-Worker-Token`.

```bash
python3 -m pip install -r workers/requirements.txt
cd workers && python3 -m prx_workers
```

На одном сервере используются `APP_URL`, `DB_DEFAULT_*` и `WORKER_API_TOKEN`
из корневого `.env`. `workers/.env` и переменные systemd могут их переопределить.
Даже `pg`-воркер обращается к PHP по HTTP. `python -m prx_workers --check-site`
проверяет адрес и токен без постановки задач. Подробности — в
[инструкции для systemd](DEPLOY-SYSTEMD.md). В браузере — относительные URL.

| Канал | Что делает |
|---|---|
| `echo` | Живая проверка PHP → Python → PHP (`prx120:probe` / монитор) |
| `document.extract` | Извлекает текст из PDF, возвращает квитанцию после записи в prx395 |
| `llm.summarize` | LLM-запрос из payload, возвращает текст |
| `embeddings.index` | Возвращает sample векторов для инфраструктурных задач |
| `semantic.index` | Индексирует тексты коллекции prx115 через PG или HTTP |

Секреты и адреса моделей — окружение, не payload. Общие клиенты `llm.py`,
`providers.py`, `llmwatch.py`, `ocr_client.py`, ресурсный учёт `usage.py`,
сторожа `watchdogs.py` не дублировать. Новый канал — пакет
`handlers/<модуль-владелец>/`, явная регистрация в `handlers/__init__.py`
и `worker.channels` в `config/prx_module.php` владельца (см. «Структура»).
Для HTTP-доставки semantic.index нужны `PRX115_API_BASE`, `PRX115_SITE_TOKEN`
(или `WORKER_SITE_TOKEN`). В PG-режиме индексация пишет в БД напрямую.

### Распознавание документов

`doc.normalize` и `doc.analyze` (пакеты `handlers/prx390_intake/` и `handlers/prx392_analysis/`) включаются только на
тестовом стенде при подключённом блоке документооборота в `application/bootstrap.php`.
[Быстрая проверка в UI](QUICK-CHECK.md).

Канал `document.extract` поддерживает локальный `tesseract` и `remote` для
`/parse` с ответом `content`. Запускается только отдельным Python-процессом;
даже при PG-очереди доступ к сайту нужен для выдачи PDF и приёмки результата.
Инструкция запуска, проверка через `echo` и диагностика стадий:
[PDF → текст](integrations/document-extractions.md).

## Владение задачей и повторные отчёты

У очереди два транспорта: прямой PostgreSQL (`PgQueue`) и HTTP → PHP
`Service_Prx120_JobQueue`. Файлового backend и автоматического переключения
между транспортами нет. Бизнес-обработчик не выбирает транспорт и не меняет
схему/статус очереди вручную.

- `claim` атомарно выбирает доступный `pending` с оставшимися попытками,
  ставит `processing`, имя воркера, пульс и увеличивает attempts.
- Heartbeat/progress и `fail` принимаются только от текущего владельца
  `processing`. Запоздавший `fail` для pending/terminal/чужого захвата даёт false;
  прямой PG больше не переводит pending обратно в processing ради такого отчёта.
- Временная ошибка: `pending`, задержка **15 × attempts²** секунд, обнуление
  `claimed_by/claimed_at` в PHP и Python. До `available_at` повторный claim невозможен.
  Исчерпание попыток или retry=false → failed.
- PHP-проверки владельца стоят в самих UPDATE, включая минимальный terminal-
  fallback. Старое чтение перед UPDATE не даёт права закрыть новый чужой захват.
  Отклонённый progress не пишет в журнал ложное продвижение.
- `complete` сохраняет историческую сверку позднего успеха: done идемпотентен,
  cancelled/failed не оживляются; ещё не захваченный pending может стать done.
  Чужой processing не перезаписывается. PHP-fallback проверяет число изменённых
  строк до публикации успешного события/уведомления.
- Подтверждённая приёмка бизнес-артефакта на сайте — отдельный доверенный
  `mark_delivered`, не право произвольного worker-отчёта менять статус.

Ограничения: владение пока определяется **именем воркера**, не уникальным
токеном попытки. Старый отчёт при повторном использовании того же имени не
отличим от нового. Поздний complete для pending не доказывает сам по себе
приёмку бизнес-артефакта; этот legacy-контракт не ужесточался. Usage и внешние
side effects не объединены в транзакцию с переходом статуса. Полная parity
свиперов/уведомлений и сетевой HTTP ещё не подтверждены.

Регрессии: `tests/Smoke/JobOwnershipIntegrationTest.php` — PostgreSQL,
включая управляемое чередование read/claim/UPDATE; Python
`workers/tests/runtime/test_queue_ownership.py` — PG SQL-контракт с подменой
соединения (не настоящий asyncpg/сервер).

## Обслуживание и уведомления

Старый прикладной планировщик удалён. Новый платформенный CLI:

```bash
bin/console portal:maintain
```

Один проход: reconcile/requeue stale, сбор результатов задач в уведомления,
outbox, дайджесты и poll мессенджеров (если настроены). Ошибка завершает команду
ненулевым кодом — оператор должен отслеживать его. Части доставки используют
свои блокировки; дополнительно исключайте параллельный запуск всей команды.
Пример cron от пользователя приложения (пути адаптировать):

```cron
* * * * * cd /srv/portal && flock -n /srv/portal/application/cache/maintain.lock bin/console portal:maintain >> /srv/portal/application/logs/maintenance.log 2>&1
```

Альтернатива — HTTP `/prx120/api/maintain` и `/prx597/api/outbox` с
`X-Worker-Token`. Не кладите токен в URL/cron-логи. Секции `schedule` манифестов
сами по себе ничего не запускают. Docker worker не запускает PHP maintenance;
таймер нужен отдельно. Общий HTTP-контроллер и опрос semantic status не
обслуживают очередь: посещения пользователей не заменяют таймер.

По умолчанию email выключен, мессенджеры не привязаны и внешние токены пусты.
Для email: `composer install`, `EMAIL_DSN`, `EMAIL_FROM`,
`PRX597_EMAIL_ENABLED=1`; настройте разрешённые каналы/шаблоны в админке.
Перед production проверьте SMTP, idempotency, retry и dead letter на тестовых
получателях. Не посылайте кадровые данные через внешние каналы по умолчанию.

## Серверные отчёты владельца очереди

Административные потребители используют `Service_Prx120_JobQueue::instance()`:

| Метод | Назначение/потребитель |
|---|---|
| `platform_metrics()` | pending/processing, failed всего и за 24 ч, done за 24 ч, две legacy-метрики зависаний; prx103 Health/Errors |
| `worker_activity()` | уникальные имена за сутки/10 минут, секунды с последнего пульса либо NULL; prx103 Health |
| `usage_today()` | сумма prompt+completion tokens и число строк usage с начала DB-дня; prx103 Health |
| `channel_metrics($channel)` | счётчики статусов по created_at за 24 ч, queued_recent, legacy-маркеры skipped/http-bridge за 7 дней; prx115 |
| `admin_activity()` | KPI за 24 ч, до 12 каналов, до 120 последних задач с ограниченной проекцией; prx595 |
| `stats()` | существующие счётчики статусов, теперь также Dev Doctor |

Все чтения идут через настроенное соединение очереди `prx120_jobs.db_group`,
не через случайный default потребителя. Новые методы находятся в существующем
Monitor-трейте, доступны через публичный JobQueue; нового универсального слоя
отчётов/SQL-фильтров нет. Числовые агрегаты нормализованы в int; отсутствие
последнего пульса — NULL. Ошибка БД распространяется в потребителя, который
сохраняет прежний диагностический fallback. Нулевые показатели сами по себе
не доказывают доступность/исправность worker-процесса.

`admin_activity` не возвращает payload/result/error/callback; остаются ID,
channel/status/visitor_id и даты. Это **доверенный административный контракт**,
не actor-aware API и не разрешение открыть отчёт любому пользователю.
`channel_metrics` квотирует канал и не возвращает содержимое задач.

Пороги не менялись при переносе: Health считает stuck по
coalesce(heartbeat_at, claimed_at, created_at), Errors — только heartbeat_at;
обе метрики используют 15 минут и не равны правилам обслуживания очереди.
`bridge` сохраняет прежнее условие: даже skipped=false считается наличием
маркера, а окно ограничено created_at, не временем завершения. Исправление
семантики и parity свиперов — отдельный следующий шаг, не скрытый рефакторинг.
Ни один отчёт не запускает обслуживание/доставку и не меняет статусы.

## Сбор завершённых задач для уведомлений

`JobQueue::pending_notifications($limit=40)` отдаёт ограниченную порцию
терминальных done/failed с владельцем (created_by либо visitor_id u:), без
notified_at; порядок id DESC. limit <= 0 — пусто без SQL. Поля совместимы с
job_update, включая payload/error: это доверенный серверный контракт, не UI/API.
`mark_notification_processed($id)` атомарно ставит notified_at только ещё не
отмеченной терминальной задаче с владельцем. Повтор даёт false и сохраняет
исходный timestamp. Оба вызова работают через db_group очереди и делегируют
конкретному внутреннему `Service_Prx120_NotificationJobs`, не читают prx597.

Notify::sweep_jobs занимается только обработкой порции и подтверждением через
фасад. При выброшенном исключении job_update задача не подтверждается;
ошибка выборки распространяется в maintenance, ошибка записи маркера прерывает
порцию как раньше. Счётчик sweep — число новых отметок, не доставленных писем.

**Перед запуском обновлённого кода выполнить db:migrate.** prx120/007 добавляет
notified_at через ADD COLUMN IF NOT EXISTS. Старые отметки не обнуляет и не
переносит. down намеренно не удаляет колонку: она могла существовать ещё до
миграции из старого runtime-DDL. Runtime больше не меняет схему очереди.

Ограничения: выборка + обработка + отметка — не единая транзакция двух модулей,
нет claim/lease на порцию. Сбой между созданием уведомления и отметкой или два
параллельных сборщика могут повторить обработку; использовать один maintenance-
процесс с блокировкой. Это не exactly-once и не квитанция SMTP/бота. Если
job_update подавил ошибку внутри себя/решил не создавать уведомление, возврат
без исключения по-прежнему считается обработкой. Дедуп канала не заменяет
атомарный inbox/outbox и этим переносом не усиливался.

## SQL-граница очереди после переноса

В prx103/prx115/prx595/prx597 прямые SQL-ссылки на `prx_120_*` устранены,
включая прежний ALTER/UPDATE в Notify. В test_queue_table_debt.py больше нет
исключений. Тест проверяет эти четыре модуля: это не аудит всей платформы и
не SQL-парсер. Новые потребители используют сервис владельца, а не добавляют
«платформенные исключения».

## Приоритеты обзора Python (17.11.2026; пересмотрено 23.11.2026)

Это рекомендации, а не описание уже внесённых исправлений. Риски `webread.py`
(граница сети, лимит загрузки) сняты удалением мёртвого модуля.

1. **Средний — конфигурация и повторяемость.** `Config.validate()` проверяет
   режим и адреса, но принимает отрицательные и неконечные значения
   интервалов (например `NaN`). Проверять положительные конечные таймауты,
   согласованность интервалов и размеры при старте; покрыть ошибочные env
   тестами. Уточнить поддерживаемый синтаксис собственного `.env`-парсера и
   рассмотреть фиксируемые зависимости и отдельные optional extras.
2. **Средний — последующее разбиение runtime.** `base.py` объединяет жизненный
   цикл, планирование, heartbeat и остановку; `queue.py` содержит оба транспорта
   и SQL. Небольшими шагами выделить эти обязанности за существующими
   интерфейсами и расширить общие контрактные тесты PG/HTTP: claim, heartbeat,
   complete/fail, retry, отмена, потеря владения и graceful shutdown.
   Существующие тесты очереди и watchdog сохранять; смену поведения отделять
   от механического рефакторинга.

## Структура `workers/`

```
workers/
├── README.md, pyproject.toml, requirements*.txt, .env.example
├── prx_workers/
│   ├── __main__.py  config.py  base.py  queue.py  usage.py  watchdogs.py  site.py  site_check.py
│   │           # runtime — очередь, сторожа, конфиг; не знает доменов
│   ├── llm.py  providers.py  llmwatch.py  ocr_client.py  docflow_trace.py
│   │           # общие клиенты без доменных знаний (ocr_client/trace — см. «Долг»)
│   └── handlers/
│       ├── __init__.py                 # реестр: HANDLERS, CONDITIONAL_CHANNELS, enabled(), active_handlers()
│       ├── prx120_jobs/                # echo, embeddings.index
│       ├── llm/                        # llm.summarize
│       ├── prx115_semantic/            # semantic.index
│       ├── prx395_document_extract/    # handler, document_extract, ocr-помощники, pdf_probe
│       ├── prx390_intake/              # doc.normalize
│       └── prx392_analysis/            # doc.analyze
├── mock/                              # мок-серверы LLM и эмбеддингов
└── tests/                             # зеркалит: runtime/, handlers/<пакет>/, clients/, mock/
```

Правила:

1. Пакет обработчика называется как модуль-владелец в `application/modules/`;
   канал из `worker.channels` манифеста ↔ файл с `CHANNEL` в этом пакете.
   Явная регистрация — только в `handlers/__init__.py` (`REGISTRY`,
   `CONDITIONAL_REGISTRY`); `.tools/portal_check.py` сверяет оба конца (нет
   канала без владельца, нет владельца без канала). Загрузка **ленивая**:
   обработчик импортируется отдельно, и сбой импорта (нет необязательной
   зависимости — `pydantic`, `langgraph`) отключает только его канал с одной
   строкой в журнал, а не весь воркер.
2. В корне `prx_workers/` — только runtime и клиенты. Всё, что знает `prx395`
   или `prx390`, живёт в их пакете. Обработчик, которому нужен PHP, объявляет
   `SITE = (префикс env, путь API, модуль, чей токен)` — `--check-site` читает
   только его.
3. Runtime не знает о пробе пера: `handlers.enabled()` спрашивает PHP,
   `__main__` лишь подмешивает trial-каналы, если ответ «включена».
4. Тесты зеркалят структуру (`tests/runtime/`, `tests/handlers/<пакет>/`,
   `tests/clients/`, `tests/mock/`); тесты пробы пера лежат вместе с ней.

Новый канал: `handlers/<владелец>/<канал>.py` с `CHANNEL`, `handle(ctx, payload)`
и, если нужен PHP, `SITE`; строка в `handlers/__init__.py`; `worker.channels`
в манифесте владельца; тест в `tests/handlers/<владелец>/`. Мёртвое удаляется
сразу: 23.11.2026 так ушёл `webread.py` (901 строка без единого импорта).

Долг: `ocr_client.py` и `docflow_trace.py` несут диагностический контекст
`doc.normalize` и нужны обоим — `document.extract` и пробе пера; обобщить до
нейтрального контекста задачи, когда проба пера будет удаляться или переделываться.

