## 1. Общее впечатление

Проект **архитектурно здоров и необычно хорошо документирован**. Для
одиночного/малого проекта дисциплина на уровне хорошего продакшн-команды:

- **Микромодульный монолит** — правильный выбор для этого этапа: один деплой,
  но модули изолированы как сервисы (свои таблицы `nj_<id>_*`, Service-слой,
  манифесты, миграции). Пути отхода к микросервисам реальные, не декларативные.
- **Четыре канала связи** (Service-вызов, шина событий, HMVC, очередь) —
  правило «не лезь в чужие таблицы» реально соблюдается в коде.
- **Асинхронный контур образцовый**: очередь в PostgreSQL (`SKIP LOCKED`,
  `pg_notify`), python-воркеры с heartbeat/ретраями/учётом ресурсов (usage.py),
  HTTP-режим для выноса воркеров на другой сервер. Проверено на живой очереди.
- **AGENTS.md/README на каждом уровне** + журнал ошибок агента
  (`docs/AGENT-LESSONS.md`) — редкий и очень ценный артефакт: платформа
  накапливает опыт вместо того, чтобы повторять грабли.
- Качество кода модулей хорошее: тонкие контроллеры, чистые сервисы
  (nj501_vat — образец), идемпотентные DDL, понятные вьюхи на Tailwind.

Главный системный риск, который подтвердила эта сессия: **расхождение
«документация/прод → свежая установка и CLI»**. На проде, где всё уже
существует, дефекты не видны; на чистой БД и в CLI они валятся каскадом.

## 3. Куда развиваться (мнение по стратегии)

### 3.1 Немедленно (до новых фич)

1. **Прогнать свежую установку в CI/песочнице после каждого релиза.**
   Все баги из §2 — из разряда «на проде не видно». Минимальный рецепт уже
   есть: `bash bin/setup-sandbox.sh` в чистой песочнице = «canary fresh install».
   Даже раз в неделю — огромный эффект.
2. **Довести тесты до регулярного запуска.** phpunit недоступен без
   packagist — mini_runner закрывает дыру, но лучше: (а) коммитить
   `vendor/` для dev-зависимостей нельзя, зато можно **раз в неделю** гонять
   тесты там, где сеть есть; (б) перевести тесты на mini_runner полностью —
   он покрывает текущие ассерты, phpunit нужен только для сложных моков.
3. **CLI-контракт платформы.** `db:migrate` — критичный путь деплоя: после
   фикса прод-пинок начнёт реально применять миграции. Перед следующим
   деплоем сверить `bin/console db:migrate --status` на проде (не отвалится
   ли 005/006 на проде — 006 как раз и лечит).
4. **80 МБ бинарник OpenSCAD в Git** (`workers/openscad-renderer/bin/openscad`).
   GitHub уже ругался. Перевести в LFS или качать на воркере при установке
   (hash-проверка + `WORKER_NJ570_SCAD_PATH`). Репозиторий похудеет на 80 МБ.

### 3.2 Ближний контур (1–2 спринта)

5. **Наблюдаемость** (уже есть в аудите P3 — подтверждаю приоритет):
   хвост ошибок `Kohana::$log` в `/nj100/admin` + счётчик 500/сутки. Цикл
   «ошибка→лог→фикс» сейчас требует SSH; а CLI-инциденты (как `_flag`) ещё и
   не попадают в веб-логи.
6. **Публичная страница поиска** `/search` с фильтрами по типам — самый
   дешёвый рост удержания: контент-конвейер (nj602/nj604) уже делает
   материалы, поиск по 6 таблицам есть, не хватает витрины.
7. **Composer-диета** (аудит P2.2) — подтвердилось grep'ом: в `application/`
   нет ни одного использования 9 пакетов. После контроля динамических
   загрузок — `composer remove`; это ускорит сборку образа и сузит поверхность
   безопасности. Оставить: symfony/mailer (почта), phpdotenv, phpunit (dev).
8. **mbregex.** Мой сборочный профиль шёл с `--disable-mbregex` (в коде
   `mb_ereg` не используется — проверено). Зафиксировать это как правило
   («mb_ereg в платформе не использовать — только preg_*»), иначе сборки
   PHP без oniguruma начнут падать неожиданно.
9. **Докрутить fresh-install в docker.** Тот же порядок-миграций баг убил бы и
   `docker compose up` с пустым томом БД. Прогнать `make fresh` в CI docker-а.

### 3.3 Стратегия продукта

10. **Сфокусироваться на 2–3 «флагманских» ИИ-сервисах вместо широкого
    каталога.** Сейчас 20+ сервисов по 90% готовности. У досье (nj598),
    профиля компании (nj591) и холодных писем (nj592) явная связка «найди
    компанию → пойми её → напиши письмо» — оформить как один продукт-воркфлоу
    («Разведка контрагента») с общей карточкой и сквозной оплатой nj601.
    Это лучше конвертирует трафик, чем 20 отдельных утилит.
11. **MCP-хаб (nj160) — конкурентное преимущество, его стоит подчистить и
    публично описать.** «Все инструменты N2J доступны твоему ИИ-агенту» —
    уникальное позиционирование; для этого нужны: публичная документация
    инструментов, token-менеджмент в личном кабинете, лимиты через nj120/usage.
12. **Контент-конвейер (nj602/nj603/nj604) довести до регулярного выпуска.**
    У платформы есть всё: генерация, модерация, расписание, новости. Публичный
    блог/новости + SEO = бесплатный входящий трафик для утилит. Очистить
    nj100-поиск под этот контент.
13. **Оплата nj601: включить после первого флагмана.** Robokassa-слоя нет в
    песочнице, но модель «сервисы бесплатны до лимита → лимиты через счётчик
    nj120/usage → продление через nj601» просится в код уже сейчас (счётчики
    уже считаются — не хватает порогов и страниц тарифа).
14. **Тех-долг Kohana — не трогать в лоб.** Конвенции проекта («не
    редактировать system/modules») правильные; стратегия миграции через
    Service-слой рабочая. Реалистичная цель на квартал — не «свернуть
    Kohana», а (а) вычистить депрекейшены STRICT_DEPRECATIONS=1 прогонами,
    (б) изолировать последние касания суперглобальных массивов в контроллерах
    (Request везде, но grep показывает оставшиеся $_GET/$_POST в сервисах).

### 3.4 Гигиена, замеченная в этой сессии

15. `routes.php` — мусорные пустые строки и дубль маршрута `universal_param`;
    `default` route с `welcome` в дефолтах конфликтует с реальнымWelcome-
    контроллером (проверить, что 404-логика не зависит от него).
16. В `.env.example` значение `DB_DEFAULT_HOST=127.0.0.1       # комментарий`
    — парсер справа trimming делает, но для глаз лучше без inline-комментариев.
17. `bootstrap.php` дважды подключает composer-автозагрузчик (root и DOCROOT
    vendor) — один раз с `is_file`, второй без. Оставить один guarded.
18. erp217/004/005 — исторически конфликтующие миграции — кандидат в
    «контрактный» чек-лист: после этой серии в `docs/AGENT-LESSONS.md` стоит
    добавить правило «явные id в миграциях → setval в той же транзакции».

## 4. Воспроизведение среды (что добавлено в репозиторий)

- **`bin/setup-sandbox.sh`** — полный автосборочный путь для закрытой сети:
  re2c (PyPI wheel) → m4 1.4.18 (патчи glibc 2.28+) → autoconf 2.69 →
  bison 3.0.4 (патч fseterr) → pkgconf → zlib 1.3.1 → OpenSSL 3.5.8 →
  libxml2 2.13.9 → curl 8.22.0 → PHP 8.4.25 (pgsql/pdo_pgsql против libpq из
  pgserver, mbstring без mbregex, opcache, curl) → PostgreSQL 16.2 (pgserver,
  порт 5432) → .env → миграции → админ → тесты → dev-сервер :8080.
- **`tests/mini_runner.php`** — мини-раннер тестов без composer/phpunit
  (поддерживает ассерты, используемые tests/Smoke и tests/Unit).
- **`bin/test`** — теперь падает в fallback на mini_runner, если vendor нет.
- **`docs/AGENT-LESSONS.md`** — уроки §2 этой сессии.

Быстрый старт в такой же песочнице:
```bash
bash bin/setup-sandbox.sh --serve     # соберёт всё и поднимет :8080
bash bin/test                         # 36/36
bin/console db:migrate --status       # состояние миграций
```

## 5. Резюме

Платформа в хорошем состоянии: архитектура выверенная, документация — редкий
случай, когда она **работает** (агенты и владелец реально сверяются с ней).
Самое слабое место — «непроверенные пути»: свежая установка, CLI, тесты.
Именно там за один день найдено 8 дефектов, половина — прод-критичные
(мёртвый CLI миграций означает, что пинок деплоя полгода не применял
миграции автоматически). Исправления внесены; регулярный fresh-install прогон
+ регулярный запуск тестов закроют этот класс проблем навсегда.
