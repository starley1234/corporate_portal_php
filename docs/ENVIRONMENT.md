# Окружение PRX

## Требования
PHP 8.4 CLI/FPM с pgsql, pdo_pgsql, mbstring, curl, openssl, JSON, session;
PostgreSQL 16+ (Docker: 17 + pgvector), Python 3.11+, Composer 2.
Node нужен только для сборки Tailwind, UI-тестов и `make architecture`;
собранные HTML/JSON коммитятся, на production Node не требуется.

```bash
bash bin/setup.sh                  # .env, секреты, runtime
# Проверьте .env: APP_URL, DB_DEFAULT_*, ADMIN_*.
make up                           # Docker: nginx/php/postgres/redis
make migrate                      # на чистой базе создаёт admin/admin
make seed                         # только если PRX_DEFAULT_ADMIN=0
```

Команды внутри Docker — в README. Bind mount корня скрывает vendor образа:
установите Composer-зависимости в смонтированный проект (через
`docker compose exec php composer install`) перед использованием email.
В закрытой сети setup создаёт только shim autoload: это **не** установленный
Symfony Mailer. Для настоящей почты обязательно `composer install`.

Нативно: `bash bin/restore-env.sh --serve`. В ограниченной сети:
`bash bin/setup-sandbox.sh` (сборка PHP и переносимый PG), затем
`PORT=8080 bash bin/serve`. Подробнее: SANDBOX-SETUP.md.

## Конфиги

`application/env.php` читает .env до bootstrap; окружение процесса важнее файла.
`application/config/modules.php` задаёт подключение и порядок миграций.
`APP_URL` задаёт canonical, ссылки писем и доверенный production-хост.
В development разрешены localhost и preview `*.e2b.app`.
`APP_INTERNAL_HOSTS` — явный CSV внутренних DNS-имён (не wildcard); Docker
задаёт `nginx`, чтобы HTTP-очередь и callbacks воркера шли внутри сети Compose.
Canonical URL остаётся APP_URL; браузер использует публичный адрес.
Не подставляйте адрес production в шаблон .env и не храните ключи в Git.

Публичный docroot — только `public_html/`. Файлы по умолчанию находятся в
`storage/` в корне проекта, вне docroot; runtime — в
`application/{cache,logs,sessions}`. В частности:

| Назначение | Путь относительно корня проекта |
|---|---|
| Локальный backend prx212 по умолчанию | `storage/prx212_file_storage/files` |

`bin/setup.sh` готовит каталоги и приватные права; prx212 также
создаёт отсутствующий каталог при первом обращении. Каталоги отключённого
docflow остаются на диске, но на свежей установке не создаются. По умолчанию новые
каталоги имеют режим `0700`, файлы prx212 — `0600`; backend может явно задать
свой `chmod`. Setup применяет `0700/0600` к существующему дереву. У процесса
PHP должен быть доступ на запись к корневому `storage`:
если его нет, исправьте владельца и права, **не** переносите его в docroot и
не ставьте `777`. Обычно PHP и CLI-задания запускаются от одного сервисного
пользователя (`DEPLOY_WEB_USER`). Setup запрещает symlink для корня и основных
каталогов storage; при обращении штатные пути prx212 также не проходят
через symlink в project/storage, а prx212 отклоняет ссылки внутри backend.

Для локального prx212 `config_data.root_path` в таблице
`prx_212_storage_backends` имеет приоритет над `local_storage_paths.default`
из конфига. Для совместимости произвольный относительный `root_path` prx212, как и раньше,
считается от рабочего каталога процесса (у CLI и FPM он может различаться),
поэтому его следует отдельно инвентаризировать и согласованно заменить на
абсолютный путь в `storage`. Старые значения `public_html/storage/...` в
настройках backend prx212 разрешаются в `storage/...`; так же
перенаправляется `storage/...` backend, если раньше он разрешался из docroot.
**Данные автоматически не копируются.** Произвольные явно заданные пути вне
project docroot не переключаются сами; путь в
другую часть `public_html` или symlink на неё отклоняется с ошибкой и требует
ручной миграции. Диагностика `bin/console dev:doctor` проверяет типовые, а не
все индивидуально настроенные backend и директории.

На одном хосте воркер берёт общие настройки из корневого `.env`.
Приоритет: окружение процесса → `workers/.env` → корневой `.env`. В Compose
внутренние адреса `postgres` и `nginx` уже настроены.
Резервируйте БД **и** файлы: `bin/backup.sh` по умолчанию включает `storage`
и старые `public_html/{storage,uploads,avatar,img}`; если переопределён
`DEPLOY_MODULE_STORAGE`/`BACKUP_PUBLIC_DIRS`, проверьте состав списка. Внешние
пути, S3 и другие пользовательские данные нужно включать отдельно. Проверяйте
состав и восстановление копии, а не только успешный запуск скрипта.

## Существующие DB-подписки и сроки документов

### Подписки prx208

`PRX208_DB_SUBSCRIBERS_ENABLED` по умолчанию равен `0`: активные строки
`prx_208_event_subscribers` не загружаются в шину. Это защитная мера: в старой
версии запрос подписок на PostgreSQL мог завершаться ошибкой, а исправление
сразу активировало бы накопившиеся обработчики. Подписки модулей через
`Event::listen` работающих модулей не зависят
от этого флага; журнал событий и прямые вызовы prx597 тоже не выключаются.
Статус «Активна» на странице подписчиков отражает только запись в БД, а не
подтверждение её исполнения. **Если DB-подписки на существующем сервере до
обновления работали, отсутствие явного `1` остановит их после обновления.**
Проведите инвентаризацию и согласуйте переход до развёртывания. События,
опубликованные при выключенной загрузке, автоматически повторно не проигрываются.
Изменяющие API `prx208_events/api`
теперь требуют POST и CSRF авторизованной сессии; проверьте и обновите старых
клиентов без CSRF. Отдельной токенной авторизации для внешних систем нет.

**Не включайте `PRX208_DB_SUBSCRIBERS_ENABLED=1` без инвентаризации.** На
staging с копией настроек и проверенной резервной копией БД:

1. Просмотрите все активные и неактивные строки в `/prx208_events/list_subscribers`
   либо в защищённой SQL-сессии: `SELECT id, event_name, module_id,
   callback_method, is_active, is_notification FROM prx_208_event_subscribers
   ORDER BY id;`. Список может содержать сведения о внутренних интеграциях —
   не публикуйте его. Подтвердите владельца, код callback, получателей и каналы,
   удалите либо выключите ненужные записи только по согласованному плану.
   Чистая БД содержит исторические демонстрационные подписки и мост очереди.
2. Особенно проверьте строки `prx120.job_done` и `prx120.job_failed` с
   `is_notification=true`: включённый мост может создать уведомление вдобавок
   к обработке той же задачи через `prx597::sweep_jobs()`. На изолированной БД
   такой дубль в колокольчике воспроизведён. Выключите избыточный мост **до**
   включения общего флага, если согласован существующий путь уведомления очереди.
   Отдельные DB-строки уведомления одного события теперь дают один вызов моста,
   но это не дедуплицирует независимые вызовы других модулей или sweep. Не
   включайте одновременно для тех же событий wildcard `proxy_to_notification_center`
   и DB-мост: их вызовы тоже независимы.
3. После аудита установите `PRX208_DB_SUBSCRIBERS_ENABLED=1` в окружении сайта
   и PHP CLI-задач, обновите процессы по правилам стенда и проверьте каждую
   нужную цепочку на тестовых пользователях и контролируемых событиях. Изменения
   списка подхватываются при новой инициализации шины, а не посреди уже работающего
   долгоживущего PHP-процесса. При сомнениях оставьте `0`; обратное переключение
   не отменяет уже выполненные действия и не удаляет уведомления из outbox.

`prx597::sweep_jobs` нужен и для Python-воркеров, завершающих задания напрямую
в PostgreSQL; расписание — [WORKERS.md](WORKERS.md#обслуживание-и-уведомления).
На тестовом PHP прямой хук очереди с нормализованным массивом payload завершился
ошибкой преобразования, уведомление появилось только после sweep. Это отдельный
существующий дефект, не гарантия доставки: sweep также может отметить задачу
обработанной после ошибки. Не меняйте `notified_at` массово и не считайте
отправку проверенной без отдельной сверки настроек, пользователей и каналов.
На чистой тестовой БД общий `/prx100/errors` запрашивает у `prx_597_outbox`
отсутствующий столбец `error` (в схеме используется `last_error`) и пропускает
этот источник. Успешная загрузка страницы не подтверждает отсутствие ошибок
outbox; проверяйте состояние отдельно и не передавайте текст ошибок без проверки
на приватные данные.

### API PDF → текст (`prx395`)

`PRX395_DOCUMENT_EXTRACT_CLIENTS` — JSON с отдельным Bearer-ключом каждой
интеграции; `{}` закрывает доступ. Параметр задаётся на PHP, не на Python.
Воркеру в любом режиме очереди нужны `APP_URL` (или `PRX120_API_BASE`), `WORKER_API_TOKEN` и
канал `document.extract`. `OCR_PROVIDER=tesseract|remote` выбирает движок;
для `remote` задайте `OCR_SERVICE_URL` до `/parse`. См. [запуск и проверку](integrations/document-extractions.md).

### Восстановление сроков prx393 (история)

> Контур предназначен для тестовых документов. [Короткая инструкция](QUICK-CHECK.md).

Для новых регистраций и изменений карточки запускается пересчёт срока; при
успешном выполнении закрытие снимает его с контроля, а возврат в работу
открывает вновь. Маршрутизация и регистрация не составляют одну атомарную
операцию: сбой слушателя фиксируется в `prx393_diag`, но не повторяется сам
и может оставить неполные данные. Это исправление **не** восстанавливает старые
сроки автоматически. До любых действий сохраните и
проверьте резервную копию БД; согласуйте с владельцем документов сверку
исторических значений. Для оценки масштаба можно выполнить только чтение:

```sql
SELECT count(*) FILTER (WHERE d.status NOT IN ('closed', 'archived') AND dl.id IS NULL) AS open_without_deadline,
       count(*) FILTER (WHERE d.status IN ('closed', 'archived') AND dl.status = 'open') AS closed_with_open_deadline
FROM prx_391_documents d
LEFT JOIN prx_393_deadlines dl ON dl.document_id = d.id;
```

Для выбранного открытого документа менеджер может использовать «Пересчитать
маршрут» в карточке. Массовая кнопка на `/sla` затрагивает **не более 200**
самых свежих открытых документов и не проверяет закрытые. Пересчёт использует
текущие данные карточки, правила и календарь: он может изменить существующие
сроки, роль, отдел и приоритет и не восстанавливает их историческое значение.
Закрытые документы с ошибочно открытым сроком, документы без срока и старые
эскалации требуют отдельного согласованного плана восстановления; не выполняйте
массовые SQL-правки вслепую.

Страница `/sla` фильтрует карточки по правам prx391 среди 60 ближайших сроков
и 20 последних эскалаций. При ограниченном доступе общие показатели скрыты;
доступная запись за пределами этих выборок на странице не появится. Лента
`/prx391_documents` также не показывает историю недоступных карточек.

**Важное оставшееся ограничение доступа.** Это не аудит всего документооборота.
На изолированном стенде пользователь только с ролью `login` получал 404 у
персональной/коммерческой карточки, но видел тему её конверта на `/inbox`, тему
и содержание предложения на `/analysis` и тему и текст черновика на `/replies`.
Эти страницы пока не фильтруют данные по доступу к карточке. До отдельного
исправления и проверки всех смежных маршрутов не используйте реальные
персональные или коммерческие документы на стенде, доступном пользователям без
полного доступа к ним. Скрытие ссылок или защита только `/sla` не устраняет
утечку; временное ограничение должно охватывать весь доступ к системе и быть
проверено на стенде. Не выдавайте всем дополнительные роли как «исправление».

`/prx393/api/health` не использует пользовательскую сессию: он отдаёт общую
статистику сроков держателю `X-Worker-Token` (приоритет: `PRX393_SITE_TOKEN`,
`WORKER_SITE_TOKEN`, `WORKER_API_TOKEN`). В production при пустом или неверном
токене API закрыт; в development при незаданном токене он открыт. Не открывайте
такой development-стенд наружу и выдавайте токен только доверенным процессам
мониторинга: этот ответ не фильтруется по правам отдельного пользователя.

Запись эскалации и публикация события не доказывают доставку: на чистой БД
нет стандартной DB-подписки на события сроков, а wildcard-мост выключен.
При формировании события адресаты роли дополнительно проверяются на доступ к
конкретной карточке; изменение прав или грифа после постановки в outbox здесь
не перепроверяется. Ранее созданные уведомления и события не очищаются. Прежде
чем полагаться на уведомления о сроках, отдельно согласуйте интеграцию, проверьте
права/получателей/каналы на staging и учтите, что уже записанные эскалации
автоматически не повторяются. При проверке через `/sla` текущий пользователь
становится инициатором события, и мост может исключить его из получателей;
проверка из CLI отличается. Строки `prx208_diag` и `prx393_diag` не содержат
текст исключения и SQL, однако общие и PostgreSQL-логи могут содержать данные
документов; проверяйте отобранные строки перед передачей.

## Перенос существующего public_html/storage

**Не выполняйте обычный live-deploy с переключением путей до копирования.**
Новый код сразу читает перенаправленные пути; если старые файлы не скопированы,
они останутся на диске, но приложение их не найдёт. Сам setup и deploy ничего
из старого дерева не перемещают и не удаляют. Проведите перенос в окне
обслуживания по согласованному плану:

1. Ограничьте доступ к сайту режимом обслуживания и остановите **всех**
   писателей: PHP/FPM и загрузки, worker, cron/systemd-таймеры `prx390:scan` и
   `portal:maintain`, внешние интеграции и ручное помещение файлов в inbox.
   Убедитесь, что закончились запущенные задачи и никакой процесс не меняет
   ни исходное, ни целевое дерево на время проверки и копирования.
2. Сделайте согласованную резервную копию БД, `storage`,
   `public_html/storage` и всех иных фактически используемых файловых backend.
   Проверьте содержимое и возможность восстановления. До перехода сохраните
   конфигурацию `.env` и настройки веб-сервера в защищённом месте.
3. Инвентаризируйте четыре `PRX390_*_DIR` и все локальные backend в БД,
   включая неактивные и используемые старыми файлами. Например, в защищённом
   терминале выполните `SELECT id, name, is_active, config_data FROM
   prx_212_storage_backends WHERE driver = 'local' ORDER BY id;` и отдельно
   `SELECT backend_id, count(*) FROM prx_212_files WHERE deleted_at IS NULL
   GROUP BY backend_id;`. Вывод конфигурации может содержать чувствительные
   сведения — не помещайте его в публичные логи. Убедитесь в свободном месте.
4. Установите новую версию, **не открывая сайт и не возобновляя запись**.
   Подготовьте владельца PHP (пример `www-data`, замените на своего):

   ```bash
   sudo env DEPLOY_WEB_USER=www-data bash bin/setup.sh
   sudo python3 bin/migrate-storage.py          # только preflight, диск не меняет
   sudo python3 bin/migrate-storage.py --apply  # копирует без перезаписи
   sudo python3 bin/migrate-storage.py --verify # все исходные каталоги и файлы совпадают
   sudo env DEPLOY_WEB_USER=www-data bash bin/setup.sh  # владелец и приватные права копии
   ```

   Команды выполняются из корня проекта. Preflight проверяет всё дерево;
   конфликтующие файлы, symlink и специальные файлы останавливают перенос
   **до копирования**. Совпадающие файлы сравниваются по SHA-256, разные не
   перезаписываются, частичная копия при ошибке удаляется, источник сохраняется.
   При конфликте разберите его вручную с сохранением обеих версий и повторите
   проверку. `--verify` возвращает ненулевой код, если чего-то не хватает.
   Запустите его **до** возобновления записи: после работы сканера старый inbox
   и новая папка закономерно могут разойтись. Повторный `--apply` после запуска
   приложения способен вернуть в inbox старые файлы; не делайте его без новой
   остановки и отдельной сверки данных.
5. Этот инструмент переносит только `public_html/storage` в `storage`, сохраняя
   относительные пути. Он **не** переносит произвольные `root_path`, S3,
   `public_html/uploads`, `avatar` или `img` и не меняет их ссылки в БД.
   Для каждого нестандартного пути составьте отдельный план: скопируйте без
   перезаписи в выделенный каталог `storage`, проверьте файлы и лишь затем
   измените соответствующий `.env` или `config_data.root_path`. Старые
   исторические ссылки и символические ссылки в `storage_path` тоже требуют
   проверки. Старые uploads/avatar/img могут по-прежнему отдаваться веб-сервером:
   инвентаризируйте их и закройте или перенесите по отдельному плану до приёма
   конфиденциальных данных. Не удаляйте их автоматически.
6. Проверьте чтение и запись **от пользователя PHP/CLI**, затем на staging
   скачивание существующих файлов с разрешённым аккаунтом и отказ гостю.
   Настройте и проверьте
   запрет прямой HTTP-выдачи старого дерева, включая физически существующий
   файл, не блокируя виртуальный `/storage/get/<id>`. Только после этого
   возобновите задачи и трафик. Сохраните старую копию вне docroot по политике
   резервирования и удаляйте исходник лишь после проверки и окончания периода
   отката. Откат одного кода недостаточен: после новых записей нужно отдельно
   согласовать восстановление/сверку актуальных файлов и БД.

`public_html/.htaccess` закрывает старый `/storage/` на Apache при включённых
`mod_rewrite` и `AllowOverride`. Для nginx нужен отдельный конфиг — `.htaccess`
он не читает. В `docker/nginx/default.conf` уже предусмотрены следующие правила;
их эквивалент нужно установить и проверить в конфигурации другого сайта:

```nginx
location = /storage { return 404; }
location ^~ /storage/ {
    rewrite ^/storage/get/[^/]+/?$ /index.php last;
    return 404;
}
```

Они должны использоваться вместе с существующим PHP-FPM location и конфигурацией
приложения. Доступ к файлам prx212 по-прежнему осуществляется через контроллер
и его ACL, а не через прямую раздачу каталога.

## Проверки

- `make check` — структурные контракты и тесты переноса без БД; тест dev-роутера
  дополнительно запускается при наличии PHP.
- `bash bin/check-fresh.sh` — временная БД, миграции дважды, PHP-тесты и CLI
  обслуживания. Требует у dev-роли право CREATE DATABASE; не для production.
- `SMOKE_URL=http://localhost:8080 bash bin/check-fresh.sh` — дополнительно HTTP
  уже работающего сайта с админом из локального .env (не временной БД).
- `source bin/_env.sh; prx_load_env .env; python3 tests/http_smoke.py` — только HTTP.
- `npm ci && npm run build:css && npm test` — локальные assets и общий UI.
- `PYTHONPATH=workers python3 -m pytest workers/tests -q` — worker regression.

Скрипт fresh не запускает и не оставляет фоновых HTTP-серверов.
Настройка maintenance timer описана в WORKERS.md. Сам worker не отправляет
PHP outbox без этого таймера.
