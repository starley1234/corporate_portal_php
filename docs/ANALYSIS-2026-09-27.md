## 2. Архитектура как она есть

**Микромодульный монолит.** Один репозиторий, один фронт-контроллер, но каждый сервис —
свой модуль: `Controller/`, `Service/`, `views/`, `config/nj_module.php`, `migrations_pg/`,
свой README/AGENTS. Общие механизмы вынесены в ядро:

1. **`nj100_platform`** — ратлимит, поиск по каталогу, «хвост ошибок», дашборд, апдейтер.
2. **`nj110_catalog`** — реестр модулей: читает 63 манифеста, строит меню, каталог
   `/services`, поиск, права видимости по ролям.
3. **`nj120_jobs`** — очередь задач: claim (`FOR UPDATE SKIP LOCKED`), heartbeat,
   watchdog, ретраи с backoff, hard-stop, `reconcile` для «залипших», учёт ресурсов
   (`nj_120_usage`: токены/модели/веб-чтение/ошибки/время), монитор `/nj120/monitor`.
4. **`nj160_mcp`** — MCP-хаб: внешние ИИ-агенты вызывают инструменты платформы,
   API-токены (sha256-хеш в БД, ключ виден один раз).
5. **`nj601_billing`** — счета/списания (Robokassa).
6. **`nj603_kicker`** — расписания/пиналки всех модулей.
7. **`erp100_base`** — авторизация, ACL (config-driven, роль admin = полный доступ),
   общий контроллер-базис, шапка/меню.

**Воркеры** (`workers/n2j_workers/`): асинхронный пул (concurrency 4), 24 канала,
LLM-слой с несколькими провайдерами (`Provider`, `resolve_model`, `llmwatch` для
пульса «модель думает N с»), webread/поиск, «usage»-трекер, сторож. Воркер умеет
работать и через PostgreSQL-очередь, и через HTTP — это редкая и полезная гибкость.

**Сквозные правила, которые реально соблюдаются** (это видно по коду):

- владение данными: таблица `nj_<id>_…` принадлежит модулю;
- миграции идемпотентны (`IF NOT EXISTS`), у 14 модулей есть аварийный
  `ensure_tables()` под env-флагом (`NJxxx_SCHEMA_AUTOCREATE=1`) — по умолчанию выключен;
- env-переменные полным слагом, примеры `.env` синхронны коду (есть сторож-тест);
- ошибки в БД, «молчащая» задача → `failed`, авто-стоп, рапорты о ходе вместо «завис»;
- свои линтеры и стенды (`.tools/php_check_all.sh`, `phpwasm_stand.mjs`,
  `bin/check-fresh.sh`, `dev:doctor`, `bin/console db:migrate --status`).

## 3. Сильные стороны (что не надо ломать)

1. **Скорость добавления нового сервиса.** `make new-module` + манифест + миграция →
   сервис уже в каталоге, в меню, с правами и в поиске. 83 модуля — доказательство,
   что конвейер работает.
2. **Очередь и мониторинг задач** — не игрушечные: SKIP LOCKED, heartbeat, watchdog,
   reconcile, `usage`-таблица, монитор с пульсом. Это уровень промышленной платформы.
3. **Единый LLM-слой в воркере** с провайдерами, моделями и учётом токенов. Сменить
   провайдера можно env-переменной, не трогая 20 модулей.
4. **Безопасность по умолчанию.** Файлы вне `public_html` закрыты nginx, `.env` — deny,
   ACL из конфига, `hash_equals` для воркер-токенов, ратлимит ~5/мин на публичных
   эндпоинтах, SSRF-фильтры в webread, никаких `exec` с пользовательским вводом.
5. **Документация как часть продукта**: `AGENTS.md`, `docs/ARCHITECTURE.md`,
   `docs/WORKERS.md`, `docs/AGENT-LESSONS.md` (2329 строк уроков), аудиты от 21–22.09.
   Плюс MCP-хаб — редкое конкурентное преимущество (инструменты платформы доступны
   внешним ИИ-агентам).
6. **Тесты Python** покрывают воркеры (294 теста), есть «песочные» стенды для PHP.

## 4. Слабые места и риски (с доказательствами)

### P0 — риск потери денег/данных и «сервис лежит»

**4.1. Деплой и миграции рассинхронизированы.** `bin/deploy.sh` умеет накатывать
миграции (`DEPLOY_AUTO_MIGRATE=1`, вызов `bin/console db:migrate`), но корневой
`update.sh` (пинок `/update/kick/<token>`) миграции **не** применяет. Схема на проде
отстаёт от кода → ошибки 500 (уже ловили на `/nj602/admin`, `/nj643/cad`).
Также в скрипте лежал зашитый дефолт `DEPLOY_BRANCH` — рабочая ветка сессии;
если её смёржить в `main`, прод застынет на старой ветке.
*(Зашитый дефолт убран 28.09.2026: ветка задаётся только на сервере.)*
*Лечение:* один путь деплоя (обёртка), обязательный `db:migrate --status` до рестарта,
`--migrate` по умолчанию, откат на предыдущий коммит одной командой.

**4.2. Нет CI.** Каталога `.github/` нет. Все «прод-только» 500-ки последних недель
(`action_archive` дважды, `_filters`, TypeError в imagegen) — класс ошибок, который
ловится прогоном `php_check_all` + `check-fresh` + pytest. Инструменты уже написаны,
не хватает автоматического запуска (GitHub Actions на pull request или pre-push хук).

**4.3. PHP-тесты почти не покрывают сервисы.** 12 файлов на 90 сервисных классов;
`phpunit` не ставится в дев-среде (packagist недоступен), работает `mini_runner`.
Критичные для денег и данных места — `JobQueue`, `Billing`, отчёты `usage` — тестами
не закрыты (кроме `Ratelimit`).

**4.4. Резервные копии только для БД.** `docs/DEPLOY-UBUNTU.md` описывает
`pg_dump | gzip` в cron. Хранилища модулей (`storage/nj580`, `storage/nj590`, архивы
CAD-деталей, загруженные файлы) в бэкап не попадают — восстановление БД без них даст
битые карточки.

### P1 — производительность, деньги, наблюдаемость

**4.5. Кэш не используется.** Один вызов `Cache::instance()` на весь проект;
`bootstrap.php` поднимает Kohana с кэшированием выключенным. При этом на каждом
запросе с меню читаются 63 манифеста (`Service_Nj110_Catalog::modules()` — static
только внутри запроса). Это десятки `include`/`stat` на каждую страницу.
*Лечение:* точечный кэш (APCu/файловый) на каталог/меню и summary-выборки на 5–10 минут.

**4.6. N+1-запросы.** 29 файлов делают запросы внутри циклов; лидеры: `nj570` (28),
`nj580` (44), `nj570`, `nj602` (41), `nj593` (34), `nj115` (28). Пока объёмы малы — не
больно, при росте таблиц станет главным источником «страница думает 5 секунд».
*Лечение:* батч через `IN (…)`/`LATERAL`, GIN-индексы `pg_trgm` под ILIKE-поиск.

**4.7. Расход токенов учитывается, но не превращается в деньги.** В
`nj_120_usage` есть `llm_calls`, `prompt_tokens`, `completion_tokens`, `elapsed_ms`
по каналам/моделям — отличная база. Но цен моделей в конфиге нет (`grep price` — пусто),
страницы «расход в рублях» и порогов/лимитов нет. При этом `Service_Nj601_Billing::charge()`
вызывают только **два** модуля (`nj606`, `nj607`), остальные 8+ LLM-модулей тратят
токены «в никуда».
*Лечение:* таблица цен (модель → цена за 1K prompt/completion), отчёт «рубли за период»
на базе `nj_120_usage`, пороги и лимиты, затем списание через `nj601` в одной точке
(хук на завершение задачи, а не 20 вызовов в модулях).

**4.8. Наблюдаемость разрознена.** Есть `/nj100/errors` (хвост ошибок из БД и логов),
`/nj120/monitor`, `/nj603/admin`, `/nj120/usage`, `dev:doctor`, но нет:
единого `/health`-эндпоинта платформы, истории глубины/времени очереди по каналам,
алертов (например, «канал молчит 10 минут» или «500 за сутки > N») — при том, что
уведомления `nj597` уже есть.

**4.9. Очередь: одна «труба».** Один сервис воркера, concurrency 4, 24 канала.
Длинные задачи (CAD nj643, imagegen nj641) делят пул с быстрыми, приоритет —
`priority, id`, без anti-starvation: поток задач с priority=0 отодвинет всё остальное.
*Лечение:* вынести 2–3 долгих канала в отдельный сервис (уже возможно через env),
добавить приоритет по возрасту задачи и метрику «ожидание в очереди».

### P2 — долг и гигиена

**4.10. `JobQueue.php` — 2451 строка, 36+ методов** в одном классе: жизненный цикл,
watchdog, reconcile, уведомления, отчёты. Работает, но любая правка — риск.

**4.11. Чужие таблицы в общих конфигах.** `nj120_jobs/config/nj120_jobs.php` содержит
18 `reconcile_hooks` с SQL по таблицам других модулей (`nj_602_*`, `nj_591_*`, `nj_643_*`…),
а `nj603_kicker/config/nj603_kicker.php` хранит расписания 14 чужих модулей (85 пар).
Это нарушает правило «владелец таблицы»: правка чужой схемы ломает ни в чём не повинный
модуль. Правильно — реестр: модуль сам объявляет свой reconcile/расписание, ядро их собирает.

**4.12. Мёртвый и лишний груз.** Модуль `yandexauth` не зарегистрирован в
`bootstrap.php` (мёртвая ветка кода и `YANDEX_OAUTH_CLIENT_ID` в примерах).
9 composer-пакетов не используются в `application/` (guzzle, phpspreadsheet, phpword,
dompdf, monolog, carbon, mqtt, amqplib, commonmark) — но тянутся в образ.
`public_html/adminer/index.php` (496 КБ) лежит в корне сайта.

**4.13. Внешние CDN на каждой странице.** Tailwind (`cdn.tailwindcss.com`),
Font Awesome (cdnjs), jQuery (code.jquery.com) — без SRI и без локального фолбэка:
любая блокировка/подвисание этих хостов = «сайт без стилей». При этом mermaid (3,2 МБ)
и three.js (592 КБ) уже локальные.

**4.14. Мобильные админки.** Владелец уже видел проблему на `/radar` и `/leads`
(исправлено в `e881b85`). Такой же `whitespace-nowrap` в таблицах ~12 админок
(nj580/590/594/595/597/600/602/603/607/609 и др.) — на телефоне горизонтальная прокрутка.

**4.15. Разные UI-паттерны в админках.** Каждая из ~14 админок сама реализует
таблицу/пагинацию/чипы/поиск (одинаковые по смыслу куски кода). Один общий JS/шаблон
(«таблица админки») убирает дубли и ускоряет следующие правки.

## 5. Куда развивать: план по направлениям

### Направление A. Надёжность контура выпуска (1–2 дня работы, максимальный эффект)

1. Один деплой: `bin/deploy.sh` — единственный путь; `update.sh`/пинок вызывают его;
   миграции по умолчанию, `db:migrate --status` в лог, откат `--rollback <sha>`.
2. CI-минимум (GitHub Actions): `php_check_all`, `pytest`, `dev:doctor`, `check-fresh`
   на каждый push. Хук pre-push как фолбэк, если CI недоступен.
3. Единый `/health` (БД, миграции, очереди, воркер, движок CAD) + алерт в `nj597`
   («канал молчит N минут», «500 за сутки»).
4. Бэкап хранилищ модулей (tar/rsync в тот же cron) + репетиция восстановления.

### Направление B. Деньги (2–3 дня)

5. Цены моделей в конфиге воркера + отчёт «токены → рубли» на `/nj120/usage`
   (данные уже есть, нужна арифметика и витрина).
6. Лимиты/тарифы: «бесплатно до N токенов в сутки», порог → мягкое предупреждение,
   превышение → 429 с понятным текстом.
7. Списание через `nj601` из одной точки (завершение задачи) вместо вызовов в модулях;
   Robokassa довести до боевого (счёт → оплата → баланс → письмо).

### Направление C. Продукт: один флагман вместо 20 утилит (3–5 дней)

Уже есть цепочка «нашёл компанию (nj642/nj591) → понял её (nj598) → написал (nj592) →
провёл серию касаний (nj612) → оценил отрасль (nj607) → нашёл лиды (nj606)».
Оформить это как **«Разведка контрагента»**: одна карточка компании с вкладками
(профиль, досье, вакансии, письма, лиды), общий прогресс и одна кнопка «начать».
Сейчас пользователь ходит по 6 разным страницам и теряет контекст.

Дополнительно:
8. **MCP-хаб (nj160) как канал продаж**: страница токенов в личном кабинете
   (создание/отзыв/лимиты — API уже есть), публичная документация инструментов,
   учёт вызовов через `nj120/usage`.
9. **Рассрочка контента/SEO**: `sitemap.xml` и OG-теги есть; добавить schema.org
   (`SoftwareApplication`), RSS статей, перелинковку «статья → сервис», страницы
   городов/направлений для вакансий (авто-режим nj642 уже это умеет).
10. **Качество ИИ**: распространить `nj639_qc` на все LLM-модули как единый
    пост-процесс (проверка дублей/языка/фактов) — доверие к ответам дороже новых фич.

### Направление D. Инженерный фон (можно волнами, по 2–3 модуля)

11. Разделить `JobQueue` на «жизненный цикл / reconcile / уведомления / отчёты»
    без смены внешнего API.
12. Реестры вместо чужих конфигов: `reconcile_hooks` и расписания `nj603` —
    объявляются модулями-владельцами.
13. Кэш каталога/меню + HTTP ETag на публичные GET-API; GIN/pg_trgm под поиск.
14. 9 неиспользуемых composer-пакетов — удалить; adminer вынести из `public_html`;
    `yandexauth` — включить или архивировать (решение владельца).
15. Общий UI-набор админок (таблица/пагинация/чипы/поиск) + мобильные таблицы
    в оставшихся ~12 админках.
16. Локальные копии Tailwind/jQuery/FontAwesome (или SRI + фолбэк) — страницы
    перестанут зависеть от внешних CDN.

## 6. Что предлагаю начать прямо сейчас

Порядок с максимальным отношением «польза/риск»:

1. **Спринт A** (надёжность): один деплой с миграциями, CI-минимум, `/health` с
   алертом, бэкап хранилищ. Это снижает риск «сервис лежит» до почти нуля и делает
   все дальнейшие изменения безопасными.
2. **Спринт B** (деньги): цены моделей + отчёт в рублях + пороги. Даже без Robokassa
   это даёт владельцу точную картину себестоимости и готовность к тарифам.
3. **Спринт C** (продукт): «Разведка контрагента» одной карточкой.

Всё из направлений D можно делать фоном — по одному пункту на спринт, не смешивая
с функциональными правками.
