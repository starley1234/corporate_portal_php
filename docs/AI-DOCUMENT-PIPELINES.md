# ИИ-пайплайны документов для корпоративных систем

**Решение:** первым делать самостоятельный API **«PDF → текст»**, а не новый реестр
или копию портала. Получатель результата — СЭД/ERP/внутренняя система. Она остаётся
источником истины для карточек, сроков, маршрутов и отправки писем. PRX принимает
файл, обрабатывает его и отдаёт результат с техническими метаданными. Первый этап реализован как `prx395`; [конфигурация и точный контракт](integrations/document-extractions.md).
Ниже — исходный разбор и дальнейшие этапы.

В `index.html` также есть ссылки на экспресс-анализ письма и сверку OCR с
оригиналом, но `pages/mail_analyse.html` и `pages/viewer.html` в этом checkout
нет. Прототипы изучены по коду, а не прогнаны против закрытого шлюза. Их не стоит
публиковать как есть: браузер прямо обращается к внутренним сервисам, ресурсы
берутся с CDN, вывод из документа и модели местами вставляется как HTML, а
JSON от модели не проверяется строгой схемой. В PRX вызовы — только с сервера,
UI (если нужен оператору) минимальный и использует локальные ресурсы.

## Распознавание: одна настройка, разные возможности

- **Разработка: `OCR_PROVIDER=tesseract`.** Для PDF нужны ещё `pdftoppm`
  (Poppler) и языковые пакеты (`rus`, `eng`) именно там, где работает Python.
  Уже есть заготовки `pypdf` и Tesseract. Для текстовых страниц читать слой PDF,
  для сканов — OCR. Смешанный PDF проверять постранично: хороший текст на
  первой странице не означает, что распознаны следующие. Лимит страниц нельзя
  превращать в молчаливое усечение. Текст — да; корректную структуру таблиц
  локальный движок не обещает.
- **Production: `OCR_PROVIDER=remote`, `OCR_SERVICE_URL`** — адрес шлюза в
  окружении воркера (`workers/.env` при отдельном запуске, корневой `.env` в
  Docker). По прототипам: `POST /parse?engine=auto&output_format=md&do_ocr=true`,
  PDF в multipart-поле `file`, результат в JSON `content`. Для таблиц есть
  дополнительный query-флаг `do_table_structure=true`. Токен — `OCR_API_KEY`
  при необходимости, таймаут — `OCR_TIMEOUT`. Настройки не принимаются от
  клиента и не передаются в браузер или payload задачи.
- **Разрыв контракта:** текущий `RemoteOcrProvider` ждёт `text`, а
  `OCR_EXTRA_PARAMS` кладёт в multipart, не в query. URL сам по себе не сделает
  старый адаптер совместимым. Новый `document.extract` использует отдельный адаптер `/parse` с явным контрактом
  (query, `content`, непустой результат и корректная классификация отказов).
  Согласовать авторизацию, лимиты, метаданные страниц и политику хранения у
  владельца шлюза; не выдумывать номер страницы или confidence, если их нет.
  Если нужен старый формат, выбирать его отдельно. Не переключать провайдер
  автоматически при ошибке: иначе тихо изменится качество и формат результата.

## Пилот: один файл, понятный статус и результат

1. Новый прикладной модуль без зависимостей от HR и архива. API: например,
   `POST /api/v1/document-extractions` с файлом возвращает `202` и `job_id`;
   `GET /api/v1/document-extractions/{job_id}` — статус и результат либо
   стабильный код ошибки. Сначала polling, webhook — только по необходимости.
   Машинная аутентификация — ключ `prx150` со scope `prx395.extract`, отдельный
   на интеграцию; чужое задание и файл не выдаются ни по ID, ни по ключу
   идемпотентности.
2. Валидировать тип, размер и лимит страниц. PDF в закрытом `prx212`, ID в
   `prx120`; Python извлекает текст, PHP возвращает результат. Согласовать TTL
   файла и результата и явно удалять по политике. Один `Idempotency-Key` на
   клиента и тело запроса: повтор не создаёт работу, другой файл с тем же
   ключом — конфликт. Без папок, cron-сканера, LLM, маршрутов и писем.
3. Результат: текст (Markdown допустим, формат указан явно), провайдер, число
   обработанных страниц, если известно, и предупреждения. Статусы: `queued`,
   `running`, `succeeded`, `failed`, `canceled`. Отличать битый/зашифрованный
   PDF, отсутствие текста, превышение лимита, недоступный OCR, таймаут и
   неподдерживаемый ответ. Повторять только временные ошибки. В логах этап,
   ID задания, длительность и код ошибки — без текста, файлов и секретов.
4. Критерий готовности: тестовые текстовый PDF, русский скан, смешанный PDF,
   пустой результат, битый файл и таймаут дают предсказуемые статусы;
   локально есть реальный прогон Tesseract, HTTP-адаптер проверен контрактным
   тестом и одним сканированным PDF из сети воркера на production-шлюзе.
   Отдельно проверить повтор, приватность между клиентами и удаление по TTL.

Когда один файл стабильно проходит весь путь, добавить **«текст → реквизиты
письма»** через платформенный LLM-клиент: строгая схема, `null` вместо догадки,
цитаты из источника для ключевых полей, никакой записи в системы потребителя
от имени модели. Только затем — пакетная подача, рубрикация и отдельный пилот
таблиц. Так каждую стадию можно проверить независимо от следующей.
