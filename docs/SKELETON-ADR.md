# Каркас PRX: решения (ADR)

Зачем: пока каркас не зафиксирован, каждый новый модуль трактует его по-своему.
Здесь — **решения**, а не код.

> **Статус ратификации (актуально на 2026-11-25):** **все 7 решений утверждены.**
> Проверка по коду показала, что Д2–Д7 уже реализованы, а не только описаны:
> Д2/Д7 — через `Prx_Hooks`, Д3 — через `Prx_Actor`/`Prx_Policy`, Д4 — через
> `Prx_DomainError`, Д5 — через `manifest_check`, Д6 — через
> `workers/prx_workers/base.py` + `job_api.py` + `site.py`. Д1 вооружён линтом в
> `make check`: сырой `Database::instance()` / `->quote()` в бизнес-модуле вне
> инфраструктуры и вне `LEGACY_SQL_MODULES` — жёсткая ошибка. Остаточные
> шероховатости (см. по каждому решению) не блокируют использование, но отмечены.
>
> **25.11.2026 — Д8 предложено:** слои доступа к данным (Model = запросы,
> Service = логика). Пилот — `prx396_pdf_chunks`; ратификация по результату
> пилота (см. Д8).

Связанные документы: [FOUNDATION](FOUNDATION.md), [MODULE_GUIDE](MODULE_GUIDE.md),
[ARCHITECTURE](ARCHITECTURE.md).

## Д1. Доступ к БД — один канонический путь  —  ✅ утверждено (вооружён линтом)

**Проблема.** Сосуществуют два стиля. Гид требует `Prx_Db` (плейсхолдеры
`:name`), но свежие модули (`prx395`–`prx398`) пишут
`Database::instance()` + `$db->quote()` и склейку строк. Причина — `Prx_Db`
не принимает явное соединение, а модулям с очередью оно нужно.

**Решение.**
- SQL обычных модулей — только `Prx_Db` (`select/one/execute/insert/transaction`).
- Дать `Prx_Db` возможность явного соединения, чтобы очередь и идемпотентность
  тоже шли через него.
- `Database::instance()` и `$db->quote()` — только внутри инфраструктуры
  (`Prx_Db`, `Prx_Idempotency`, `prx120`), не в бизнес-коде модулей.

**Что даёт.** Один читаемый путь; инъекция через «забыл quote» становится
невозможной; новый разработчик копирует правильный образец.

---

## Д2. Тонкое ядро  —  ✅ утверждено (реализовано в коде)

**Проблема.** `Controller_Prx102_Base` (база всех страниц) знает про
бизнес-модули: `prx110` (Избранное), `prx300` (оргконтекст), `prx599`
(kick-сессии). Правка любого из них задевает все страницы.

**Решение.** База страницы не зависит от бизнес-модулей. Избранное,
оргконтекст, кик-сессии подключаются подписками/хуками/сервисами в точках
входа, а не `class_exists` внутри `before()/after()`.

**Что даёт.** Бизнес-модуль можно менять, не боясь сломать весь портал.

---

## Д3. «Policy» — одно определение и один путь проверки  —  ✅ утверждено (реализовано в коде)

**Проблема.** Слово «политика» означает разное: `Prx_Policy` — это
`view/edit/scope` (объектные правила записи), а `Policy_Prx395_*::ownerId()` —
резолвер владельца. Плюс три способа спросить «можно?»: `can()`,
`actor()->require()`, `Policy`. `can()` содержит неявный bypass для админа и
владельца — правило доступа прячется в базовом классе.

**Решение.**
- Развести явно: **политика записи** (наследует `Prx_Policy`, отвечает «можно ли
  эту запись») и **владение** (кто владелец запроса) — разные вещи с разными именами.
- Один путь проверки: RBAC страницы — `$this->actor()->require('<acl>')`;
  объект — политика. Неявный bypass из общего `can()` убрать.
- Один сценарий в `MODULE_GUIDE` и scaffold.

**Что даёт.** Новый разработчик не гадает, что писать, и не обходит права случайно.

## Д4. Контракт ошибки модуля  —  ✅ утверждено (реализовано в коде)

**Проблема.** Машинный `Prx150_Error` (JSON `{error:{code}}`), страничный
`HTTP_Exception`, и машинный класс переиспользован в UI-контроллерах.

**Решение.** Зафиксировать таблицу «канал → как сообщаем об ошибке»:
- страница/UI → `HTTP_Exception` (403/404/…) с человеческим текстом;
- внешний машинный API → `Prx150_Error` (JSON с кодом);
- не переиспользовать машинный класс ошибок в UI.

**Что даёт.** Предсказуемые ответы и коды на обоих каналах.

## Д5. Манифест — закрытый список секций  —  ✅ утверждено

**Проблема.** `config/prx_module.php` растёт ad-hoc секциями (`card_view`,
`nav_paths`, `family`, `catalog`, `worker`, `schedule`, `recent`, `search`,
`health`, `cleanup`, `api_scopes`…). Единой схемы нет — `manifest_check`
проверяет только `id/slug/status/audience/acl`.

**Решение.** Зафиксировать список секций и их поля в одном месте (таблица в
`FOUNDATION.md` §6). Новая секция — только решением, с обновлением
`manifest_check`. Неизвестный ключ — предупреждение (со временем — ошибка).

**Что даёт.** Манифест остаётся контрактом, а не свалкой.

---

## Д6. Контракт worker-задачи  —  ✅ утверждено (реализовано в коде)

**Проблема.** Протокол PHP↔Python (`_check`, `_download`, `_report_failure`,
коды `PERMANENT_CODES`, `X-Worker-Token`/`X-PRX-Worker-Attempt`) копируется в
каждом обработчике.

**Решение.** Это не код модуля, а **рантайм воркера**
(`workers/prx_workers/`). Единый helper задаёт протокол; модуль объявляет
только канал, лимиты и свою логику.

**Что даёт.** Обработчики короткие и одинаковые; протокол меняется в одном месте.

---

## Д7. Границы ядро ↔ модуль  —  ✅ утверждено (реализовано в коде)

**Проблема.** `Prx150_Principal` (ключевое понятие) живёт в модуле, а ядро зовёт
`prx110/prx300/prx599`. Граница размыта в обе стороны.

**Решение.**
- Ядро (`application/classes/`) не знает о бизнес-модулях. Поперечные вещи —
  через `Manifest`, события или интерфейсы, объявленные в ядре.
- Модуль может звать ядро. Ядро — модуль только через объявленный контракт
  (событие/фасад/интерфейс), а не прямой вызов сервиса.
- Ключевые абстракции — в ядре; их реализации (напр. машинный principal) — в модуле.

**Что даёт.** Понятно, что можно менять без каскада по всему порталу.

## Д8. Слои доступа к данным: Model = запросы, Service = логика  —  🔶 предложено (пилот prx396)

**Проблема.** Д1 унифицировал API доступа к БД (`Prx_Db`), но не место SQL.
Инвентаризация (25.11.2026): ≈200 сайтов `Prx_Db::` в 20 бизнес-модулях при
≈29 800 строк Service-кода. SQL стоит вперемешку с бизнес-ветвлениями и
тернарниками (`$status_sql`); хелперы `_row/_all/_exec/_int_or_null/_num_or_null`
скопированы в 8+ файлов семейства prx390–393, у prx597 — свой Base
(`_one/_all/_exec/_val`), у prx103 — своя `_one`. Каждый модуль решает одну и
ту же задачу по-своему. Концентрация: prx597 (8 812 строк Service, топ-файлы
1 624/1 238/1 048), prx300/Import (1 462), prx115/Semantic (1 022),
prx120/JobQueue (1 507, инфраструктура). Повторяющиеся SQL-паттерны:
`ON CONFLICT` (28 файлов), `::jsonb` (25), `ILIKE` (9), `COUNT(*) FILTER` (4).

**Варианты.**
- **A. Статус-кво:** SQL в Service через `Prx_Db`. Одинаково во всех модулях,
  гейтится Д1; но Service толстеет, хелперы плодятся, запросы не тестируются
  отдельно от логики.
- **B. Model-слой:** Service — сценарий; `Model_Prx<id>_<Сущность>` — запросы.
  Читаемость и изоляция тестов; цена — контракт, scaffold и доки одним заходом.
- **C. Гибрид:** Model только для тяжёлой аналитики, остальное на A. Две
  практики = тот разнобой, который Д1 только что ликвидировал.

**Решение (предложено).** Пилот варианта B на `prx396_pdf_chunks`; ратификация
— по результату пилота (дифф, читаемость, что поймал линт). Канон, если
ратифицирован, меняется одним заходом: docs + `make new-module` + проверки.

**Контракт Model (проверяемый):**
- Файл `classes/Model/Prx<id>/<Сущность>.php`, класс `Model_Prx<id>_<Сущность>`
  — по таблице модуля (`Model_Prx396_Batches`, `Model_Prx396_Parts`).
- Один публичный метод = один запрос с говорящим именем
  (`Model_Prx396_Parts::counts_by_batch($id)`).
- Только `:param`. Исключение — динамические IN/VALUES-списки, собранные из
  уже приведённых к int значений (Kohana-плейсхолдеры не умеют списки).
- Никакой логики, HTTP-кодов, Storage, событий; возврат — `array`/`int`/`?array`.
- Транзакцию владеет Service (`Prx_Db::transaction`); Model транзакций не
  открывает и «умных» составных методов не содержит.
- Гейт Д1 сканирует Model вместе с Service: сырой DB запрещён и там.
- Если два запроса нужны атомарно — это транзакция в Service, не «умная» модель.

**Что даёт.** Service читается как сценарий, SQL — как SQL; запросы
тестируются изолированно; скопированные хелперы заменяются явными методами
Model; место для общего базового слоя семейства модулей, если понадобится.

**Не менять.** ORM не вводим (только явный SQL через `Prx_Db`); инфраструктура
(prx120, Kohana-драйверы) вне этого решения; существующие модули переводятся
по касанию, топ-страдальцы (prx597, prx300/Import, prx115) — отдельными
короткими спринтами при желании владельца, не автоматически.

## Как проверяем

- **Д1 — утверждено и вооружено.** Статический линт в `make check`
  (`.tools/portal_check.py`): сканирует все `application/modules/*/classes/**/*.php`
  на `Database::instance()` и `->quote()`. Инфраструктура (`prx120_jobs`,
  Kohana-драйверы `PostgreSQL`/`PostgreSQL_PDO`, ядро в `application/classes/Prx/*`)
  исключена. Текущий долг перечислен в `LEGACY_SQL_MODULES` и сообщается как
  `note`; модуль вне списка с сырым DB — жёсткая ошибка. Чтобы «вооружить» модуль
  — вычеркните его из `LEGACY_SQL_MODULES` только после полного перевода на `Prx_Db`.
- **Д2, Д7 — реализовано и вооружено.** Ядро не знает о бизнес-модулях:
  `Prx_Hooks` в `Pages.php`/`Welcome.php`/`Auth.php` (меню, план «Рабочего
  стола», ссылка на аккаунт, вторым фактором управляет `account.login_stage2`;
  второй шаг входа вынесен в `Controller_Prx599_2fa`). Автопроверка в
  `portal_check`: любой токен `prx###` в коде `application/classes`
  (комментарии не считаются) — жёсткая ошибка; легальны только каркас `prx102`
  и фасады `prx208`/`prx212` (объявленный контракт Д7).
- **Д3 — реализовано:** `Prx_Actor::can()` делегирует `Prx_Acl` (без неявного
  bypass для админа/владельца), `require()` бросает `HTTP_Exception`; объектные
  правила — в `Prx_Policy` (принимает `Prx_Principal`, едино для человека и ключа prx150).
- **Д4 — реализовано:** `Prx_DomainError` — единый доменный класс на оба канала;
  `Prx150_Error extends Prx_DomainError` (наследник, не отдельная иерархия). Машинный
  канал ловит базовый `Prx_DomainError`; `Prx150_Error` не используется в UI вне prx150.
- **Д5 — реализовано:** `manifest_check.py` — закрытый список секций; неизвестный
  ключ → `WARNING` (со временем — ошибка).
- **Д6 — реализовано:** протокол PHP↔Python централизован в `workers/prx_workers/
  base.py` (`BaseWorker`) + `job_api.py` + `site.py`; обработчик объявляет только
  `CHANNEL`, лимиты и логику `handle(ctx, payload)`.
