## 1. Зачем это

Цена входа в задачу до 01.10.2026 и после:

| Что читалось | Было | Стало |
|---|---|---|
| корневой `AGENTS.md` | 43 КБ целиком (~13 000 токенов) | тот же файл, но нужный раздел берётся по индексу |
| памятка крупного модуля (`nj643_cad`) | 33 КБ (~10 000 токенов) | 36 КБ с индексом, но читается карточка (7,5 КБ) и 1–2 раздела |
| все модульные документы (124 файла) | 490 КБ | те же файлы; читаются по разделам, целиком — никогда |

Читать 490 КБ не нужно и никогда не нужно было: задача почти всегда живёт
в одном модуле. Но ничто и не мешало памятке расти — у неё не было владельца,
следящего за объёмом, — а агенту нечем было получить из неё **только нужное**.

Отсюда два инструмента и один протокол:

* `.tools/context_pack.py` — карточка модуля (≤ 8 КБ) и чтение памятки
  по разделам;
* `.tools/doc_budget_lint.py` — потолки и проверка, что карточка собирается
  по каждому модулю;
* протокол ниже — что делать по шагам и что писать обратно.

Прицел простой: **типовая правка модуля должна укладываться в ~15 тыс. токенов
входа**, а не в 25.

## 2. Протокол: три шага

### Шаг 1. Карточка модуля

```bash
python3 .tools/context_pack.py pack nj643_cad --write
# → .context/nj643_cad.md (в git не хранится), ~4–8 КБ
```

Что внутри (всё — из файлов модуля, без пересказа кода):

* назначение, адрес, группа, статус — из манифеста `config/nj_module.php`;
* «Состояние работ» — раздел памятки модуля (на чём остановились);
* таблицы — из `migrations_pg/`; каналы очереди, расписание, чистки, поиск —
  из манифеста;
* события, env, MCP-инструменты;
* классы с **публичными методами** и числами строк — API модуля без открытия
  файлов на 2 600 строк;
* маршруты — из `init.php`;
* зависимости в обе стороны (кого зовём, кто зовёт нас) и обработчики воркеров;
* **проверки модуля** — тесты, тесты воркеров, стенды и страницы HTTP-дыма
  с готовыми командами (или честное «покрытия нет»);
* **открытые пункты** — из разделов «Долги»/«Куда развивать» памятки;
* фрагмент правил/ловушек из памятки.

Если карточка не влезла в бюджет — она сама скажет, что выбросила, и эти
блоки читаются по требованию (шаг 2).

### Шаг 2. Раздел, а не файл

```bash
python3 .tools/context_pack.py section "Правила" --module nj643_cad
python3 .tools/context_pack.py section "Очередь|Воркер" --module nj120_jobs
python3 .tools/context_pack.py section "Чек-лист" --path AGENTS.md
```

Первая команда печатает **только** раздел «Правила…» (3,6 КБ вместо 36 КБ),
вторая — любой из перечисленных. Аргумент — регулярное выражение по заголовкам,
поэтому `"Долги|TODO"` тоже работает.

Документы больше 12 КБ обязаны иметь индекс разделов с номерами строк и
размерами — по индексу видно, что стоит читать, а что нет. Показать или
обновить индекс:

```bash
python3 .tools/context_pack.py index application/modules/nj643_cad/AGENTS.md          # показать
python3 .tools/context_pack.py index application/modules/nj643_cad/AGENTS.md --write  # обновить в файле
```

### Шаг 3. Работа и запись обратно

Работаем только с файлами модуля; чужие модули не читаем — нужный сервис
назван в карточке (`Зовёт: …`). **Чем проверять — тоже в карточке**: блок
«Проверки модуля» даёт готовые команды (тест модуля, тест воркера, стенд,
страница дыма). Если этого блока нет в списке — покрытия у модуля нет, и первый
шаг работы — стенд или страница руками, а не правка вслепую. Проверяем точечно:

```bash
bash .tools/php_check_all.sh application/modules/<модуль>   # по ходу
bash .tools/php_check_all.sh application                   # перед завершением
python3 .tools/doc_budget_lint.py                          # бюджет доков
```

В конце правки — **запись знания обратно в модуль**, иначе следующая сессия
заплатит за тот же контекст ещё раз:

* раздел «Состояние работ» в `AGENTS.md` модуля — 3–5 строк: что сделано,
  где остановились, следующий шаг;
* если появилось правило, ловушка или контракт — они идут в соответствующий
  раздел `AGENTS.md` модуля, а не в чат;
* если раздел вырос из общего — заводим новый раздел с понятным заголовком
  (по нему его найдёт `section`).

## 3. Что читать в каждой ситуации

| Ситуация | Читать |
|---|---|
| Правка внутри модуля | карточка (`pack`) + `section` по нужной теме |
| С чего начать в модуле | `context_pack.py backlog [--module X]` — открытые пункты из памяток |
| Новый модуль | `docs/MODULE_GUIDE.md` (16 КБ) + `docs/templates/module-AGENTS.md` |
| Воркеры, LLM, очередь | `docs/WORKERS.md` (12 КБ) |
| Вёрстка, страницы | `AGENTS.md` §7 (пункты 10–20) через `section "Макет страниц"` |
| Облик модуля, дизайн v6 | `docs/DESIGN-SYSTEM.md` (12 КБ) + `design_audit.py --module X`; вьюху эталона (70 КБ) не читать |
| Миграции | `docs/MODULE_GUIDE.md` §4 + `AGENTS.md` §2 п. 4 |
| Деплой, прод | `docs/DEPLOY-UBUNTU.md` (13 КБ) |
| Окружение, среда | `docs/ENVIRONMENT.md` (5 КБ) или `docs/SANDBOX-SETUP.md` (10 КБ) |
| Что уже ломалось | `docs/AGENT-LESSONS.md` — читать по датам через `section`, не целиком |

«Всегда» читаются только два файла: корневой `AGENTS.md` (доктрина) и памятка
своего модуля. Остальное — по ситуации и по частям.

## 4. Потолки (их держит `doc_budget_lint.py`)

| Документ | Потолок | Правило |
|---|---|---|
| `AGENTS.md` | 54 000 Б | потолок можно только опускать |
| `README.md` | 9 000 Б | вход в проект |
| `docs/CONTEXT.md` | 26 000 Б | этот протокол |
| `docs/ARCHITECTURE.md` | 42 000 Б | архитектура и реестр модулей |
| `AGENTS.md` модуля | 12 000 Б | больше — обязателен индекс разделов |
| `AGENTS.md` модуля | 40 000 Б | предел даже с индексом: разделить |

Точные числа — в `.tools/doc_budget_lint.py` (`ALWAYS_READ`, `MODULE_DOC_CAP`,
`MODULE_DOC_HARD`); таблица выше повторяет их для человека.

Проверка запускается в общем прогоне (`.tools/php_check_all.sh`, CI) и падает
с командой починки рядом с ошибкой. Индекс в файле тоже сверяется: если он
разошёлся с содержимым (правка сдвинула строки) — CI скажет, чем обновить.

Почему потолок, а не «просто писать короче». Потолок срабатывает в момент
дописывания, и это единственный момент, когда автору видно цену: чтобы
добавить 5 КБ прозы, надо что-то сократить. Правило «поменьше писать» не
срабатывает никогда.

## 5. Шаблон раздела «Состояние работ»

Раздел — контракт между сессиями. Формат намеренно жёсткий: 5 строк, дальше
ссылки, а не пересказ.

```markdown
## Состояние работ

- Готовность: рабочий (что уже работает).
- Сделано: 30.09 — живой ряд на /cad, авто-остановка зависших.
- В работе: разбор `geometry/verify` при пустом ответе движка.
- Следующий шаг: прогнать `nj643_cad_stand.php` после правки `check_code`.
- Долг: см. раздел «Куда развивать» (читать целиком не нужно).
```

Правила:

* дата у каждой записи — иначе через месяц непонятно, что ещё верно;
* «следующий шаг» — одна конкретная команда или файл, не направление;
* устаревшее удаляем: раздел живёт как журнал, а не как музей;
* раздел заменяет собой переписку: агент следующей сессии начинает с него.

## 6. Шаблон контекст-пака (что считается хорошим)

Хорошая карточка — из чего состоит:

1. **Чем является модуль** — назначение, адрес, статус (из манифеста).
2. **Где остановились** — «Состояние работ».
3. **Факты** — таблицы, каналы, расписание, env, события, MCP.
4. **API** — классы и публичные методы, маршруты.
5. **Границы** — кого зовём, кто зовёт, где обработчик воркера.
6. **Правила модуля** — фрагмент памятки, самое ценное из прозы.
7. **Чем проверять** — тесты, стенды, страница дыма готовыми командами (или
   честное «покрытия нет»: тогда первый шаг — стенд).
8. **Что осталось** — открытые пункты модуля: из чего выбирать следующую задачу.
9. **Куда идти за деталями** — конкретные файлы и разделы.

Плохая карточка — пересказ кода (устареет к следующему коммиту), SQL целиком
(его место в файле), «архитектурный обзор» (не нужен для правки).

Карточка **не заменяет** памятку: она — вход. Памятка остаётся местом, где
живёт знание, а карточка его индексирует.

## 7. Модуль за сессию

* **Одна сессия — один модуль.** Смешивание двух модулей в одной сессии платит
  за оба контекста; если правка всё же нужна в чужом модуле — это отдельная
  задача со своей карточкой. Исключение (владелец, 20.10.2026): однотипные
  калькуляторы (вьюхи «форма + результат» без своей БД) — по 3–5 за сессию.
  Сквозной переход на дизайн v6 владелец заказал одним спринтом (20.10.2026).
* **Чужой модуль читаем только через его сервис.** Сигнатура — контракт,
  внутренности — не наше дело (правило владения таблицами, `AGENTS.md` §2.2).
* **Правка — точечная.** Не переформатируем файлы целиком, не «улучшаем»
  соседнее: каждая лишняя строка диффа — это токены на чтение и ревью.
* **Ответ — в файлы, а не в чат.** Итог сессии обязан быть виден репозиторию:
  код, `AGENTS.md` модуля, при необходимости урок в `AGENT-LESSONS.md`.
* **Урок — проверкой.** Новое правило из этой сессии должно закрепиться
  тестом, линтером или строкой чек-листа (правило 14 дней, `AGENTS.md` §0).

## 8. Чек-лист помодульной задачи

- [ ] `context_pack.py pack <модуль> --write` — прочитан `.context/<модуль>.md`
- [ ] Нужные детали — `section` по разделам, а не чтение памятки целиком
- [ ] Чужие модули не открывались; их сервисы — по сигнатурам из карточки
- [ ] Проверки модуля прогнаны (блок «Проверки модуля» в карточке: тест, стенд, страница)
- [ ] `bash .tools/php_check_all.sh application/modules/<модуль>` — чисто
- [ ] `bin/test` (или `tests/mini_runner.php`) — дымовые тесты зелёные
- [ ] `python3 .tools/doc_budget_lint.py` — бюджет доков в порядке
- [ ] `AGENTS.md` модуля: «Состояние работ» обновлён, правила — если появились
- [ ] Большая памятка получила/сохранила актуальный индекс разделов
- [ ] Новый env — в `.env.example` и `workers/.env.example`
- [ ] Ответ короткий: что изменено, чем проверено, что дальше

## 9. Инструменты

| Команда | Что делает |
|---|---|
| `context_pack.py pack <модуль> [--max N] [--write]` | карточка модуля (по умолчанию ≤ 8 КБ) |
| `context_pack.py pack --list` | модули и размеры их памяток |
| `context_pack.py backlog [--module M] [--limit N]` | очередь работы: открытые пункты модулей |
| `context_pack.py section "<регэксп>" --module M \| --path FILE` | только нужный раздел |
| `context_pack.py index <файл.md> [--write]` | индекс разделов с номерами строк и размерами |
| `doc_budget_lint.py [--report]` | потолки, индексы, сборка карточек по всем модулям |
| `make brief m=<модуль>` | то же, что `pack --write`, короткая команда |
| `make backlog [m=<модуль>]` | очередь работы по модулям |
| `make doc-index f=<файл>` | обновить индекс разделов в документе |

Аргумент `section` — регулярное выражение без учёта регистра: `"Правила"`,
`"Долги|TODO"`, `"^Состояние"`. Если ничего не нашлось, команда печатает список
разделов файла — сразу видно, что искать.

## 10. Как ставить задачу (шаблон для владельца)

Пять строк вместо абзаца — и сессия не тратит половину бюджета на выяснение
контекста:

```
Модуль: nj501_vat (или «новый модуль: …»)
Задача: что должно стать иначе, словами владельца
Где видно: /vat, /vat/api/calc (страница, кнопка, кнопка API)
Проверка: чем владелец убедится — команда, страница, кейс
Не трогать: что заведомо не в этой задаче
```

Модуль в первой строке важен не бюрократии ради: по нему собирается
контекст-пак (≤ 8 КБ) и находятся связанные сервисы. Задача без модуля
(«сделай красиво везде») стоит как десять помодульных.

## 11. Развилка дальше (осознанно не сделано)

* **Корневой `AGENTS.md` не разрезан** на «ядро + приложение». Разрезание
  сэкономило бы ещё ~8 КБ на сессию, но ценой риска потерять правило при
  переносе; сейчас достаточно индекса и чтения по разделам. Если файл упрётся
  в потолок 48 КБ — это следующий законный шаг, а не авария.
* **Карточки не коммитятся** (`.context/` в `.gitignore`): они производные,
  а репозиторий не должен хранить 80 сгенерированных файлов, которые
  устаревают между коммитами.
* **Модульные документы массово не переписывались**: 41 модуль без раздела
  «Состояние» — предупреждение линтера, а не ошибка. Механическая вставка
  шаблона в 41 файл дала бы шум в диффе и не дала бы знания; раздел
  заполняется в первой же сессии по модулю.
* **Автоматический подсчёт токенов не делается**: байты честнее (не зависят
  от модели и языка), а перевод «1 КБ ≈ 250–400 токенов» — прикидка для
  человека, а не метрика для отчёта.
