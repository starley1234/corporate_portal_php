# Архитектура и процессы как код

Модель организации (архитектура, процессы, решения, гипотезы) живёт в YAML, а из неё собираются
три вещи: **страница для людей**, **данные для программ** и **граф, по которому можно спрашивать**.

```
arch/*.yaml  ──►  dist/architecture.html   страница (открывается офлайн, один файл)
             ──►  dist/architecture.json   данные для агентов и скриптов
             ──►  граф: arch ask / impact / path, MCP-сервер
```

## Запуск (Windows — двойной клик)

1. Установите **Node.js LTS** с [nodejs.org](https://nodejs.org/ru) (галочка «Add to PATH» уже стоит).
2. Распакуйте репозиторий и запустите **`start.bat`** — он поставит зависимости, проверит модель,
   соберёт страницу и откроет её в браузере.
3. Дальше — команды через `arch.bat`: `arch.bat status`, `arch.bat ask "что делает DLP"`.

**macOS / Linux:** `./start.sh` — те же шаги (поставить, проверить, собрать, открыть).

Подробно, включая подключение ассистента и разбор ошибок: **[`Запуск.md`](Запуск.md)**.

## Три команды, которые отвечают на большинство вопросов

```bash
npm run status                       # что есть, как дела, что делать дальше
npm run arch -- ask "что делает DLP" # ответ с цитатой: вкладка, блок, строка
npm run arch -- impact dlp           # что затронет изменение объекта
```

## Что где лежит

| Путь | Что внутри |
|---|---|
| `arch/` | источник истины: вкладки разделов, решения, гипотезы, реестр сущностей |
| `arch/pipelines/` | карточки пайплайнов: один файл — один пайплайн, с `uses`/`via` и `ref` |
| `arch/entities.yaml` | один компонент — один id (+ старые имена в `aliases`) |
| `arch/inventory.yaml` | что реально существует: системы, владельцы, источник выгрузки |
| `arch/invariants/` | правила «чего быть не должно» — проверяются сами |
| `arch/controls/` | требования: формулировка, чем обеспечена, чем подтверждена |
| `profiles/` | профили домена: общий словарь для нескольких проектов (см. `profiles/README.md`) |
| `exports/` | выгрузки разделов в один HTML для смежников (не коммитятся) |
| `dist/` | собранная страница и данные (коммитятся: работают офлайн) |
| `scripts/` | `arch.mjs` (CLI), `mcp.mjs` (сервер для ассистента), `build.mjs`, `lib/` |
| `src/` | оболочка страницы (`shells/`) и движок отрисовки (`js/engine/`), без зависимостей |
| `tests/` | тесты на `node:test` |
| `dept/` | отдельный проект: портфель процессов подразделения, решения совета и план квартала |
| `snapshots/` | снимки состояния (`arch snapshot`, `arch diff`): страница, данные и копия `arch/` |

## Команды

Все команды — `node scripts/arch.mjs <команда>` (в репозитории: `npm run arch -- …`; на Windows: `arch.bat …`).

| Команда | Что делает |
|---|---|
| `status [--json]` | сводка: размеры модели, покрытие реестром, проверки, гипотезы, что делать дальше |
| `graph [--coverage] [--dot] [--cypher [--out файл]]` | граф: сущности, связи, покрытие; экспорт в Graphviz и Neo4j |
| `ask "<вопрос>" [--limit N]` | поиск по модели как по графу знаний: фрагмент + место |
| `impact <id> [--depth N]` | что затронет изменение объекта |
| `entity [<id>]` | реестр сущностей или карточка объекта |
| `path <id> <id>` | кратчайшая цепочка связей между объектами |
| `hypo [<id>] [--status …]` | гипотезы: вопрос, варианты, чем проверяем, итог |
| `inventory [--missing]` | сверка модели с реальностью: что нарисовано, что существует |
| `invariants` | правила «чего быть не должно»: где нарушены и на какой вкладке |
| `controls [--missing]` | требования и чем они обеспечены; `--missing` — только пробелы |
| `export <вкладка\|раздел> [--out файл]` | один HTML-файл для смежников: без Node, интернета и сервера |
| `tabs` / `show <вкладка>` | список вкладок / выжимка вкладки |
| `map [--missing]` | карта перехода AS-IS → TO-BE и её покрытие |
| `adr [<id>] [--status …]` | журнал решений |
| `contract` | контракт слоёв: кто чем пользуется и через что можно |
| `snapshot` / `diff` | снимок состояния и сравнение с ним |
| `add-node` / `add-edge` / `layout` | правки схем с откатом и черновой раскладкой |
| `lock [--list] [--force]` | замочки замороженных разделов |
| `init <каталог> [--profile имя]` | новый проект из каркаса или из профиля домена |
| `profiles` | доступные профили домена |
| `check [--strict]` | проверки модели (ошибки останавливают сборку) |

Глобальные флаги: `--dir <проект>` (или `ARCH_DIR`), `--json` — машинный вывод.

## Поделиться разделом

Нужно показать коллегам не весь сайт, а один раздел — выгрузите его в отдельный файл:

```bash
npm run arch -- export tobe/04-guardrails     # одна вкладка → exports/guardrails.html
npm run arch -- export solutions              # раздел целиком
npm run arch -- export tobe --out C:/share/tobe.html    # куда положить файл
```

Что получается: **один `.html`**, который открывается двойным кликом на любом компьютере — без Node,
без интернета, без папки рядом. Внутри только выбранные вкладки и подпись «Выдержка из модели
архитектуры, дата». Если в модели есть ошибки, выгрузка отменяется: смежникам не уходит сломанное.
Выгрузки складываются в `exports/` и в git не попадают.

## Требования и пробелы

Отдельный вопрос — «что от нас требуют и чем это закрыто». Это тоже данные, а не таблица в письме:

```bash
npm run arch -- controls              # 15 требований: 14 обеспечено, 1 без покрытия
npm run arch -- controls --missing    # только пробелы — то, что нужно решить или сделать
npm run arch -- controls --area ИБ    # только одна область
npm run arch -- impact dlp            # что затронет изменение и какие требования держатся на этом компоненте
```

Файлы `arch/controls/*.yaml`: `id`, `title`, `area` (ИБ / Данные / Эксплуатация / Процесс),
`satisfied_by: [dlp, policy-gate]`, `evidence`, `note`. Пустой `satisfied_by` — это пробел,
и он честно показывается на вкладке «Требования и покрытие» и в списке «что дальше».
Инструмент при этом остаётся моделью, а не GRC-системой: сроки аттестации и подписи живут в своих
системах, здесь — только связи. Полезная связка: `arch impact <компонент>` показывает, какие
требования он закрывает и какие останутся без покрытия, если его убрать, — это первый вопрос
на любом изменении.

## Несколько проектов на одном словаре

Профиль домена — это общий словарь: типы узлов, разделы, стартовые вкладки, сущности и правила.
Из него поднимается новый проект за одну команду, и он сразу проходит проверки:

```bash
npm run arch -- profiles                                  # какие есть: minimal, platform, department
npm run arch -- init ../team-a --profile platform         # сервис №1
npm run arch -- init ../team-b --profile platform         # сервис №2 — те же слова и цвета
```

Зачем: когда проектов больше одного, «gateway» в одном и «шлюз» в другом должны означать одно
и то же — иначе свести модели потом дороже, чем договориться сразу. Формат профиля и как
добавить свой домен — [`profiles/README.md`](profiles/README.md).

## Граф и ассистент (MCP)

Модель можно спрашивать инструментами, а не чтением файлов. `/mcp`-сервер отдаёт
`arch_status`, `arch_ask`, `arch_impact`, `arch_entity`, `arch_hypotheses`, `arch_show`,
`arch_graph`, `arch_check`:

```json
{ "mcpServers": { "arch-graph": { "command": "node", "args": ["/путь/к/scripts/mcp.mjs"] } } }
```

Граф можно выгрузить в Neo4j (или любую Cypher-совместимую базу):

```bash
npm run arch -- graph --cypher --out exports/graph.cypher    # число узлов и связей — в шапке файла
cat exports/graph.cypher | cypher-shell -a bolt://localhost:7687 -u neo4j -p <пароль>
```

Экспорт идемпотентный (`MERGE`), в шапке файла — число узлов и связей, а `--notes` добавляет
«шумные» связи упоминаний. Проверка «числа совпадают» — в тестах.

Принцип: **сначала граф, потом файлы**. Агенту не нужно читать 500 КБ YAML, чтобы ответить
на вопрос — он получает фрагменты со ссылками на место.

## Что проверяется

`npm run check` ловит: ссылки связей и маршрутов на несуществующие узлы, дубли `id`, неизвестные
`kind`, разрывы маршрутов, число ячеек в таблицах, `{id}` без описания компонента, перекрытия узлов,
ошибки карты перехода, журнал решений и гипотезы, реестр сущностей (занятые `aliases`, неизвестный
`ref`, отсутствие владельца или класса данных), инвентарь (ссылка на несуществующую сущность, дубли),
типы связей (`rel`: неизвестный тип — ошибка), инварианты (`arch/invariants/`: путь в обход gateway, песочница с прямым выходом наружу), требования
(`arch/controls/`: ссылки на несуществующие компоненты, дубли) и контракт слоёв.

```bash
npm run check       # модель
npm test            # тесты: модель, раскладка, сборка, CLI, замочки, граф, гипотезы, MCP, сводка, выгрузка
npm run build       # arch/ -> dist/
npm run serve       # посмотреть dist/ в браузере
```

CI (`.github/workflows/ci.yml`) делает то же и следит, что закоммиченный `dist/` собран из
актуального `arch/`.

## Как это устроено

- **Одна вкладка — один вопрос.** Вкладка отвечает на свой вопрос и переиспользуется в других.
- **Разделы-слои** задаются в `meta.sections`: `primary` (целевое), `asis` (текущее),
  `solution` (прикладное), `governance` (управление). `locked: true` замораживает раздел.
- **Один компонент — одна сущность.** Узел схемы либо совпадает с id сущности, либо ссылается на
  неё через `ref:`.
- **Связь означает действие, а не подпись.** У стрелки есть тип: `rel: uses | carries | runs_on |
  enforces`; без него — `flow`. Так граф отвечает на «кто кого вызывает» и «где граница доверия»,
  а не только «что написано на стрелке».
- **Решения и гипотезы** — файлы, а не переписка: `arch/decisions/`, `arch/hypotheses/`.
- **Внешний вид страницы** — `meta.ui` (оболочки `panel`/`classic` в `src/shells/`), без CDN и
  внешних шрифтов: файл открывается офлайн.

`dist/` и `snapshots/` руками не правятся; `src/` — только при изменении движка или оболочки.
