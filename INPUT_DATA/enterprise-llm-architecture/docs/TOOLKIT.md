# Движок как инструмент для любой предметной области

Движок не знает, что такое «LLM», «DLP» или «AS-IS». Он знает разделы, узлы, связи, решения,
гипотезы и проверки. Поэтому тот же репозиторий описывает что угодно: платформу, процесс,
производственный участок, склад.

Где вы сейчас: реестр сущностей, `ref`, граф и MCP уже работают; соответствие требованиям
и формальная онтология — план (помечено ниже).

## Что даёт каркас

| Возможность | Где | Зачем |
|---|---|---|
| Источник истины — YAML | `arch/*.yaml` | правится диффом, читается человеком и машиной |
| Два потребителя одной модели | `dist/architecture.html`, JSON + CLI | человек смотрит схему, агент — выжимку |
| Разделы с ролями и замочками | `meta.sections`, `locked: true` | прошлое заморожено, целевое защищено |
| Программа перехода как данные | `arch/map.yaml` → вкладка «Карта перехода» | видно, что сохраняем, переносим, выводим |
| Журнал решений | `arch/decisions/*.yaml` | спорное зафиксировано со статусом |
| Гипотезы | `arch/hypotheses/*.yaml` | варианты и проверка до решения |
| Один компонент — один id | `arch/entities.yaml`, `ref:` | связи не рвутся между вкладками |
| Граф и поиск | `arch ask`, `impact`, `path`, MCP | вопросы к модели без чтения файлов |
| Сверка с реальностью | `arch/inventory.yaml` → `arch inventory` | что нарисовано, но не существует, и наоборот |
| Контракт слоёв | `uses` / `via` во вкладке | «кто чем пользуется» проверяется |
| Снимки и сравнение | `arch snapshot`, `arch diff` | что изменилось с прошлого ревью |
| Чужой проект | `arch init <каталог>`, `--dir` | инструмент не привязан к репозиторию |

## Плейбук: восемь шагов

1. **Каркас.** `npm run arch -- init <каталог>` — минимум, который проходит проверки.
2. **Границы.** В `meta.yaml` описать разделы: «как есть», «как надо», прикладные решения,
   управление. Роли — из четырёх.
3. **AS-IS без улучшений.** Нарисовать то, что есть, включая неудобное; `hidden: true` и
   `banner`, чтобы прошлое не выдавало себя за будущее.
4. **TO-BE по возможности теми же id** — совпадающий id значит «тот же компонент».
5. **Программа перехода.** `arch/map.yaml`: `keep` · `move` · `drop` · `new` · `tbd`;
   `arch map --missing` показывает забытое.
6. **Спорное — в решения.** `arch/decisions/` со статусом `proposed`. Пока решение не принято,
   часть схемы — гипотеза.
7. **Прикладное — через контракт.** `uses: [...]` (что занимает у платформы) и `via: [...]`
   (через какие узлы разрешены обращения).
8. **Заморозить и снять снимок.** `locked: true` на стабильных слоях, `arch snapshot` — база
   для сравнения.

**Что ломается, если шаг пропустить**

| Пропущено | Чем кончается |
|---|---|
| Границы разделов | AS-IS и TO-BE смешиваются |
| AS-IS | не с чем сравнивать, переход — список хотелок |
| Программа перехода | непонятно, что выводим, а что переносим |
| Журнал решений | спорное возвращается в переписку каждые две недели |
| Контракт слоёв | команды изобретают свой путь в обход платформы |
| Реестр сущностей | граф распадается: один компонент под пятью именами |
| Замочки и снимок | непонятно, что и когда менялось |

## Кто что делает

Агент силён в переборе и проверке: `status`, `ask`, `impact`, `check`, `grep`, `add-node`/`add-edge`
(с откатом), `layout` (черновик раскладки), `map --missing`. Человек решает содержательное: где
границы, что считать целевым, какой вариант принимаем, что считается риском.
Граница простая: **агент не закрывает решение со статусом `proposed` и не снимает замочек.**

## Несколько сервисов в одном репозитории

```
services/<сервис>/arch/        своя модель и вкладки
shared/entities.yaml           общий реестр компонентов домена
shared/meta-profile.yaml       общий профиль: kinds, названия, базовые проверки
```

Каждый сервис проверяется и собирается отдельно (`--dir`, `ARCH_DIR`). Общее: `kinds`,
реестр сущностей, формулировки инвариантов. Своё: вкладки, решения, карта перехода.
Профили домена для этого и заведены: `profiles/<домен>.yaml` + `arch init --profile <домен>`
(см. `profiles/README.md`); в этом репозитории пример — `profiles/platform.yaml`.

## Привязка к требованиям и стандартам (сделано)

Соответствие требованиям можно сделать объектом того же графа:

```yaml
# arch/controls/01-ib.yaml
id: IB-01
title: "Синхронная проверка данных до вызова модели"
satisfied_by: [dlp, policy-gate]
evidence: "ADR-010, конфигурация gateway"
```

Дальше — матрица покрытия (`arch controls --missing`): какие требования не обеспечены ни одним
компонентом. Инструмент при этом остаётся моделью, а не GRC-системой: сроки аттестации, сканы
актов и подписи живут в своих системах, здесь — только связи.

## Онтология: что уже сделано и что дальше

Сделано: реестр сущностей с типами и владельцами, `aliases` для старых имён, `ref` у узлов,
типизированные связи в графе (`flow`, `uses`, `carries`, `runs_on`, `enforces`, `affects`, `tests`,
`transition`, `about`) — тип задаётся в самой схеме опцией `rel`,
экспорт `--dot` и `--cypher --out` (Neo4j), **инварианты** `arch/invariants/*.yaml` (`arch invariants`,
проверяются в `check`), **выгрузка раздела** в один HTML для смежников (`arch export`),
**профили домена** `profiles/*.yaml` (`arch profiles`, `arch init --profile`).

Дальше по порядку:

| Шаг | Что делаем | Как проверяем |
|---|---|---|
| 1 | ~~типы связей вместо подписей: `runs_on`, `carries`, `enforces`, `satisfies`~~ **сделано**: опция `rel` у связи | граф отвечает на «где проходит граница доверия» |
| 2 | ~~требования как объекты и матрица покрытия~~ **сделано**: `arch/controls/*.yaml` | `arch controls --missing` |
| 3 | ~~инварианты как запросы к графу (`arch/invariants/*.yaml`)~~ **сделано** | `check` ловит нарушения до ревью |
| 4 | ~~экспорт графа в хранилище (Neo4j и подобные)~~ **сделано**: `arch graph --cypher --out` | число узлов и связей в файле совпадает (тест) |
| 5 | ~~общий профиль домена для нескольких сервисов~~ **сделано**: `profiles/*.yaml`, `arch init --profile` | чужой проект собирается в CI (job `toolkit`) |

Чего не делать: не тащить OWL, SPARQL и тяжёлые редакторы онтологий в инструмент, который должен
открываться одним файлом и правиться в git. Достаточно: один id, один тип, явные связи.

## Границы применимости

| Ограничение | Что это значит |
|---|---|
| Инструмент не моделирует | не считает нагрузку и стоимость; числа на схемах — ответственность автора |
| YAML разрастается | правило «одна вкладка — один вопрос» |
| Дубли — главный враг | сначала `ref`, потом реестр; иначе описания расходятся |
| Проверки не заменяют ревью | `check` ловит структуру, содержание — только человек |
| Замочки — не защита | настоящая защита — CODEOWNERS и защита ветки в git |
