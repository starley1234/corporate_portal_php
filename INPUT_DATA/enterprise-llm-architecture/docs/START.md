# С чего начать

Репозиторий — это **модель организации процессов, описанная данными**. Из неё собираются:
страница для людей (`dist/architecture.html`), файл для программ (`dist/architecture.json`)
и граф, по которому можно задавать вопросы (`arch ask`, MCP-сервер).

Ниже — пять минут на вход. Читать всё подряд не нужно.

## Кто вы и что открыть

| Кто | Что открыть | Что запустить |
|---|---|---|
| Руководитель подразделения | `docs/DEPARTMENT.md` — что даёт инструмент, роли, план | `npm run arch -- status` |
| Архитектор, инженер платформы | `docs/CONTEXT.md`, страница «Общий вид» | `npm run arch -- status`, затем `arch show <вкладка>` |
| Запуск (Windows / macOS / Linux) | `Запуск.md` | двойной клик по `start.bat` или `./start.sh`, дальше `arch.bat status` |
| Ответственный за ИБ | `docs/IB-AND-GAPS.md` | `arch impact dlp`, `arch ask "обход DLP"` |
| Владелец процесса, бизнес-аналитик | `docs/KNOWLEDGE-BASE.md`, `docs/GRAPH-RAG.md` | `arch ask "<вопрос>"`, `arch hypo` |
| Ассистент (агент) | `AGENTS.md`, этот файл | MCP-сервер: `node scripts/mcp.mjs` |
| Новый сотрудник | этот файл, затем страница в браузере | `npm run build && npm run serve` |

## Три команды, которые отвечают на большинство вопросов

```bash
npm run arch -- status               # что есть, как дела, что делать дальше
npm run arch -- ask "что делает DLP" # ответ с цитатой: вкладка, блок, строка
npm run arch -- impact dlp           # что затронет изменение объекта
```

`status` — единственная команда, которую стоит запомнить. Она же подсказывает следующие шаги.

## Что где лежит

| Путь | Что внутри | Кому |
|---|---|---|
| `arch/` | источник истины: вкладки, решения, гипотезы, реестр сущностей | все, кто меняет модель |
| `arch/entities.yaml` | один компонент — один id + старые имена (`aliases`) | архитектор |
| `arch/inventory.yaml` | что реально существует: системы, владельцы, источник | ИТ, архитектор |
| `arch/hypotheses/` | гипотезы: вопрос, варианты, чем проверяем, итог | владелец процесса |
| `arch/decisions/` | журнал принятых решений (ADR) | архитектор, ИБ |
| `docs/START.md` | эта страница | все |
| `docs/DEPARTMENT.md` | зачем это подразделению и как встроить в работу | руководитель |
| `docs/GRAPH-RAG.md` | граф, гипотезы, наглядность, MCP | архитектор, аналитик |
| `docs/KNOWLEDGE-BASE.md` | база знаний холдинга: как строить | аналитик, ИТ |
| `docs/IB-AND-GAPS.md` | развёртывание с точки зрения ИБ и пробелы | ИБ |
| `docs/FORMAT.md` | формат файлов модели (что можно написать во вкладке) | тот, кто правит YAML |
| `docs/TOOLKIT.md` | как применять движок к любой предметной области и что дальше | тот, кто тиражирует |
| `scripts/arch.mjs` | командная строка: `status`, `ask`, `impact`, `hypo`, `check`, `build` | все |
| `scripts/mcp.mjs` | MCP-сервер для ассистента | агент |
| `dist/` | собранная страница и данные (коммитятся: работают офлайн) | все |
| `dept/` | отдельный проект подразделения (портфель процессов) | подразделение |

## Правила, чтобы было не накладно

| Правило | Почему |
|---|---|
| Сначала команда, потом файл | `ask` и `impact` отвечают на 80% вопросов без чтения YAML — дешевле по времени и токенам |
| Один компонент — одна сущность | иначе граф теряет связи, а «что затронет изменение» отвечает неверно |
| Гипотеза ≠ решение | можно рассматривать варианты, не ломая целевую архитектуру |
| Меняете `arch/` — запустите `npm run check` и `npm run build` | страница и граф собираются из модели; устаревший `dist/` ловится CI |
| Не править `dist/` руками | перезапишется при сборке |

## Ритм работы подразделения

| Когда | Что делаем | Чем |
|---|---|---|
| Раз в неделю | смотрим состояние и следующие шаги | `arch status` |
| Перед изменением процесса | оцениваем последствия | `arch impact <объект>` |
| Есть сомнение в решении | заводим гипотезу с вариантами | новый файл в `arch/hypotheses/` |
| Гипотеза проверена | фиксируем итог, решение — в журнал | `arch hypo <id>`, `arch/decisions/` |
| Раз в месяц | смотрим, что нарисовано, но не используется, и сверяем с реальностью | `arch graph --coverage`, `arch inventory`, `arch status` |

## Если что-то не работает

| Симптом | Что сделать |
|---|---|
| `npm run check` падает | в выводе указан файл и место; частая причина — `id`, которого нет в схеме, или незакавыченное `Название: продолжение` в YAML |
| `ask` ничего не находит | сократите запрос до одного-двух слов из модели: `DLP`, `Gateway`, `гипотеза` |
| `impact` пишет «не найдена» | посмотрите реестр: `arch entity`; возможно, у объекта другое имя — добавьте его в `aliases` |
| MCP-клиент не видит сервер | проверьте запуск: `echo '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' \| node scripts/mcp.mjs` |
| Страница не открывается | `npm run build`, затем `npm run serve` |

## Для агента: короткая инструкция

1. `arch_status` (или `npm run arch -- status`) — общая картина и следующие шаги.
2. `arch_ask` / `arch_entity` — найти объект и место, где он описан.
3. `arch_impact` — прежде чем предлагать изменение.
4. `arch_hypotheses` — прежде чем предлагать новое решение: возможно, вопрос уже проверялся.
5. YAML читать только после шагов 1–4 и только нужный кусок. После правки — `npm run check`, `npm run build`.
