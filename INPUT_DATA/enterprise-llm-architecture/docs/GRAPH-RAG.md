# Граф модели: гипотезы, наглядная документация и графовый поиск

Этот документ отвечает на четыре вопроса:

1. можно ли в инструменте **прикидывать гипотезы** («что если сделать иначе»);
2. как сделать **документацию наглядной**;
3. как **агенту быстро ориентироваться** в модели и видеть объекты и связи как граф;
4. где здесь **графовый поиск для принятия решений** (graph RAG) и нужен ли нам чужой проект.

Короткий ответ: да, всё четыре вещи делаются на том, что уже есть. Модель и так хранится
данными, а не картинками, — не хватало только явных связей между одинаковыми объектами
и команды «спроси модель». Это добавлено, работает и проверяется тестами.

---

## 1. Что было не так

| Что мешало | Как проявлялось |
|---|---|
| Один компонент — много имён | Gateway нарисован как `gw`, `gw-v2`, `p-gw`, `h-gw`, `n-gw`. Для человека это один шлюз, для поиска — пять разных узлов |
| Связи жили внутри вкладок | «Что сломается, если убрать DLP» приходилось выяснять глазами по шести схемам |
| Знание лежало текстом | Ответ на вопрос искали поиском по словам, без понимания, что рядом, а что далеко |
| Гипотезы жили в головах | Варианты «pgvector или Qdrant» обсуждались в переписке и не попадали в модель |
| Агент читал YAML | Дорого по токенам и без гарантии, что он увидит связи, а не только текст |

---

## 2. Что добавлено

| Что | Где | Зачем |
|---|---|---|
| **Реестр сущностей** | `arch/entities.yaml` | один канонический id на компонент + список старых имён (`aliases`) |
| **Граф модели** | `scripts/lib/graph.mjs` | сущности, связи (поток, использование, влияние, переход), фрагменты знания |
| **Вкладка «Реестр сущностей»** | раздел «Управление» | видно, какие объекты встречаются в нескольких вкладках, а какие осиротели |
| **Гипотезы** | `arch/hypotheses/*.yaml` → вкладка «Гипотезы» | вопрос, варианты, чем проверяем, итог |
| **Команды** | `arch graph`, `arch ask`, `arch impact`, `arch path`, `arch entity`, `arch hypo` | ориентирование и проверка «что если» из терминала |
| **MCP-сервер** | `scripts/mcp.mjs` | агент спрашивает модель инструментами, а не чтением файлов |
| **Экспорт** | `arch graph --dot`, `arch graph --cypher` | картинка для людей и загрузка в Neo4j при росте |

Проверки: `npm run check` теперь ловит неизвестный `ref`, занятый `alias`, дубли гипотез,
неизвестные статусы, ссылки гипотез на несуществующие вкладки.

## 3. Гипотезы: как прикинуть «что если»

Гипотеза — отдельная запись, а не правка схемы. Поэтому можно рассматривать варианты, ничего
не ломая в целевой архитектуре.

**Порядок работы (4 шага):**

| Шаг | Действие | Команда или файл |
|---|---|---|
| 1 | Сформулировать вопрос и 2–3 варианта с плюсами, минусами, стоимостью и риском | новый файл `arch/hypotheses/NN-имя.yaml` |
| 2 | Посмотреть, что затронет каждый вариант | `arch impact <объект>` — где нарисован, кто зависит, какие решения уже приняты |
| 3 | Записать, чем проверяем (замер, пилот, мнение эксплуатации) и когда | поля `evidence` в том же файле |
| 4 | Зафиксировать итог: подтверждена / опровергнута / отложена; итог переносится в журнал решений | `status`, `verdict`, затем запись в `arch/decisions/` |

**Пример из репозитория.** Гипотеза `H-001` — «PostgreSQL + pgvector вместо отдельного Qdrant»:

```bash
npm run arch -- hypo H-001        # вопрос, допущения, два варианта, что и когда замеряем
npm run arch -- impact postgres   # что уже опирается на PostgreSQL, а что на Qdrant
npm run arch -- ask "pgvector"    # решения и текст, где это уже обсуждалось
```

**Правило, которое снимает споры:** пока гипотеза открыта, всё, что на неё опирается, —
предположение. Как только проверка закончена, появляется итог, а решение уходит в журнал
`arch/decisions/`. Одно место — одна правда: не нужно искать, «что мы решили в чате».

## 4. Наглядная документация

| Способ | Что видно | Команда |
|---|---|---|
| Вкладки HTML | схемы, таблицы, гипотезы с вариантами, реестр сущностей | `npm run build` → `dist/architecture.html` |
| Вкладка «Состояние модели» | размеры, покрытие, гипотезы и готовый список «что требует внимания» | `npm run build`, затем раздел «Управление» |
| Картинка графа | объекты и связи без вкладок и координат | `arch graph --dot > model.dot`, затем `dot -Tsvg model.dot -o model.svg` |
| Загрузка в базу графов | граф для запросов и визуализации в Neo4j | `arch graph --cypher > model.cypher` |
| Ответ с цитатами | фрагмент + место (вкладка, блок, строка) | `arch ask "вопрос"` |

Зачем это: новому человеку не нужно читать все вкладки. Он открывает реестр сущностей, находит
свой объект, видит, где тот нарисован, — и только потом идёт в конкретную вкладку. Начальник
подразделения видит гипотезы и их итоги, а не переписку.

## 5. Агент и граф: MCP

MCP — общий язык, которым ассистент (Claude, Cursor, любой клиент с поддержкой MCP) спрашивает
инструмент. Наш сервер отдаёт модель, а не файлы.

**Подключение** (пример для клиента с настройкой MCP-серверов; начните с `arch_status` — он отдаёт сводку и следующие шаги):

```json
{
  "mcpServers": {
    "arch-graph": {
      "command": "node",
      "args": ["/путь/к/репозиторию/scripts/mcp.mjs"]
    }
  }
}
```

**Инструменты:**

| Инструмент | Что отвечает |
|---|---|
| `arch_ask` | фрагменты модели по вопросу, с указанием вкладки и блока |
| `arch_impact` | где объект нарисован, входящие и исходящие связи, волны зависимостей |
| `arch_entity` | карточка объекта: id, тип, владелец, старые имена, вкладки |
| `arch_hypotheses` | гипотезы: вопрос, варианты, доказательства, итог |
| `arch_show` | выжимка вкладки без координат |
| `arch_graph` | статистика графа и покрытие реестром |
| `arch_check` | ошибки и предупреждения модели |

**Дисциплина работы агента** (записана в `AGENTS.md`): сначала `arch_ask` или `arch_entity`,
потом точечное чтение файла — и только если без него нельзя. Это дешевле и точнее, чем чтение
YAML целиком: агент получает связи, а не 500 КБ текста.

Проверка руками:

```bash
echo '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | node scripts/mcp.mjs
```

## 6. Графовый поиск для решений

«Графовый RAG» — это когда ответ собирается не по похожести слов, а по связям: нашли объект —
подтянули его окружение, решения и записи, где он упоминается. У нас три режима.

| Вопрос при принятии решения | Что делает граф | Команда |
|---|---|---|
| «Что это и где описано?» | ищет фрагменты и объекты, объединяя имена через реестр; указывает место | `arch ask` |
| «Что затронет изменение?» | идёт по связям в обратную сторону: кто использует, кто зависит | `arch impact` |
| «Как связаны A и B?» | кратчайшая цепочка связей, честно говорит «связи нет» | `arch path dlp vector-store` |

Почему это работает без векторной базы: модель небольшая и уже структурированная — несколько
сотен сущностей и связей. Здесь точное совпадение имён и связей даёт более объяснимый
результат, чем «похожесть». Векторный поиск понадобится для больших текстов (договоры, протоколы) —
он уже предусмотрен в базе знаний (`docs/KNOWLEDGE-BASE.md`), но это другой слой.

**Как это меняет решения.** Пример: обсуждается отказ от отдельного DLP-сервиса. Вместо
«кажется, он везде» — `arch impact dlp` показывает все вкладки, где он нарисован, входящие связи от Gateway, три
решения (`ADR-010`, `ADR-011`) и гипотезу `H-002`, которая как раз проверяет другой порядок
проверок. Разговор идёт про факты модели, а не про воспоминания.

## 7. Проект с GitHub: брать или нет

Смотрели свежие проекты, которые превращают репозиторий в граф знаний для агента
(например, `Graphify-Labs/graphify`, `vitali87/code-graph-rag`, `Egonex-AI/Understand-Anything`).

| Их идея | Нам подходит? | Почему |
|---|---|---|
| Разбор кода через tree-sitter (~36 языков) | **нет** | Наш источник — уже структурированные YAML. Разбирать нечего: модель и есть готовый граф |
| Типизированные узлы и связи | **да** | Взяли: `flow`, `uses`, `affects`, `tests`, `transition` |
| Метка происхождения связи (извлечено / выведено / под вопросом) | **частично** | У нас связь либо нарисована в схеме, либо выведена из текста — это видно по типу связи |
| Команды `query` / `path` / `explain` | **да** | Наши `ask` / `path` / `impact` |
| MCP-сервер для ассистента | **да** | Сделали свой, без зависимостей |
| «God nodes» и сообщества (кластеры) | **позже** | Полезно, когда граф вырастет: показывать 5 объектов, от которых зависит всё |
| Векторного хранилища нет | **да** | Совпадает с нашим подходом: объяснимость важнее «похожести» |

**Вывод.** Идея «репозиторий → граф знаний для агента» уместна, но в чистом виде нам не нужна:
она про извлечение структуры из кода, а у нас структура уже есть. Забираем формат (узлы, связи,
команды, MCP) и дисциплину «сначала граф, потом файлы». Не забираем парсер кода — это лишняя
сложность без выгоды.

Где чужой подход пригодится: когда подразделение начнёт автоматизировать **чужой** код
и чужие базы данных. Тогда понадобится слой, который читает SQL-схемы и код и привязывает их
к нашим сущностям (см. этап 3 ниже).

## 8. Как это превращается в инструмент организации процессов

| Вид работы | Что даёт граф |
|---|---|
| Разработка ПО | реестр компонентов вместо «пяти имён одного сервиса»; `impact` перед изменением; решения и гипотезы рядом со схемой |
| Автоматизация процессов | процесс описывается как маршрут и узлы; `impact` показывает, какие подразделения затронет изменение регламента |
| Создание баз данных | сущности и связи = черновик модели данных; экспорт `--cypher` сразу грузится в графовую базу |
| Принятие решений | вопрос → фрагменты с цитатами → влияние → гипотеза с вариантами → решение в журнале |
| Ввод нового сотрудника | реестр сущностей, карта связей, гипотезы: понятно, что уже решено и что ещё проверяется |
| Аудит и ИБ | права и классы данных у сущностей; видно, где проходит граница доверия |

**План, четыре этапа.** Каждый этап заканчивается тем, что можно показать.

| Этап | Срок | Что делаем | Результат |
|---|---|---|---|
| 1. Сейчас | готово | реестр сущностей, граф, `ask/impact/path`, гипотезы, MCP | агент и человек отвечают на вопросы по модели без чтения YAML |
| 2. Порядок в именах | сделано | реестр сущностей и покрытие; у каждой сущности владелец и класс данных, `check` предупреждает, если их нет | «один объект — одно имя» во всей модели |
| 3. Связь с реальностью | сделано | инвентарь `arch/inventory.yaml` и команда `arch inventory`: что нарисовано, но не существует, и что существует, но не описано; заменить стартовый список выгрузкой из CMDB | модель перестаёт расходиться с жизнью |
| 4. Решения на потоке | 3–6 месяцев | гипотезы и решения ведутся в одном месте; `ask` отвечает на вопросы по базе знаний; экспорт в графовую базу при росте | подразделение принимает решения по фактам, а не по памяти |

## 9. Ограничения (честно)

| Ограничение | Что это значит | Когда решать |
|---|---|---|
| Поиск по словам, без смысла | «увольнение» не найдёт «расторжение договора» | когда подключим большие тексты — добавить векторный слой в базу знаний |
| Связи только там, где нарисованы или упомянуты | граф не знает того, чего нет в модели | этап 3: подтягивать из учётных систем |
| Реестр покрывает не всё | у вкладок AS-IS и вкладок-процессов свои id (шаги, ошибки) — это нормально | этап 2: добавлять `aliases` по мере надобности |
| Один проект — один граф | `dept/` собирается отдельно | при желании — общий реестр в отдельном файле |
| Большой граф | при тысячах узлов файл-граф станет медленным | порог: ~5 тыс. узлов → Neo4j через `--cypher` |
| Инвентарь статичен | это снимок, а не живая инвентаризация | обновлять выгрузкой из CMDB по расписанию (раз в месяц) |

## 10. Шпаргалка

```bash
npm run arch -- status                 # состояние и что делать дальше (одна команда)
npm run arch -- graph                  # сколько сущностей, связей, фрагментов
npm run arch -- graph --coverage       # покрытие реестром по вкладкам
npm run arch -- ask "что делает DLP"   # ответ с цитатами
npm run arch -- impact dlp             # что затронет изменение
npm run arch -- path dlp vector-store  # как связаны два объекта
npm run arch -- entity gateway         # карточка объекта, старые имена
npm run arch -- hypo                   # журнал гипотез
npm run arch -- hypo H-001             # одна гипотеза с вариантами
npm run arch -- graph --dot > model.dot # картинка для Graphviz
npm run arch -- graph --cypher > model.cypher # загрузка в Neo4j
node scripts/mcp.mjs                   # MCP-сервер для ассистента
```

Что почитать дальше: `docs/FORMAT.md` — как устроены файлы модели; `docs/DEPARTMENT.md` —
как этим пользоваться подразделению; `docs/KNOWLEDGE-BASE.md` — база знаний холдинга.

## 11. Для руководства: короткая версия

Три предложения, которых обычно достаточно для разговора:

1. Знания компании лежат в Teamcenter, 1С и документообороте, но **связи между ними держат люди**:
   что деталь в PLM и позиция в 1С — одно и то же, помнит конкретный инженер.
2. Обычный чат с документами находит похожие тексты, но не проходит по цепочке
   «деталь → изделие → заказ → поставщик → рекламация → письмо».
3. Мы строим слой знаний: граф связей, поиск и LLM **внутри защищённого контура**, где
   конфиденциальные данные не покидают компанию. Граф собирается из связей, которые уже есть
   в системах, — без дорогой обработки. LLM добавляет язык там, где это даёт измеримый выигрыш.

**Чем граф отличается от «загрузим документы в чат»**

| Вопрос | Чат с файлами | Граф знаний |
|---|---|---|
| Ответ в одном документе | хорошо | хорошо (граф не нужен) |
| Цепочка через несколько систем | не умеет | основной сценарий |
| Точный код изделия («АБВГ.123456.001») | часто промахивается | точный поиск по коду + смысл |
| Откуда взят ответ | фрагменты текста | конкретные объекты и документы |
| Права доступа | зависит от инструмента | права источников на каждом узле |

**Пять вопросов, на которые появляется ответ**

| Вопрос | Что даёт |
|---|---|
| Что затронет замена детали? | извещение, изделия по составу, заказы, рекламации, письма |
| Почему так решили? | цепочка «документ → извещение → решение» вместо поиска по папкам |
| Что мы знаем о поставщике? | досье: заказы, рекламации, сертификаты — в одном ответе |
| Где дубли и расхождения? | одна деталь под разными кодами в разных системах |
| Есть ли аналог? | поиск по связям и характеристикам, а не по названию |

**Как докажем (пилот, а не обещания):** 30–50 реальных вопросов с известными ответами →
замер «сейчас» по времени → пилот на 1–2 сценариях (влияние изменения и история решения) →
метрики: доля верных ответов, время против ручного поиска, доля ответов со ссылками, ноль
нарушений прав, стоимость запроса → решение о продолжении **по метрикам**.

**Что нужно от руководства:** владельцы 2–3 сценариев; read-only доступ к копиям систем;
подтверждение правила «эти данные — confidential, обработка локальной моделью»; время
подразделения на инвентаризацию; владелец модели прав в ИБ.

**Честные риски:** грязные данные и дубли (сопоставление сущностей — часть работы, а не побочный
эффект), сложные права (начинаем с read-only и запрета по умолчанию), ошибки модели (ответ всегда
со ссылками, запись в системы не делаем), чертежи и CAD не читаем — берём метаданные из PLM.

> Мы связываем данные PLM, ERP и документооборота в один граф знаний и даём сотрудникам вопросы
> на естественном языке с ответами и ссылками на источники. Начинаем со связей, которые уже есть
> в системах, и подключаем LLM там, где она даёт измеримый выигрыш. Всё — внутри существующего
> защищённого контура. Расширяем по результатам пилота.
