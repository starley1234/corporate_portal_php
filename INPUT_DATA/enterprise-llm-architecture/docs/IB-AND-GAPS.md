# ИИ на предприятии: как развернуть с учётом ИБ и чего не хватает

Две части: сначала — что в проекте уже придумано про безопасность и в каком порядке это разворачивать; потом — чего в проекте нет, чтобы на предприятии стало действительно лучше.

---

## Часть 1. Как здесь устроено развёртывание с учётом ИБ

### 1.1 Главная идея: один вход и проверка до модели

Сотрудник не обращается к модели напрямую. Он попадает на **один вход** (чат, бот, скрипт, IDE — неважно), и дальше запрос идёт по цепочке:

```
Сотрудник → общий вход → проверка личности и лимитов → проверка текста (DLP)
          → параллельно: модель начинает готовить ответ и защита проверяет запрос
          → ответ придерживается и не показывается, пока защита не вынесла решение
          → проверка самого ответа → показ сотруднику
```

Четыре правила, на которых всё держится (они записаны как решения и проверяются автоматически):

1. **Нашли секрет — модель не вызывается вообще.** Не «вызовем и потом посмотрим», а сразу остановка.
2. **Ответ нельзя увидеть раньше решения защиты.** Модель может уже писать текст, но сотрудник его не получит, пока не будет вердикта «можно».
3. **Если проверка сломалась или не успела — считаем, что нельзя.** Не «наверное, можно»: для чувствительных данных ошибка защиты означает запрет.
4. **Для облачной модели проверка «на лету» не спасает.** Если запрос уже ушёл внешнему поставщику, отозвать его нельзя. Поэтому для секретных данных — только своя модель внутри компании, либо проверка **до** отправки.

### 1.2 Два уровня проверки

| Уровень | Что делает | Когда срабатывает |
|---|---|---|
| Быстрый | Небольшая модель-фильтр смотрит запрос на запрещённые темы, попытки взлома инструкций, признаки утечки | Всегда, параллельно с генерацией ответа |
| Глубокий | Более крупная модель разбирает подозрительный запрос и спорные случаи | Только если быстрый сказал «подозрительно» |
| Проверка ответа | Отдельная проверка готового текста: те же правила, но для ответа | Каждый ответ; усиленная — если запрос был спорным |

Смысл: не тормозить обычные запросы и при этом не пропускать спорные.

### 1.3 Сеть: зоны и запреты

Система разложена по зонам, между которыми разрешены только конкретные связи: вход · сервисы · защита и GPU · знания · выход в облако. Каждая связь описана таблицей «кто инициирует, куда можно, куда нельзя» — это готовое задание для настройки сети.

Отдельно: **локальная модель живёт в закрытом сегменте с GPU**, песочницы для кода — на отдельной машине (чтобы не давать доступ к управлению контейнерами на основной), выход в облако — только через один шлюз.

Два реальных долга текущей версии, которые надо закрыть в первую очередь:

- веб-поиск в чате ходит **напрямую**, минуя проверку;
- опубликованные порты Docker **обходят** сетевой экран (правила для Docker пустые).

То есть сегодня в контуре есть два места, через которые можно обойти защиту. Пока они есть, все остальные меры — теория.

### 1.4 В каком порядке разворачивать (9 шагов)

| Шаг | Что делаем | Как понять, что получилось |
|---|---|---|
| 0 | Замер «как сейчас»: скорость ответа, очереди, объёмы | Есть цифры, с которыми потом сравнивать |
| 1 | **Один вход** для всех: чат, скрипты, боты, агенты | 100% обращений к модели проходят через проверку, обходов нет |
| 2 | Отдельный сервис поиска по документам с правами доступа | Нельзя получить чужой документ; качество не хуже, чем было |
| 3 | Распознавание документов (OCR) как отдельный сервис с запасным локальным вариантом | Одинаковый результат и там, и там; есть таймауты и очередь |
| 4 | **Своя модель** на GPU внутри компании | Отвечает, работает с русским, доступна по группам |
| 5 | Защита в режиме наблюдения: считает риск, но не блокирует | Видно, сколько ложных срабатываний и задержек |
| 6 | Защита в режиме блокировки | Заблокированный ответ физически не доходит до сотрудника |
| 7 | Масштабирование и отказоустойчивость | Нагрузочные тесты, договорённости по скорости, восстановление после отказа |
| 8 | Закрыть обходы: поиск и порты | Прямого выхода в интернет из чата больше нет |
| 9 | Прикладные задачи на данных предприятия | Проверочные примеры и метрики «до/после», права источников соблюдены |

Порядок не случайный: сначала убираем обходы и ставим один вход, потом добавляем свою модель, и только потом включаем блокировки. Если включить блокировки раньше, сотрудники найдут обход — и вернуть доверие будет сложно.

### 1.5 Что уже решено, а что нет

**Решено (2 решения):** проверка текста синхронная, до вызова модели; ответ выдаётся только после решения защиты.

**Не решено (9 вопросов):** какая именно своя модель; как разделять «облако или локально» по типу данных; как подключить базу знаний; какие таймауты защиты и когда считать «нельзя»; объём базы знаний; права разных подразделений в поиске; какое хранилище использовать; как переносить права из учётных систем; как выделить отдельную очередь для массовой обработки.

Это нормальное состояние проекта: девять открытых вопросов — это список того, что нужно решить **до** запуска, а не «недоделки». Каждый закрывается записью решения с датой и последствиями.

## Часть 2. Чего не хватает

Ниже — то, чего в проекте нет. Часть вопросов касается безопасности, часть — людей и денег. Отсортировано по влиянию.

### 2.1 Первые пять: без них «лучше» не станет

| Чего нет | Почему это важно | Что сделать |
|---|---|---|
| **Права из учётных систем** (кто какие документы и записи вправе видеть) | Иначе поиск по документам станет способом обойти права в 1С и PLM: сотрудник увидит в ответе то, что ему не положено. Это самый большой риск из всех | Реестр систем и их ролей; права переносятся на каждый фрагмент документа; по умолчанию — запрещено; проверка на реальных ролях |
| **Реестр данных по классам** | Нельзя решить «в облако или локально», если неизвестно, какие данные секретные. Сейчас это решается на глаз | Список видов данных: открытые, внутренние, секретные, персональные — с владельцем каждого |
| **Закрытие обходов** (поиск в чате, порты Docker) | Пока они есть, любые проверки обходятся одним нажатием | Шаг 8 плана; проверка: попытка обойти защиту должна упираться в отказ |
| **Встраивание в работу, а не «ещё один чат»** | Люди не уходят из 1С и PLM в отдельное окно. Инструмент, который стоит в стороне, не используется | Кнопки и подсказки в тех системах, где работают: заявка, карточка, документ |
| **Обучение и правила использования** | Без правил сотрудники либо не пользуются, либо копируют в чат секретные документы | Короткая политика: что можно, что нельзя, что делать при ошибке; обучение по ролям; «проводники» в подразделениях |

### 2.2 Безопасность: что стоит добавить

| Чего нет | Простыми словами | Что сделать |
|---|---|---|
| **Порядок действий при инциденте** | Что делать, если сотрудник всё-таки отправил секрет или защиту обошли: кто останавливает, кому сообщает, что проверяет | Написать сценарий на одну страницу и один раз проиграть его как учения |
| **Регулярная проверка на взлом** | Защиту проверяли при запуске, дальше — только при обновлениях | Раз в квартал: набор попыток обхода (инъекции в запрос, в документы, в ответы поиска) |
| **Защита от «отравленных» документов** | Если в базу знаний попадёт документ с вредной инструкцией, модель может её выполнить | Проверка загружаемых документов; ограничение того, что документ может «приказывать» модели |
| **Обезличивание персональных данных** | Сейчас маскирование просто есть как функция; качества и правил нет | Правила обезличивания + проверка, что после обработки человека не узнать |
| **Требования к внешним поставщикам моделей** | Облачная модель — это передача данных третьей стороне | Договорные условия: где обрабатываются данные, сколько хранят, кто ещё имеет доступ |
| **Учёт и выдача доступов** | Сервисные доступы к модели есть в схеме, но нет порядка выдачи и отзыва | Заявка, срок, владелец, регулярная проверка «кому ещё нужен» |

### 2.3 Качество: что стоит добавить

| Чего нет | Почему важно | Что сделать |
|---|---|---|
| **Контроль качества на реальном потоке** | Проверки есть при выпуске обновлений; между ними качество может тихо упасть | Еженедельная выборка реальных запросов с проверкой по эталонам (в проекте это уже описано — включить как постоянную практику) |
| **Обратная связь от сотрудников в дело** | Кнопка «ответ неверный» есть, но нет процесса: кто и когда это разбирает | Каждый разбор ошибки превращается в новый проверочный пример; раз в месяц — разбор накопившегося |
| **Показатели пользы, а не только правильности** | «Ответ верный» ≠ «инструментом пользуются» | Считать долю случаев, прошедших через инструмент, и долю принятых ответов |
| **Понятный список эталонов по каждой задаче** | Сейчас эталоны описаны для пяти направлений завода | По каждой прикладной задаче — свои 20–50 примеров с верными ответами |

### 2.4 Эксплуатация: чего не хватает

| Чего нет | Простыми словами | Что сделать |
|---|---|---|
| **Договорённости по скорости и доступности** | Не сказано, за какое время должен отвечать чат и что считается сбоем | Записать целевые цифры (например, 95% ответов быстрее N секунд) и что делать при нарушении |
| **Дежурство и разбор сбоев** | Непонятно, кто поднимает трубку, если всё встало | Дежурный, инструкции на типовые сбои, журнал происшествий |
| **Откат версий** | Модель и инструкции для неё обновляются, а как вернуть вчерашнее состояние — не описано | Хранить версии, уметь переключаться за минуты |
| **Резервное копирование и восстановление** | Для данных и моделей не заданы допустимое время простоя и потери данных | Задать и проверить один раз на практике |
| **Учёт расходов** | Бюджеты есть, а кто сколько потратил — нет | Отчёт по подразделениям: запросы, стоимость, самые дорогие задачи |

### 2.5 Люди, деньги, управление

| Чего нет | Почему это важно | Что сделать |
|---|---|---|
| **Юридическая позиция по ответственности** | Кто отвечает за ошибку в ответе и можно ли на него ссылаться в работе | Короткое заключение юристов: где ответ — справка, где нужен человек, что писать в документах |
| **Экономика** | Без расчёта «сколько стоит один случай» нельзя понять, где инструмент дороже ручной работы | Считать стоимость на случай по каждой задаче |
| **Портфель задач и приоритеты** | Иначе приоритет достаётся тому, кто громче просит | Готовая модель — в папке `dept/` этого же репозитория |
| **Метрики программы для руководства** | Отчитываться «внедрили столько функций» — путь к закрытию бюджета | 5–7 показателей: процессы в работе, польза в часах, доля случаев через инструмент, нарушения безопасности (ноль), стоимость на случай |
| **Покупка готового вместо своей разработки** | Часть задач дешевле купить, но проверять надо совместимость с требованиями ИБ | Обзор рынка до разработки; критерии «покупаем» и «делаем сами» |

## Часть 3. Три вещи с наибольшим эффектом

Если выбирать только три направления, где вложение даёт больше всего:

1. **Права доступа из учётных систем.** Без них нельзя безопасно пускать людей к корпоративным документам — а именно там основная польза. Это же снимает главный риск ИБ.
2. **Закрыть обходы и держать один вход.** Дешёво, быстро, и без этого вся защита бессмысленна. Плюс это то, что покажет проверка: контроль реально работает.
3. **Встроить в рабочие места и научить людей.** Иначе инструмент останется «интересной штукой», а эффекта в отчётности не будет.

---

## Что делать на этой неделе

1. Проверить, закрыты ли два обхода: прямой веб-поиск в чате и опубликованные порты Docker.
2. Составить список видов данных с пометкой «открытые / внутренние / секретные / персональные» и владельцем — хотя бы на одну страницу.
3. Написать одну страницу «что делать при инциденте с ИИ» и назначить ответственного.
4. Выбрать одну прикладную задачу и проверить на ней перенос прав из учётной системы — до всякой разработки.
5. Назначить владельца метрик и завести таблицу: сколько случаев, сколько минут, сколько через инструмент.

## Как это проверить, а не пересказать

Требования из этого документа заведены объектами модели: `arch/controls/01-ib.yaml`,
`02-data.yaml`, `03-ops.yaml`. Каждое ссылается на компоненты (`satisfied_by`), которые его
закрывают, и на доказательство. Что не закрыто — видно одной командой:

```bash
npm run arch -- controls --missing     # сейчас: OP-02 «данные на диске зашифрованы»
```

Связка на каждый день: `npm run arch -- impact dlp` — что затронет изменение компонента и какие
требования на нём держатся (и останутся ли они без покрытия, если компонент убрать).

Смысл: список пробелов перестаёт быть мнением и становится данными, которые обновляются вместе
с моделью. Инструмент не заменяет GRC: сроки аттестации, акты и подписи живут в своих системах.
