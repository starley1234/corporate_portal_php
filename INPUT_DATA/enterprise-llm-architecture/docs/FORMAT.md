# Формат arch/*.yaml

```
arch/
  meta.yaml          заголовки страницы, ui (оболочка), sections (разделы), kinds (id -> [цвет, название])
  components.yaml    описания компонентов: id -> текст (показывается по клику на узел с тем же id)
  map.yaml           карта перехода AS-IS -> TO-BE (необязательно; собирает отдельную вкладку)
  decisions/NN-*.yaml  журнал решений (ADR), необязательно; собирает вкладку «Журнал решений»
  lock.yaml          замочки залоченных разделов: sha256 содержимого вкладок (создаёт `arch lock`)
  <раздел>/NN-имя.yaml   вкладки; порядок на странице = порядок разделов, затем имён файлов
```

Разделы задаются в `meta.yaml`, по умолчанию — `tobe` и `asis`:

```yaml
sections:
  - { dir: tobe, label: "TO-BE", role: primary, locked: true }   # основной, всегда виден; заморожен
  - { dir: solutions, label: "Решения", role: solution }         # прикладной слой, открыт для правок
  - { dir: asis, label: "AS-IS", hidden: true, role: asis,       # скрыт за переключателем
      banner: "**ТЕКУЩЕЕ СОСТОЯНИЕ.** Только для сравнения." }
```

`hidden: true` — вкладки раздела скрыты за кнопкой; `banner` — текст, который добавляется
в начало каждого `lead` раздела. Разделов может быть сколько угодно и с любыми именами
(например, `asis`, `interim`, `tobe`).

`role` определяет, как раздел участвует в карте перехода: `primary` — целевой (к его узлам
привязываются `tobe`-позиции), `asis` — текущее (его узлы считаются AS-IS), `solution` —
прикладной слой (в карте не участвует), `governance` — раздел управления: именно в него
складываются сгенерированные вкладки («Карта перехода», «Журнал решений»), чтобы не менять
замороженный `primary`-раздел. По умолчанию: первый раздел — `primary`, скрытые — `asis`,
остальные — `solution`; если раздела с `role: governance` нет, сгенерированные вкладки идут
в первый раздел.

`locked: true` — раздел заморожен: его вкладки нельзя менять, `check`/`build` сверяют их с
`arch/lock.yaml`, а `add-node`/`add-edge`/`layout` в залоченном разделе отказывают. Состояние —
`npm run arch -- lock --list`; поставить замочки — `npm run arch -- lock`; переставить после
осознанной правки — `npm run arch -- lock --force`. Хеш нормализует перевод строки (LF) и BOM,
поэтому не зависит от ОС.

## Оболочка страницы (`ui.shell` в `meta.yaml`)

```yaml
ui:
  shell: panel      # panel (по умолчанию) | classic
```

`panel` — меню слева (название, режим, поиск, разделы списком, листание вкладок);
`classic` — прежний вид: шапка и лента вкладок сверху, скрытые разделы за переключателем.
Оболочки лежат в `src/shells/<имя>/`, движок схем у них общий.

Вкладка: `title`, `overview` (режим «Общий вид») и `detail` («Подробно»); в каждом `lead` (текст сверху) и `blocks` (список блоков).

Отдельной шапки на странице нет: `heading` и `subtitle` из `meta.yaml` стоят вверху меню, там же
переключатель «Общий вид / Подробно» и поиск; список разделов скроллится ниже них. Вкладки сгруппированы
по разделам: у каждого раздела свой список (пункт — `Название раздела · N. Заголовок вкладки`).
Раздел сворачивается кликом по заголовку, скрытые разделы (`hidden: true`) раскрываются кнопкой
внизу меню, вкладки ищутся полем поиска, а легенда типов узлов показывается под каждой схемой —
только для тех `kinds`, что на ней есть.

## Тексты
Мини-разметка: `**жирный**`, `` `код` ``, `[текст](https://…)`; остальной HTML (`<br>`) проходит как есть. Подписи узлов, связей и зон — обычный текст без разметки.

## Блоки
Один блок = один тип + необязательный `title` (заголовок h3 над блоком).

| тип | значение |
|---|---|
| `scheme` | схема (ниже) |
| `sequence` | диаграмма последовательности (ниже) |
| `table` | `{head: [..], rows: [[..], ..], center: [номера колонок с 0]}` |
| `cards` | список `{title, text, color, chips: [..]}` (`chips` — необязательные теги) |
| `steps` | список пунктов нумерованного списка |
| `note` / `warn` | текст в рамке / красная рамка (`style:` — необязательный CSS) |
| `heading` | заголовок без рамки |
| `capacity` | интерактивный калькулятор нагрузки |
| `html` | сырой HTML — только в крайнем случае |

## Схема (`scheme`)
```yaml
- scheme:
    size: [1200, 420]                       # ширина, высота холста
    groups: [[x, y, w, h, Подпись], ..]     # пунктирные зоны (необязательно)
    nodes:
      - {id: gw, at: [555, 130, 110], label: gateway, sub: личность, DLP, kind: core}
    edges:
      - ow -> gw                            # сплошная
      - ow --> search: подпись              # пунктирная (необязательная/служебная) + подпись
      - gw -> ll: {label: ключ, kind: data, rel: uses, via: [[1,2],[3,4]]}
    routes:                                 # подсвечиваемые цепочки
      Локальная: user -> proxy -> gw
      С пояснением: {path: a -> b, note: текст при выборе}
    hint: подсказка под схемой
```
- `at: [x, y, ширина]` — центр узла; без `at` узел сам встанет в «лоток» под схемой (с предупреждением) — потом расставьте.
- `kind` — ключ из `kinds` в `meta.yaml` (цвет и легенда). Без `kind` — внешний.
- Опции узла: `sub`, `info` (текст по клику; `{id}` подставляет компонент из components.yaml), `stack`, `dash`, `pill`.
- Опции связи: `label`, `kind`, `out`/`in` (сторона `l r t b`), `via` (ломаная вручную), `label_at`, `both`, `tag` (группа из `toggles`), `rel` (тип связи, см. ниже).
- Новым связям `via` не нужен — линия строится сама.

### Тип связи (`rel`)

Подпись отвечает на вопрос «что написано на стрелке», тип — «что происходит». Без типа все связи
в графе одинаковые, и на вопрос «где проходит граница доверия» граф не отвечает.

| `rel` | Что означает | Пример |
|---|---|---|
| `flow` | поток запроса или данных (по умолчанию, писать не нужно) | `user -> ingress` |
| `uses` | вызывает или задействует другой компонент | `gw-v2 -> dlp-v2: {rel: uses, label: sync}` |
| `carries` | несёт данные: ответ, метрики, вердикт | `router-v2 --> out-v2: {rel: carries}` |
| `runs_on` | развёрнут на узле, VM или хосте | `vm-llm -> vm-llmgpu: {rel: runs_on}` |
| `enforces` | обеспечивает правило, политику или требование | `c-rec -> c-gw: {rel: enforces}` |
| `satisfies` | закрывает требование из `arch/controls/` (резерв под матрицу покрытия) | `dlp -> IB-01` |

Неизвестный тип — ошибка `check`: закрытый список, чтобы через полгода не появилось пять
синонимов одного и того же. Тип видно в `arch show <вкладка>`, `arch node <id>` и в `graph --json`
(раздел `byEdge`); в Neo4j он становится типом связи (`[:USES]`, `[:CARRIES]`).

## Последовательность (`sequence`)
```yaml
- sequence:
    width: 1600
    actors: [{id: u, label: Клиент, kind: app}, ..]
    messages:
      - u -> gw: prompt                      # вызов
      - gw --> u: {label: ответ, note: пояснение при выборе шага}   # возврат (пунктир)
    phases: [[1, 3, Синхронные проверки]]    # номера шагов с 1
```

## Карта перехода (`arch/map.yaml`, необязательно)

Связывает позиции текущего состояния с узлами целевого; из файла собирается вкладка
**«Карта перехода»** (последней в основном разделе, `role: primary`).

```yaml
title: Карта перехода AS-IS → TO-BE
entries:
  - { asis: dlp, tobe: dlp-v2, status: move, note: "Regex-DLP остаётся синхронным" }
  - { asis: boot, status: tbd,  note: "заменяется GitOps — решение не зафиксировано" }
  - { tobe: policy-v2, status: new, note: "Policy & Response Gate — новое" }
```

- `asis` — id из `components.yaml` или узел схемы раздела с `role: asis`;
- `tobe` — узел схемы раздела с `role: primary` (обязателен для `status: new`);
- `status`: `keep` сохраняется · `move` переходит · `drop` выводится · `new` новое, нет в AS-IS · `tbd` не решено.

Проверяется: известность id с обеих сторон, обязательные поля, повторы.
Покрытие (что из AS-IS не упомянуто) — `npm run arch -- map --missing`.

## Журнал решений (`arch/decisions/*.yaml`, необязательно)

Один файл — одно архитектурное решение. Из каталога собирается вкладка **«Журнал решений (ADR)»**
в разделе с `role: governance`: сводная таблица в «Общем виде», полные тексты в «Подробно».

```yaml
id: ADR-006
title: Multi-tenancy и ACL в RAG
status: proposed                      # proposed | accepted | rejected | superseded
date: 2026-11-05                      # необязательно (рекомендуется ДДДД-ММ-ДД)
owner: Архитектор платформы           # необязательно, но у proposed обязателен на практике
due: 2026-12-04                       # необязательно: к какому сроку решаем
links: [ tobe/08-ocr-rag-tools, solutions/01-pipelines-platform ]   # необязательно, id вкладок
context: "Недопустимо смешать ACL разных подразделений: фильтры UI не защищают выдачу."
decision: "ACL применяется в retriever на каждый чанк, а не только фильтрами в UI."
need:                                 # необязательно, но для proposed — зачем: что мешает решить
  - "Модель прав: группы, подразделения, проекты и правила наследования."
  - "Golden set: 50–100 вопросов с эталонными ответами."
consequences:                         # необязательно, список
  - "Плюс: выдача ограничена правами источника."
  - "Минус: чанк без метки недоступен никому (default-deny)."
supersedes: ADR-002                   # необязательно, для status: superseded
```

Поля `owner`, `due` и `need` отвечают на вопрос «почему решение до сих пор предложено, а не принято»:
`check` предупреждает, если у `proposed` нет владельца или списка `need`, а на вкладке журнала
у открытых решений видно, кто решает и чего не хватает. Список: `arch adr --status proposed`.

Обязательны `id`, `title`, `status`, `context`, `decision`. Проверяются: уникальность `id`,
известный `status`, существование вкладок из `links`, формат `date`, наличие `supersedes`
у заменённого решения. Список и фильтр — командой:

```bash
npm run arch -- adr                       # все решения со статусами
npm run arch -- adr --status proposed     # только открытые
npm run arch -- adr ADR-006               # решение целиком
npm run arch -- adr --json                # для агента
```

Открытое решение — это гипотеза, а не обязательство: пока `status: proposed`, соответствующая
часть схемы считается необязательной. Перевод в `accepted` и история — через git.

## Контракт слоёв (`uses` и `via` во вкладке)

Прикладной раздел (`role: solution`) описывает, что он занимает у платформы. Это машиночитаемый
контракт: видно, кто чем пользуется, и что нельзя менять, не спросив потребителя.

```yaml
title: Пайплайны подразделения
uses: [ edge-v2, gw-v2, dlp-v2, policy-v2, router-v2, qwenlocal-v2, ocr-v2, rag-v2, audit-v2 ]
via: [ e-gw, e-guard ]        # к моделям — только через эти узлы схемы
overview:
  …
```

- `uses` — список id узлов платформы (виден в схемах раздела `primary`). `uses: []` —
  «ничем не пользуюсь»: явный ответ вместо молчания. Отсутствие `uses` у прикладной вкладки —
  предупреждение `check`.
- `via` — узлы **своей** схемы, через которые разрешены обращения к моделям (узлы `kind: egress`
  и `kind: local` — выход в облако и локальная модель). `check` перебирает все пути к таким
  узлам: если найдётся путь, не проходящий ни через один `via`-узел — это ошибка, а не
  пожелание. Заданный `via`, не лежащий ни на одном пути, — предупреждение: проверка не
  срабатывает.

Так инвариант «ни один вызов LLM не идёт в обход ingress → gateway → DLP → guard» перестаёт быть
текстом в документации и становится проверкой. Обзор контракта:

```bash
npm run arch -- contract            # кто что использует + обратный индекс
npm run arch -- contract --json     # для агента
```

Обратный индекс показывает, сколько прикладных решений висит на каждом узле платформы, и где
узлы не востребованы ни одним решением (считается по каноническому виду платформы — первой
вкладке раздела `primary`; переопределить можно через `meta.yaml`: `contract: {reference: tobe/01-platform}`).
«Не используется» — подсказка, а не ошибка: клиентские и выходные узлы решений не занимают.

Канонический вид нужен потому, что один компонент часто рисуют в разных разрезах под разными id
(`gw-v2` в сводной схеме, `cy-gw` в последовательности, `p-gw` в детальной). Контракт это не
исправляет, но делает видимым. Дальше — общий реестр сущностей и `ref` у узлов (см. `arch/entities.yaml`
и `docs/TOOLKIT.md`).

## Требования и покрытие (`arch/controls/*.yaml`, необязательно)

Требование — такой же объект модели, как компонент: у него есть формулировка и список того,
чем оно обеспечено. Из файлов собирается вкладка **«Требования и покрытие»** в разделе `governance`.

```yaml
# один файл — одна область; внутри может быть список требований
- id: IB-01
  title: "Текст проверяется до вызова модели: запрещённое не уходит провайдеру"
  area: ИБ                     # ИБ | Данные | Эксплуатация | Процесс
  source: "Внутренняя политика ИБ, п. 4.2"   # необязательно: откуда требование
  satisfied_by: [ dlp, policy-gate ]         # компоненты: id сущности или узла схемы
  evidence: "Синхронный DLP на входе; при BLOCK модель не вызывается."
- id: OP-02
  title: "Данные на диске зашифрованы"
  area: Эксплуатация
  satisfied_by: []             # пусто — пробел
  note: "Не сделано: шифрование томов не внедрено. Это пробел, а не описание."
```

Правила проверки: `id` обязателен и не повторяется; `satisfied_by` — список, каждый id должен
существовать (в реестре сущностей или на схеме) — иначе ошибка; пустой `satisfied_by` без `note`
даёт предупреждение: непонятно, это пробел или ещё не разобрались. `area` — из закрытого списка.

Пробелы не валят `check`: это не поломка модели, а очередь решений. Их видно в `arch status`
и командой `arch controls --missing`; фильтр по области — `--area ИБ`.

Связь работает и в обратную сторону: `arch impact <компонент>` перечисляет требования, которые на
нём держатся, и предупреждает, если он единственный исполнитель — то есть при его удалении
требование останется без покрытия.

## Инварианты (`arch/invariants/*.yaml`, необязательно)

Правило «чего быть не должно» — то, что нельзя проверить глазами на сорока вкладках.
Один файл — одно правило. `npm run check` проверяет их вместе с остальной моделью,
`npm run arch -- invariants` показывает отчёт по-человечески.

```yaml
id: INV-001
title: Модель вызывается только через ingress, gateway и DLP
status: active            # active | draft (черновик не валит check)
severity: error           # error → ошибка check, warn → предупреждение
rule: no-bypass           # no-bypass | no-edge | reachable
tabs: [ tobe/01-platform, tobe/03-request-path ]   # id вкладок или разделы
from: [ webclient, p-clients ]     # откуда
to: [ router-v2, p-ll ]            # куда
through: [ gw-v2, dlp-v2 ]         # через что обязан проходить путь (для no-bypass)
why: "одна фраза: зачем это правило"
```

| `rule` | Что означает | Что нужно указать |
|---|---|---|
| `no-bypass` | путь из `from` в `to` обязан проходить через **все** узлы `through` | `through` обязательно |
| `no-edge` | между `from` и `to` не должно быть прямой связи (в любую сторону) | `from`, `to` |
| `reachable` | из `from` должен быть путь в каждый `to` (контур не разорван) | `from`, `to` |

Как считается: берутся только связи `edges` схем — не текст и не `routes`. Узлы, которых нет
на вкладке, пропускаются, поэтому одно правило может покрывать несколько вкладок с разными
именами узлов. Если правило не нашло ни одного своего узла, `check` предупреждает: скорее
всего опечатка или вкладку переименовали.

Правила, которые сейчас заведены в проекте: `arch/invariants/01-model-through-gateway.yaml`
(обход gateway и DLP), `02-sandbox-no-direct-egress.yaml` (песочница с выходом в интернет),
`03-secrets-isolated.yaml` (секреты рядом с внешними системами), `04-routes-reachable.yaml`
(разорванный контур). Ещё два инварианта проверяются контрактом слоёв (`via` выше).

## Раскладка

`at: [x, y, ширина]` расставляется вручную, но черновик делает команда:

```bash
npm run arch -- layout <вкладка> o                 # расставить узлы без at (missing)
npm run arch -- layout <вкладка> o --mode zone    # разложить по зонам groups (--all — все узлы)
npm run arch -- layout <вкладка> o --mode flow    # слоями по потоку слева направо
npm run arch -- layout <вкладка> o --dry          # показать, не меняя файл
```

Алгоритм детерминирован (одинаковый вход → одинаковый выход), разводит перекрытия и,
если узлы не помещаются, расширяет `size` схемы (об этом будет WARN). Результат — черновик:
финальную композицию всё равно правит человек.

## Проверки
`npm run check` (или `build`) проверяет: ссылки связей и маршрутов на узлы, дубли id, неизвестные kind, число ячеек в таблицах, `{id}` в info, пересечения узлов и выход за холст (предупреждения), замочки залоченных разделов (`locked: true`) против `arch/lock.yaml`, журнал решений (уникальность `id`, статусы, ссылки) и контракт слоёв (`uses` ссылается на существующие узлы платформы; `via` реально перекрывает все пути к моделям). Отдельно: `npm test` — тесты компилятора, раскладки, сборки, CLI, замочков, журнала решений и контракта.
