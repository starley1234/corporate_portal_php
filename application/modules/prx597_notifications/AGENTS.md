* Центр уведомлений платформы. Единственный слой доставки пользователю:
  колокольчик (опрос `/prx597/api/unread`), почта, Telegram, MAX.
* **Модуль-источник не отправляет ничего сам**: он объявляет событие в
  манифесте (`notify.events` в `config/prx_module.php`) и зовёт
  `Service_Prx597_Notify::emit()`. Всё остальное — здесь.
* **prx217 удалён** 09.10.2026 (дубль). Мост prx208 → prx597:
  `EventBus::_bridge_to_prx597()` (раньше клал в мёртвые таблицы prx_217_*).
  Почтовый транспорт переехал сюда: `Service_Prx597_Mail::send_direct()`
  (им пользовались prx612/prx613/prx661).
* Новые события: только `Notify::emit()` / `Notify::notify()` — не INSERT.
* Письма: только `Notify::send_email()` (symfony/mailer, `EMAIL_DSN`) или
  `Service_Prx597_Mail` для разовых писем «по кнопке». Транспорт ровно один.
* email_status: none = письмо не требовалось (не ошибка).
* API-контроллер (`Controller/Prx597/Api`): `before()` отвечает 401/403 и
  ставит `$_halt`, но Kohana выполняет действие ВСЁ РАВНО — каждое действие
  обязано начинаться с `if ($this->_halt) return;` (06.10.2026 анонимный
  опрос колокольчика падал EMERGENCY «read property id on null»). Стенд
  `tests/Contracts/prx597_api.php`.
* Опасные действия — двойное нажатие (`data-prx-arm`): чистка, сброс лимитов,

* Вёрстка по эталону: крошки + h1, KPI, 2/3 + 1/3, ничего мельче `text-xs`.

Сводка (`/prx597/admin`) открывается полосой «Как идёт уведомление»: источник → реестр
→ лимиты → outbox → канал → DLQ, с живыми цифрами из `Service_Prx597_Engine::stats()`
(`views/prx597/partials/summary.php`, 23.11.2026). Журнал источников-событий шины — `/prx208_events`.

## Состояние (16.11.2026)

- Каналы: `in_app` (колокольчик), `email`, Telegram, MAX. Пользовательские
  UI/API видят только готовые каналы; админка — `channels(FALSE)`.
- Сводки разделены по `user_id + channel + group_key`; при отправке права и
  подписки проверяются повторно. Общие повторы и DLQ — ручное действие.
- Тишина по правилам: наружу только то, что требует действия; важность из
  категории; у письма есть выключатель; письмо — одна мысль; сводка раз в
  сутки без повторов; предохранитель на источник.
- Шаблоны: `placeholders` в реестре — CSV-строка. Адресное сообщение —
  `Notify::system_message()`, только внутреннее, независимо от подписок.
- Осталось на сервере: живая проверка SMTP/ботов и расписание prx603.
- Подробная история решений — `docs/history/prx597-notifications.md`.

## Проверки модуля

- `make test-contracts` — все изолированные PHP-контракты, включая
  `tests/Contracts/prx597_{engine,delivery,api,hook}.php`. Engine включает
  `tests/Contracts/fixtures/prx597_{queue,settings,admin}.php`.
- Без PHP CLI — WASM по инструкции `tests/README.md`.
- JS: `npm test` — существующий общий набор UI/CSRF-тестов.
- `bash .tools/php_check_all.sh application/modules/prx597_notifications`.
- Полное соответствие драйверов — только `Base::channel_driver()`, не ucfirst.
  `channels()` — настроенные транспорты, `user_channels()` — пользовательский
  набор без непригодной самостоятельной привязки MAX business.
- `Notify::user_pref_fields()` принимает PATCH: отсутствующее поле не меняется;
  checkbox формы отправляет скрытый `0` перед `1`. Не возвращать скрытые каналы
  через `events.channels`, `binding`, `prefs` или клетки событий.
- Дедуп доставки — `Notify::_delivery_dedup(user_id, channel, key)`: хеш
  помещается в VARCHAR(160); глобальный ключ без получателя терял рассылки.
- Сводка НИКОГДА не группируется только по group_key. Обязательное событие
  не обходит роли; обязательная запись in_app уже добавляется в `plan_for()`.
- Тихие часы: -1 = конфиг, одинаковые границы = без паузы. Ошибка сводки —
  `_failed_delivery()` (pending/backoff/dead), не тупиковое присваивание failed.
- Env ботов: `PRX597_NOTIFICATIONS_*` → `PRX597_*` → короткие старые имена.
  Служебная авторизация — общий `WORKER_API_TOKEN`, не PRX597_WORKER_TOKEN.

## Как модулю попасть в центр уведомлений

1. Объявить событие в `notify.events` манифеста.
2. Позвать `Service_Prx597_Notify::emit()` в момент события.
3. Не изобретать свою доставку.

Полный контракт, примеры и миграции — `docs/integrations/prx597-events.md`.

## Грабли, на которые уже наступали

* PostgreSQL BOOLEAN приходит как `'t'`/`'f'` — приводить через
  `Service_Prx597_Base::_truthy()`, иначе «выключить» не выключалось.
* `Database::query(Database::UPDATE, …)->execute()` — фатал: драйвер
  возвращает int. Только `query()`.
* Схема создаётся сама (`Schema::ensure()` из `Ensure_tables()`): миграции не
  обязательны, но DDL правится ТОЛЬКО в `Schema.php` — иначе разъезд.
* Счётчик непрочитанных держит триггер (`prx_597_unread`), не `COUNT(*)`.
* Обязательное событие (`mandatory`) нельзя выключить ни пользователю, ни
  админу — это только для безопасности и денег.
* Пока человек ничего не выбрал, наружу не уходит НИЧЕГО (владелец,
  16.10.2026): умолчания настроек и пустые клетки матрицы для почты,
  Telegram и MAX значат «нет». Колокольчик исключение — он включён всегда.
  Новый внешний канал или событие автоматически включённым не бывает.
* Вебхуки ботов всегда отвечают 200: иначе Telegram/MAX долбят повторами.

## Вьюхи админки

`views/prx597/admin.php` — каркас вкладок и общие переменные; содержимое каждой
вкладки лежит в `views/prx597/partials/<tab>.php` (summary, queue, events,
message, templates, channels, limits, journal) и подключается через
`include __DIR__`. Новую вкладку добавляйте парой «каркас + partial», чтобы
файл админки не рос обратно.

## Долг владения очередью (23.11.2026)

Прямой SQL этого модуля к `prx_120_*` — замороженный legacy-долг, не
постоянное платформенное исключение. Инвентарь/целевые контракты владельца —
`docs/WORKERS.md`; `test_queue_table_debt.py` запрещает рост ссылок в четырёх
проверенных модулях. Новые чтения/записи — только через сервис prx120.
В Notify остаются ALTER notified_at, выборка и UPDATE отметки в чужой
таблице. Переносить в миграции/контракт prx120 с сохранением существующих
отметок и идемпотентности; этим спринтом доставка не переработана.
