## Состояние работ (16.10.2026, ночь): тишина по правилам

Владелец: «Посмотри как уведомления сделать более лаконичными и по-правилам
(я плохо знаю теорию и могу дать неверные указания)… Отработай свои
предложения». Шесть правил внедрены, каждое — с проверками в стендах.

1. **Наружу — только то, что требует действия.** `Engine::_seen_on_site($row)`
   перед тихими часами и лимитами смотрит строку колокольчика по
   `outbox.inbox_id`: прочитано → пропуск «Прочитано на сайте», убрано в
   архив → «Убрано в архив на сайте». То же правило внутри сводки. Сообщение
   не теряется — уходит в журнал с причиной. Выключатели
   `delivery.skip_when_read` / `skip_when_archived` (умолчание — да).
2. **Важность из категории.** `Registry::priority_for($event, $explicit)`:
   security 1, billing 2, system 3, jobs 5, content 6, social 7; незнакомая
   категория — 5; явное значение модуля побеждает; шкала 1..9 (меньше —
   важнее). Зовётся из `Notify::emit()`.
3. **У каждого письма есть выключатель.** `Notify::unsub_token/_url/_verify/
   _apply/_headers`: подписанная HMAC ссылка, страница `/prx597/unsub`
   (`Controller/Prx597/Unsub.php`, без сессии — пропуск в подписи), два вида
   отказа: «Больше не присылать это событие» (`scope=event`, снимает клетки
   внешних каналов, объявленных у события) и «Отключить письма»
   (`scope=channel` → `*_enabled = FALSE`). Колокольчик не трогаем; для
   `mandatory` отказ вежливо отклоняется. В письме — заголовки
   `List-Unsubscribe` и `List-Unsubscribe-Post: One-Click` (RFC 8058);
   POST с «одним кликом» получает пустой ответ 200. Секрет:
   `PRX597_NOTIFICATIONS_UNSUB_SECRET`, иначе `WORKER_API_TOKEN`, иначе APP_URL.
4. **Письмо — одна мысль.** `Render::subject_line()` (зовётся из
   `Channel::_subject()`): без «Уведомление:»/«PRX.ru:», без переводов строк,
   до 60 знаков. Контрактный стенд проверяет это по шаблонам манифестов.
5. **Сводка — раз в сутки и без повторов.** `digest.per_day` = 1 (вторая
   сводка за сутки откладывается до следующего окна, сообщения не теряются),
   одинаковые события склеиваются в строку «… (и ещё N)», прочитанное на
   сайте из сводки вычёркивается. Тема сводки — «Сводка уведомлений (N)».
6. **Предохранитель на источник.** `Limits::bucket_source()` +
   `limits.source_hour` (почта 120/час на событие у всех): при превышении
   рассылка встаёт до конца часа, в `prx_597_settings` пишется `alert.source`,
   а панель на вкладке очереди показывает баннер «Предохранитель» и метку
   «за час: N» у каждого события ленты (`Engine::feed_events()` отдаёт
   `c_hour`).

## Состояние работ (16.10.2026, вечер)

**Владелец: «по умолчанию у пользователей должны быть отключены уведомления»,
и его уточнение: колокольчик на сайте остаётся включённым.**
Значит: наружу (почта, Telegram, MAX) центр не шлёт ничего, пока человек сам не
отметит нужное; лента внутри сайта работает всегда — она не беспокоит.

- Умолчания исправлены во всех трёх местах, где они жили: код
  (`Notify::prefs_default()` — внешние `*_enabled` и старые `on_done`/
  `on_failed` = FALSE, `in_app_enabled` = TRUE), DDL
  (`Schema::tables()/alters()` — `DEFAULT FALSE` для внешних и `TRUE` для
  `in_app`, плюс `ALTER COLUMN … SET DEFAULT` для баз, поднятых раньше:
  `ADD COLUMN IF NOT EXISTS` умолчание существующей колонки не меняет) и API
  (`Api::_public_prefs()`).
- `Registry::sub_enabled()`: пустая клетка «событие × канал» — «нет» для
  внешних каналов и «да» для in_app. Согласие на внешнюю доставку живёт только
  в `prx_597_subs` и появляется по клику человека; снятый колокольчик молчит.
  Исключение одно — `mandatory` (безопасность/деньги): всегда in_app.
- Включённая клетка включает и сам способ доставки (`Registry::save_sub()`
  зовёт `Notify::save_prefs($uid, [$channel.'_enabled' => TRUE])`), иначе
  человек, отметивший событие в колонке «почта», ждал бы письма в тишине.
  Обратное неверно: галочка канала сама клетки не трогает.
- Доставка (`Engine::_deliver`, `_send_digest`) перепроверяет то же правило:
  выключенное после постановки в очередь не уходит. Явные каналы от модуля
  (`emit(..., ['channels' => …])`) тоже не разрешение слать — выключатели
  человека сильнее.
- Разово гасим «включения по умолчанию» (`Notify::_defaults_off_once()`,
  отметка `prefs.defaults_off`): выключаем только внешние каналы и старые
  флаги писем, только у тех, у кого нет ни одной явной клетки матрицы, и
  ровно один раз. Колокольчик уборка не трогает.
- `recipient_ids()` (объявление администрации) уважает явный отказ: если
  строки настроек есть, пустой список честнее рассылки отказавшимся; «все
  вошедшие» — только пока настроек нет ни у кого.
- Интерфейс: плашка «На сайте уведомления видны всегда, а письма и мессенджеры
  выключены — так у всех по умолчанию» с кнопкой «Настроить» (показывается,
  пока не включён ни один внешний канал), подписи в обеих карточках настроек и
  подсказка «способ доставки включён, но ни одно событие не отмечено».

## Состояние работ (16.10.2026, день): присутствие и «своё» событие

Владелец: «Не слать пользователю уведомление, если он сам инициировал событие и
находится на сайте. Пример: запустил обзор github, он сделался, я его смотрю —
и мне приходит внутреннее уведомление! Зачем?»

- **Присутствие.** Таблица `prx_597_presence` (`user_id` → `seen_at`), DDL в
  `Schema::tables()`, миграция `pgMigration_Prx_597_004_Presence`. Метку ставит
  колокольчик: он и так опрашивает `/prx597/api/unread` раз в 45 секунд, а
  вкладка добавляет `?visible=1`, только когда она открыта на виду
  (`document.visibilityState`). Свёрнутая или чужая вкладка присутствием НЕ
  считается — иначе уведомление о своём событии пропадало бы у того, кто ушёл.
  Запись не чаще раза в 20 секунд (несколько вкладок одного человека), старые
  строки убирает `Notify::presence_gc()` в проходе движка.
- **Правило на входе.** `Notify::_recipients()`: если событие помечено `self`
  и человек на сайте (`presence.minutes`, 3 минуты), получатель вычитается —
  колокольчик молчит, причина уходит в лог `Kohana::$log` («вы на сайте»).
  Настройка-выключатель `presence.skip_self` (таблица `prx_597_settings`,
  по умолчанию включено).
- **Правило на выходе.** Признак «своё» кладётся в строку очереди
  (`Notify::_enqueue()` пишет `payload.self`, в `data` он не попадает), а
  `Engine::_self_and_online($row)` перепроверяет присутствие в момент отправки —
  и в обычном проходе (`_deliver`), и внутри сводки (`_send_digest`). Причина
  пропуска: «Своё событие, вы на сайте — наружу не шлём» (`prx_597_log`).
  Зачем второй раз: между постановкой и отправкой проходят минуты (сводка —
  до суток), и человек мог зайти на сайт уже после неё.
- **Кто ставит `self`:** `Notify::notify()` — по виду события `job_done` (задача
  очереди, отчёт, сборка — итог заказа самого человека); явно в `emit()` —
  prx593 `prx593.review.done` и prx667 `prx667.build.done`. **Сбой не помечается
  никогда** (`prx593.review.error`, `prx667.build.error`, `job_failed`): сбой —
  просьба о действии, его будим и когда человек на сайте.
- **Чего НЕ делаем:** не глушим произвольные события «один получатель без
  инициатора» — под это правило попадёт чужое событие (заказ, ответ, приёмка),
  а его терять нельзя. Модуль говорит о «своём» событии сам.
- **Если таблицы нет** (база старее миграции) правило молчит, а уведомления
  работают как раньше: `seen_recently()` ловит исключение и отвечает «не видели».
- Стенд: `.tools/prx597_engine_stand.php` + `prx597_queue_cases.php` (SQL метки,
  окно, молчание для `self` при присутствии, доставка без присутствия),
  `.tools/prx597_delivery_stand.php` (строки 85/0: `payload.self` + присутствие —
  пропуск, без присутствия — доставка, чужое событие будим, то же в сводке).
- **Шкала важности в админке.** Вкладка «Лимиты»: блок «Важность событий по
  категориям» — строки «число + подпись + код категории» и по две стрелки,
  одной формой на всю шкалу (`name="move" value="<категория>:-1|1"`), у краёв
  кнопки выключены. `Registry::priority_move($category, $dir)` меняет местами
  соседей **по значениям**, а не перенумеровывает: набор чисел остаётся
  конфиговым (1, 2, 3, 5, 6, 7), поэтому «Задачи» не уезжают на 4 и не
  выпадают из сводки (`priority.digest_from = 5`). Итог пишется в настройку
  `priority.by_category` строкой `security=1,billing=2,…` — читается в базе
  как та же лестница, что на экране; `Registry::priority_map()` кладёт её поверх
  конфига. Контроллер: `Controller/Prx597/Admin.php::_priority_move()` (POST +
  CSRF, как остальные действия вкладки). Проверки — в
  `.tools/prx597_admin_cases.php` (12 стрелок, выключенные края, подсказка про
  пороги, перенос «Задач» выше «Системных», сохранение и чтение настройки).

  права и ошибки записи) и `prx597_notify_contract_cases.php` (контракт
  `notify` в манифестах модулей-источников, миграции, идемпотентность синхронизации).
- JS: `node --test tests/Js/prx597_notifications.test.mjs` и
  `node --test tests/Js/prx597_ai_template.test.mjs` (13 проверок вместе).
- `bash .tools/php_check_all.sh application/modules/prx597_notifications`.
- Полное соответствие драйверов — только `Base::channel_driver()`, не ucfirst.
  `channels()` — настроенные транспорты, `user_channels()` — пользовательский
  набор без непригодной самостоятельной привязки MAX business.
- `Notify::user_pref_fields()` принимает PATCH: отсутствующее поле не меняется;
  checkbox формы отправляет скрытый `0` перед `1`. Не возвращать скрытые каналы
  через `events.channels`, `binding`, `prefs` или клетки событий.
- Дедуп доставки — `Notify::_delivery_dedup(user_id, channel, key)`: хеш
  помещается в VARCHAR(160); глобальный ключ без получателя терял рассылки.
- Сводка НИКОГДА не группируется только по group_key. Обязательное событие
  не обходит роли; обязательная запись in_app уже добавляется в `plan_for()`.
- Тихие часы: -1 = конфиг, одинаковые границы = без паузы. Ошибка сводки —
  `_failed_delivery()` (pending/backoff/dead), не тупиковое присваивание failed.
- Env ботов: `PRX597_NOTIFICATIONS_*` → `PRX597_*` → короткие старые имена.
  Служебная авторизация — общий `WORKER_API_TOKEN`, не PRX597_WORKER_TOKEN.

## Как модулю попасть в центр уведомлений

Три шага. Без первого события нет в реестре — `emit()` его не доставит.

### 1. Объявить событие в манифесте

`application/modules/<ваш_модуль>/config/prx_module.php`:

```php
'notify' => [
    'events' => [
        'mymodule.order.paid' => [
            'title'        => 'Заказ оплачен',
            'description'  => 'Клиент оплатил заказ — деньги пришли',
            'category'     => 'billing',      // system|billing|jobs|content|security|social
            'icon'         => 'fas fa-sack-dollar',
            'channels'     => 'in_app,email', // через запятую
            'roles'        => 'login',        // login|manager|admin, через запятую
            'ability'      => 'mymodule.view',// пусто — доступно по ролям
            'digest'       => TRUE,           // FALSE — только немедленно, без сводки
            'placeholders' => 'order_no,amount,pay_url',
        ],
    ],
],
```

Декларация подхватывается сама: `Registry::sync_manifests()` читает все
манифесты (не чаще раза в час) и сливает их с ручными правками админа —
ручное не затирается, если `source = 'manual'`.

Склейка в сводку — **по умолчанию включена**: уведомление не превращается в
спам само по себе. Не склеивают только срочные события, и это пишут явно
(`'digest' => FALSE`): ошибки сборки, безопасность, деньги. Склейка работает,
когда человек выбрал режим (умолчание — раз в сутки, `digest.default`), и
касается только внешних каналов: в колокольчике событие видно сразу.

Приоритет — одна шкала на все механизмы: **меньше значит важнее**
(`1` критично, `5` обычное, `9` фоновое). До 16.10.2026 тихие часы и склейка
читали число наоборот, поэтому `1` была и критичной, и почти неважной сразу.
Конфиг: `priority.quiet_skip = 1` (что не ждёт утра), `priority.digest_from = 5`
(что можно копить).

События, которые модули заводили сами (`source = 'runtime'`), до 16.10.2026
не умели копиться в сводку — режим «раз в сутки» у человека ничего не менял.
Разовая правка `Registry::apply_digest_default_once()` (зовётся из
`Notify::ensure_tables()`, закрывается отметкой `registry.digest_default`)
включает им склейку и не трогает строки манифестов, события, заведённые
человеком, и всё, что он уже правил руками.

### 2. Позвать emit() в момент события

```php
Service_Prx597_Notify::emit('mymodule.order.paid', [
    'order_no' => $order->id,
    'amount'   => number_format($order->sum, 0, '.', ' '),
    'pay_url'  => '/orders/'.$order->id,
], [
    'user_id'  => (int) $order->user_id,          // кому; 0/нет — по roles/ability
    'priority' => 3,                              // 1..10, МЕНЬШЕ — важнее
    'href'     => '/orders/'.$order->id,          // куда ведёт клик
    'dedup'    => 'order-'.$order->id,            // не слать то же самое дважды
]);
```

`emit()` ничего не шлёт синхронно: пишет строку в ленту (`prx_597_inbox`/
`prx_597_notifications`) и ставит задания в очередь `prx_597_outbox`. Доставка
— отдельным проходом `Engine::run()` (HTTP `/prx597/api/outbox` по расписанию
раз в 5 минут, с токеном воркера).

Легаси-сигнатура `Notify::notify($user_id, $kind, $title, $body)` работает и
дальше: тип события выводится через `kind_event()`, код вида
`prx597.legacy.<kind>`.

### 3. Не изобретать доставку

Никаких своих `mail()`, своих таблиц уведомлений и своего «ещё одного»
колокольчика. Каналы, шаблоны, лимиты, тихие часы, привязку мессенджеров и
архив пользователь настраивает один раз — на `/prx597?tab=settings`.

## Грабли, на которые уже наступали

* PostgreSQL BOOLEAN приходит как `'t'`/`'f'` — приводить через
  `Service_Prx597_Base::_truthy()`, иначе «выключить» не выключалось.
* `Database::query(Database::UPDATE, …)->execute()` — фатал: драйвер
  возвращает int. Только `query()`.
* Схема создаётся сама (`Schema::ensure()` из `Ensure_tables()`): миграции не
  обязательны, но DDL правится ТОЛЬКО в `Schema.php` — иначе разъезд.
* Счётчик непрочитанных держит триггер (`prx_597_unread`), не `COUNT(*)`.
* Обязательное событие (`mandatory`) нельзя выключить ни пользователю, ни
  админу — это только для безопасности и денег.
* Пока человек ничего не выбрал, наружу не уходит НИЧЕГО (владелец,
  16.10.2026): умолчания настроек и пустые клетки матрицы для почты,
  Telegram и MAX значат «нет». Колокольчик исключение — он включён всегда.
  Новый внешний канал или событие автоматически включённым не бывает.
* Вебхуки ботов всегда отвечают 200: иначе Telegram/MAX долбят повторами.
