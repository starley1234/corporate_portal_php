# Модуль prx110_catalog — Каталог сервисов

Реестр публичных сервисов PRX (ядро платформы, диапазон 100–199).
**Один источник правды** для: каталога и Избранного в сайдбаре, карточек
главной, чипов раздела, быстрого поиска и подсказок иконок в /prx118_links.

## Как добавить сервис на главную/в меню (без правки чужого кода)

1. В модуле сервиса создайте `config/prx_module.php`:

```php
<?php defined('SYSPATH') or die('No direct script access.');
return [
    'id'        => 503,                      // номер модуля
    'slug'      => 'ndfl',
    'title'     => 'Калькулятор НДФЛ',
    'short'     => 'НДФЛ 13/15%: расчёт удержания и «на руки»',
    'icon'      => 'fas fa-file-invoice',
    'href'      => '/ndfl',
    'group'      => 'Финансы',
    'sort'       => 503,
    'created_at' => '2026-10-23', // дата первого появления модуля в репозитории
    'updated_at' => '2026-10-23', // обновлять при изменении сервиса/манифеста
    'keywords'  => 'ндфл 13 подоходный налог зарплата на руки',
    'api'       => ['/prx503/api/calc'],
    'card_view' => 'prx503/card',             // views/prx503/card.php — виджет главной
];
```

2. Подключите модуль в `application/bootstrap.php`.
3. Готово: модуль появится в `/services` и палитре «Все» с учётом видимости,
   на главной (если есть `card_view`) и в чипах своих страниц. Пользователь
   может закрепить его звёздочкой в Избранном; постоянное меню не расширяется.
   В рабочий каталог попадают только сервисы с итоговым состоянием `approved`;
   остальные состояния видны на `/portal-plan` с учётом аудитории и ACL.
4. В каждом новом манифесте указывайте `created_at` и `updated_at` в формате
   `YYYY-MM-DD`: первое — дата создания модуля, второе — дата последнего
   изменения сервиса. При изменении поведения или контента сервиса обновляйте
   `updated_at`; не используйте дату checkout/mtime файлов.

## API класса

- `Service_Prx110_Catalog::modules()` — манифесты (sort asc);
- `::get($slug)` — манифест по slug/названию модуля/id;
- `::home_cards($ctx, $limit)` — модули с `card_view`, видимые пользователю;
  при лимите стабильные идут первыми (разгрузка главной);
- `::menu_items()` — единственный постоянный пункт «Все сервисы» (`/services`).
  Остальные сервисы — в каталоге и персональном «Избранном»; `pin` не расширяет меню.
- `::header_nav()` — чипы раздела для шапки текущей страницы (NULL вне каталога);
- `::picker_icons()` — иконки для пикера /prx118_links;
- `::visible_modules($ctx)` — манифесты с итоговым состоянием `approved`
  с учётом аудитории и ACL; `wip` — лишь в контексте `preview`;
- `::plan_modules($ctx)` — манифесты для `/portal-plan`: все состояния
  (approved/wip/unpublished/archived) с полем `state`, с учётом аудитории и ACL;
- `::resolve_state($m)` — итоговое состояние каталога и плана: технический
  архив, иначе явное решение, иначе `unpublished` для `catalog:false` или `wip`.
  `::state_label($state)` даёт текст бейджа;
- `::search_json($ctx)` — JSON для палитры «Все сервисы» (кнопка в сайдбаре) и 3D-карты (`/prx110/api/catalog`);
  у item есть title/short/href/group/status, `api` и `nav_paths`: только
  относительные пути из манифеста (внешние и `//…` отбрасываются). `nav_paths`
  помогает подсветить закреплённый сервис на его вложенных/алиасных страницах.
- `::groups_summary($ctx)` / `::group_modules($slug, $ctx)` — для страницы /services;
- `::user_context()` — guest/logged/user_id/roles/admin/agent текущего запроса;
- `::resolve_status($m)` / `::resolve_audience($m)` — статус/аудитория с фолбэками
  (legacy badge/hidden → дефолты); `::can_see($m,$ctx)` — матрица видимости.
- `Service_Prx110_Favorites::items($user_id)` — сохранённые в БД закладки,
  отфильтрованные каталогом по текущей аудитории (сервис «в работе» — `wip`,
  ещё не одобренный на витрину, — закрепляется и виден тем, кого пускают
  аудитория и ACL: его страницы уже работают; `unpublished`/архив/нет доступа —
  нет; `Catalog::open_in_progress()`); `::mark_active()` отмечает
  наиболее точный href/alias. `::set()` задаёт явное состояние, `::import()`
  объединяет допустимые ссылки (до 100) без перезаписи существующих.

## Жизненный цикл и аудитория (новые поля манифеста, опциональны)

```php
'status'   => 'beta',     // draft|beta|stable|deprecated (beta — фолбэк из badge)
'audience' => 'public',   // public|auth|admin|agent (auth — фолбэк для hidden)
'catalog'  => FALSE,      // без решения → unpublished
'pin'      => TRUE,       // устаревшее поле; короткое меню не расширяет
```

- `sitemap` => ['/calendar/2026', …] — необязательный список ДОПОЛНИТЕЛЬНЫХ адресов
  модуля для `sitemap.xml` (страницы годов, разделов). Сам `href` попадает в карту
  автоматически, если модуль публичный (audience=public) и не draft. Собирает
  `Service_Prx602_Sitemap` (prx602_content); адрес — только `/путь` без query и `{шаблонов}`.
- Рабочий каталог `/services` показывает только итоговое состояние `approved`,
  не любой `status: stable`. `wip` виден в плане и в предпросмотре API каталога
  (`?agent_preview=1`, админ или агент), но не на `/services`. Фильтрация ссылок
  не заменяет проверку доступа в контроллерах.
- Без строки в `prx_110_publications` сервис в `wip`, даже с `status: stable`.
  Исключения: `catalog: false` даёт `unpublished`, а статус разработки
  `deprecated` всегда означает технический архив. `resolve_manifest_state()`
  используется только в подсказке плана.
- `/services` — компактный указатель: иконка, название, звёздочка; `short`
  показывается в хабе `/services/<group>` и как подсказка при наведении.
  Рабочие сервисы идут перед отдельным блоком «Инструменты платформы».
  Звёзды остаются в строках, список Избранного — только в боковой панели.
  Поле «Найти сервис» (общий partial с планом) ищет по обоим блокам, но не по
  содержимому платформы.
- `hidden` остаётся алиасом `audience='auth'` (аккаунтные страницы).
- Статус разработки: явный `status` → `badge='beta'` → `draft`.
  Инвентарь prx218 не участвует ни в вычислении статуса, ни в публикации.

## Страницы и маршруты модуля

- `GET /services` — SSR-каталог по группам (контроллер `Prx110_Catalog::action_index`);
- `GET /services/<slug>` — хаб группы (`action_group`, slug = group_slug);
- `GET /prx110/api/catalog` — JSON реестра видимых сервисов для палитры «Все сервисы» и `/orbit`; `user_id` обозначает текущую сессию, чтобы вкладка не показала каталог другого аккаунта.
- `GET /prx110/api/favorites` — видимые закладки текущей сессии;
  `POST` туда же принимает `csrf`, `account_id`, `href`, `pinned=1|0`.
  `account_id` только обнаруживает смену сессии в старой вкладке: user_id для
  чтения и записи берётся исключительно из Auth. У гостя API отвечает 401.
- Таблица `prx_110_favorites` создаётся миграцией
  `pgMigration_Prx_110_005_Favorites`; после обновления выполнить `bin/console db:migrate`.

## Контроллер сервиса при этом

```php
$this->set_menu(class_exists('Service_Prx110_Catalog')
    ? Service_Prx110_Catalog::menu_items()
    : []);
```

## Не делать

- Не редактировать `modules/`, `system/`.
- Не загружать манифесты через `Kohana::$config->load('prx_module')` — конфиг-каскад
  смёржил бы манифесты всех модулей в один массив. Только явное сканирование каталогов.

### Управление публикацией

`Service_Prx110_Publication::set_state()` проверяет `prx112.approve` и сохраняет
`approved`, `wip`, `unpublished` или `archived` в `prx_110_publications`. Решение
содержит `decided_by`, `decided_at`, `note`; при изменении состояния или комментария
выходит `prx110.publication.changed`. Только явное `approved` публикует сервис;
аудитория, ACL и технический архив остаются ограничениями. Каталог и план
защищены от ручного изменения. `prx218` остаётся только инвентарём.

Переход на схему `110_009`: бэкап → `bin/console db:migrate` →
`bin/console prx110:publication:backfill` (сверить предлагаемые состояния и
список модулей) → `bin/console prx110:publication:backfill --apply=1` →
включение нового кода и сверка `/services`. CLI новой версии нужен на шаге
подготовки; не направлять HTTP-трафик на новый код до backfill. При несовместимых
версиях схемы остановить трафик на время перехода.

Backfill предлагает `approved` для прежних `stable`, кроме `catalog:false` и
технического архива, и добавляет `backfill:protected` каталогу и плану. Он
не перезаписывает ни одного существующего решения. Если аудит выявил, что
кандидат не должен быть одобрен, внести явное `wip` до открытия HTTP-трафика.
Повторный запуск должен показать `would_insert=0 inserted=0`. Production-откат —
через бэкап; `down()` только для dev, комментарии при откате теряются.
