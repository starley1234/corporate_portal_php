## Назначение

«Диалог двух ИИ»: владелец задаёт тему — два агента обсуждают её по делу,
обмен за обменом. Ход ведёт сервер (очередь nj120), агенты при необходимости
ищут в интернете, а готовые материалы диалога индексируются общей семантикой
(nj115), чтобы агенты опирались на документы владельца, а не на память модели.
Разговор публикуется одной кнопкой и становится публичной страницей разбора.

## Маршруты и API

- `GET /dialog` — рабочий стол (гостю — плашка входа): форма быстрого старта,
  примеры тем, счётчики, мои диалоги.
- `POST /dialog/new` — создать диалог; `quick=go` сразу ставит подбор
  участников, `quick=edit` открывает диалог с настройками.
- `GET /dialog/<id>` — страница диалога: статус-ряд, лента реплик с поисками,
  материалы, настройки, лента событий (чужой опубликованный — вид для чтения).
- `GET /dialog/status/<id>` — JSON хода (поллит страница; `revision` растёт —
  JS перезагружает ленту).
- `POST /dialog/<id>/<action>` — `start`, `pause`, `stop`, `say`, `quick`,
  `settings`, `publish`, `delete`, `knowledge_add`, `knowledge_delete`,
  `knowledge_reindex` (CSRF; AJAX → JSON, иначе 303 + плашка).
  `start`, `quick` и `say` с `resume=1` требуют права `nj662.start`;
  `stop` — жёсткая остановка (снимает задание с очереди), `pause` — мягкая.
- `GET /dialog/list` — ПУБЛИЧНЫЙ каталог опубликованных разговоров
  (поиск `q`, пагинация, `per`).
- `GET /dialog/read/<id>` — страница ЧТЕНИЯ разговора (крупный шрифт, узкая
  колонка, управлений нет): опубликованный — всем, черновик — владельцу и
  админу. В sitemap НЕ заявлена: там остаётся `/dialog/<id>` (адрес не меняем,
  чтобы не дробить выдачу).
- `GET /dialog/all` — сводка ВСЕХ диалогов сайта (опубликованные и нет) по
  праву `nj662.manage` (админ): поиск по теме/владельцу/номеру, фильтр по
  статусу, просмотр без действий (решения — на странице диалога).
- `POST /dialog/api/{context,turn,progress,quick,fail,tick}` — приёмная
  воркера (`X-Worker-Token`; вне `KOHANA_ENV=development` пустой токен = закрыто).

## Очередь

- Каналы: `nj662.dialog` (один обмен: поиск → реплика A → реплика B → сводка)
  и `nj662.quick` (подбор участников). Постановка —
  `Service_Nj120_JobQueue::push` (`timeout_sec` 1800/900, `max_attempts` 2).
- Обработчик: `workers/n2j_workers/handlers/nj662_dialog.py` (реестр в
  `handlers/__init__.py`).
- **Ход ведёт сайт**: воркер отдаёт обмен в `/dialog/api/turn`, а следующий
  обмен ставит `apply_turn`. Воркер не знает ни моделей, ни настроек — всё
  приходит из `/dialog/api/context`.
- «Диалог не идёт» (пауза, отмена, устаревший обмен) — это **мирный стоп**
  задачи (`{"stopped": true, "reason": …}`), а не падение: иначе пауза
  выглядит как авария в мониторе очереди.
- Reconcile в манифесте: обмен доставлен, если его реплики лежат в
  `nj_662_messages`; подбор доставлен, если диалог уже не в статусе `quick`.
- Порог «воркер молчит» поднят в `nj120_jobs.silent_stop_channels`
  (`nj662.dialog` 1800 с, `nj662.quick` 900 с): обмен — это несколько вызовов
  модели и чтение страниц.
- `POST /dialog/api/tick` — пиналка обслуживания: `close_if_dead` лечит
  осиротевшие диалоги (задача закрыта или воркер молчит дольше
  `limits.run_stale_min`) и `knowledge_refresh` догоняет индексацию материалов.

## Интернет-поиск агентов

- Настройка `ddg` — **бюджет на диалог**: 0 (умолчание) = не выходить,
  1 = один раз, 2 = дважды… Каждый поиск = запрос модели → выдача DuckDuckGo
  (`webread.ddg_text`) → чтение найденных страниц (`webread.fetch` +
  `to_markdown`, до `limits.pages_max`).
- Пустая выдача бюджет НЕ тратит (`_web_search` возвращает `None`): «утка»
  промолчала — агенты работают на материалах, а владелец не теряет поиск.
- Запрос формулирует модель (`NJ662_MODEL` важнее модели участника); мусорный
  ответ заменяется запасным запросом из слов темы.
- Правила в подсказке: факты и цифры — только из материалов и найденного,
  чего нет — говорить прямо (иначе агенты сочиняют ссылки).

## Материалы диалога (RAG)

- Владелец добавляет текст или ссылку (страницу читает САЙТ:
  `fetch_page` — только http(s) и только наружу, `is_public_host` закрывает
  SSRF). Пустая запись не создаётся: честный отказ лучше «проиндексировано
  ничего».
- Индексация — общая семантика nj115: коллекция `nj662`, сущность
  `nj662_knowledge`, канал `semantic.index` (`Service_Nj115_Semantic`).
- В подсказку агентам попадает `limits.in_prompt` материалов по
  `limits.in_prompt_chars` знаков: сначала подбор по смыслу (nj115), при
  отказе — по словам темы, затем свежие. Происхождение видно в поле `how`
  («по смыслу», «по словам», «материал диалога»).

## Правила, которые нельзя нарушать

1. **Ход ставит сайт, не воркер.** После `apply_turn` следующий обмен уходит в
   очередь сам; воркер, который «продолжает разговор» сам, теряет паузу и
   идемпотентность ретрая.
2. **`apply_turn` идемпотентен**: реплики обмена уже есть — обмен принят,
   дублей не создаём (ретрай задачи не должен удваивать реплики).
3. **Модели — из конфига.** Список живёт в `config/nj662_dialog.php` строкой
   `провайдер::модель; …`; код о составе списка не знает. Спецификация уходит
   в воркер БЕЗ изменений (воркер разбирает её сам).
4. **Бюджет поиска — счётчик на диалог**, а не «поиск в каждом обмене»:
   `searches_used` растёт только когда поиск что-то нашёл.
5. **Пауза и отмена — не ошибка.** `close_if_dead` судит только живой диалог
   (`running`/`quick`), а задача воркера закрывается миром.
6. **Публикация — решение владельца**: `set_public` только для своего диалога
   (админ — исключения не имеет), снятый с публикации отдаёт 404 всем, кроме
   владельца. Публичный вид не показывает настройки, материалы и журнал
   поисков — это рабочие вещи владельца.
7. **Никакого `window.confirm`**: «Стоп» — вторым нажатием (`data-n2j-arm`),
   удаление диалога — окном (`data-n2j-confirm`), оба из общего app.js;
   после ответа такие формы (`data-nj662-follow`) идут по `redirect` сервера.
8. **Статус-ряд без полос хода**: спиннер + этап + секундомер одним рядом
   (дизайн-эталон `/pages/required_design_sample`); счётчики считает сервер
   (`counters_text`), JS их не собирает.
9. **Ссылки читает сервер только наружу**: `fetch_page` отклоняет не-http(s),
   локальные и служебные адреса (`is_public_host`).
10. **Запуск — по праву `nj662.start`** (роль `vip` или админ, решение
    владельца 09.10.2026). Проверяется и в контроллере (форма), и в сервисе
    (очередь): кнопку убрать мало. Читать опубликованные разговоры и вести
    свои прежние диалоги может любой аккаунт.
11. **Счётчик обменов идёт от начала диалога**: `turn` — сделано с первого
    запуска, `pairs` — план. Ни пауза, ни стоп, ни своя реплика его не
    обнуляют («обмен 3 из 5» → «обмен 4 из 5»). Больше обменов — владелец
    добавляет их в форме реплики или в настройках (потолок `limits.pairs_max`).

## Не трогать / подводные камни

- Порядок маршрутов в `init.php`: статические сегменты (`dialog/list`,
  `dialog/status/<id>`, `dialog/api`, `dialog/new`) ВЫШЕ ловящих
  `dialog/<id>(/<action>)` — иначе `list` съедается как `<id>`.
- `dialog/<id>/<action>` ограничен белым списком действий: опечатка должна
  давать 404, а не 500.
- Форма настроек несёт по два поля на участника (`a_model` + `a_model_custom`,
  `b_model` + `b_model_custom`), поэтому модели читаются ТОЛЬКО через
  `Service_Nj662_Models::from_form($post, 'a_')`. Прямое `$_POST['model']` —
  путь к потере модели участника.
- `Service_Nj662_Dialog::limits()` работает и как словарь (`limits()`), и как
  значение (`limits('pairs_max', 12)`) — не смешивать формы в одном месте.
- `status_json` обязан отдавать `revision`: по его росту JS понимает, что
  лента изменилась, и перезагружает страницу. Уберёте — страница «застынет».
- Выжимка обмена копится в `summary` диалога, но ПОВТОР той же сводки не
  добавляется: иначе подсказка растёт одним и тем же текстом.
- `nj_662_dialogs.job_id` — задача ТЕКУЩЕГО обмена: по нему `close_if_dead`
  понимает, что ход осиротел. «Стоп» обнуляет его (задача снята принудительно).
- **Своя реплика пишется в ТЕКУЩИЙ обмен** (`turn` тот же, что уже сделан).
  Занять `turn + 1` нельзя: по номеру обмена `apply_turn` отличает принятый
  обмен от ретрая, и реплика владельца выглядела бы как «обмен уже доехал» —
  агент промолчал бы. Поэтому в `worker_context` историю берёт
  `history_for_worker`: окно обменов ПЛЮС реплики владельца (`who = 'user'`),
  иначе при `context_pairs = 0` они выпадали бы из подсказки.
- Пауза и стоп ставят `finished_at`: секундомер страницы считает «от начала до
  финала» и без даты тикал бы всё время стоянки. `start` дату обнуляет.
- Роль `vip` создаётся миграцией `pgMigration_Nj662_002_Access_Vip` и выдаётся
  на `/nj595/admin` — своей страницы у роли нет и не нужно.
