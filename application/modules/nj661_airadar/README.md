# nj661_airadar — ИИ-радар (slug: airadar)

## Что это

Личный инструмент владельца (audience admin): конвейер следит за прогрессом ИИ
и смежным — открытые модели и веса, фреймворки, окна возможностей (бесплатные
токены хороших моделей, щедрые лимиты, ранний доступ), прорывы с практической
применимостью, недооценённые ниши. Копит **базу знаний из фактов** (не воду),
использует её в конвейере (не делает работу заново и учитывает сделанное ранее),
присылает **письма** с отчётом и идеями, что реализовать на n2j (с пользой и
местом применения).

**Витрина для людей и поисковиков**: `/airadar/catalog` — каталог опубликованных
отчётов (свежие сверху, поиск, пагинация) и `/airadar/report/<id>` — страница
отчёта. Обе публичные, как у трендов GitHub. Отчёт публикуется по умолчанию;
владелец может снять его с публикации — тогда страница отдаёт 404 всем, кроме
владельца и администратора, и адрес уходит из карты сайта.

Использованные наработки: nj593_trends и nj605_radar (конвейер воркера: ddgs +
webread + один LLM-вызов со строгой JSON-схемой, дедуп, живые этапы),
nj602_content (постановка задач по расписанию), nj654_similar (RAG-паттерн:
эмбеддинги + косинус для семантического дедупа фактов), nj613_digest (письмо
через nj597 + троттлинг).

## Конвейер

```
cron → /airadar/api/tick (токен) → tick(): пора? → run + JobQueue 'nj661.airadar'
  ↓ python-воркер nj661_airadar.handle(ctx, {run_id, limits})
  1. Источники (каждый в своём try): HuggingFace API (свежие/лайки),
     OpenRouter /api/v1/models (бесплатные = «окна», новые, 128k+), RSS
     гигантов (HF/OpenAI/DeepMind/Meta/Mistral/Qwen/Phoronix), ddgs-поиск
     («утка го»), lmarena.ai/leaderboard;
  2. POST /airadar/api/items → сайт дедупит по url_hash (готовое не возвращается,
     необработанные `new` повторяются; лимит после дедупа) + отдаёт контекст базы знаний;
  3. webread новых страниц (кап, бюджет, паузы);
  4. LLM-анализ батчами (строгий JSON): relevant/category/score/why,
     facts[{text,tags}] (не вода, с числами), ideas[{title,body,benefit,fit}];
  5. POST /airadar/api/analysis → факты/идеи в базу знаний (дедуп по хешу:
     факт повторился → sightings++, дубль не создаётся);
  6. POST /airadar/api/report_input → LLM пишет {title,summary,highlights} →
     POST /airadar/api/report → nj_661_reports + решение о письме
     (mail_due: троттлинг + порог скор/идеи) → Nj597_Mail;
  7. POST /airadar/api/finish.
```

Источники смешиваются round-robin (богатый HF не вытесняет остальных из
среза), статистика по источникам видна на дашборде; зависший прогон
закрывается сверкой с очередью nj120 (`_catch_up`); контекст модели —
`NJ661_AIRADAR_CONTEXT` в workers/.env (например 16000 для локальной Gemma).

## Правила модуля

- **Аудитория**: admin (личный инструмент). Страницы — `can('nj661.airadar')`
  (admin проходит всегда); API — токен воркера; cron дёргает `/airadar/api/tick`.
- **LLM и сеть** — только в python-воркере (канал `nj661.airadar`), не в HTTP.
  Модель — env `NJ661_AIRADAR_MODEL`, иначе дефолт воркера.
- **База знаний**: факт = нормализованный текст (fact_hash) + эмбеддинг
  (ctx.embed в воркере, хранение JSON-текстом) для семантического дедупа
  (косинус ≥ knowledge.dup_cosine → «уже известно»); недавние факты и частые
  теги — контекст промпта анализа («учитывать сделанное ранее»).
- **Письмо**: не чаще mail.every_days и только если есть находка ≥
  mail.min_score ИЛИ новая идея; адрес — mail.to_email (пусто = не слать,
  админка показывает подсказку). Кнопка «Прислать письмо» игнорирует троттлинг.
- **Дедуп работы**: материалы — по url_hash за всё время; идеи — по
  нормализованному заголовку (повтор поднимает скор, не создаёт дубль).
- **PHP-ловушки**, которые здесь уже учтены (не возвращать): `$a = $x AND $y`
  присваивает ДО сравнения — только скобки или `&&`; `query()` у Request —
  вторым аргументом ПИШЕТ (сеттер) — читать одним аргументом.

## Публичный слой

| Адрес | Кто видит | Что там |
|---|---|---|
| `/airadar/catalog` | все | опубликованные отчёты: дата, сводка, числа прогона, поиск, 10/20/50 строк |
| `/airadar/report/<id>` | все (опубликованный) | полный отчёт: главное, разделы по категориям, факты, идеи, статистика |
| `/airadar`, `/items`, `/facts`, `/ideas` | владелец, администратор | прогоны, материалы, база знаний, идеи |
| `/airadar/report/<id>/publish` | владелец, администратор | снять/вернуть отчёт (POST, CSRF, два клика) |

Каталог и опубликованные отчёты попадают в `/sitemap.xml` (руками в
`Controller_Nj602_Api::action_sitemap`: модуль непубличный, поэтому его extras в
манифесте пропускаются).

## Живой ход сбора

«Собрать сейчас» уходит fetch-ом (`X-Requested-With: XMLHttpRequest` → JSON,
обычная форма — 303, как раньше). Карточка «Ход сбора» на дашборде появляется
сразу и живёт по дизайн-эталону: спиннер + этап + секундомер одним неразрывным
рядом, лестница «Источники → Чтение → Анализ → Отчёт» (пройденные зелёные,
текущий жирный), счётчики (источников/страниц/кандидатов/отобрано/фактов/идей),
ошибка прогона и строка «Источники: …». Опрос `/airadar/progress` раз в 3 с,
секундомер между опросами тикает локально; по завершении страница
перезагружается — свежий отчёт уже в разметке.

## Рассуждающие модели (Qwen3.5 и подобные)

Локальные «thinking»-модели тратят `completion_tokens` на reasoning_content.
Инцидент 15.10.2026: `2953` из `3000` токенов ушли на размышления, ответ
оборвался (`finish_reason=length`) на `"score": 92,` — «ни одного материала».

Что делает воркер (`.tools` не нужен, всё само):

1. смотрит `usage` каждого вызова анализа (`_llm_finish_reason`,
   `completion_tokens_details.reasoning_tokens`);
2. при обрыве по лимиту поднимает бюджет ответа с 3000 до
   `NJ661_AIRADAR_OUT_TOKENS` (по умолчанию 8000; не больше половины
   `NJ661_AIRADAR_CONTEXT`) и дробит оставшиеся пачки, а при reasoning-токенах
   даёт по одному материалу на вызов — весь бюджет достаётся ему;
3. при reasoning-токенах дополнительно отключает размышления
   (`chat_template_kwargs.enable_thinking=false` + `reasoning_effort=none`).
   Сервер, который этих полей не знает, отвечает 400/422 — воркер повторяет
   тот же запрос без них. Сервер, не принимающий большой `max_tokens`,
   возвращает прогон к базовым 3000 (`stats.output_capped_by_provider`).
4. если сервер молча игнорирует отключение размышлений и модель всё равно
   съедает бюджет, помогает только модельный выбор: модель без рассуждений
   (`NJ661_AIRADAR_MODEL`), больше `NJ661_AIRADAR_CONTEXT` (если модель её
   держит) или выключенный thinking в настройках самого сервера модели;
5. если разобрать всё равно не удалось, прогон падает с понятной причиной:
   «модель израсходовала N токенов на размышления из M … включите
   `NJ661_AIRADAR_THINK=0` или увеличьте `NJ661_AIRADAR_OUT_TOKENS`».

Ручки (env воркера важнее конфига сайта `config/nj661_airadar.php`
`limits.out_tokens` / `limits.think`): `NJ661_AIRADAR_THINK=auto` — решить по
первому ответу, `0` — отвечать без размышлений сразу (быстрее и дешевле),
`1` — не глушить их вовсе. Для слабого локального сервера рабочий вариант —
`NJ661_AIRADAR_THINK=0`.

Проверка: `PYTHONPATH=workers python3 -m pytest workers/tests/test_nj661_airadar.py -q`
(отдельные тесты на обрыв, рост бюджета, дробление пачек, отказ провайдера от
полей отключения и от большого ответа). На панели прогона видно запись этапа
«…; рассуждения модели» и в stats — `reasoning_tokens`, `output_truncated`,
`output_capped_by_provider`, `last_analysis_error`.

## Неполный прогон — не провал (21.10.2026)

Прогон #12: 5 источников, 284 кандидата, 120 принято, 114 проанализировано,
отчёт собран — а на панели «остановлен» и «ValueError: LLM не вернула items».
Причина: один неразобранный ответ модели закрывал прогон как `fail`, даже когда
потерян 1 материал из 20.

Теперь (воркер `nj661_airadar.py`):

1. `webread.json_objects()` вытаскивает **все** целые объекты ответа: массив
   верхнего уровня, JSON в прозе, а также объекты из оборванного по токенам
   батча — битый хвост отбрасывается, остальное сохраняется.
2. `_normalize_row()` чинит разнобой полей (`relevant: "true"`, `score: "85"`,
   нет `ideas`, факт без `tags`) вместо того, чтобы выбрасывать материал целиком;
   пустой огрызок объекта (`{"id": 2, "relevant": true}`) по-прежнему не считается
   разобранным.
3. Повтор пачки идёт с усиленной инструкцией «только JSON» (`strict`), а
   неразобранный ответ больше не считается отказом провайдера: серия сбоев
   (`NJ661_AIRADAR_MAX_FAILS`, по умолчанию 5) считается только по сетевым/HTTP
   ошибкам.
4. Прогон закрывается `done`, если разобрана бо́льшая часть (потеряно не больше
   10%, минимум 3 материала): отчёт и факты сохраняются, а число необработанных
   видно в `error` прогона (на панели — жёлтая заметка, не красная ошибка) и в
   сводке отчёта. `fail` остаётся для большой потери или нуля материалов.
5. В stats добавлены `aborted` (`deadline` | `provider`), `last_analysis_raw`
   (первые 400 символов ответа модели) и `last_analysis_model` — по ним видно,
   что именно вернула модель, а не только «пустой JSON».

## Диагностика пустых отчётов (15.10.2026)

До исправления ошибки анализа/JSON пропускались, прогон всё равно завершался
`done`, а ошибка редактора давала заголовок «ИИ-радар: сводка за …» и пустую
сводку. Необработанные URL уже попадали в дедуп и больше не возвращались.
Контекст включал до 40 фактов без общего ограничения; до 8 материалов делили
3000 токенов ответа. Это воспроизводимые дефекты, но конкретный отказ модели
9–12 октября можно подтвердить только журналом реального воркера.

`25 материалов / 40 фактов / 15 идей` — пределы выборки **отчёта**, не число
вызовов LLM и не общий лимит накопленной базы. `кандидатов: 0` в старых отчётах
мог быть отсутствующим полем stats, а не нулём найденного. Старые отчёты и
пометки отправки автоматически не переписываются.

После обновления **сайта и воркера** перезапустите воркер и нажмите «Собрать
сейчас». Миграций не требуется. `new` из прошлых прогонов снова доступны для
анализа. В пределах 45-минутной задачи анализ имеет мягкий бюджет 40 минут,
после него сохраняется явно неполный отчёт с `pending`; остаток — в следующий
запуск. Три последовательных пустых/ошибочных ответа прерывают анализ, а не
расходуют время на все 120 материалов. Отказ редактора не уничтожает находки:
отчёт содержит сводку по сохранённым данным с предупреждением.

Для проверки конкретного инцидента нужны строки `nj661_airadar` из
`workers/logs/n2j-worker.log` (и ротаций), `nj661` из
`application/logs/n2j-site.log`, id задачи, имя модели и значение
`NJ661_AIRADAR_CONTEXT`, `NJ661_AIRADAR_OUT_TOKENS` **без токенов доступа и
содержимого .env**. В новых логах: run_id, id материалов, размер промпта,
бюджет ответа, режим размышлений, ошибка; в stats: `analyzed`, `pending`,
`analysis_errors`, `last_analysis_error`, `reasoning_tokens`,
`output_truncated`, `output_capped_by_provider`, `report_fallback`,
`embedding_errors`. `api_report` отвергает отчёт, если
материалы приняты, но ни один не проанализирован.
