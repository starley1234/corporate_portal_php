# nj643_cad — «CAD-детали»

Описали деталь словами → получили параметрическую 3D-модель и файлы для
изготовления: **STEP** (CAD и заказ), **STL** (3D-печать), **GLB** (просмотр) и
**ракурсы** (PNG, чтобы видеть деталь прямо на странице).

## Как это работает

```
описание словами
      │
      ▼
  LLM (воркер) ──► параметрический Python-код build123d + схема параметров
      │
      ▼
  проверка кода у нас (только build123d/math, без файлов/сети/eval)
      │
      ▼
  внешний движок  POST <адрес из NJ643_CAD_API>/v1/cad/verify-and-build
      │            (X-API-Key; компиляция, геометрия, стресс-тест границ, экспорт)
      │            адрес живёт только в workers/.env — нигде не печатается
      ▼
  файлы → /cad/api/upload (base64)   итог → /cad/api/result
      │
      ▼
  /cad/<code>: 3D в браузере, файлы, ползунки, правка словами, ревизии
```

Почему так: движок живёт вне сайта и требует ключ — **ключ знает только воркер**,
сайт его не дёргает. Общение сайта и воркера идёт через очередь задач каналом
`nj643.cad` (как у nj591/nj570), поэтому нет ни блокирующих HTTP-запросов из PHP,
ни утечки ключа в браузер.

## Страницы и API

* `GET /cad` — описание детали (форма) + мои детали карточками с превью,
  чипы «Все / Готовые / Собираются / С ошибкой», поиск, «Строк:» (12|24|48);
* `GET /cad/<code>` — деталь, компактно в две колонки: слева 3D-просмотр на
  Canvas 2D (`?rev=N` — выбранная ревизия) с метриками (габарит, объём, тела,
  границы размеров) прямо под холстом, размеры, замечания проверки (только когда
  они есть) и свёрнутое задание с кодом модели; справа файлы, история ревизий
  ссылками, правка словами, действия. Ракурсов движка на странице нет — их
  смотрит 3D, а PNG остаются превью в списках (владелец, 27.09.2026);
* `GET /cad/<code>?rev=N` — показать ревизию N: файлы и 3D берутся ИМЕННО её
  (раньше всегда показывалась последняя, и «смотрю только ревизию 1» читалось как
  поломка). По умолчанию — последняя. Режим просмотра (ракурс, вращение,
  приближение) браузер помнит ОДНИМ ключом `n2j:cad3d:mode` на весь сайт;
* `GET /cad/file/<id>` — файл модели (`?download=1` — скачать с понятным именем);
* `GET /cad/archive/<code>[/<rev>]` — вся ревизия одним ZIP: STEP, STL, GLB, код
  модели и `README.txt` (габарит, объём, размеры с границами, что зачем, ссылка
  на деталь). Архив собирается на лету и не хранится, ZIP пишем сами — на проде
  может не быть расширения zip;
* `GET /cad/admin` — управление: детали с превью, владельцем (почта), статусом и
  УДАЛЕНИЕМ, журнал обращений к движку, расход ИИ и раздел «Удаления»
  (`nj_643_audit`: кто, что и когда убрал — деталь мягко, а файлы с диска); Проверки движка тут нет
  (владелец, 27.09.2026) — состояние видно по журналу;
* `GET /cad/api/status/<code>` — живой статус-ряд сборки (эталон `/trends/<code>`);
* `POST /cad/api/run` — «собрать заново» / «пересобрать по параметрам» (владелец + CSRF);
* `POST /cad/api/cancel|delete` — остановить сборку / удалить деталь;
* `POST /cad/api/upload|result` — приём от воркера (`X-Worker-Token`).

## Воркер

Канал `nj643.cad` (`workers/n2j_workers/handlers/nj643_cad.py`):

1. `generate` — LLM пишет код модели и схему параметров (строгий JSON);
2. `revise` — LLM правит существующий код по просьбе словами;
3. `rebuild` — код не меняется, новые значения параметров;
4. `check` — диагностика движка (кнопка в управлении).

Далее: проверка кода → `verify-and-build` → при отказе движка ИИ чинит код
(`NJ643_FIX_ATTEMPTS`, по умолчанию 2 попытки) → файлы на сайт → итог.

Когда сборка закончилась, владельцу уходит уведомление сайта (`Service_Nj597_Notify`:
«Деталь готова: …» / «Деталь не собралась: …») со ссылкой на ту самую ревизию — раньше
о неудачной сборке никто не сообщал, а об удачной узнавали, держа страницу открытой.
Отправляет их сам сервис приёмки (`_notify_owner`): задача очереди закрывается через
`mark_delivered`/`mark_failed_from_site`, минуя хук nj597 в JobQueue.

Перед обращением к ИИ воркер стучится в `/health` движка (`NJ643_PREFLIGHT=0`
отключает): если движка не видно, прогон останавливается сразу и с разбором
причины — шесть минут ожидания и три промпта «починить код» на мёртвом движке
владельцу не нужны.

Переменные окружения — в `workers/.env.example`, блок `nj643_cad`:
`NJ643_API_BASE`, `NJ643_SITE_TOKEN`, `NJ643_CAD_API`, `NJ643_CAD_API_KEY`
(или общий `TOOLFORGE_API_KEY`), `NJ643_MODEL`, `NJ643_FIX_ATTEMPTS`,
`NJ643_TIMEOUT` (10 мин на запрос), `NJ643_BUDGET` (общий бюджет прогона),
`NJ643_META_MODEL` (модель для метаинформации: схема, название, замечания),
`NJ643_META` (0 — второй прогон выключен), `NJ643_MAX_CODE`, `NJ643_CAD_RETRIES` и `NJ643_CAD_RETRY_DELAY` (повторы при
сетевых обрывах), `NJ643_CAD_PROXY` (если адрес воркера не в белом списке),
`NJ643_CAD_CA_BUNDLE` / `NJ643_CAD_INSECURE` (сертификат), `NJ643_PREFLIGHT`,
`NJ643_HEALTH_TIMEOUT`.

## Что важно знать про движок

* Формат успешного ответа `verify-and-build` в контракте не зафиксирован
  (схема ответа — свободный объект), поэтому разбор терпимый: файлы берём из
  base64-полей и по ссылкам, вид определяем по имени/ключу и по «магическим»
  байтам, отчёт читаем из `geometry/verify/stress` в нескольких вариантах имён.
  Сырые ключи ответа сохраняются в `report.response_keys` — по ним видно, что
  движок вернул на самом деле.
* Код модели исполняет движок, поэтому перед отправкой он проверяется у нас:
  разрешены только `build123d`, `math` и стандартные типы, запрещены
  `os/sys/subprocess/socket/open/eval/exec/...`.
* «Движок недоступен» — это НЕ ошибка кода: соединение закрывается на
  рукопожатии TLS, когда адрес воркера не в белом списке движка (проверено
  26.09.2026: с другого адреса `/health` движка отвечает `status: ok`). Воркер
  повторяет сетевые обрывы (по умолчанию 3 попытки), пишет причину на страницу
  детали без самого адреса (владелец, 27.09.2026: «не пиши нигде url движка») и
  предлагает выход: добавить IP воркера в разрешённые у движка либо задать
  `NJ643_CAD_PROXY`; для самоподписанного сертификата — `NJ643_CAD_CA_BUNDLE`.
  Проверка руками — `curl -v --max-time 20 <адрес из NJ643_CAD_API>/health`
  с сервера воркера.
* При сбое код модели и схема параметров всё равно сохраняются — кнопка
  «Собрать заново» пересобирает по ним (обращения к ИИ больше не нужно).
* Стресс-тест границ — то, чего не видно при сборке с одними значениями:
  if-модель падает на min/max, на странице появляется кнопка
  «Попросить ИИ починить границы» (правка словами с текстом сбоев).

## Качество конструкции в промпте

Владелец (27.09.2026): «в воркер добавь промпт, чтобы модель старалась и делала
максимально хорошие конструкции». В `SYSTEM_CODE` раздел «КАЧЕСТВО КОНСТРУКЦИИ»:
сначала подумать о назначении и нагрузке, крепёж (Ø3.4 — M3, Ø4.5 — M4,
Ø5.5 — M5) и зенковки, фаски 45°×0.5-1 мм и скругления R0.5-R3, рёбра жёсткости,
зазоры 0.2-0.4 мм, стенки ≥ 1.5 мм, нависания ≤ 45°, порядок построения
«тела → булевы → фаски в конце», в `notes` — что сделало деталь хорошей.
`SYSTEM_FIX` запрещает упрощать конструкцию ради «лишь бы собралось»: крепёж и
фаски чинят, а не выбрасывают.

## Правила

1. **Движок не дёргаем из PHP.** Только через канал `nj643.cad`.
2. **Ключ — только воркеру.** В `.env.example` сайта `NJ643_*` нет.
   **Адрес движка не печатаем нигде** (владелец, 27.09.2026): он задаётся в
   `workers/.env` (`NJ643_CAD_API`), в коде дефолта нет, в ошибках и в прогрессе
   для сайта — только имя переменной и путь запроса.
3. **Деталь открывается по коду-ссылке**, менять её может владелец или
   управление (`nj643.admin`).
4. **Успех и ошибка всегда доходят до сайта** (`/cad/api/result`): молчащий
   воркер = «нет пульса», а это запрещено (владелец: «непонятный финал
   недопустим»).
5. **Файлы ревизий не перезаписываются**: правки приходят новыми ревизиями,
   старые файлы остаются как история.
6. **Живой ряд** — общий механизм `partials/live_status` + `partials/live_status_js`;
   авто-остановка застрявшего воркера живёт в `/cad/api/status/<code>`.
7. **Файлы показываются строго по ревизии.** «Файлы · ревизия N» — только её файлы;
   если их нет, так и написано. Бесхозные файлы старого воркера (`revision_id = 0`)
   привязываются к последней ревизии детали, а `api_upload` больше не принимает
   файл без ревизии.
8. **Лимит `max_tokens` не применяем.** Модель сама решает, сколько ей нужно:
   с лимитом 9000 ответы приходили обрезанными («JSON не найден целиком»), потому
   что лимит съедали рассуждения модели, а сборка уходила на повторные попытки.
9. **Ревизию можно удалить** — любую, кроме последней (она показывает текущее
   состояние детали): в «Истории» иконка удаления, подтверждение вторым кликом.
10. **Расход ИИ объясняется.** Воркер пишет в `usage[].note`, из чего сложились
   токены (знаки ответа, где начинается JSON, знаки кода, рассуждения модели,
   обрезка по лимиту) — это видно на странице детали и в `/cad/admin`.
11. **Копия детали не тратит ИИ.** «Сделать по образцу» (на странице детали и в
   карточке списка) создаёт новую деталь из того же кода модели: движок собирает
   её заново, модель не вызывается. Итерации «а если на 5 мм длиннее» идут
   копией, а не правкой рабочей детали.
12. **Мелочи удобства живут в браузере.** Точное значение размера рядом с
   ползунком, «вернуть размеры ИИ», масса по материалу (объём × плотность),
   черновик описания, печать карточки и построчный diff кода при сравнении
   ревизий (`?rev=N&cmp=M`) — на стороне страницы; проверяются без браузера:
   `node .tools/cad_ui_smoke.mjs`.
16. **Код и метаинформация пишутся разными прогонами.** Первый прогон (`SYSTEM_CODE`) —
   только код модели: так он качественнее, потому что модель занята геометрией, а не схемой
   и описанием. Второй (`SYSTEM_META`) считает по ГОТОВОМУ коду схему параметров, название,
   назначение и замечания — на своей модели (`NJ643_META_MODEL`, пусто → `NJ643_MODEL`),
   выключается `NJ643_META=0`. Мета-проход не критичен: не ответил — схему соберёт
   `schema_from_code` по значениям из `kwargs.get(...)`, деталь не потеряется.
17. **Правка словами тоже обновляет метаинформацию** — по новому коду, чтобы схема и подписи
   на странице не разъезжались с деталью. В цикле починки по ошибке двигателя мета-проход
   зовётся только если правка завела новый параметр.
15. **Ползунки — это размеры сборки, а не подписи.** У движка нет поля «значения
   параметров»: он собирает деталь на `default` из схемы. Поэтому `_build_once`
   подставляет выбранные значения и в схему, и в `kwargs.get(...)` кода — иначе
   новая ревизия получит старые размеры.
14. **Код модели проверяется до движка.** Разбор через `ast` (синтаксис, режим
   алгебры, отсутствие кода на импорте), сравнение кода со схемой параметров и
   выравнивание схемы по коду; на починку модель получает адрес ошибки, крайние
   значения и запрет упрощать деталь. Крайние значения чинятся один раз, удачная
   сборка не затирается неудачной правкой.
13. **Управление показывает состояние.** `/cad/admin`: состояние движка по
   журналу (последний успешный вызов, доля успеха за сутки, последняя ошибка),
   расход ИИ по дням с итогами за сутки и неделю, выгрузка реестра деталей —
   `/cad/admin?export=csv`.

## Готовность к деплою

1. `git pull` (ветка с модулем), миграции обычным путём
   (`pgMigration_Nj_643_001_Cad_Tables` создаёт таблицы `nj_643_*`; сервис
   дополнительно поднимает их сам);
2. в `workers/.env` — `NJ643_CAD_API` (адрес движка, обязателен с 27.09.2026),
   `NJ643_CAD_API_KEY` (или `TOOLFORGE_API_KEY`); при необходимости
   `NJ643_API_BASE=https://n2j.ru/cad/api`;
3. перезапуск воркера (промпты и проверки кода живут в воркере — без перезапуска
   изменения не подействуют);
   * правило воркера: любое утверждение о build123d в промпте проверяется запуском
     (`pytest tests/test_nj643_cad.py` — эталонный пример из промпта собирается
     локальным build123d; без пакета тест пропускается);
   * `_engine_hints` в воркере переводит настоящие тексты ошибок движка
     («Failed creating a fillet…», «No depth provided», «BRep_API: command not
     done») в конкретный совет модели на починку.
4. проверки: `/cad` (список), сборка одной детали, копия «по образцу»,
   сравнение ревизий (`?rev=N&cmp=N-1`), печать карточки, переключение ревизий `?rev=N`,
   режим 3D после перезагрузки страницы, `/cad/admin` (превью, почта владельца,
   удаление — без кнопки проверки движка).
