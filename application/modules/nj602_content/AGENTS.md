## Назначение
Автономный контент-конвейер: по расписанию `nj603_kicker` создаёт фоновую задачу, воркер ищет свежие источники, читает их через общий `webread`, сверяется с базой знаний NJ-560/RAG и сохраняет статью на модерацию.

## Автономный режим
- Пустая тема означает `__AUTO_TRENDS__`, а не ошибку и не необходимость ручного ввода.
- Воркер сам мониторит технический прогресс, науку, коммерцию, производство, автоматизацию, цифровые артефакты и легальные способы повышения дохода.
- Политика, религия, войны, военные конфликты и партийная борьба фильтруются до поиска источников и в промпте.
- Расписание по умолчанию — один запуск в 2 часа; один сбор одновременно, зависший `collecting` старше двух часов закрывается ошибкой.

## Конвейер
1. Пиналка `nj603` вызывает `create_draft()` напрямую (расписание `content`).
2. PHP ставит `nj602.article` в `nj120`.
3. Python-воркер (`nj602_article.py` → `nj602_research.py`, выключается `NJ602_RESEARCH=0`):
   - **тема**: 8 запросов «{год} study/report/benchmark/статистика», кандидаты ранжируются
     (цифры в сниппете, свежий год, первоисточник), похожие на уже опубликованное — штраф;
   - **plan** (ИИ, ~700 ток.): 6–7 запросов RU+EN + вопросы «сколько/кто/когда» + ракурсы;
   - **search/read**: DDG по всем запросам, ранг по авторитетности хоста/цифрам/году, ≤2 страниц
     с хоста, читаем до `NJ602_RESEARCH_MAX_SITES` (8) по `NJ602_RESEARCH_MD_CAP` (5000) знаков;
   - **extract** (ИИ, пакеты ≈14k знаков): факты `{src, fact, kind, when, why}`; без цифры/имени
     факт отбрасывается; если фактов с цифрами < `NJ602_MIN_FACTS` (8) — добор по вопросам плана;
     < 3 фактов — статья падает с понятной ошибкой (лучше нет статьи, чем вода);
   - **angle** (ИИ): тезис, рабочий заголовок с цифрой, 4–6 разделов с фактами, практика, подвохи,
     при сравнимых данных — таблица;
   - **write** (ИИ, `NJ602_RESEARCH_MIN_CHARS` 3500 … ×1.8): только по фактлисту, каждый факт
     со ссылкой `[n]` = номер источника; обязательные разделы в конце; штампы запрещены;
   - **critic**: детерминированная метрика (ссылки, разные источники, чисел на 1000 знаков,
     штампы, обязательные разделы → 0..10) + ИИ-рецензент (score/novelty/water, замечания).
     Если рецензент < `NJ602_CRITIC_MIN` (6) или метрика < 4 — одно переписывание по замечаниям,
     остаётся вариант с лучшей метрикой.
4. RAG (`/content/api/knowledge_search`) передаётся только как «о чём мы уже писали», факты оттуда не берутся.
5. Проход «enrich» размечает заголовок/лид/теги/Mermaid по готовому тексту (получает тезис и рабочий заголовок).
6. На сайт уходят `sources` (нумерованные), `facts`, `quality`; статус `review` либо `published` при `NJ602_AUTO_PUBLISH=1`.
7. После успеха статья сохраняется как заметка через `/content/api/knowledge_remember`.

Метрика `quality`: `{score, critic, novelty, water, facts, facts_numeric, citations, sources_cited,
numbers, banned[], revised, thesis, title_hint, pipeline}`. В `trace` фазы `plan|sources|read|facts|
angle|critic|rewrite` — видно в журнале `/nj602/admin`, где сбор «сдулся».

## Модерация и ручная правка (`/nj602/admin`)
- Список статей: поиск по заголовку/теме/коду, фильтр по статусу, пагинация
  `page` + «Строк:» (20/50/100, выбор запоминается браузером `n2j:per:/nj602/admin`).
  AJAX-обновление строк ходит с ТЕМИ ЖЕ фильтрами в адресе — список и «стр. k из m».
- Массовые действия: галочки в строках (чекбоксы привязаны к форме `nj602-bulk`
  атрибутом `form`), «отметить всё на странице», «Опубликовать выбранные» и
  «Отклонить выбранные» (второе — в два шага).
- Ручная правка `/nj602/admin/edit/<id>`: заголовок, лид, тело (Markdown) и
  mermaid-схема с превью. Сохранение не меняет статус публикации.
- «Перегенерировать схему» (блок «Модерация» и страница правки) ставит воркеру
  ту же задачу конвейера в режиме `mode=mermaid`: воркер забирает тело статьи
  через `/content/api/article/<code>`, перерисовывает схему и возвращает её
  через `/content/api/mermaid/<code>`. Текст и публикация не трогаются.
- «Починить схемы» (карточка «Схемы статей», плюс «Починить схемы у выбранных»
  в массовых действиях) чинит УЖЕ СОХРАНЁННЫЕ схемы БЕЗ ИИ: задача
  `mode=mermaid_fix` с пачкой кодов, воркер нормализует текст каждой схемы и
  возвращает изменённые. Прогресс — `GET /nj602/admin/mermaid_fix_status`
  (status/stage/elapsed_sec/error + fixed/skipped/total из результата задачи).
  Бейдж «не рисуются: N» считает `mermaid_broken_count()` — оценка прямо в SQL,
  чтобы страница не тянула тексты схем; точный список даёт `mermaid_suspects()`.
  Починка и перегенерация схем работают и при выключенном конвейере.

## Mermaid: схемы, которые рисуются
- В промпте прохода 2 (и при перегенерации) жёстко требуется: объявление
  `flowchart TD` первой строкой, КАЖДАЯ связь — на отдельной строке, без
  однострочных схем и без «&»-склеек узлов.
- Санитайзер `_validate_mermaid` нормализует ответ модели, а не только
  проверяет: выносит объявление, раскладывает связи построчно, раскрывает
  «&»-цепочки, «;» читает как разделитель, не трогает текст в кавычках и
  оставляет без изменений схемы с `subgraph`.
- Разбор идёт ТОКЕНАМИ (узел → стрелка → узел), а не резкой по стрелкам: иначе
  однострочник «A[\"…\"] --> B{\"…\"} B -->|\"…\"| C[\"…\"]» разваливался в мусор
  (пример владельца 26.09) — именно поэтому схемы не рисовались.
- Если модель склеила несколько диаграмм (второй `flowchart TD` — хоть с новой
  строки, хоть в той же), остаётся ОДНА: с наибольшим числом связей, при
  равенстве — первая. Второе объявление — синтаксическая ошибка для mermaid.
- Подписи стрелок всегда приводятся к кавычкам (`-->|\"текст\"|`), серединные
  подписи («A -- текст --> B») переводятся в канон. Результат идемпотентен:
  повторная нормализация ничего не меняет.
- Отдельно чинится частая ошибка модели — кавычка ПОСЛЕ закрывающей скобки
  фигуры: `D{"Развитие}"` → `D{"Развитие"}` (mermaid 10.9.3 на такой записи
  падает с «Syntax error in text»; живой случай 26.09 —
  `C --> D{"Направления развития}"`). Ремонт идёт ДО выбора диаграммы,
  иначе токенизатор неверно разбирает склейку двух схем. Тот же признак
  добавлен в `mermaid_looks_broken()` и в SQL-оценку бейджа, иначе статья
  с такой схемой не попала бы в «Починить схемы».
- Если модель не дала схему — строится детерминированный каркас из «## »-разделов
  статьи; публикация без схемы не считается ошибкой.

## RAG и защита от зацикливания
- Внутренняя база — сервис `Service_Nj560_Knowledge`, семантическая индексация идёт через очередь `nj115`.
- RAG используется только как контекст; факты требуется перепроверять по свежим источникам.
- Ключ заметки детерминированный, одинаковая статья повышает `hits`, но не создаёт дубль.
- Нельзя подменять свежий webread-контекст одной внутренней базой.
- Не добавлять прямые вызовы поисковиков или LLM в PHP HTTP-запрос.
