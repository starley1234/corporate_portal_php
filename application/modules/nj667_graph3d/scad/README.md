# scad/ — библиотека геометрии сборки (nj667_graph3d)

Здесь OpenSCAD-части, из которых `Service_Nj667_Build::scad()` собирает один
самодостаточный файл. Разделение по зонам ответственности (просьба владельца,
12.10.2026, `source_data/manual.md`):

| Файл | Зона |
|---|---|
| `core/math.scad` | вектора: `orient_up`, `edge_up`, `vsum` — ничего про изделие |
| `core/connector.scad` | узел-коннектор: `connector()`, `arm_geometry()`, `join_beam()` |
| `node_types/<тип>.scad` | **только сечение**: профили палочки/паза/стенки + габарит `bb_w`/`bb_t` |
| `generators/assembly.scad` | режимы вывода: сборка, раскладка деталей, одна деталь |
| `data/*.scad` — нет | данные графа не лежат в git: их пишет PHP в блок сборки |

Порядок склейки (важен): параметры → тип узла → математика → коннектор →
генератор → данные. Имена переменных не должны повторяться: в OpenSCAD
повторное присваивание в той же области видимости — ошибка, а не перезапись.

## Почему один файл, а не `use <core/math.scad>`

Воркер рендерит через `workers/n2j_workers/scad.py`, а его
`check_includes()` разрешает `include`/`use` **только** из `BOSL2/` (белый
список, чтобы код пользователя не читал файлы хоста). Поэтому PHP склеивает
части сам и отдаёт в воркер готовый текст. Побочный плюс: собранный `.scad`
— artifact сборки (`storage/nj667/<code>/build-<id>.scad`), его можно отдать
человеку и отрендерить ровно тот же STL у себя.

## Контракт типа узла

Новый тип = один файл в `node_types/` + запись в `config/nj667_graph3d.php`
(`build.types`). Файл обязан определить ровно четыре вещи:

```openscad
bb_w = <габарит сечения по X, мм>;      // для паза и стенки (core/connector)
bb_t = <габарит сечения по Y, мм>;
module stick_profile() { ... }           // реальная палочка (визуализация сборки)
module slot_profile()  { ... }           // паз: сечение + tolerance
module outer_profile() { ... }           // стенка луча: паз + wall_thickness
```

Математика углов, кластеризация узлов, дедупликация и спецификация в типе
узла не живут: их считает `Service_Nj667_Build` на PHP — иначе BOM на сайте и
STL в OpenSCAD разъедутся (см. правило в `AGENTS.md`).

## Чем рендерить собранную модель

```sh
openscad -o model.stl build-12.scad                                        # любой сборки
openscad -o model.stl --export-format=binary --hardwarnings build-12.scad  # 2021.01+
```

Воркер выбирает сам: один раз спрашивает `--help` у бинаря и передаёт только
те флаги, которые тот знает, — старая сборка на неизвестный флаг не начинает
рендер вовсе (`Unknown --export-format option 'binary'`). Пол языка —
**2019.05**: `core/math.scad` пользуется `let()` и `norm()`, до этой версии
модель не парсится, и воркер такой бинарь отвергает, не начиная CSG. Без
`--export-format` модель иногда приезжает ASCII: `nj667_graph3d.py` переписывает
её в бинарный STL, потому что и страница, и `stl_stats()` на сайте ждут
разметку `84 + 50·N` байт.

GLB, который крутится на `/graph3d/b/<code>`, — не вывод OpenSCAD: его лепит
из того же STL `workers/n2j_workers/glb.py` (склеенные вершины, нормали, мм как
есть). Локально glTF из `openscad` не получить (`--export-format` знает лишь
csg/cxml/nef/off/amf/ast/dxf/svg/png), поэтому для печати берите STL, а glTF
остаётся делом сайта.
