# LDAP-авторизация

Необязательный драйвер `Auth_Ldap`: по умолчанию модуль отключён, работает
обычный `Auth_ORM`. При включении **все** входы по паролю проверяются LDAP;
запасного входа по локальному паролю и автоматического создания аккаунтов нет.
Логин LDAP должен точно совпадать с `username` уже созданного пользователя PRX.
Его роль `login`, подтверждение email, остальные роли и второй фактор TOTP
остаются локальными и проверяются существующим кодом портала. Пароль LDAP в БД
не записывается. Отключённого в LDAP пользователя нельзя заново авторизовать;
уже выданные сессии не проверяются по LDAP на каждом запросе — для немедленного
отзыва также заблокируйте локального пользователя и завершите его сессии.

## Подключение

1. Установите PHP-расширение `ldap` для **той же версии PHP-FPM**, что обслуживает
   портал, и CLI (например, пакет `php-ldap` на Ubuntu). Перезапустите FPM.
   Для Docker расширение в базовом образе не устанавливается. Соберите и
   пересоздайте PHP-контейнер явно:

   ```bash
   docker compose build --build-arg INSTALL_LDAP=1 php
   docker compose up -d --no-deps php
   docker compose exec php php -m | grep -i '^ldap$'
   ```

   При следующей пересборке снова укажите build-arg. Настройте доверенный CA
   **внутри контейнера**, например через собственный образ или compose override с
   read-only CA-файлом и соответствующим `ldap.conf`; установка CA только на хосте
   недостаточна. Подготовьте доверенный CA в системном хранилище LDAP-клиента (`ldap.conf`,
   `TLS_CACERT`/`TLS_CACERTDIR`); сертификат сервера должен соответствовать имени
   хоста. Проверка сертификата обязательна, самоподписанный сервер без доверенного
   CA не сработает. Не отключайте проверку сертификатов.
2. Создайте в каталоге отдельную сервисную учётную запись только с правом поиска
   пользователей в нужном подразделении. Пользователь PRX создаётся заранее в
   `/prx595/admin`, с тем же `username`, ролью `login` и подтверждённым email.
   Права администратора и другие роли назначаются исключительно в PRX: LDAP-группы
   не импортируются. Убедитесь, что в каталоге по каждому логину находится ровно
   одна запись и её bind разрешён.
3. В корневой `.env` (или защищённое окружение FPM) добавьте, подставив реальные
   значения. Секрет сервисного аккаунта не коммитьте и не публикуйте:

   ```dotenv
   PRX_LDAP_ENABLED=1
   PRX_LDAP_URI=ldaps://ldap.example.org:636
   PRX_LDAP_BASE_DN="ou=people,dc=example,dc=org"
   PRX_LDAP_BIND_DN="cn=portal-reader,ou=services,dc=example,dc=org"
   PRX_LDAP_BIND_PASSWORD="секрет-сервисной-учётной-записи"
   PRX_LDAP_LOGIN_ATTRIBUTE=uid
   PRX_LDAP_STARTTLS=0
   ```

   Для Active Directory обычно используют `PRX_LDAP_LOGIN_ATTRIBUTE=sAMAccountName`.
   Вместо LDAPS допустим `ldap://ldap.example.org:389` **только** с
   `PRX_LDAP_STARTTLS=1`; простое соединение без TLS отклоняется. URI задаётся без
   пути и встроенных логина/пароля. Для AD base DN может быть корнем домена или
   ограниченным OU; не используйте такой base, где логин встречается дважды.
4. Перезапустите FPM и проверьте вход обычного пользователя, неправильный пароль,
   блокировку (снятие роли `login`), второй фактор и недоступность LDAP. При
   ошибке соединения, недоверенном сертификате или нехватке настроек вход закрыт;
   LDAP-секреты и ответы в журнал не пишутся. Входящий HTTPS и штатная защита
   формы входа обязательны. На разных FPM-узлах настройки и CA должны совпадать.

Отключение и аварийный откат: выставьте `PRX_LDAP_ENABLED=0` и перезапустите
FPM — вернётся исходный `Auth_ORM` с локальными паролями. Заранее храните
аварийный локальный административный пароль отдельно и ограничьте доступ к
настройкам сервера. Локальные пароли не синхронизируются с каталогом.

Флажок «запомнить меня» при LDAP-входе намеренно не создаёт постоянный токен;
старые cookie ORM в LDAP-режиме не используются. При переключении режимов
необходимо завершить активные сессии и отозвать старые постоянные токены; после
отката старые неотозванные ORM-cookie снова могут сработать. Смена/сброс пароля
через локальные формы меняет только локальный пароль, а не LDAP; управлять LDAP
паролями следует в каталоге. LDAP-пароль используется также для проверки текущего
пароля через `Auth::check_password()`.

## Проверка

`make check`, `bash .tools/php_check_all.sh`, `php tests/Contracts/ldap_auth.php`.
Стенд использует фальшивый LDAP и не заменяет проверку с настоящим сервером,
сертификатами, PHP-FPM и портальной БД.
