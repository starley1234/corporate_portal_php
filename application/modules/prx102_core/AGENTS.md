## Назначение
Фундамент приложения: базовый контроллер всех страниц (шаблон, меню, ACL),
аутентификация (Kohana Auth + OAuth Яндекса), модели пользователей и ролей.

## Состояние
- **17.11.2026:** `after()` только для HTML вошедшего пользователя получает
  видимое Избранное через публичный `Service_Prx110_Favorites` и передаёт его
  шаблону и карточкам до рендера; ответ не кэшируется. Сбой БД логируется и
  показывается в sidebar, но не блокирует страницу миграций. API без шаблона
  не выполняет эту выборку. Принудительный выход прерывает запрос редиректом,
  который нельзя поглощать общим `catch`; API каталога отвечает при этом 401 JSON.
- **07.10.2026:** серверная подсветка пунктов sidebar понимает `active_paths`;
  шаблон сохраняет и восстанавливает `scrollTop` навигации между переходами
  по ссылкам, чтобы длинное меню не прыгало к началу.
- Готовность: рабочий костяк, используется всеми модулями.
- ВАЖНО: таблицы users/roles/user_* БЕЗ префикса — legacy ядра; переименование
  согласовывать отдельно (затрагивает Kohana Auth).

## Не трогать / подводные камни
- Не менять контракт `before()` базового контроллера «между делом» — от него
  зависят все модули.
- Проверка прав: централизованно `$this->can($ability, $object)`; не писать
  свои разрозненные проверки ролей в контроллерах.
- Пароли: только через Kohana Auth (`AUTH_HASH_KEY` из .env).

## Граница HTTP (23.11.2026)

Общий HTTP-контроллер не обслуживает очередь и не пишет диагностический кэш
классов. Обслуживание — `portal:maintain` по таймеру.

UI требует CSRF независимо от Authorization/X-Worker-Token. Базовый `machine_request()` возвращает FALSE; исключение разрешено только endpoint с обязательной собственной аутентификацией.

## Серверное чтение ролей

`Service_Prx102_Users::actors_with_role(string $role): array<Prx_Actor>` —
контракт для подбора кандидатов фоновой операции. SQL к `users/roles/roles_users`
остаётся в prx102. Учитываются существование пользователя и роль `login`
(блокировка — её снятие); имя роли передаётся параметром, пустое имя даёт [].
Возвращаются ID и полный набор ролей, порядок по ID, без профиля/пароля/токенов.
Кэша нет: следующий вызов видит снятие `login` или любой другой роли.

Это не HTTP endpoint, не вход пользователя и не разрешение на бизнес-объект.
Например, prx393 затем проверяет каждого кандидата через policy prx391;
без этого отправлять содержимое чувствительного документа нельзя.
Контракты: `WorkflowBoundariesTest` (PostgreSQL) и
`tests/Contracts/workflow_boundaries.php` (изолированный).

## Точки расширения страницы (25.11.2026)

База страницы больше не вызывает бизнес-модули напрямую. Избранное (`prx110`),
оргконтекст (`prx300`) и сторож сессии «выйти везде» (`prx599`) подключаются
через `Prx_Hooks` (`application/classes/Prx/Hooks.php`) из `init.php` своих
модулей. Модуль не подключён — обработчика нет, поведение деградирует мягко.
Имена точек: `nav.favorites`, `actor.org`, `auth.session_check`. Решение и
границы — `docs/SKELETON-ADR.md` (Д2, Д7).

## PostgreSQL BOOLEAN: только Model_Prx102_User::is_active() (26.11.2026)

PDO/pgsql возвращает BOOLEAN строкой `'t'`/`'f'`; `(int) 't' === 0`, поэтому
любое `(int)`-приведение users.active считает всех деактивированными (прод-инцидент
26.11: «Аккаунт деактивирован администратором» при `active = t`). Единственный
способ чтения — предикат `Model_Prx102_User::is_active($value)`
(`TRUE/1/'1'/'t'/'true'`, strict). Место-прецедент: `Service_Prx597_Base::_truthy()`
и prx597/AGENTS.md. Гварды входа/сессии (Prx102 Base/Auth, application Auth)
и виды prx595 обязаны идти через него; в SQL — литералы TRUE/FALSE.
