## Состояние

Диагностический сервис владельца `/embedbench`: один и тот же материал
прогоняется через **два** пути получить вектор, и отчёт говорит, что брать для
какой задачи. Это не витрина и не поиск — это ответ на вопрос «какой у меня
эмбеддинг-путь основной и не пора ли переехать». Аудитория — `admin`.

Сравниваются ровно два пути, каждый со своим адресом в `workers/.env`:

| Сторона | Ключ | Переменные | Что умеет |
|---|---|---|---|
| Текстовый | `text` | `EMBEDDING_API_URL` + `EMBEDDING_MODEL` | OpenAI-совместимый `/v1/embeddings`, пачка текстов одним запросом |
| Мультимодальный | `mm` | `EMBEDDING_MM_API_URL` + `EMBEDDING_MM_MODEL` (+ `EMBEDDING_MM_DIALECT`) | `mmembed`: текст и картинка в одном пространстве, каждый вход — отдельный запрос |

## Карта

* `init.php` — маршруты: `GET /embedbench`, `POST /embedbench/run`,
  `GET /embedbench/result/<id>`, `GET /embedbench/api/status`,
  `POST /embedbench/api/worker_result`. `api` объявлен ДО `result/<id>`, иначе
  слово «api» уехало бы в страницу результата как id.
* `Controller_Nj671_Bench` — форма, запуск, отчёт. Гость не отбрасывается 403, а
  получает общую плашку входа; форма и запуск требуют `admin` (иначе 403),
  POST — CSRF.
* `Controller_Nj671_Api` — `status` (только админ: в отчёте видны адреса
  внутренних сервисов) и `worker_result` (строгий `WORKER_API_TOKEN`, без
  development-обхода).
* `Service_Nj671_Bench` — ВСЯ логика показа: `shape`, `side`, `metric_rows`,
  `query_rows`, `notes`, `decision`, `reason`, `grade`, `display`, `brief`,
  `history`, `corpora`. Расчёта метрик здесь нет и быть не должно.
* `views/671/index.php` — две карточки путей (что видит сайт), форма прогона,
  история. `views/671/result.php` — вердикт, таблица задач, метрики, где пути
  разошлись, замечания, паспорт путей, сырой jsonb.
* `migrations_pg/pgMigration_Nj_671_001_Embedbench_Runs.php` — только `nj_671_runs`.

Воркер (Python):

* `workers/n2j_workers/embbench.py` — корпуса, два движка, метрики, `decide()`,
  `run()`, `report()`. Единственное место, где считается арифметика.
* `workers/n2j_workers/handlers/nj671_embedbench.py` — канал `nj671.bench`:
  прогон + доставка `POST /embedbench/api/worker_result`.
* `workers/nj671_bench.py` — CLI: тот же прогон без сайта и очереди
  (`python -m nj671_bench --corpus catalog --quick`).

## Поток прогона

```
форма → POST /embedbench/run ──► INSERT nj_671_runs (queued)
                              └► Service_Nj120_JobQueue::push('nj671.bench',
                                     {run_id, corpus, quick}, timeout 600)
воркер: embbench.run() ──► POST /embedbench/api/worker_result (X-Worker-Token)
сайт: Vision::run_apply() ──► status done|error, result jsonb, finished_at
страница: Vision::run_watch() дожимает прогон из nj_120_jobs, если доставка
          не прошла, и отдаёт подсказку «задачу никто не взял»/«канал не в
          WORKER_CHANNELS» вместо вечного «Считаю…»
```

Маршрут идёт через общий слой прогонов (`Vision::run_create/run_get/run_watch/
run_apply/run_live/table_exists/runs_last_hour`), как у остальных модулей с
очередью: своя копия «прогон + очередь + дожим» разошлась бы с общей через
неделю.

## Контракт отчёта (`result` jsonb)

```
status, title, elapsed_ms,
corpus        {key, title, docs, queries, quick}
engines.text  {key, base_url, model, ok, error, dims, notes[], repeat,
               quality{recall1, recall3, mrr, related, unrelated, margin},
               latency{total_ms, per_item_ms},
               images{supported, checked, ok, margin, note}, rows[]}
engines.mm    то же самое
agreement     корреляция попарных косинусов на одних описаниях (НЕ качество)
decision      {winner: text|mm|both|none, summary, reasons[], tasks[]}
              reasons[] = {code, value|side|error|text|mm}
              tasks[]   = {task: text_index|cross_modal|one_space|any, pick, delta?, speed?}
```

`shape()` различает ТРИ состояния записи (`state`), и путать их нельзя:

| `state` | Что лежит в `result` | Что показывает страница |
|---|---|---|
| `full` | отчёт с `engines`, метриками и решением | обычный отчёт сравнения |
| `summary` | сводка: `winner`, `text_ok`, `mm_ok`, `agreement` (без `engines`) | «прогон выполнен, дошла только сводка» + отправка в CLI |
| `empty` | ничего | «отчёт пуст» |

Сводка — не отказ: в ней сказано, что ответило, но цифр нет. Писать про неё
«ни один путь не ответил» значит врать о состоянии серверов (живой случай
22.10.2026).

Коды причин (`reason()` в службе обязана знать каждый): `only_one`, `both_off`,
`mm_better`, `text_better`, `same_quality`, `text_faster`, `images_ok`,
`images_weak`, `text_unstable`, `mm_unstable`, `dims_differ`. Новый код в
воркере без строки в `reason()` — «сырой код» на странице, поэтому
`tests/Unit/EmbedbenchServiceTest::test_every_known_reason_has_words` держит
список.

## Дожим и почему отчёт не подменяется

Страница зовёт `Vision::run_watch()`, а тот при необходимости добирает
результат из задачи очереди (`_catch_up`). Это спасение для случая «доставка не
дошла»: воркер посчитал, а сайт не принял.

Грабли, на которые владелец наступил 22.10.2026 («у меня всё настроено и всё
доступно», а страница сказала «Ни один путь не ответил — причина не записана»):

* `Vision::_catch_up()` перезаписывал результат **терминального** прогона
  (status `done`) тем, что лежало в `nj_120_jobs.result`. Дожим нужен только
  для `queued`/`running`;
* обработчик возвращал в задачу короткую сводку без `engines`, поэтому
  перезапись стирала отчёт. Теперь в задаче лежит полный отчёт (~5 КБ: в нём
  нет векторов), а признак `summary_only` прямо говорит, что это он.

Решение вынесено в чистую функцию `Vision::catch_up_plan($run, $job)` — она не
ходит в БД и возвращает одно из четырёх: `none` (не трогать), `apply` (прогон
не закрыт, а задача отдала результат), `heal` (в записи сводка, а в задаче
отчёт — чиним старые испорченные записи), `fail` (задача провалена окончательно
— показать причину). Проверка живёт в `.tools/nj671_embedbench_stand.php`.

Правило на будущее: **терминальный прогон не переписываем** — что доставили, то
и показываем; пересчёт — только по кнопке. Результат задачи — это итог задачи,
и он бывает КОРОЧЕ отчёта.

## Две модели — два пути, и путать их нельзя

Стенд мерит ровно то, что настроено, поэтому имя модели в `EMBEDDING_MODEL`
имеет значение:

* **текстовый путь** — `EMBEDDING_API_URL` + `EMBEDDING_MODEL`, модель типа
  `embeddings` (`text-embedding-qwen3-embedding-0.6b`);
* **мультимодальный** — `EMBEDDING_MM_API_URL` + `EMBEDDING_MM_MODEL`, отдельный
  сервис (`OmniEmbed`, llama.cpp с проектором, vLLM), потому что LM Studio
  мультимодальные эмбеддинги по `/v1/embeddings` не отдаёт.

Живой случай 22.10.2026: в `EMBEDDING_MODEL` попало имя мультимодальной модели
(`qwen3-vl-embedding-2b`) — видимо, скопированное из блока nj653. Сервер
(llm.toolforge.ru, LM Studio) ответил `{"error":"No models loaded. Please load a
model in the developer page…"}`, то есть выглядел пустым, хотя в нём лежала
`text-embedding-qwen3-embedding-0.6b`. Старые пути при этом работали: и
`Llm_Provider_Toolforge::embeddings()`, и `application/config/llm.php` по
умолчанию подставляют именно 0.6b. То есть «раньше работало» — это «раньше
никто не просил VL-модель у LM Studio».

Что теперь делает стенд (`_preflight_model()` в `embbench.py`):

1. Один `GET /models` **до** запросов. Нет модели в списке — запросов к
   `/embeddings` не будет вовсе.
2. Очевидное расхождение в имени (`Qwen/Qwen3-Embedding-0.6B` против
   `qwen3-embedding-0.6b`) чинится само, с пометкой в паспорте: логика
   `_best_name()` уже написана для мультимодального клиента, второй копии нет.
3. Несовместимое имя — понятная ошибка: что сервер отдаёт, какое значение
   вписать в `EMBEDDING_MODEL`, и отдельная фраза «это VL-модель, ей место в
   `EMBEDDING_MM_API_URL`».
4. Если отказ всё же пришёл от сервера (имя сверено раньше не было), тело
   ответа и подсказка под код уходят на страницу — см. ниже.

## Когда путь не отвечает: что видно в отчёте

Отказ пути — не приговор отчёту. Стенд обязан назвать причину словами сервера,
иначе владелец ищет её не там.

* `llm.EmbeddingClient` больше не роняет `raise_for_status()` (одна строка
  «Client error '400 Bad Request'»), а бросает `EmbeddingServerError`: адрес,
  модель, число входов и символов, **тело ответа** и подсказка под код
  (400 — модель/размер пачки, 404 — не тот путь, 413 — слишком большой запрос,
  422 — формат, 5xx — сервер). 401/403 остаются `LlmConfigError` с указанием
  переменной, откуда взялся токен.
* Ошибка называет **шаг**: «документы», «запросы», «повторяемость». Голый 400
  не говорил даже, что именно отправили.
* Отказ на пачке (`batch too large`) отличается от «модель не найдена» одним
  опытом: те же входы по одному. Если поодиночке работает — прогон
  продолжается, а в замечания попадает «поставьте `EMBEDDING_BATCH_SIZE=1`».
  На 401 и таймаутах одиночные повторы не делаются: это только жгло бы время.
* При отказе 4xx стенд спрашивает `GET {base}/models` и показывает список
  моделей сервера, а если запрошенной модели там нет — говорит об этом прямо.
* В паспорте пути написано, отправляется ли токен (`токен отправляется:
  EMBEDDING_API_KEY` / `токен НЕ отправляется: …`). Значение токена не
  попадает в отчёт никогда.
* Если обе стороны указывают на один адрес и/или одну модель, это отдельное
  замечание: сравнение сервера с самим собой подтверждением не считается.

## Правила решения (воркер)

* Качество меряется на одном материале: `recall@1/@3`, MRR, разделимость
  (related − unrelated). Порог «вообще не шум» — 2 пункта recall@1.
* Скорость — `per_item_ms`; порог «уже разница» — 1.5×.
* Повторяемость — косинус двух векторов одного текста; ниже `0.999` — «вектор
  дрожит» (годится для поиска, не годится для дедупликации).
* `cross_modal` — проба «картинка ↔ подпись»: маржа выше нуля значит, что
  картинка ближе к своей подписи, чем к чужой. Текстовый путь картинок не
  видит вовсе, поэтому здесь у него нет шансов by design.
* `dims_differ` — разные размерности. Это НЕ ошибка, но и не повод складывать
  векторы в одну таблицу: одинаковые 1024 у двух моделей не означают общее
  пространство. Страница обязана сказать это словами.

## Вывод, который стенд защищает

1. **Основной путь для текста — `EMBEDDING_API_URL`.** Батчи, дешёвая модель,
   предсказуемая задержка. Всё, что сегодня ищет по тексту (nj115, похожие
   записи, RAG), должно жить на нём, пока стенд не покажет просадку ≥ 2 пунктов.
2. **`EMBEDDING_MM_API_URL` — только там, где есть картинки.** Кросс-модальный
   поиск, «похожие фото», проверка каталога по фото. Для чистого текста он
   дороже на порядок и, как правило, не лучше.
3. **Одно пространство на всё — отдельное решение, а не «за компанию».** Оно
   оправдано, если текст не просел и вход не подорожал больше чем втрое;
   иначе две таблицы дешевле, чем один общий индекс.
4. **Смешивать пути в одной таблице нельзя никогда** — даже при совпадении
   размерностей. Признак смешения — «похожесть» на чужие записи в поиске.

## Инварианты

* Метрики считает ТОЛЬКО воркер. Вторая реализация арифметики на PHP
  разошлась бы с CLI после первой правки; служба переводит цифры в слова.
* Пороги (`limits`, `thresholds`) совпадают с `embbench.decide()`; меняя их в
  одном месте, менять и в другом — иначе текст «почему так решили» врёт.
* Стенд НЕ занимает текстовый путь при отсутствии `EMBEDDING_MM_API_URL`:
  `MmEmbeddingClient.from_env()` умеет падать на текстовый адрес, и это
  сравнение сервера с самим собой. `mm_engine_from_env()` читает только свой
  ключ (закреплено тестом).
* Только `nj_671_runs`. Прогон с отчётом — это данные, а не настройки: чистка
  через 180 дней объявлена манифестом (`cleanup`), руками ничего не удаляем.
* `result` пишется через `Vision::run_apply()` (jsonb через `DB::expr`): прямая
  запись в `DB::update()->set()` даёт «invalid input syntax for type json» и
  вечный «Считаю…» — грабля nj645/nj646.
* `0` — законное значение (0 мс, 0 картинок). «Нет данных» — `NULL`, и только
  тогда в таблице «—»; `(int) $x ?: '—'` печатает «—» вместо настоящего нуля.

## Проверки

```bash
# воркер: корпуса, метрики, решение, обработчик, доставка (19 тестов)
cd workers && python -m pytest tests/test_nj671_bench.py -q

# служба показа без PHPUnit
php tests/mini_runner.php EmbedbenchService

# стенд: служба + обе вьюхи + плашка входа, без БД
php .tools/nj671_embedbench_stand.php

# что сервер эмбеддингов думает о запросе — без воркера и очереди
curl -s https://<хост>/v1/models -H "Authorization: Bearer $EMBEDDING_API_KEY"
curl -s -X POST https://<хост>/v1/embeddings \
     -H "Authorization: Bearer $EMBEDDING_API_KEY" -H "Content-Type: application/json" \
     -d '{"model":"<EMBEDDING_MODEL>","input":["тест"]}'

# без PHP в песочнице — тот же стенд в WebAssembly
node .tools/phpwasm_stand.mjs .tools/nj671_embedbench_stand.php
```

Стенд проверяет то, чего не видит линтер: что у выключенного пути «—», а не
«0 %»; что разные размерности дают красное замечание; что при одном рабочем
пути вердикт всё равно честный; что пустой отчёт не роняет страницу.
