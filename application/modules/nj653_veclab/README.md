# nj653_veclab — Лаборатория векторов

- Страница: `/veclab` — три опыта над мультимодальной эмбеддинг-моделью
  (проверка модели, своя коллекция и сравнение пары); поиск по смыслу после
  отправки открывается отдельно на `/veclab/result/<id>` с запросом, прогрессом
  и находками, без возврата фокуса к мобильному полю ввода. При сбое сохранения
  кадра или очереди запрос и причина остаются на той же странице ошибки; поиск
  из истории можно открыть повторно
- `/veclab/map` — **карта сходства**: вся коллекция одной картинкой. Точки
  раскладываются по косинусам (MDS, `Service_Nj653_Map`), похожее сбивается в
  кучки, линия между точками = пара ближе порога. Считает сервер, рисует
  обычный SVG — внешних библиотек нет
- `/veclab/admin` — **админка коллекции** (роль admin): вся коллекция всех
  посетителей, отбор по посетителю/виду/модели/подстроке/возрасту, массовое
  удаление по галочкам и по отбору, «убрать копии» по порогу близости и
  полная очистка со словом подтверждения. Все действия POST + CSRF
- Что получает человек: кросс-модальный поиск (коллекция картинок и текстов —
  запрос обычными словами), косинусная близость с человеческой оценкой и
  честный паспорт модели: какой формат запроса она понимает, какая
  размерность, сколько миллисекунд на вектор
- Векторы считает воркер (канал `nj653.embed`,
  `workers/n2j_workers/handlers/nj653_veclab.py`), хранит и ищет по ним сайт
  (pgvector, `Service_Nj653_Store`)
- Единого формата мультимодального `/v1/embeddings` у локальных серверов нет,
  поэтому клиент `workers/n2j_workers/mmembed.py` перебирает известные
  диалекты и запоминает рабочий; перебор виден на странице
- API: `POST /veclab/api/{probe,add,search,compare,seed,forget}`,
  `GET /veclab/api/{status,items,about}`, `POST /veclab/api/photo_file` и
  `POST /veclab/api/worker_result` (для воркера, по `X-Worker-Token`).
  `GET /veclab/api/about` — самоописание: модель, размерность, пределы,
  перечень методов и список MCP-инструментов
- **MCP** (`config/mcp.php`, хаб nj160, `/mcp/api/rpc`): `nj653_status`,
  `nj653_collection`, `nj653_remember`, `nj653_search`, `nj653_compare`,
  `nj653_result` и админский `nj653_probe`. У агентов своя коллекция
  (`visitor = 'mcp'`), чужие посетительские элементы им не видны. Счёт
  вектора асинхронный: инструмент отдаёт `run_id`, результат забирается
  `nj653_result` через несколько секунд (так же устроен nj550_jobs)
- Таблицы `nj_653_runs` и `nj_653_items` (чистка через 30 дней); кадр
  удаляется сразу после подсчёта вектора, в коллекции остаётся превью ~96 px
- Коллекция личная: элемент принадлежит `visitor`, поиск идёт только по своим
- Картинки можно добавлять **пачкой**: кнопка «сразу несколько» берёт до 12
  файлов (`limits.bulk_max`), подпись каждой — имя файла, текст из поля
  становится общей подписью. Один прогон, свой слот кадра на каждую картинку
  (`nj_653` photo-слоты 1…24), к модели они всё равно идут по одному запросу
- **Основной сервер — свой сервис эмбеддингов** (OmniEmbed на
  Qwen3-VL-Embedding-2B, `https://embed.toolforge.ru`; токен `oes_…`
  обязателен на всех путях). У него два интерфейса, и клиент понимает оба:
  `POST /v1/embeddings` с `messages=[[…]]` (диалект `omni_messages`, пачкой,
  ширина вектора через `dimensions`) и `POST /v2/embed` в формате Cohere
  Embed v2 (диалект `cohere_inputs`). Сервис опознаётся по `GET /healthz`, и
  доктор показывает его паспорт: модель, бэкенд, устройство, загружена ли
  она в память. Те же два диалекта подходят и к vLLM
- **Входы не едут пачкой.** Сервер считает пачку conversations одним батчем,
  и вектор входа зависит от соседей по запросу: одна и та же картинка,
  посланная вдвоём, давала косинус 0,77 сама с собой, а один и тот же текст —
  0,9989. Поэтому картинка — всегда отдельный запрос, а тексты пачкой только
  при явном `EMBEDDING_MM_BATCH>1`. На странице это видно проверкой
  «Повторяемость: одна картинка дважды»
- Воркер подключается к серверу так же, как чат `/meal`: если адрес
  эмбеддингов совпадает с адресом LLM-провайдера, берутся его токен и прокси,
  а имя модели сверяется с `GET /v1/models` — в запрос уходит точный id, и
  LM Studio поднимает модель сам (JIT), вручную грузить не нужно
- Диагностика из командной строки: `python3 workers/nj653_doctor.py` — он
  сначала спрашивает у сервера `GET /v1/models` и говорит, загружена ли
  вообще модель из `EMBEDDING_MODEL`
- У LM Studio JIT-загрузка привязана к ТИПУ модели: `/v1/chat/completions`
  поднимает llm и vlm, `/v1/embeddings` — только тип `embeddings`. GGUF-сборка
  Qwen3-VL-Embedding числится как `llm` (раздел LLM в «My Models»), поэтому
  чат с ней работает, а эмбеддинги отвечают «No models loaded». Воркер это
  распознаёт по `GET /api/v0/models` и говорит прямо
- Тогда включается **режим описания**: картинку описывает vision-модель через
  чат (как в `/meal`), а вектор по описанию даёт текстовая эмбеддинг-модель с
  того же сервера. Поиск словами работает; это честно подписано в паспорте и
  в итоге самопроверки (жёлтый, не зелёный). Выключается
  `EMBEDDING_MM_FALLBACK=off`
- Если все пробы диалектов падают с ОДНИМ и тем же ответом сервера, виноват
  сервер, а не формат: чаще всего в LM Studio не загружена модель
  (`lms load <имя>` либо включить Just-In-Time model loading) или не задан
  `EMBEDDING_API_KEY`. Клиент такой случай распознаёт и пишет это прямо,
  не перебирая остальные форматы впустую

## Как получить НАСТОЯЩИЕ мультимодальные эмбеддинги

LM Studio тут не помощник: он раздаёт модель по типу (`GET /api/v0/models`),
а GGUF Qwen3-VL-Embedding числится `llm`, и `/v1/embeddings` его не отдаёт.
Нужен сервер, который умеет считать вектор по картинке.

**0. Свой сервис (OmniEmbed) — то, что используется сейчас.** Модель держит
в памяти сам, токен обязателен на всех путях. Настройка в `workers/.env`:

```ini
EMBEDDING_MM_API_URL=https://embed.toolforge.ru/v1
EMBEDDING_MM_API_KEY=oes_...          # без него HTTP 401 на ЛЮБОМ запросе
EMBEDDING_MM_MODEL=mradermacher/Qwen3-VL-Embedding-2B-GGUF
EMBEDDING_MM_DIALECT=omni_messages    # можно не задавать — подберётся сам
EMBEDDING_MM_FALLBACK=off             # режим описания больше не нужен
EMBEDDING_MM_DIMENSIONS=1024          # 64…2048 и ровно столько же, сколько в миграции
```

Что уходит на сервер в диалекте `omni_messages` (форма из документации
сервиса, vLLM-совместимая):

```json
{"model": "mradermacher/Qwen3-VL-Embedding-2B-GGUF",
 "messages": [[
   {"role": "system",
    "content": [{"type": "text", "text": "Represent the user input for image retrieval."}]},
   {"role": "user", "content": [
      {"type": "image_url", "image_url": {"url": "data:image/png;base64,…"}},
      {"type": "text", "text": "кот на диване"}]},
   {"role": "assistant", "content": [{"type": "text", "text": ""}]}]],
 "continue_final_message": true, "add_special_tokens": true,
 "encoding_format": "float", "dimensions": 1024}
```

Три вещи здесь обязательны, и без них вектор получается мусорным:

1. инструкция — **отдельное** `system`-сообщение (модель instruction-aware;
   вклеенная в текст инструкция попала бы в вектор как содержимое);
2. содержимое — всегда **список частей**, даже когда часть одна;
3. пустое `assistant`-сообщение в конце плюс `continue_final_message` —
   иначе pooling снимает вектор не с того токена.

Ширину вектора режет сам сервис (матрёшка 64…2048); значение вне этих границ
воркер серверу не шлёт и подрезает вектор у себя (`fit_dims`).

Резервный диалект `cohere_inputs` ходит на `POST /v2/embed`
(`inputs=[{content:[…]}]`, `output_dimension`, ответ
`{"embeddings": {"float": [[…]]}}`) — тот же путь поддерживает vLLM.

**1. llama.cpp (та же GGUF-сборка, отдельный порт).** В llama.cpp поддержку
картинок в `/v1/embeddings` добавили: каждый элемент `input` может быть
объектом `{"content": [{"type":"image_url",…},{"type":"text",…}]}` — это наш
диалект `oai_content`, клиент найдёт его сам. Нужны ДВА файла: модель и
`mmproj-*.gguf` (проектор зрения) из того же репозитория квантов.

```sh
LLAMA_MEDIA_MARKER='<__media__>' llama-server \
  -m Qwen3-VL-Embedding-2B-f16.gguf \
  --mmproj mmproj-Qwen3-VL-Embedding-2B-f16.gguf \
  --embedding --pooling last --embd-normalize 2 \
  -c 8192 -ngl auto --host 0.0.0.0 --port 1237
```

Затем в `workers/.env`: `EMBEDDING_MM_API_URL=http://127.0.0.1:1237/v1`
(чат и остальные модули остаются на LM Studio). Маркер картинки клиент всё
равно переспросит у `GET /props` — без `LLAMA_MEDIA_MARKER` сервер выбирает
его случайно при старте.

**2. vLLM (исходные веса, не GGUF).** `Qwen/Qwen3-VL-Embedding-2B` поддержан
как pooling-модель:

```sh
vllm serve Qwen/Qwen3-VL-Embedding-2B --runner pooling \
  --served-model-name qwen3-vl-embedding-2b --host 0.0.0.0 --port 1237
```

Клиент подойдёт диалектом `chat_messages` или `oai_content`.

Проверка в обоих случаях одна: `python3 workers/nj653_doctor.py` — он скажет,
какой софт на том конце, какой формат подошёл и связывает ли модель текст с
картинкой. Как только сервер отвечает по-настоящему, режим описания
выключается сам.

Инструкции для агента — см. `AGENTS.md` рядом.
