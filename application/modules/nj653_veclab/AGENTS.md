## Контракт

- Страницы: `GET /veclab` — вкладки «Коллекция и поиск», «Сравнение пары»,
  «Проверка модели»; `GET /veclab/result/<id>` — результат поиска отдельно
  от формы (запрос, живой статус, находки), без возврата мобильного фокуса.
  Прочие режимы продолжают показывать результат на месте по `/veclab/api/status`.
- `GET /veclab/map` — карта сходства (`Controller_Nj653_Map`,
  `Service_Nj653_Map::build()`, вьюха `653/map`). Чужую коллекцию
  (`?visitor=`) открывает только админ: на карте чужие превью.
- `GET /veclab/admin` + `POST /veclab/admin/{delete,delete_filtered,
  delete_duplicates,truncate}` — админка коллекции, роль admin, POST + CSRF,
  после действия редирект 303 с `?flash=`.
- API (`Controller_Nj653_Api`, свой JSON-контроллер — НЕ `Controller_Vision_Base`):
  `POST /veclab/api/probe|add|search|compare|seed|forget`,
  `GET /veclab/api/status?id=`, `GET /veclab/api/items`,
  `POST /veclab/api/photo_file`, `POST /veclab/api/worker_result`.
- Payload воркеру: `{run_id, mode, inputs: [{slot, text, has_image, instruction}]}`.
  Ответ воркера: `{run_id, status, mode, model, dims, dialect, elapsed_ms,
  kinds, vectors, …}`; у `probe` — ещё `passport`, `checks`, `cross`.
- MCP (`Service_Nj653_Mcp`, хаб nj160): `nj653_status`, `nj653_collection`,
  `nj653_remember`, `nj653_search`, `nj653_compare`, `nj653_result`,
  админский `nj653_probe`. Коллекция агентов — `visitor = 'mcp'`; чужие
  прогоны и элементы через MCP не отдаются. Ответ асинхронный: `run_id` →
  `nj653_result`.
- `Service_Nj653_Map` — чистая логика карты: `build($items, $link)` →
  `{points:[{id,label,kind,preview,x,y,near_id,near,near_cos}], links, pairs,
  note}`; координаты 0…1, раскладка детерминированная (старт степенного
  метода не случайный, иначе карта «пляшет» при каждом открытии).
- `Service_Nj653_Veclab` — чистая логика (оценка близости, `shape`, `hits`,
  `safe_preview`, `probe_verdict`); `Service_Nj653_Store` — таблицы, кадры
  слотов и поиск по векторам.
- Конфиг `config/nj653_veclab.php`: `limits` (photo_mb, per_hour, items_max,
  text_max, top, timeout_sec), `scale` (пороги словесных оценок),
  `instructions`, `samples` (коллекция «одной кнопкой»).

## Правила для агента

1. **Векторы в `nj_653_runs.result` не попадают.** 2048 чисел в jsonb на
   каждый прогон — это мусор в базе и в мониторе очереди. Контроллер удаляет
   `vectors` из массива перед `Vision::run_apply`, воркер — перед возвратом
   результата задачи. Ломать это нельзя.
2. **Поиск считает PostgreSQL, а не PHP.** `Store::search()` — это `<=>`
   pgvector (или функция-фолбэк `nj_653_vec_dist` для `real[]`).
   `Service_Nj653_Veclab::cosine()` существует только ради сравнения пары и
   тестов.
3. **HNSW при 2048 измерениях не строится** — у pgvector предел 2000. Миграция
   создаёт индекс только при `dims <= 2000`; при большей ширине поиск идёт
   полным перебором, и страница об этом честно пишет. Не «чинить» урезанием
   вектора: размерность задаётся один раз при создании колонки.
4. **Диалект запроса — не константа.** Формат мультимодального
   `/v1/embeddings` у llama.cpp, vLLM, LM Studio и mlx-serve разный; клиент
   перебирает кандидатов и запоминает рабочий. Новый формат добавляется в
   `mmembed.DIALECTS` + `build_body` + подпись в `Service_Nj653_Veclab::DIALECTS`.
   Первыми в списке стоят диалекты своего сервиса (OmniEmbed) — `omni_messages`
   и `cohere_inputs`, поэтому автоопределение попадает с первой пробы. Диалект
   может ходить по СВОЕМУ пути: `DIALECT_PATHS` + `MmEmbeddingClient.endpoint()`
   (`cohere_inputs` → `<корень>/v2/embed`), а `parse_vectors` понимает и
   Cohere-ответ `{"embeddings": {"float": […]}}`.
5. **Форму `omni_messages` менять нельзя по вкусу** — она взята из
   документации сервиса: инструкция отдельным `system`-сообщением
   (Qwen3-VL-Embedding instruction-aware, вклеенная в текст она попадёт в
   вектор как содержимое), содержимое всегда списком частей, в конце пустое
   `assistant`-сообщение плюс `continue_final_message` и
   `add_special_tokens` — без них pooling снимает вектор не с того токена.
   См. `_messages()` и `DEFAULT_INSTRUCTION`.
6. **Ширину вектора режет сервер.** В `omni_messages` это `dimensions`, в
   `cohere_inputs` — `output_dimension` (матрёшка, 64…2048; вне границ —
   HTTP 422, поэтому `_clamp_dims()` такое значение серверу не отдаёт). `fit_dims` на
   стороне воркера остаётся только страховкой для серверов попроще.
7. **Пачка меняет вектор — не батчить.** `MmEmbeddingClient._chunks()` шлёт
   каждый вход с картинкой отдельным запросом, а тексты складывает в пачку
   только при `EMBEDDING_MM_BATCH>1` (по умолчанию 1). Причина — не экономия:
   у сервера вектор входа зависит от соседей по запросу (одна и та же
   картинка вдвоём давала 0,77 сама с собой). Проверки: «Повторяемость: одна
   картинка дважды» в `run_probe` и строка «Пачка не меняет вектор» в докторе.
8. **Свой сервис опознаётся по `GET /healthz`** (`MmEmbeddingClient.health()`,
   `server_probe()` → `software="omniembed"`). Оттуда же в паспорт и в вывод
   доктора идут модель, бэкенд, устройство и `loaded`; при `loaded: false`
   доктор предупреждает, что модель не в памяти.
   **Подключение берётся у чата.** `MmEmbeddingClient.from_env()` ищет в
   реестре провайдеров (`llm.provider_for_url`) того, кто ходит на тот же
   адрес, и забирает его токен и прокси; понимает спеку
   `TOOLFORGE::модель`. Не заводить для эмбеддингов отдельную схему настроек:
   /meal работал именно потому, что шёл через реестр.
   **Тип модели важнее формата.** `lmstudio_kinds()` читает родной REST
   LM Studio (`/api/v0/models`) и знает `type`: llm | vlm | embeddings.
   `/v1/embeddings` поднимает только embeddings — отсюда «No models loaded»
   при верном имени и включённом JIT. Не лечится повтором и загрузкой руками.
   **Режим описания (`mode="caption"`)** — запасной путь, не замена: картинка
   → `vlm.img_msg` + `LlmClient` (тот же путь, что /meal) → описание →
   текстовая эмбеддинг-модель. Обязан быть виден: паспорт (`mode`,
   `mode_note`), жёлтый вердикт `probe_verdict`, строка в докторе. Молча
   подменять механизм нельзя — это другое качество поиска.
   **Имя модели сверяется с `GET /models`** (`ensure_model`): при промахе в
   запрос уходит точный id, и LM Studio грузит модель сам (JIT). Повтор
   запроса после «model not found» — один, как в `LlmClient`.
   Диалект `plain_text` обязан оставаться последним: он «работает» всегда, но
   картинку молча выбрасывает.
   **Но сначала — не врёт ли диагноз.** Если сервер отвечает одинаково на
   любое тело («No models loaded», `invalid_api_key`, `model_not_found`),
   формат ни при чём: `mmembed.SERVER_FAULTS` ловит такие ответы, перебор
   останавливается на первой пробе, а в ошибку идёт причина и список моделей
   из `GET /v1/models` (`MmEmbeddingClient.list_models`). Новый типовой ответ
   сервера добавляется строкой в `SERVER_FAULTS`, а не ещё одним диалектом.
5. **Коллекция личная.** Элемент принадлежит `visitor`; поиск, список и
   удаление — только по своим. На картинках бывает что угодно.
6. **Превью в разметку — только через `safe_preview()`** (белый список
   `data:image/(png|jpeg|jpg|webp);base64,…`): в базе лежит строка от
   браузера, и она попадает прямо в `src`.
7. **Кадры не едут в payload очереди.** Браузер шлёт картинку в запрос,
   контроллер кладёт её файлом (`Store::photo_save`), воркер забирает
   `/photo_file` и после приёмки файл удаляется (`Store::photo_drop`).
8. **Входы прогона хранятся в `result.pending`** (подпись, текст, превью) и
   сопоставляются с `vectors` по индексу. При повторе задачи `pending` не
   теряется; ошибки сохранения кадра и постановки в очередь тоже оставляют его
   в созданном прогоне и возвращают `run_id` для страницы ошибки.
9. Полос прогресса нет: ход работы показывает общий статус-ряд
   (`partials/live_status`).

## Env

Все ключи — в `workers/.env` (хвост `workers/.env.example`):
`EMBEDDING_MM_API_URL|API_KEY|MODEL|DIMENSIONS|BATCH|TIMEOUT|DIALECT`
(пусто → общий `EMBEDDING_*`), `NJ653_API_BASE`, `NJ653_SITE_TOKEN`.
`EMBEDDING_DIMENSIONS` на момент миграции задаёт ШИРИНУ колонки `embedding` —
менять её потом нельзя, только новой миграцией.

9. **Слотов у прогона много, а не два.** Массовая загрузка кладёт каждую
   картинку в свой слот (`Service_Nj653_Store::SLOT_MAX`), `Api::_slot()`
   читает либо поля `text/image/preview` с номером слота, либо элемент
   массива `items`. Приёмка `add` уже умела несколько векторов (ею же
   пользуется «Примеры») — менять её не пришлось.

## Как тестировать

- Python: `cd workers && python3 -m pytest tests/test_nj653_mmembed.py
  tests/test_nj653_veclab_handler.py -q` (сервер поддельный, модель не нужна).
- PHP-логика и вьюхи без БД: `N2J_ROOT=<repo> node phpwasm_stand.mjs
  .tools/nj653_veclab_stand.php` (включая проверки сохранения `pending` при
  ошибке картинки/очереди) или `php tests/mini_runner.php VeclabService`.
- Живая модель: поднять мок `python3 workers/mock/mock_mmembed_server.py`
  (порт 1236) и прогнать `python3 workers/nj653_doctor.py` — он печатает
  паспорт, перебор диалектов и три пробы. Свой сервис мок играет при
  `MOCK_MM_OMNI=1`: появляются `/healthz`, пачка `messages` в
  `/v1/embeddings` и Cohere-путь `/v2/embed`; `MOCK_MM_KEY=oes_test123`
  заставляет его требовать `Authorization: Bearer`, как настоящий сервис.
- На сайте: `/veclab` → «Проверить модель» (ничего прикладывать не надо) →
  «Примеры» → поиск словами.
