# nj550_jobs — «Работа 2 Оффер» (Job 2 Offer)

Публичный сервис поиска вакансий: город + направление → вакансии с джоб-бордов
и карьерных страниц компаний. Воркер: ddgs + LangChain-ранжирование.

- Страницы: `/jobs` (форма), `/jobs/<code>` (статус/результат, поллинг 3 с)
- API: `GET /nj550/api/status/<code>`
- Очередь: канал `nj550.jobs` (`workers/n2j_workers/handlers/job_search.py`)
- Таблицы: `nj_550_searches`, `nj_550_results` (UNIQUE search_id+url_hash)

## Как течёт данных

1. `POST /jobs` → валидация → лимит по Visitor::uid() → INSERT nj_550_searches
   (status=new) → push `nj550.jobs` → куки предпочтений → redirect /jobs/<code>.
2. Воркер: 2–4 запроса к поисковику **с паузами** (NJ550_SEARCH_DELAY),
   опционально fetch страниц (по умолчанию выключен), затем LangChain:
   LLM возвращает {summary, jobs[]} — url-ы фильтруются по входным
   (анти-галлюцинация). Pg-режим пишет в БД сам; http — в job.result.
3. `Service_Nj550_Jobs::reconcile()` дозаписывает результат лениво (как nj540).

## Правила для агентов

- **Бережный режим поисковика — священен.** Паузы (NJ550_SEARCH_DELAY) и число
  запросов (NJ550_MAX_QUERIES ≤ 4) не уменьшать/не убирать: бан поисковика
  убивает сервис целиком. Новые источники нагрузки согласовывать.
- `reconcile()` идемпотентен (ON CONFLICT DO NOTHING); url без http:// и
  url вне входных данных воркера отбрасываются.
- Идентификация — только через общий `Visitor::uid()`; не привязываться к IP
  (у мобильных операторов он общий на тысячи людей).
- Тона/ключи не синхронизируются с воркером (в отличие от nj540) — промпт
  ранжирования самодостаточен.
- Миграция 001 применена — не редактировать, только новая поверх.

## Админка и MCP

- `/nj550/admin` (роль admin): последние поиски, фильтр по статусу,
  перезапуск (admin_requeue) и удаление (admin_delete) — только POST+CSRF.
- MCP-инструменты (`config/mcp.php`): nj550_recent_searches, nj550_get_search,
  nj550_create_search (лимит агента 30/час, visitor_id='mcp-agent').
  Хаб — nj160_mcp, каталог `/mcp`.
