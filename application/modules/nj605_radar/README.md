# Радар заказов (nj605_radar)

Опишите, **что вы ищете** (например, «поставка металлоконструкций», регион) —
платформа будет следить за открытыми источниками и приносить находки спроса:
закупки, запросы поставщиков, объявления — с оценкой «насколько вам подходит»
и коротким пояснением.

- **Мои радары** — создание и управление наблюдениями (`/radar`): пауза/включение,
  сбор «сейчас», удаление (с подтверждением);
- **Лента находок** — свежие находки, отсортированные по релевантности,
  с бейджем «из какого радара»;
- **Оценка 0–100** — LLM оценивает каждую находку и объясняет, почему она
  подходит («взял в работу» / «не интересно» для разбора);
- **Уведомления** — горячие находки (85+) приходят колокольчиком, не чаще раза
  в час.

Первый сбор запускается сразу после создания радара, дальше — каждые ~30 минут.
Лимит — до 10 радаров на пользователя (шум и очередь задач под контролем).

## Как это устроено

```
создание радара → задача nj120 (nj605.radar) → python-воркер (открытые источники)
→ LLM-оценка релевантности → находки в /radar + уведомление (nj597)
```

Воркер ищет по нескольким формулировкам («закупка», «тендер», «коммерческий
тендер», «запрос предложений», «ищу поставщика» — расширяется через
`NJ605_RADAR_QUERIES`) и дополнительно делает таргетированный `site:`-поиск по
площадкам закупок (по умолчанию zakupki.gov.ru, rostender.info, b2b-center.ru,
tenderplan.ru; переопределяется `NJ605_RADAR_SITE_DOMAINS`). Дедупликация — по
URL, а не по сайту: агрегаторы тендеров дают несколько найденных заказов
с одного домена. Каждая находка помечена источником (host площадки).

Прямого публичного API у госпорталов и площадок нет (SOAP-интеграция ЕИС требует
ЭЦП юрлица, выгрузки — FTP на сотни ГБ); поэтому воркер честно ищет только
публичную выдачу площадок и не парсит их HTML напрямую.

Сервис для зарегистрированных пользователей (находки привязываются к аккаунту).
Источники — только открытые; никаких «слитых» баз.

## Формы и перезагрузка (26.09.2026)

Владелец: «запустил радар, поискала, честно отработала, перезагрузила страницу —
создала ещё один запрос, и давай его ещё раз отрабатывать, и так далее по кругу».
Причина: ответ на POST оставался «страницей формы», и F5 повторяла отправку —
каждая перезагрузка создавала новый радар и новый сбор.

Правило модуля (и всех страниц с формами):

* любой POST завершается **редиректом на чистый GET** (303) либо JSON-ответом
  для AJAX-кнопки «Собрать» — страница на POST не рендерится;
* одинаковый запрос у того же пользователя (с учётом региона) — **не новый
  радар**: включаем существующий и запускаем сбор (`existing` в ответе сервиса);
* сообщения о результате — через **сессию** (`Session::instance()->get_once('nj605_flash')`),
  а не `?flash=` в адресе: ссылка короткая, и F5 сообщение не повторяет
  (старые ссылки с `?flash=` продолжают работать).

## Страница радара `/radar/<code>` (26.09.2026)

Владелец: «на новой странице „Радар создан — сбор уже идёт“, хотя он завершён;
и адрес в строке мне не нравится, не лаконичный. Может, с находками по запросу
другую страницу сделать? Чтобы было логичнее и лаконичнее».

* `/radar` — форма, «Мои радары» и общая лента; `/radar/<code>` — ОДИН запрос:
  живой статус-ряд сбора, итог последнего прогона и **его** находки;
* создание радара редиректит сразу на `/radar/<code>`: состояние показано
  фактически (ряд «идёт сбор» → «Готово»), а не текстом из URL, который переживал
  завершение сбора;
* «взял в работу» / «не интересно» работают и на странице радара
  (`/radar/<code>?item=N&st=taken`) — действия идемпотентные;
* общий скрипт обеих страниц — `views/605/js.php` (одна копия: AJAX-«Собрать»,
  двухклик-удаление, фильтр «новых N»);
* чужой радар отдаёт 404 (не подтверждаем существование чужих запросов).

## Админка

`/radar/admin` — все радары и находки (роль admin); просмотр, пауза, удаление.
