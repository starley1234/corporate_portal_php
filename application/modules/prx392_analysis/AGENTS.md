## Состояние

MVP: профиль `classify_extract_v1`, прогоны `prx_392_runs`, предложения
`prx_392_suggestions`, канал `doc.analyze`, проверка человеком и применение в
prx391. Модель — только `local::…`; проверка выполняется до очереди.

## Границы

Модуль читает текст через `Service_Prx390_Intake` и карточку через
`Service_Prx391_Documents`. Пишет только свои две таблицы. В карточку попадает
исключительно через `Service_Prx391_Documents::apply_analysis()` после явного
действия. Права не решает и ACL не обходит.

## Маршруты

- `/analysis` — очередь предложений и журнал прогонов.
- `POST /analysis/run/<document_id>` — постановка `doc.analyze`.
- `POST /analysis/accept/<suggestion_id>` — применить (можно с правками).
- `POST /analysis/reject/<suggestion_id>`.
- `GET /prx392/api/input/<run_id>`, `POST /prx392/api/result/<run_id>`,
  `/prx392/api/health` — API воркера.

## Права

Текущий `acl.php` ограничивает контур admin. Пользовательские queue/accept/reject
принимают `Prx_Actor`, требуют `prx392.run`; карточку проверяет prx391 по actor.
`reject` тоже проверяет видимость документа до записи статуса и reviewed_by.
Пустой actor не повышается до system. Worker input/result читают карточку через
явный `document_for_processing()`; это не HTTP-read API для пользователей.

## Структура сервиса

`Service_Prx392_Analysis` — публичный фасад. Чтение прогонов, предложений и
сводки вынесено в `Service_Prx392_Runs`; постановка задач и разбор ответа
модели остаются в `Analysis`. Runs читает только `prx_392_*`; заголовки
карточек получает одним batch-вызовом
`Service_Prx391_Documents::headers_for_processing($ids)` на порцию, без N+1.
Контракт возвращает только id/reg_no/subject по ID, не типы/текст/историю.
Он доверенный, без actor/ACL; текущие списки по-прежнему admin-only, не
объявлять их безопасными для произвольной ролевой выдачи.

Порядок порции — created_at DESC, id DESC, limit <= 0 — пусто.
Прогоны без карточки остаются с NULL reg_no/subject (бывший LEFT JOIN).
Предложения без карточки отбрасываются (бывший INNER JOIN), но уже после
ограничения порции: наличие сирот может дать меньше limit строк без добора.
Это намеренно ограниченный batch, не сквозная пагинация по всем живым карточкам.
Ошибки lookup не маскируются под заголовки/пустой успешный результат.

## Контракт предложения

```json
{"type":"claim","type_confidence":0.94,
 "fields":{"outbound_no":{"value":"118","quote":"…","confidence":0.9}},
 "summary":"…","risk":{"level":"high","reasons":["…"]},
 "findings":[{"kind":"deadline","text":"…"}]}
```

PHP нормализует значения: тип только из `prx_391_types` (иначе `other`),
дата — `Y-m-d`, ИНН — 10/12 цифр, сумма — число, срок — 1..365 дней.
Валидация схемы — на сайте, не в воркере.

## Очередь и надёжность

Payload: `run_id`, `document_id`, `profile`. `input_hash` дедуплицирует
одинаковый текст/модель/промпт: повторная кнопка не плодит прогоны. Задача
помечается доставленной после записи предложения. Ответ модели без полей и
summary отклоняется, прогон получает `failed`.

## Ограничения

`max_input_chars` (60000) обрезает гигантские тексты; цитаты ограничены
500 символами. Внешние провайдеры запрещены конфигом. Промпт-инъекция в
документе не может изменить права: результат — только данные, не команды.

## Проверки

`python3 -m pytest workers/tests/handlers/prx390_intake/test_docflow.py` (нормализация/парсер JSON),
`python3 .tools/portal_check.py`, `bash .tools/php_check_all.sh`.

Контракт типов/отказов — `tests/Contracts/docflow_access.php`; PostgreSQL-регрессия
скрытого предложения и reviewed_by — `DocflowAccessTest`. Это не проверка реального LLM.

`AnalysisHeadersIntegrationTest` проверяет минимальную batch-проекцию, свежесть
названий, порядок/лимит, дубли ID, отсутствующие карточки и форму списков.
`test_docflow_access.py` теперь проверяет SQL-владение во всех четырёх docflow-
модулях (classes/views), служебные чтения — по списку явных вызывающих сервисов,
views — без автоматизации, Task — с единственным разрешённым scan-вызовом.
Это лексический ratchet, не полноценный SQL/PHP-парсер и не граница безопасности.
