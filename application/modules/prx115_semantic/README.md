# prx115_semantic — эмбеддинги и семантический поиск

Единая точка платформы для векторов: коллекции, индексация через очередь
(`semantic.index`), KNN-поиск (`pgvector <=>` или `real[]` + `prx_115_vec_dist`
на vanilla PostgreSQL — режим выбирается автоматически).

## Быстрый старт

```php
Service_Prx115_Semantic::index_texts('demo', 'note', [
    ['id' => '1', 'text' => 'Покупка молока'],
    ['id' => '2', 'text' => 'Отчёт по бюджету'],
]);

// после обработки воркером:
$results = Service_Prx115_Semantic::search('demo', 'что купить?', 5);
```

Настройка эмбеддинг-сервера: `EMBEDDING_API_URL`, `EMBEDDING_API_KEY`,
`EMBEDDING_MODEL`, `EMBEDDING_DIMENSIONS` (см. `.env.example`).
Для локальной разработки без GPU: `make mock-embed` (workers/mock/).

## Панель /prx115 (для владельца)

Одна страница отвечает на вопрос «модуль работает?»:

- **метрики**: коллекции, векторы, задач за сутки, провалов;
- **источники индексации** — покрытие: сколько текстов ДОЛЖНО быть в индексе,
  сколько актуально, сколько отстало, сколько мусора, худшее покрытие в %;
- кнопки **«Догнать»** (поставить в очередь только изменившееся) и
  **«Убрать мусор»** (векторы исчезнувших записей);
- **приём векторов**: в http-режиме воркер отдаёт векторы на
  `POST /prx115/api/vectors` с токеном `WORKER_API_TOKEN`; точка объявлена в
  `$public_actions` контроллера — иначе общий шлюз входа отдаёт HTML-страницу
  403 ещё до проверки токена (разбор — в `AGENTS.md`, «Не трогать»);
- **проверка поиска**: живой запрос к эмбеддинг-серверу с пометкой, нашлось
  вектором или по словам;
- **живой статус** последней задачи канала и «Повторить» для провалившейся.

## Источники индексации (покрытие и догон)

`application/config/prx115.php` → `sources`: ключ → `title`, `collection`,
`entity`, `sql`. SQL обязан отдавать `id`, `content` (текст ровно такой же,
как уходит в `index_texts()`), `metadata`. Новый модуль подключается одной
записью в конфиге — код править не нужно.

Ключ «текст не менялся» — `content_hash` (md5): его считает и сайт, и воркер,
и PostgreSQL, поэтому повторная индексация пропускает актуальные тексты, а
покрытие считается одним SQL без выгрузки текстов в PHP.

## Поиск

- `search.max_distance` (косинусная дистанция, по умолчанию 0.6) — результаты
  дальше порога отбрасываются: без порога KNN «находил» что угодно.
- `search.hybrid` — если в пределах порога ничего нет, добавляются совпадения
  по тексту (ILIKE) с пометкой `match = 'text'`.
- `cache.*` — векторы поисковых запросов кэшируются в `prx_115_query_cache`
  (та же модель + запрос = без вызова эмбеддинг-сервера), чистятся по сроку и
  размеру, доступны в /prx100/cleanup.
- `GET /prx115/api/health` — состояние модуля одной структурой (движок,
  эмбеддинги, покрытие, проблемы); 503, если есть проблемы. Читается и по
  токену воркера, и администратором — годится для внешнего мониторинга.

## Журнал поисков

`GET /prx115/api/search` (и тестовый поиск на /prx115) пишет запрос в
`prx_115_searches`: что искали, сколько нашлось (смыслом или словами), был ли
ответ из кэша, сколько занял вызов и текст ошибки. Панель показывает последние
запросы и сводку за сутки («пустых», «ошибок», «из кэша», среднее время) —
по ней видно, ПОИСК РЕАЛЬНО НАХОДИТ, а не только «сколько векторов в базе».
Держим `searches.keep` последних записей (0 — журнал выключен); отсутствие
таблицы (миграция не применена) поиск не ломает.

## SQL
Таблицы `prx_115_collections`, `prx_115_vectors`, `prx_115_query_cache`,
`prx_115_searches`; функция
`prx_115_vec_dist` (косинусная дистанция для режима без pgvector). В docker-стеке
используется pgvector 0.8 с HNSW-индексом.
