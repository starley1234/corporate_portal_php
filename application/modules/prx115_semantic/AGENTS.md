## Назначение
Единое хранилище векторов платформы и KNN-поиск. Другие модули индексируют
свои сущности (`index_texts`) и ищут (`search`) — никаких своих таблиц
с эмбеддингами больше нигде.

## Состояние
- Готовность: рабочий (миграции 001–003, сервис, API, python-обработчик
  `semantic.index`, панель `/prx115`).
- Проверено на стендах: запись векторов (pg-режим и мост через сайт),
  KNN-поиск, порог/гибрид/кэш запросов, покрытие источников, догон и уборка
  мусора, журнал поисков — 91 проверка на реальном коде и конфиге
  (`.tools/prx115_stand.php`), 43 проверки точек API
  (`.tools/prx115_api_stand.php`), 31 проверка страницы `/prx115`
  (`.tools/prx115_view_stand.php` — вид рендерится без PHP-warning) и тот же
  SQL на живом PostgreSQL (`.tools/prx115_pg_stand.py`).

## Как пользоваться другим модулям
```php
// проиндексировать (асинхронно, очередь):
Service_Prx115_Semantic::index_texts('prx401_tasks', 'prx401_task', [
    ['id' => '12', 'text' => 'Заголовок + текст задачи', 'metadata' => ['status' => 'new']],
]);

// при удалении сущности:
Service_Prx115_Semantic::delete_entity('prx401_tasks', 'prx401_task', ['12']);

// найти (синхронно, уместно в запросе):
$results = Service_Prx115_Semantic::search('prx401_tasks', 'задачи по бюджету', 10);
// $results[i]['entity_id'], ['content'], ['distance'] (меньше = ближе), ['match']
// match = 'vector' — семантика; 'text' — векторный порог не прошёл, совпадение по словам
```

**Повторная индексация ничего не пересчитывает зря**: `queue_index()` (и
совместимый `index_texts()`) сравнивает md5 текста с `prx_115_vectors.content_hash`
и пропускает неизменившиеся тексты. `['force' => TRUE]` — пересчитать всё.

## Покрытие, догон и уборка мусора
Источники индексации живут в `application/config/prx115.php` → `sources`:
ключ → `title`, `collection`, `entity`, `sql` (SQL отдаёт `id`, `content`,
`metadata`). По этому реестру:

- `coverage()` — «сколько текстов ДОЛЖНО быть в векторах»: всего, с вектором,
  с актуальным хешем, без вектора, устаревших, мусорных (вектор есть, записи
  нет). Недоступный источник — строка с `error` и `coverage = NULL`, а НЕ «100 %»;
- `reindex($collection, $limit, $opts)` — кнопка «Догнать»: ставит в очередь
  только отсутствующие/устаревшие тексты (одна задача на пачку `batch_size`);
- `prune($collection, $older_days = 7)` — «Убрать мусор»: удаляет векторы
  исчезнувших записей; предохранитель — не трогаем векторы, обновлявшиеся
  последние N дней.

Правило для нового модуля: текст в `sql` источника обязан совпадать с тем,
что уходит в `index_texts()` (иначе хеш не сойдётся и покрытие будет вечно
неполным), а источник обязан перечислять все свои записи — без фильтров и LIMIT.

## Таблицы
- `prx_115_collections` — коллекции (name unique, модель, размерность).
- `prx_115_vectors` — векторы; UNIQUE (collection_id, entity, entity_id);
  embedding: `vector` (pgvector + HNSW) ИЛИ `real[]` + функция `prx_115_vec_dist`
  (vanilla PostgreSQL). Тип определяется автоматически, код един.
  `content_hash` (md5 текста, миграция 002) — ключ «текст не менялся».
- `prx_115_query_cache` — кэш векторов поисковых запросов: `qhash` = md5(модель +
  текст запроса), vector jsonb, hits, used_at. Чистится сам (30 дней / 500 строк)
  и доступен в /prx100/cleanup. Кэш — ускоритель: его отсутствие не ломает поиск.
- `prx_115_searches` — журнал поисков (миграция 003): коллекция, запрос, сколько
  нашлось и чем (`vector_hits`/`text_hits`), `cached`, `ms`, `error`, автор,
  время. Пишется из `Service_Prx115_Semantic::log_search()`, подрезается сам до
  `searches.keep` (по умолчанию 200); читается панелью (`recent_searches()`,
  `search_stats()`). Журнал вспомогательный: его отсутствие не ломает поиск.

## Очередь
- Канал `semantic.index` (payload: collection, entity, items[≤batch_size]).
- Два режима, оба доводят работу до конца: **pg** (у воркера есть база —
  пишет векторы сам) и **http-bridge** (базы нет — считает векторы и отправляет
  пачками по 50 в `POST /prx115/api/vectors` с токеном воркера). Тихий
  `{"skipped": "http-mode"}` — убран, это была потеря данных.
- Этапы видны в `/prx120/monitor` и `/prx120/task/<id>`: «Проверяю коллекцию» →
  «Считаю векторы» (тик 20 с, лимит `PRX115_EMBED_TIMEOUT` = 180 с) →
  «Записываю векторы i/N» → «Готово: N векторов».
- «Выполняется, пульс N мин» — это НЕ про семантику: строка осталась
  processing, а пульс не идёт (процесс воркера умер или задача осиротела при
  рестарте). Закрывают её: python-воркер (`release_own_orphans` при старте,
  фоновый `PgQueue.sweep_stale_standalone`) и сайтовый
  `Service_Prx120_JobQueue::requeue_stale` из `portal:maintain` по таймеру.
  Открытие страницы и опрос статуса больше не запускают уборку.
- Пульс задачи — `coalesce(heartbeat_at, claimed_at, started_at, created_at)`:
  так его считают и правила уборки, и монитор. Предельный возраст задачи —
  `GREATEST(timeout_sec * 3, PRX_JOB_MAX_AGE_SEC=3600)` секунд.
- Диагноз по конкретной задаче — `/prx120/task/<id>`, блок «Что с задачей».

## Не трогать / подводные камни
- Поиск синхронный: Llm::get_embedding + один SQL. Массовый перегенерант
  индексов — только через очередь; «Догнать» тоже только ставит задачи.
- Литералы векторов: только через `_vector_literal()` (floats `%.7F`,
  независимы от локали).
- Если окружение сменилось с vanilla PG на pgvector ПОСЛЕ применения
  миграции — таблица останется real[]: нужен ручной ALTER (или `make fresh`).
- Хеш текста — md5: он есть в PHP (`md5`), python (`hashlib.md5`) и в самом
  PostgreSQL (`md5(text)`), поэтому свежесть считается прямо в SQL. Это ключ
  кэша/пропуска, а не защита: коллизии здесь безобидны.
- **Точки воркера обязаны быть в `$public_actions`.** `Controller_Base::before()`
  для неавторизованного бросает `HTTP_Exception_403` и отдаёт HTML-страницу
  «Access Denied» — до собственной проверки токена дело не доходит. Именно на
  этом 23.10.2026 упала задача 2234: «HTTP 403: сервер вернул HTML вместо JSON».
  Сейчас `protected $public_actions = ['vectors', 'health']`; личность внутри
  проверяют `_authorize_worker()` (векторы) и двухпутевой health. Добавляя новую
  точку для воркера, сначала допишите её в этот список, иначе получите тот же
  HTML 403 при верном токене (`tests`-стенд `.tools/prx115_api_stand.php`
  воспроизводит проверку входа и ловит регресс).

## Граница HTTP (23.11.2026)

Пустой worker-секрет закрывает API даже в development. Только `vectors` объявляет машинный POST через `machine_request()` и обязательно проверяет worker-токен в before(). Остальные POST, включая административный AJAX, требуют CSRF независимо от заголовков.

## Чтение очереди через владельца (23.11.2026)

Прямой SQL этого модуля к `prx_120_*` удалён. Публичные методы
`Service_Prx120_JobQueue` используют настроенное соединение очереди и только
читают данные; диагностический fallback остаётся у экрана. Исключения этого
модуля удалены из `test_queue_table_debt.py`, возвращать SQL-зависимость нельзя.
Контракты/пороги/ограничения — `docs/WORKERS.md`, PostgreSQL-регрессии —
`QueueReportsIntegrationTest`. Наличие административного метода не заменяет ACL
страницы; общий пользовательский read API здесь не добавлен.
Панель использует channel_metrics('semantic.index') вместо трёх прямых
агрегатов. Даты/статусы/legacy bridge-маркеры сохранены, payload не возвращается
новым методом; список channel_jobs остаётся отдельным существующим контрактом.
