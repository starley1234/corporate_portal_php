## Назначение
Единая очередь фоновых задач монолита: PHP ставит задачи (`push`), python-воркеры
из `workers/` выполняют (LLM, эмбеддинги, файлы). Таблица PostgreSQL, а не
отдельный брокер — атомарность с бизнес-данными и ноль лишней инфраструктуры.

## Состояние
- Готовность: **рабочий** (миграция, сервис, HTTP-API, minion-задача).
- Python-сторона: `workers/prx_workers/` (queue.py, base.py, handlers/).

## Ключевые классы
| Класс | Роль |
|---|---|
| `Service_Prx120_JobQueue` | ВЕСЬ доступ к очереди из PHP. `push/claim/heartbeat/complete/fail/cancel/get/stats/requeue_stale` |
| `Controller_Prx120_Api` | HTTP-API `/prx120/api/*` для воркеров на чужом сервере (токен `WORKER_API_TOKEN`, заголовок `X-Worker-Token`) |
| `Model_Prx120_Job` | ORM-модель `prx_120_jobs` (jsonb-поля — строками) |
| `Task_Prx120_RequeueStale` | cron: вернуть в pending задачи без heartbeat дольше timeout |

## Таблицы (полное владение)
- `prx_120_jobs` — задачи. Статусы: `pending → processing → done|failed|cancelled`.
  Ключевые поля: `channel`, `payload` jsonb, `result` jsonb, `priority` (меньше =
  раньше), `attempts/max_attempts`, `available_at` (отложка/backoff),
  `heartbeat_at` (живость воркера), `callback_url`.
- `prx_120_job_events` — журнал: created/claimed/heartbeat/done/failed/cancelled.
- `prx_120_usage` — учёт токенов/моделей по задаче. С миграции 005 (25.10.2026)
  **без каскада от `prx_120_jobs`**: уборка монитора и правило 60 дней не стирают
  историю (раньше `/graph3d/usage` показывал только последние задачи).
  Колонки `payload_brief` (скалярный срез payload: prompt, project_id…) и `status`
  — чтобы отчёт читался без задачи. Своя чистка `prx120_usage`, 400 дней.

- `prx_120_budgets`, `prx_120_budget_alerts` (миграция 006, 25.10.2026) — бюджеты
  токенов: индивидуальные лимиты день/месяц на `visitor_id` (0 — по роли,
  −1 — безлимит) и отметки «уже предупредили» (владелец × период × порог).

## Бюджеты токенов (prx120/006)
- `Service_Prx120_Budget`: `limits()` (роль из `config/prx120_budget.php` →
  индивидуальная строка сильнее), `spent()`/`state()` по `prx_120_usage` за
  календарные день и месяц, `check()`, `after_usage()` (90 %/100 % →
  колокольчик prx597 `system`, один раз на период), `save()`, `overrides()`,
  `top_today()`.
- `JobQueue::push()` с `visitor_id` при исчерпанном бюджете бросает
  `Prx120_Budget_Exception` (код 429, текст для человека). Отключить проверку
  вызову — `'budget' => FALSE`; глобально — `PRX120_BUDGET_ENFORCE=0` (учёт и
  предупреждения остаются). Служебные задачи без `visitor_id` не считаются.
- Страницы: `/prx120/budgets` (админ, `prx120.usage.admin`) — умолчания, форма,
  «кто ближе к потолку», выданные; `/tasks` и центр контроля prx600 показывают
  карточку `120/_budget` (доля числом и точками, полос нет).
- Умолчания: anon 30 тыс./день, login 150 тыс., vip 600 тыс., admin ∞; месяц
  ×10–20. Меняются env `PRX120_BUDGET_DAILY_<ROLE>` / `..._MONTHLY_<ROLE>`.
- Служебные ключи `s:<модуль>` (`s:prx602` — контент, `s:prx600`) — роль
  `system`, по умолчанию ∞ (`PRX120_BUDGET_DAILY_SYSTEM`). 25.10.2026 они
  считались `anon` и /content встал на 30 тыс. молча — отказ был только в
  логе. Теперь `create_draft/retry` при отказе очереди переводят статью в
  `error` с причиной, а /prx602/admin показывает карточку бюджета `s:prx602`
  со ссылкой «Изменить лимит» (`/prx120/budgets?key=s:prx602`).

## Порог авто-остановки «воркер молчит»
- Общий: env `PRX_SILENT_STOP_SEC` (по умолчанию 240 с) — пульс идёт каждые
  30 с, молчание дольше нескольких минут = мёртвый воркер.
- Поканальный (06.10.2026): config `prx120_jobs.silent_stop_channels`
  (канал => секунды); эффективный порог = max(общий, канал). Понадобилось
  для prx661.airadar — конвейер с локальной LLM, генерация занимает минуты,
  общий порог снимал живую задачу. Одиночная задача (`auto_stop_silent($id)`)
  сначала узнаёт свой канал и останавливается её порогом.
- Проверяет `.tools/prx120_silent_stand.php` (резолюция порогов, разбор
  свипа на проходы, минуты в причине).

## Нюансы / не трогать
- SQL для pg собирается PHP-склейкой ВНЕ строки: `error = ".$this->_db->quote($msg)."`
  — точка-склейка ВНУТРИ двойной кавычки уезжает в PostgreSQL как текст и
  роняет запрос «ошибка синтаксиса (".")» (release_mine, 06.10.2026; ловит
  стенд prx120_silent_stand).
- Драйвер PostgreSQL возвращает для UPDATE — число строк, для INSERT — массив;
  поэтому все RETURNING-запросы выполняются с типом `Database::SELECT` (см.
  комментарий в коде). Не «исправляйте» это, не понимая драйвер
  `application/modules/PostgreSQL/`.
- Параметры в SQL не биндятся (pg_query без prepare) — только `$db->quote()`.
- `claim()` использует `FOR UPDATE SKIP LOCKED` — не убирать, иначе задачи
  будут дублироваться между воркерами.
- Backoff при retry: `15 * attempts²` секунд.

## Контракт «результат доставлен ⇒ Готово» (26.09.2026)

Монитор показывал «Ошибка» у задач, чьи артефакты уже лежали на сайте
(статьи/досье/карты/отчёты). Причина: приёмка не закрывала строку очереди, а
свипер отказывал задачи по таймауту пульса РАНЬШЕ, чем возвращал в очередь.

Правила, обязательные для всех модулей с очередью:

1. **Приёмка артефакта закрывает задачу** — сразу после того, как результат
   записан в БД сайта:
   ```php
   Service_Prx120_JobQueue::instance()->mark_delivered($job_id, 'что принято');
   ```
   Идемпотентно: processing/pending/свежий failed → done; cancelled не
   воскрешает. НЕ использовать `complete()` из приёмки: он требует
   `claimed_by = <воркер>` и не оживляет failed.
2. **Нет колонки `job_id`** — задача находится по payload:
   `find_for_delivery('канал', 'watch_id', $id)` (пустой ключ = только по каналу).
3. **Новый канал ⇒ строка в `reconcile_hooks`** (`config/prx120_jobs.php`):
   SQL-условие «артефакт виден». Оно же через `reconcile_outcomes()` оживляет
   failed за 24 ч, если результат доехал после отказа свипера.
4. Порог отказа в `requeue_stale()` = порог возврата = `GREATEST(timeout*2, 900)`;
   строки с `attempts >= max_attempts` в pending не возвращаются (claim их не
   берёт — был вечный «Ожидает»).
5. Воркер держит пульс до конца дожима задач при остановке (`base.run`:
   `_drain()` → отмена heartbeat) — не менять порядок.

## Почему строка висела в «Выполняется» вечно (28.09.2026)

Владелец: «Почему монитор воркеров ВСЕГДА показывает зависший процесс?» (пример —
`/prx120/task/969`, `semantic.index`, попытки 3/3, «Выполняется»). Причин было три,
и все три устранены:

1. **Авто-стоп молчащих задач не работал вообще.** `auto_stop_silent()` и
   `auto_stop_stalled()` собирали SQL внутри двойной кавычки:
   `"… error = 'молчит '.max(1, (int) round($floor / 60)).' мин …'"` — в
   PostgreSQL уходил этот PHP-код, запрос падал с синтаксической ошибкой, а
   `catch (Throwable $e)` глушил её в лог. Обещание «нет пульса 4 мин — гасим»
   не наступало никогда. Теперь минуты считает PHP и подставляет ЧИСЛО; за этим
   следит `.tools/php_sql_lint.py` (шаг `php_check_all.sh`).
2. **Правила смотрели на голый `heartbeat_at`.** Если он NULL (монитор такие
   строки и считает «застрявшими»), сравнение `NULL < now() - …` даёт NULL — ни
   одно правило не срабатывало. Теперь и в PHP (`_pulse_sql()`), и в python
   (`queue.py: PULSE_SQL`) пульс — одно выражение:
   `coalesce(heartbeat_at, claimed_at, started_at, created_at)`
   (у pending — `coalesce(available_at, created_at)`).
3. **Не было предела возраста.** Живой пульс (фоновая петля воркера) при
   зацикленном обработчике означал «Выполняется» навсегда. Правило
   «предельный возраст»: `GREATEST(timeout_sec * 3, PRX_JOB_MAX_AGE_SEC)`
   (по умолчанию 3600 с, `0` — выключить) по
   `coalesce(started_at, claimed_at, created_at)` → `cancelled`.

Плюс два усиления:

* **Уборка без крона** — `maybe_maintain()` в `Prx100_Base::before()`: дешёвый
  `COUNT` зависших на любом заходе на сайт; если они есть — advisory-lock
  `pg_try_advisory_lock(120120)` и `requeue_stale()` (ровно один запрос из
  десятка). Раньше уборка висела только на кроне prx603 и открытии
  `/prx120/monitor`.
* **Правило в своём try/catch** — `_rule()`: падение одного правила пишется
  в лог и не отключает остальные (раньше исключение в середине оставляло
  разбор незавершённым).

Как проверять правила очереди, не дожидаясь живого зависания:

* `.tools/php_check_all.sh application` — в том числе `php_sql_lint` (PHP-код в
  тексте SQL);
* `.tools/prx120_monitor_stand.php` (phpwasm) — гоняет НАСТОЯЩИЙ
  `Service_Prx120_JobQueue` на записывающей «базе»: `monitor_health`,
  `monitor_jobs`, `channel_jobs`, `diagnose`, `events` (16 проверок) и
  выгружает собранный SQL в `/tmp/prx120_sql.json`;
* `.tools/prx120_monitor_pg_stand.py` — берёт этот SQL и исполняет на живом
  PostgreSQL (схема — прямо из миграций 001/002/004): монитор обязан
  открываться, этап задачи приходит с временем, а старый (сломанный) вариант
  запроса база обязана отвергнуть;
* `workers/tests/test_queue_sweep_pulse.py` — контракт правил python-свипера
  (5 тестов, есть функциональный прогон на живом PG через `PRX_TEST_PG_DSN`).

Монитор теперь считает «застряли» тем же выражением, что и уборка
(`silent_now` = пульс молчит дольше `PRX_SILENT_STOP_SEC` (240 с),
`stalled_now` = прогресс стоит дольше `PRX_STALLED_PROGRESS_SEC` (600 с),
`stuck` = их объединение), а в карточке задачи `/prx120/task/<id>` появился
блок «Что с задачей»: возраст пульса и последнего рапорта, ближайшее правило и
через сколько секунд оно сработает.

## Почему падал `/prx120/monitor` (28–29.09.2026)

Страница монитора отдавала 500:

```
Database_Exception [ 0 ]: ОШИБКА: столбец ev.created_at не существует
application/modules/prx120_jobs/classes/Service/Prx120/JobQueue.php:886
```

Причина — не схема и не миграция, а РАСХОЖДЕНИЕ ВНУТРИ ОДНОГО ЗАПРОСА.
В `monitor_health()` «чем занят воркер сейчас» собиралось через
`LEFT JOIN LATERAL (… ev)`: подзапрос выбирал только `e.message`, а внешний
SELECT читал ещё и `ev.created_at AS stage_at`. PostgreSQL такой запрос
отвергает целиком — и падал весь монитор, хотя остальные девять запросов
страницы были исправны.

Для линтеров это НЕ ошибка: SQL синтаксически верен, `e.created_at` в таблице
`prx_120_job_events` есть, PHP-код в строке отсутствует. Такую ошибку видит
только сама база — поэтому проверять надо исполнением.

Правило: **любой SELECT с псевдонимом-подзапросом (`LATERAL`, `ev`/`u`/`j`)
проверяется на живом PostgreSQL.** Стенды для этого:
`.tools/prx120_monitor_stand.php` (собирает SQL настоящим сервисом) →
`.tools/prx120_monitor_pg_stand.py` (исполняет на живом PG, схема — из
миграций; есть контроль: «запрос без `created_at` обязан упасть»).

Тот же шаблон у `monitor_jobs()` и в `Controller_Prx120_Tasks::action_index()`
(там `created_at` в подзапросе был) — при правке одного места сверяйте все три.
