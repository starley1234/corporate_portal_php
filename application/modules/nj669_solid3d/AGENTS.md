# nj669_solid3d — памятка

## Состояние

Новый самостоятельный сервис `/solid3d` «3D-детали». Одна деталь на проект,
LLM → встроенный OpenSCAD; VLM только описывает фото (один раз); 0–2 починки
ошибок сборки; проверка ракурсов VLM — отдельная задача `nj669.verify`,
запускается только администратором.
GLB/STL/SCAD и три PNG, числовые параметры, именованные контрольные точки,
история с пагинацией, откат, шаблон из опубликованного, каталог,
модерация с закреплённой версией и карточкой, отмена/этапы/пульс очереди,
карточка каталога, которую после первой удачной сборки подбирает дешёвая модель
(владелец полей не получает; администратор перегенерирует), копилка тематических идей
модератору; настройки, квоты и уведомления. Сквозная production-проверка
ещё не подтверждена; эксплуатационные ошибки исправляются по сообщениям владельца.

## Карта

* `Controller_Nj669_Solid3d`: страницы, собственные POST с CSRF, выдача файлов.
* `Service_Nj669_Solid3d`: только nj_669_solid3d_*; транзакции, advisory per-user и
  блокировка проекта; квоты, ревизии, модерация, приёмная воркера.
* `Service_Nj669_Workspace`: metadata-снимки, checkpoint, live/cancel, notify.
* `Service_Nj669_Parameters`: только размеченные литералы заголовка четырёх типов
  (`@param` число, `@bool`, `@choice` число из списка, `@text` строка до 40 знаков),
  `normalize` проверяет значения, `apply` меняет только позиции литералов исходника,
  `restore` берёт значения из JSON версии; никакого исполнения SCAD в PHP.
  Значения ползунков живут в `params` версии (миграция 004).
  Пересборка размеров — `code_only` той же ревизии: `pending_source`/`pending_params`,
  `repairs=0`, без LLM и VLM; `source`/`files`/`params` меняются только при успехе.
  Модели, SCAD, `build_log` и блок `#solid-check` выводятся только модератору.
* `Service_Nj669_Assist`: tasks/ideas, квоты/снимки/terminal/дедлайн помощников.
* `Controller_Nj669_Solid3dWorker extends Controller_Nj120_Api`: строгий заголовок
  WORKER_API_TOKEN, нет development-обхода; `context/upload/result/fail`, `assist_context/result/fail`.
* Приёмная — только Controller_Nj669_Solid3dWorker, маршруты nj669_solid3d_*.
  Общие имена Controller_Nj669_Worker/nj669_worker могут быть заняты старым
  NJ669. Не возвращать их: CFS подхватит чужой класс. Путь /solid3d/w не меняется.
* Только `nj_669_solid3d_*`, не короткие имена: реальная `nj_669_revisions`
  принадлежит истории сцен (`spot_id/scene_json/author_id`), не трогать её.
* `000_Solid3dNamespace` идёт ПЕРЕД 001: распознаёт раннюю установку деталей
  по полной схеме projects/revisions и переименовывает только её таблицы.
  При конфликте обеих баз/неоднозначности — остановка без удаления/слияния.
* `001` — projects/revisions/events/settings/quotas; `002` — metadata, labels,
  tasks/ideas. Исправление инцидента заменило в них только имена объектов;
  расширение схемы дальше — новыми миграциями. Уже применённые 001/002 не
  сбрасывать: перенос делает 000. Её down пустой, остальные down только
  в `nj_669_solid3d_*`. DO-блок передаётся одним run_query, НЕ run_script.
* `workers/n2j_workers/handlers/nj669_solid3d.py`: каналы nj669.generate и nj669.verify.
* `workers/n2j_workers/handlers/nj669_assist.py`: nj669.ideas/caption.
* `workers/n2j_workers/solid.py`: встроенный SCAD без include/use/import/surface,
  headless через scad._run, STL→GLB через общий glb.py, три PNG ракурса.
* `public_html/assets/js/nj669-solid3d.js`: формы/двухшаговое удаление/поллинг.
* Общий viewer `nj667-stl.js` получает DOM-контракт в собственной nj669/project
  с пустым data-status; очереди/таблицы/view Graph3D не подключать.

## Инварианты

* `current_revision_id` только после удачной приёмки; ошибка не затирает модель.
* `published_revision_id` закреплён: незавершённая/приватная правка не публична.
* `review_revision_id` и `review_meta` закреплены при submit, модератор
  утверждает именно их. Публичные страницы/поиск/remix читают published_meta,
  не рабочие title/summary/tags. Ответ помощника карточки пишет только draft.
* Файлы вне public_html, выдача проверяет ID версии; фотоданные не в очереди.
* У worker callback два токена, terminal/error/deleted не воскресить.
* Таймауты сборки/помощников — asyncio.wait_for (сборка 1650, помощники 480, проверка ракурсов 540 секунд; задача очереди verify — 600), как в
  BaseWorker. Не использовать asyncio.timeout: на действующем воркере этого
  API нет. Регрессия test_nj669_timeout.py исполняет все 3 канала с удалённым
  атрибутом timeout, проверяет отмену, callback ошибки и сохранение usage.
* Проверка ракурсов (`nj669.verify`): `queue_verify` требует флаг модератора
  (второй рубеж после контроллера), квоту не списывает, текущую версию не меняет.
  Токен — `vlm_run_token` версии; повторная приёмка закрытой проверки идемпотентна.
  Вердикт пишет только `vlm_status/visual_ok/review/vlm_checked_at`.
* Название необязательно: `title_for()` берёт начало описания. Карточку владелец
  не редактирует: её пишет помощник `caption` (авто после первой удачной сборки,
  квота владельца); перегенерирует только администратор (квота администратора).
  `Service_Nj669_Workspace::edit` — служебная правка, в HTTP не выставлена.
* Автозаполнение браузера выключено на всех полях и формах модуля
  (`autocomplete="off"` + `data-n2j-no-remember`). Стенд проверяет каждое поле.
* Новая задача — снимок parent/model/vision/repairs, max_attempts=1; ресурсные
  вызовы используют общий LlmClient и BaseWorker usage.py.
* Регистрация достаточна и для ИИ-правок. Различие с ACL nj667 намеренное.
* NULL-квота наследуется, 0 запрещает. Начальные поля — effective user limits.
* Квота считает только запуски с LLM за день: ревизии с `llm_run=TRUE` (миграция 005)
  и tasks caption/ideas (ideas модератора тратят квоту модератора). Пересборка размеров
  (`code_only`) и ручной пересчёт кода квоту не тратят. Оба enqueue используют advisory 669 по uid.
* Отмена/терминальная очередь закрывают приёмную, чистят staging, current
  остаётся прежним. Только публичные JobQueue status_of/cancel, не SQL чужой БД.
* Уведомления build.done/error — после commit, идемпотентные callbacks,
  ошибки центра уведомлений не ломают модель.
* Временная выгрузка (`nj669.export`): таблица `nj_669_solid3d_exports` (миграция 006),
  `expires_at` = финиш + 1 час. Постановка требует `uid > 0`, право чтения версии и
  готовую версию (`done`); одна активная выгрузка на пользователя и проект. Квоту,
  LLM/VLM, версию, `current`, каталог и историю не трогает. Таймауты: задача 900,
  бюджет 840 сек. Зависшие (`queued|running` старше 20 минут) переводятся в `error`.
  Reconcile в nj_module.php смотрит `status IN ('done','error')`.
* Удаление не возвращает дневную квоту; история живого проекта хранится
  бессрочно, удалённые проекты/версии и завершённые tasks чистятся реестром после 180 дней.
  Идеи сохраняются отдельно (task FK SET NULL), редактируются модератором.
* Сервис в каталоге через manifest, pin не добавлять.

## Проверка

Команды и эксплуатационные ограничения — README. PHP-стенд использует реальные
классы, контроллеры, роуты и views; БД/очередь/сессия подменены. Python-тесты
проверяют pipeline с AI/движком-заглушками, JS — формы/поллинг и viewer-контракт.
`.tools/nj669_worker_route_stand.php` исполняет реальные Route → Internal Client
→ автозагрузку → NJ120 API → action, даже при чужом Controller_Nj669_Worker;
проверяет 403 JSON без токена, 200 с токеном и 405 на GET для всех 7 действий.
PGlite также воспроизводит чужую таблицу сцен, rollback старого сбоя,
новый up×2/down/up без её изменения и перенос ранних 001/002 с данными/FK/ID.
Для production обязательна отдельная дымовая проверка настоящего OpenSCAD/Xvfb
и vision-провайдера; тесты не означают, что production обновлён.
