# Система Событий (prx208_events)

## Описание

Модуль `Система Событий` (`prx208_events`) — это центральное связующее звено (Event Bus) PRX-системы. Он реализует паттерн "Издатель-Подписчик" (Pub/Sub), обеспечивая слабую связанность (Loose Coupling) между модулями.

**Зачем это нужно:**
Модуль "Задачи" не должен знать о существовании модуля "Уведомления" или "Бонусы". Он просто объявляет: *"Задача №10 завершена"*. Все остальные модули, кому это интересно, подписываются на это событие и реагируют самостоятельно.

## Основные возможности

*   **Централизованная шина (EventBus):** Единая точка входа для всех событий системы.
*   **Гибкая подписка:** Подписка через код (`init.php`), через базу данных или через API.
*   **Автоматическое проксирование:** мост в центр уведомлений (prx597) на уровне ядра шины — включается конфигом.
*   **Логирование и аудит:** Сохранение истории всех событий в БД (`prx_208_events`) для последующего анализа.
*   **Умная фильтрация уведомлений:** Автоматическое исключение инициатора события из списка получателей уведомлений (чтобы не получать уведомления о собственных действиях).
*   **REST API:** Интерфейс для публикации и мониторинга событий внешними системами.

## Настройка

Конфигурация находится в `application/config/prx208_events.php`. Журнал
событий в БД включён, файловый лог шины и wildcard-мост в prx597 выключены.
Загрузка DB-подписок также **выключена по умолчанию**: активная строка в БД
сама по себе не означает, что обработчик запускается. Кодовые `Event::listen`
работают независимо от этой настройки.

`PRX208_DB_SUBSCRIBERS_ENABLED=1` допускается только после инвентаризации и
проверки исторических callback/уведомлений на staging: иначе возможно повторное
уведомление или выполнение старой логики. Порядок проверки и ограничения —
в [ENVIRONMENT.md](../../../docs/ENVIRONMENT.md#существующие-db-подписки-и-сроки-документов).

## Использование

### 1. Публикация события

Используйте `Service_Prx208_EventBus` для отправки данных в шину:

```php
$payload = [
    'task_id' => 123,
    'status'  => 'closed',
    'target_user_ids' => [45, 46, 47], // Массив получателей для уведомлений
];

// Публикация (третий параметр - ID текущего пользователя/инициатора)
Service_Prx208_EventBus::instance()->publish('prx502.task_done', $payload, $current_user_id);
```

### 2. Подписка на событие

#### Способ А: Через код (статическая регистрация)
Обычно делается в `init.php` вашего модуля:

```php
Service_Prx208_EventBus::instance()->listen('prx502.task_done', function($payload, $event_name, $initiator_id) {
    // Ваша логика
});
```

#### Способ Б: Через БД (динамическая регистрация)
После аудита и разрешения загрузки DB-подписок оператором в интерфейсе модуля
(`/prx208_events/list_subscribers`) можно создать запись:
*   **Event Name:** `prx502.task_done`
*   **Callback Method:** `Model_ClassName::method_name`
*   **Is Active:** Да

Изменения подхватываются при следующей инициализации шины. Переключение флага
не проигрывает пропущенные события.

### 3. Интеграция с Центром Уведомлений (prx597)

Мост `is_notification` в активной DB-подписке передаёт событие в `prx597`
только при разрешённой загрузке DB-подписок. Независимый wildcard-мост
`proxy_to_notification_center` по умолчанию выключен; не включайте оба пути
для одного события без устранения дублей. Для новых интеграций предпочтителен
явный `Service_Prx597_Notify::emit()` с объявлением события в манифесте.

**Особенности DB-моста:**
*   `target_user_id` (int) — одиночный получатель.
*   `target_user_ids` (array) — список получателей; дубли и недопустимые ID отбрасываются.
*   Поля данных `user_id`, `user_ids`, `recipients`, `channels` и `force_self`
    не добавляют адресатов и не обходят настройки события. Для шаблона их можно
    передать внутри `data`. Роли, каналы и индивидуальные подписки проверяет prx597.
*   **Исключение инициатора:** получатель, переданный как `initiator_id` при публикации, не уведомляется.
*   **Принудительная отправка:** `'force_notification' => true` разрешает уведомить инициатора; остальные ограничения prx597 сохраняются.

Мост не проверяет доступ получателя к конкретному документу: это обязанность
модуля-источника. Повторы независимых прямых вызовов и sweep не дедуплицируются.

## API Интерфейс

API использует авторизованную сессию и права конкретного действия; токен для
внешних систем здесь не реализован. Изменяющие запросы требуют POST и поле
`csrf` из сессии. Это изменение контракта для прежних клиентов без CSRF.

*   `POST /prx208_events/api/publish_event` — опубликовать событие с JSON в `payload`.
    `event_id` в ответе равен `null`: шина не возвращает ID; ответ не подтверждает
    успешное выполнение слушателей или доставку уведомлений.
*   `GET /prx208_events/api/get_events` — получить список последних событий.
*   `POST /prx208_events/api/subscribe` — создать новую подписку.
*   `POST /prx208_events/api/unsubscribe` — удалить или деактивировать подписку.

## Структура таблиц

*   `prx_208_events`: Журнал всех произошедших событий.
*   `prx_208_event_subscribers`: Реестр подписчиков и правил проксирования.

## Безопасность и права доступа

*   `prx208_events.list_events` — Просмотр лога событий.
*   `prx208_events.manage_subscriptions` — Управление подписчиками.
*   `prx208_events.publish_event` — Право на ручную публикацию событий.
