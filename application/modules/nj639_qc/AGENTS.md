## Состояние
- **Ручной режим**: фото изделия + эталоны + правило (текст + варианты вердикта)
  + выходная JSON-схема → прогон в очередь nj120 (канал `nj639.analyze`).
- **Авторежим** — источники кадров: IP-камера (Snapshot URL / RTSP / ONVIF),
  FTP / Hot-Folder, HTTP-объект, локальная папка (агент), очередь сообщений
  (Kafka / RabbitMQ / MQTT). Триггеры: `timer` (опрос N сек), `webhook`
  (датчик/ПЛК по секретному URL), `motion` (задел под edge-CV).
- **Воркер** `workers/n2j_workers/handlers/nj639_qc.py`: захват кадра →
  подготовка общим `vlm.prepare_b64` (1400 px, JPEG — как /label, /meal,
  /plant) → VLM (`NJ639_VISION_MODEL` → общая `VLM_MODEL`) с эталонами/
  правилом/схемой → валидация JSON-схемой → запись результата в `nj_639_runs`
  (pg-режим напрямую) + POST `/qc/api/worker_result` (X-Worker-Token).
- **Пресеты на странице** (`views/639/index.php`): пять готовых наборов
  «правило + варианты вердикта + JSON-схема» и две демо-кнопки, которые
  подставляют снимки из `public_html/assets/demo/nj639/` — сервис проверяется
  без своих файлов и без камеры. Там же «Демо-источник»: HTTP-источник на
  кадр этого же сайта для проверки авторежима.
- **08.10.2026 — замок «только по аккаунту»** (решение владельца): сервис работает по
  бесплатному аккаунту. Гость вместо рабочей формы видит плашку входа — общий partial
  `application/views/partials/auth_wall.php` через `Gate::wall('qc')`
  (`application/classes/Gate.php`); API отдаёт 401 JSON
  `{ok:false,error:'auth',login:'/auth/login?return_url=qc'}`
  (`application/classes/HTTP/Exception/401.php`). Воркерские точки (`worker-result`,
  `worker-upload`, `photo_file`, `cron-poll`, `webhook`) замок пропускает: у них свой
  `X-Worker-Token`, проверяют его сами. Страница результата и карточки источников — по аккаунту.

## Починено 05.10.2026 (сервис не работал вживую)
1. **Дефис в адресе API = 404.** Kohana ищет метод `action_source-fire`,
   поэтому кнопка «Тест» у источника и документированный `worker-result`
   молча не работали. Маршрут `nj639_api` получил `->filter()`, который
   переводит дефисы в подчёркивания; страница зовёт `/qc/api/source_fire`.
2. **Кадр уезжал в модель 512-пиксельным** — на таком кадре царапины и сколы
   не видно, модель начинала угадывать. Теперь общий `vlm.prepare_b64`
   (1400 px) и честная пометка «кадр мелкий» в задании модели.
3. **`NJ639_API_BASE` с полным путём** `/qc/api/worker_result` + добавленный
   воркером путь = 404 на доставке вердикта. `_result_path()` понимает обе
   формы; в `.env.example` теперь семейная форма `https://n2j.ru/qc/api`.
4. **Снимок с телефона уезжал целиком**: страница не уменьшала кадр, и
   мегабайты base64 ложились в payload задачи общей очереди (урок nj646).
   Теперь кадр и эталоны ужимает `N2JVision.shrink` в браузере, а `enqueue()`
   отбивает задачи тяжелее `PAYLOAD_MAX_B64` (6 МБ) внятной ошибкой.
5. **`apply_result()` падал на отсутствующем `schema_ok`** (E_WARNING →
   исключение Kohana → 500 в приёмке воркера) — добавлен `??`.
6. **Результат смывало перезагрузкой страницы**: `location.reload()` после
   вердикта заменён на добавление строки в журнал без перезагрузки.
7. **Правило из формы главнее сохранённого**: текст и варианты, которые
   человек видит на экране (в том числе из пресета), уходят в прогон, даже
   если в списке выбрано старое правило.
- **Периодика по таймеру** — единый cron nj603 (расписание `qc` в
  `nj603_kicker`): планировщик пиналки вызывает `cron_poll()` напрямую,
  сайт ставит задачи созревшим timer-источникам (паттерн nj605 `collect`).

## Архитектура «событие → кадр → VLM → схема → ответ + БД»
Кадры в VLM НЕ шлются потоком (VLM медленные/дорогие). Только по триггеру:
1. событие (webhook от датчика/ПЛК, cron-таймер, очередь, file-drop) → захват
   одного кадра;
2. воркер шлёт кадр + эталоны в vision-модель одним запросом;
3. ответ валидируется выходной JSON-схемой (jsonschema на воркере, fallback —
   свой валидатор типов);
4. результат — в `nj_639_runs.verdict` (JSONB) + доступен по `/qc/api/result/<id>`.

## Безопасность (обязательный слой)
1. **SSRF**: кадры с камер/HTTP на воркере проходят `_assert_capture_host`:
   запрет link-local/169.254.169.254 (метаданные облака) ВСЕГДА; private/
   loopback/reserved — только при `NJ639_ALLOW_LAN=1` (камеры в локальной сети).
2. **Rate limit** через `nj100_platform` по `nj_639_runs.client_ip`
   (`NJ639_RATE_PER_MINUTE`/`NJ639_RATE_PER_HOUR`); счётчик — та же таблица.
3. **Без exec с пользовательским вводом**: единственный subprocess — `ffmpeg`
   (RTSP), аргумент — строка URL из настроек, через список аргументов (нет
   shell), таймаут; прочие источники — stdlib (`ftplib`) / библиотеки.
4. **Валидация схемы без eval**: подмножество draft-07 на чистых сравнениях
   типов (PHP) и `jsonschema` (Python fallback — свой валидатор).
5. **Авторизация колбэков воркера**: `X-Worker-Token` = `WORKER_API_TOKEN`
   (`_token_ok`), как nj605. Webhook — секретный токен в `config.webhook_token`.
6. Лимиты входа: размер изображения (`NJ639_MAX_IMAGE_MB`, 15), число эталонов
   (`NJ639_MAX_IMAGES`, 6), длина правила 4000, варианты ≤ 12×200 симв.

## API
```
POST /qc/api/run            ручной прогон (multipart file | data_urls; rule/schema/variants/refs)
GET  /qc/api/result/<id>    статус + verdict (lazy reconcile задачи nj120)
GET  /qc/api/runs           последние прогоны
GET  /qc/api/rules          правила
GET  /qc/api/rule/<id>      одно правило для формы (text/variants/schema_json/refs)
POST /qc/api/rule_save      создать правило
POST /qc/api/rule_refs      прикрепить эталонные изображения к правилу (data URLs)
POST /qc/api/source         создать источник (webhook → webhook_url)
GET  /qc/api/sources        источники
POST /qc/api/source_fire    тест захвата источника («Собрать сейчас»)
POST /qc/api/cron_poll      пиналка nj603 (X-Worker-Token)
POST /qc/api/worker_result  приём результата воркера (X-Worker-Token)
GET  /qc/webhook/<token>    аппаратный триггер (датчик/ПЛК), опц. file/data_url
```

## Эталоны
- Ручной прогон: `refs` — data-URL эталонов. К НОВОМУ правилу они сохраняются
  в `nj_639_refs` (файлы erp212); к существующему — дополняют базу.
- Если `refs` не переданы — берутся сохранённые эталоны правила (`refs_for_rule`).
- Форма (`rule/<id>`) возвращает эталоны как data-URL для показа.

## Чем проверять без цеха
- Кнопки «Демо: деталь с дефектом» / «Демо: годная деталь» — кадр и эталон
  лежат в `public_html/assets/demo/nj639/` (синтетические снимки корпуса,
  1024 px, ~80 КБ): дефектный экземпляр отличается трещиной у угла, царапиной
  и перекошенной этикеткой.
- Кнопка «Демо-источник» заводит HTTP-источник на
  `<origin>/assets/demo/nj639/part-defect.jpg` — «Тест» прогоняет захват
  целиком (воркер качает кадр по сети, как с камеры).
- Своя камера: в источник годится любой публичный snapshot-URL, отдающий
  JPEG. Камеры в локальной сети закрыты, пока не задан `NJ639_ALLOW_LAN=1`.
- Стенд без БД: `N2J_ROOT=<repo> node phpwasm_stand.mjs .tools/nj639_qc_stand.php`;
  воркерная часть — `cd workers && python3 -m pytest tests/test_nj639_qc.py`.

## Ограничения (осознанные)
- RTSP требует `ffmpeg` на воркере; очередь — `paho-mqtt` / `stomp.py` /
  `kafka-python`. Без пакета источник честно сообщает «не установлен» и задача
  падает с понятной причиной (ретрай по очереди).
- `motion` (edge-CV) — задел: детектор движения монтируется отдельно к
  `trigger=motion`; сам по себе пока эквивалентен `timer`.
- Кадр по-прежнему едет base64 ВНУТРИ задачи очереди (у nj650/nj651 он лежит
  файлом на сайте, воркер забирает его через `/photo_file`). Здесь так
  нельзя: в авторежиме кадра на сайте вообще нет — его добывает воркер.
  Поэтому действует потолок `Service_Nj639_Qc::PAYLOAD_MAX_B64` (6 МБ) и
  уменьшение кадра в браузере.
