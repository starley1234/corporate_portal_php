# Контроль качества изделий (nj639_qc)

Проверка брака по фото с помощью VLM: эталон, правило поиска дефектов и
выходная JSON-схема ответа. Ручная загрузка фото изделия или автоматический
захват кадров из источника (камера, FTP, очередь, вебхук).

## Принцип

Кадры не шлются в vision-модель потоком. Работает схема
**событие/триггер → захват кадра → VLM-анализ → JSON-схема → ответ + запись в БД**:

1. триггер (таймер / внешний webhook от датчика или ПЛК / детектор движения)
   запускает захват одного кадра;
2. воркер отправляет кадр + эталоны + правило + схему в VLM;
3. ответ проверяется по вашей JSON-схеме и пишется в журнал `nj_639_runs`;
4. статус/вердикт доступен по API и в интерфейсе.

## Что умеет

- **Ручной режим** — фото изделия сличается с эталоном по правилу.
- **Элементы правила** — текст дефектов, управляемые варианты вердикта
  (годен / брак: царапина / …), выходная JSON-схема.
- **Эталоны** — одно или несколько изображений к правилу; сохраняются в БД и
  автоматически подхватываются при прогоне по выбранному правилу.
- **Авторежим** — источники: IP-камера (Snapshot URL / RTSP / ONVIF), FTP /
  Hot-Folder, HTTP-объект, локальная папка, очереди (Kafka / RabbitMQ / MQTT).
- **UI** — ручной режим, настройка источников, история прогонов с вердиктами.
- **Пресеты** — кнопки «Царапины и сколы», «Этикетка», «Комплектность сборки»,
  «Сварной шов / пайка», «Пересчёт изделий»: одним кликом заполняют правило,
  варианты вердикта и выходную JSON-схему.
- **Демо без своих файлов** — кнопки «Демо: деталь с дефектом» и «Демо: годная
  деталь» подставляют снимки из `public_html/assets/demo/nj639/`, а
  «Демо-источник» заводит HTTP-источник на кадр этого же сайта, чтобы
  проверить авторежим там, где промышленной камеры нет.

## Безопасность

| Угроза | Мера |
|---|---|
| SSRF | на воркере запрет link-local/метаданных облака всегда; private-адреса камер — только `NJ639_ALLOW_LAN=1` |
| Command injection | `ffmpeg` (RTSP) — только список аргументов, без shell; прочее — stdlib/библиотеки |
| DoS | rate limit по IP (мин/час) через общий слой `nj100_platform` |
| Инъекция в схему | валидация без `eval`, подмножество draft-07 |
| Подделка результата | колбэки воркера по `X-Worker-Token`; webhook — секретный токен |

## API

```bash
# ручной прогон (multipart)
curl -F 'file=@product.jpg' \
     -F 'rule_text=трещины, сколы на корпусе' \
     -F 'variants=годен, брак' \
     -F 'schema_json={"type":"object","required":["verdict"],"properties":{"verdict":{"type":"string"}}}' \
     /qc/api/run

# статус/вердикт
curl /qc/api/result/1
```

## Воркер

```bash
# workers/.env
NJ639_VISION_MODEL=openrouter::google/gemini-2.5-flash  # пусто — общая VLM_MODEL
NJ639_API_BASE=https://n2j.ru/qc/api                    # воркер сам добавит /worker_result
NJ639_SITE_TOKEN=<WORKER_API_TOKEN сайта>
NJ639_ALLOW_LAN=0                                       # 1 — камеры в локальной сети
```

Кадр готовится общим слоем `vlm.prepare_b64` (1400 px, JPEG) — тем же, что у
`/label`, `/meal`, `/plant`. Ожидание модели (`NJ639_LLM_TIMEOUT`, по умолчанию
240 с) обязано быть меньше `timeout_sec` задачи (сайт ставит 1200).

См. `AGENTS.md` для полного контракта (каналы, таблицы, ограничения).
