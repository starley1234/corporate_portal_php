## Адреса

`/prx595/admin` (пользователи: поиск, создание, карточка), `/prx595/admin/roles`
(роли), `/prx595/admin/activity` (активность). Манифеста в каталоге нет —
раздел только для администраторов, вход с дашборда.

## Данные

Ядро БЕЗ префикса (approved, схема не меняется): `users`, `roles`,
`roles_users` (Auth ORM). Блокировка = снятие роли `login` (Auth-гейт входа).
Активность — очередь `prx_120_jobs.visitor_id` (`u:<id>` / `g:<ubid>`).

## Особенности

* Пароль хэширует фильтр ORM Auth (`$user->password = '…'`).
* Себе нельзя снять `admin` (контроллер отклоняет и проверяет пост-фактум).
* `login`/`admin` — системные роли: удалить нельзя; свою роль можно удалить
  только при нуле пользователей.
* Удалений пользователей нет (только блокировка) — история артефактов
  сохраняется. Опасные действия — two-click (armed).
* Активность: KPI за 24 ч (всего / u: / g: / уникальные), разрез по каналам,
  последние 120 задач, последние 8 регистраций.

## Связь с предпочтениями (prx600)

24.10.2026: у каждого пользователя в списке и в карточке — иконка-мозг →
`/prx600/admin/owner/u:<id>` («Предпочтения и действия»: профиль интересов,
лента событий, задачи воркеров, входы, рекомендации с причинами и адресные
правила). В «Активности» ключи `u:`/`g:` кликабельны и ведут туда же. Данные
prx600 этот модуль не читает — только ссылается.

## Env

Новых переменных нет.

## Правила для агента

* Только роль admin (гейт в before()).
* Ядро users/roles/roles_users — БЕЗ изменения схемы; блокировка = минус роль login.
* Правка ролей: DELETE+INSERT в roles_users (переписываем набор целиком).
* Себе: admin снять нельзя (двойная проверка: до и после сохранения).
* Опасные действия — двойное нажатие `data-prx-arm` (app.js), window.confirm запрещён.
* Активность читает prx_120_jobs.visitor_id — не писать туда пользовательские данные.
* Вёрстка по эталону: крошки+h1, KPI, 2/3+1/3, таблицы py-2.5/text-sm.

## Чтение очереди через владельца (23.11.2026)

Прямой SQL этого модуля к `prx_120_*` удалён. Публичные методы
`Service_Prx120_JobQueue` используют настроенное соединение очереди и только
читают данные; диагностический fallback остаётся у экрана. Исключения этого
модуля удалены из `test_queue_table_debt.py`, возвращать SQL-зависимость нельзя.
Контракты/пороги/ограничения — `docs/WORKERS.md`, PostgreSQL-регрессии —
`QueueReportsIntegrationTest`. Наличие административного метода не заменяет ACL
страницы; общий пользовательский read API здесь не добавлен.
action_activity получает kpi/channels/jobs через admin_activity; выборка
новых пользователей Auth этим спринтом не переработана. Очередь отдаёт только
ID/channel/status/visitor_id/даты, без payload/result/error/callback.
