# prx395_document_extract — PDF → текст (асинхронно)

Машинный API для СЭД/ERP не зависит от сессий, HR, LLM или `docflow`.
`/prx395_document_extract` — отдельный административный UI: сессия + CSRF и
своё пространство владельца, недоступное машинным ключам. Пробный PDF проходит
тот же конвейер; стадии видны в `/prx120/monitor`.

**Разделение с `prx450`.** `prx395` — асинхронный: пачки PDF, очередь `prx120`
и Tesseract, ответ `202` + polling, приватные артефакты `prx212` с настраиваемым TTL (по умолчанию 24 ч).
`prx450` — синхронный: один документ, внешний OCR-шлюз, ответ сразу, файл
не хранится. Оба модуля остаются: это разные задачи.

- Доступ — ключ `prx150` + scope `prx395.extract`. Своей карты токенов нет:
  `Service_Prx395_Clients` и `PRX395_DOCUMENT_EXTRACT_CLIENTS` удалены.
  Ключ, лимит и отзыв — в `/prx150_api_hub`.
- `POST /api/v1/document-extractions`: Bearer-ключ + `Idempotency-Key` +
  multipart `file`. Ответ `202` `{job_id, status_url}`. Идемпотентность —
  платформенная (`Prx_Idempotency`): тот же ключ и тот же файл → тот же
  `job_id`; другой файл → `409 idempotency_conflict`; истёкший TTL →
  `409 idempotency_key_expired`. `prx120::push` и ссылка на задание лежат
  в одной транзакции с ключом.
- `GET /api/v1/document-extractions/<id>`: проверка владельца **до** чтения
  очереди, `Cache-Control: no-store`. Состояние и попытка берутся из prx120.
- Публичные `submit/status` принимают `Prx_Principal`: API передаёт
  `Prx150_Principal`, UI — `Prx_Actor`; `submit_sample` принимает только actor.
  Скалярные ID владельца и массивы на входе сервиса не поддерживаются.
- `Policy_Prx395_Extraction::ownerId()` проверяет UI ACL / API scope и только
  затем вычисляет внутренний `api_client_id`: ключ > 0, пользователь < 0.
  Контроллеры не кодируют владельца. Формат БД/идемпотентности сохранён.
  Чужое задание не видно даже portal-admin; организация не объединяет владельцев.
  Проверка владельца и TTL выполняется в SQL до чтения очереди/результатов.
- `/prx395/worker/health`: проверяет тот же токен и сообщает, загружен ли
  старый контур для каналов `doc.*`; `--check-site` не ставит задач.
- `/prx395/worker/<id>/file|result`: `X-Worker-Token` переносится и в PG,
  и в HTTP-режим; `X-PRX-Worker-Attempt` соответствует взятой попытке.
  Результат публичен для владельца только после `complete` той же попытки
  с квитанцией. Сохранение для одной попытки идемпотентно.
- Исходник и текст — приватные артефакты `prx212` с `module=prx395`, без имён
  от пользователя. В очереди ни текста, ни PDF, ни ключей, только ID задачи,
  метки стадий, код отказа/квитанция. В модуле только связь ID и метаданные.
- Владеет `prx_395_extractions` и `prx_395_results`; читает очередь и файлы
  только через публичные сервисы. При ошибке не логировать тело HTTP/документ.
- По истечении `PRX395_RESULT_TTL_HOURS` результат недоступен. `prx395:purge` запускать таймером: удаляет
  исходники/результаты, подчищает старые файлы без ссылок после аварий.

## Состояние

Контур prx150 использует типизированных principal, scope, идемпотентность и
изолированного владельца задания. `MachineExtractionAccessTest` проверяет
реальные ключи и внутренний HTTP-dispatch на PostgreSQL: 401/403/404/429,
отзыв/истечение ключа, TTL, UI/API-изоляцию, журнал и HMAC IP. Это не сетевой
HTTP/E2E-тест. Изолированные `extraction_access.php` / `machine_access.php`
проверяют policy и время жизни контекста. Worker-контур не менялся.
Сквозная загрузка PDF, OCR и админка в браузере требуют отдельного стенда.

Запуск, ошибки, проверки и лимиты — в [инструкции](../../../docs/integrations/document-extractions.md).

## Граница HTTP (23.11.2026)

Worker-контроллер наследует обычный `Controller`, без сессий и UI-bootstrap. Общий `respond()` проверяет worker-токен до действия, формирует JSON ошибок и no-store. Контракты: `make test-contracts`.

## UI и подключение API

Страница использует page_header и плоские prx-card по эталону; на мобильном
загрузка/процесс идут перед справкой API. Справа — ключ/scope, curl для
POST/GET, статусы, идемпотентность, лимиты и TTL. Примеры не содержат реальных
ключей, ID 42 условный. UI/API-владельцы разделены, что явно написано в справке.
Результат выводится как экранированный текст; есть копирование. При ожидании
работает прежнее обновление раз в 3 с, секундомер и этап получены от prx120
только после проверки владельца через Extraction::status(). Это не новый API.
Двойная отправка формы блокируется; sample передаётся hidden-полем, не кнопкой.
Проверки: tests/Contracts/extraction_ui.php, tests/Js/prx395.test.mjs;
модуль добавлен в DONE/DARK_DONE дизайн-аудита. Живой OCR и browser/E2E
не подтверждаются этими тестами.

Выбор файла: доступный с клавиатуры file input поверх области click/drop;
имя выводится только textContent. JS предварительно проверяет расширение и
размер из `PRX395_MAX_PDF_BYTES`, серверная проверка PDF остаётся решающей. Загрузка и результат
занимают всю ширину основной колонки, справка API — соседнюю колонку на
широких экранах. Тесты prx395.test.mjs проверяют имя/ошибки и разметку.

## Лимиты PRX395_*

Корневой `.env` для PHP и Python; `workers/.env` переопределяет его только
для воркера. `config/prx395_document_extract.php` + `Service_Prx395_Limits`
и `limits.py` задают одинаковые диапазоны и дефолты. Новые задания получают
явный `expires_at`, `timeout_sec` и `max_attempts`; дефолт колонки неизменен.
`Storage::save` применяет лимит prx395 только для его PDF, а не ко всем файлам.
Контракты `extraction_limits.php` и worker `test_limits.py` сверяют дефолты с
корневым `.env.example`. Скорость по-прежнему задаётся ключом prx150.
