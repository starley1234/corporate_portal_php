# MCP Hub — живой каталог MCP-серверов и один шлюз для агентов

`/mcphub` — публичный каталог MCP-серверов и их инструментов: что умеет сервер,
нужен ли ключ, работает ли он прямо сейчас, сколько у него звёзд и насколько
свежий код. Каталог **собирает себя сам**: администратор нажимает «Найти и
добавить» и при желании указывает тематику.

Рядом — **Meta-MCP шлюз** `POST /mcphub/mcp` (Streamable HTTP): агент подключает
один адрес и получает семь корневых инструментов вместо сотен чужих схем.

## Два разных MCP — не путать

| | `/mcp` (nj160) | `/mcphub` + `/mcphub/mcp` (nj676) |
|---|---|---|
| Что это | MCP **этого сервиса** | каталог MCP **всего мира** |
| Инструменты | сервисы N2J: организации, профили, письма, закупки | семь инструментов-шлюза к чужим серверам |
| Кому | «сделай что-то на n2j.ru» | «мне нужны погода, база данных, документация…» |

Разделять их правильно: у них разные задачи, разные права и разные ключи.
Соединять тоже есть смысл — но не кодом, а ссылками: обе страницы объясняют
соседнюю, а `/mcp` остаётся точкой входа для своих инструментов.
Глобальный каталог при этом доступен без ключа: без него работают поиск,
статус и вызов серверов, которым не нужна авторизация.

## Как работает автосборка

1. **Поиск проектов.** GitHub API: теги `mcp` / `mcp-server`, поиск по имени и
   описанию (`"mcp server" in:name,description`), целевой запрос по тематике
   («базы данных», «финансы», …). Дополнительно — поиск в интернете
   (DuckDuckGo), чтобы поймать проекты без тегов; берутся только ссылки на
   GitHub.
2. **Отсев.** Дубликаты (сайт отвечает, что уже есть), архивные репозитории,
   старый код, слишком мало звёзд.
3. **Разбор README.** Пакет npm/PyPI с точной версией, удалённый адрес
   (SSE / streamable HTTP), имена переменных окружения, транспорт, авторизация.
4. **Описания.** LLM пишет по-русски: что делает, что именно умеет, кому
   пригодится, категории. Русский текст лежит **рядом** с оригиналом
   (`name_ru` / `description_ru`), а не вместо него: карточку читает человек,
   а шлюз и агент по-прежнему работают с английскими словами автора. Уже
   собранные карточки догоняет отдельный канал `nj676.translate` (см.
   «Русский каталог»). Без модели карточка всё равно собирается по фактам
   GitHub — каталог не остаётся пустым (описание тогда на языке README, обычно
   английском; задайте `NJ676_MODEL`, чтобы тексты были русскими).
5. **Живая проверка.** Удалённый сервер получает `initialize` + `tools/list`;
   в карточку попадают реальные схемы, задержка и статус (работает / недоступен).
6. **Запись.** Карточка публикуется сразу (`origin = auto`). Тексты карточек под
   ручной модерацией автосборка не перезаписывает; ручной перевод
   (`ru_source = manual`) модель тоже не трогает.
7. **Отчёт.** Каждая карточка прогона оставляет строку в `nj_676_run_items`:
   добавлена / обновлена / пропущена и **почему**. Админка показывает это
   списком на `/mcphub/admin?tab=runs&run=<id>` (пункт `#runs-log`), не заставляя
   листать лог воркера.

Всё это — задача очереди `nj676.discover`; HTTP-запрос только ставит её и
показывает живой статус-ряд (`/mcphub/api/status/<id>`).

## Спрос агентов: каталог растёт под то, что реально просят

Каждый поиск через шлюз (`hub_search_tools`) и каждая строка поиска на сайте
пишутся в `nj_676_search_log`: текст запроса (до 200 символов), нормализованная
форма для группировки, сколько карточек и инструментов нашлось, sha256 ключа
агента. Ни аргументов вызова, ни ответов, ни токенов там нет; записи старше
`NJ676_DEMAND_KEEP_DAYS` (180 дней) удаляются ночным пинком.

Из этого журнала строится «спрос» — и он же управляет автосборкой:

1. **Мгновенно.** Поиск агента, который ничего не нашёл, ставит прогон
   автосборки по этой теме. Ограничители: только при `NJ676_AUTO_DISCOVER=1`,
   пауза `NJ676_DEMAND_MIN_SEC` (30 мин), потолок `NJ676_DEMAND_MAX_DAY` (6 в
   сутки), одна тема не повторяется 14 дней. Анонимный поиск на сайте прогоны
   не ставит — только копит спрос.
2. **По расписанию.** Ночной пинок берёт самый частый запрос без ответа
   (`Service_Nj676_Demand::next_theme`) и собирает по нему. Выключить —
   `NJ676_AUTO_DEMAND=0`, тогда собирается «самое заметное», как раньше.
3. **Вручную, но в один клик.** В `/mcphub/admin` карточка «Спрос агентов»:
   запросы за 7/30/90 дней, у каждого — «нашлось / не нашлось ни разу» и
   кнопка «Собрать».

Русская тема в worker'е переводится моделью в 2–3 английские поисковые фразы
(«погода» → `weather forecast`): GitHub ищет по английским словам, и
`topic:mcp-server погода` не находит ничего. Без модели тема ищется как есть.

## Глобальный каталог: официальный реестр MCP

Кроме автосборки из GitHub каталог сливается с **registry.modelcontextprotocol.io** —
там серверы описаны машинно (`server.json`: имя с проверенным пространством,
версия, репозиторий, пакеты, удалённые адреса). Это делает каталог
действительно всемирным и обновляется повторным импортом.

- кнопка в админке «Обновить из реестра» → задача `nj676.registry`;
- воркер читает `/v0.1/servers` постранично и отдаёт пачки на
  `POST /mcphub/api/registry-batch`;
- сайт склеивает записи по `registry_name`, затем по репозиторию и удалённому
  адресу — дубликатов не появляется;
- тексты карточек с `origin = manual` импорт не перезаписывает;
- стартовая витрина «С чего начать» (`featured`) заводится миграцией 004 — это
  публичные серверы, которые подключаются ссылкой (погода, математика,
  документация, GitHub, Notion…). Живой статус у них появляется после проверки.

## Админка: пять вкладок, а не одна простыня

`/mcphub/admin` разбит по смыслу — каждая вкладка отвечает на один вопрос и
грузит только свои данные:

| Вкладка | Адрес | Зачем |
|---|---|---|
| **Сборка** | `/mcphub/admin` | одна кнопка «Найти и добавить», «Обновить из реестра», что именно делает кнопка |
| **Карточки** | `/mcphub/admin?tab=cards` | таблица каталога, «Проверить схемы», «Проверить удалённые», ручная правка |
| **Поиск и текст** | `/mcphub/admin?tab=quality` | смысловой индекс (`#semantic`) и русский перевод (`#translate`) |
| **Спрос агентов** | `/mcphub/admin?tab=demand` | что спрашивают через шлюз и по чему не нашлось |
| **Прогоны** | `/mcphub/admin?tab=runs` | итог прогона, отчёт по строкам (`#runs-log`) и журнал |

Старые ссылки работают сами: `?run=N` открывает «Прогоны» (и `#runs-log` —
отчёт), `?slug=...` открывает «Карточки» с формой правки. Кнопки после действия
возвращают на свою вкладку (`?tab=quality#translate` и т.п.), а не в общий
список.

## ИИ-анализ каталога: «что работает и чего не хватает»

Числа отвечают «сколько», но не «что делать». Кнопка **«Проанализировать
каталог»** (`/mcphub/admin?tab=build#analysis`) отвечает на два вопроса
владельца сразу:

- **состояние** — что реально работает, у кого какая задержка, что мешает
  остальному (нужен ключ, адрес не проходит проверку, проба не отвечает,
  вызовы падают) и что чинить первым;
- **пробелы** — какие темы агенты спрашивают, а каталог молчит, и что из этого
  стоит собирать. Темы из отчёта кликабельны: кнопка сразу ставит «Найти и
  добавить» с готовой формулировкой.

Как устроено (те же правила, что у перевода и живой проверки):

- снимок данных снимается **на сайте** при постановке (`snapshot`, миграция
  016): числа, живые примеры, причины недоступности, падающие вызовы, спрос.
  Он сохраняется рядом с отчётом — видно, на каких данных модель сделала вывод;
- модель работает **в воркере** (канал `nj676.analysis`): сайт не ждёт LLM.
  Воркер забирает снимок `GET /mcphub/api/analysis-get?id=N` и отдаёт отчёт
  `POST /mcphub/api/analysis-finish`;
- отчёт **нормализуется** (`Analysis::normalize_report()`): только известные
  поля, строки обрезаны, лишние ключи выбрасываются. В админку не попадает
  произвольный ответ модели;
- модель получает правило «пустой список честнее выдумки»: если запросов без
  ответа нет, `gaps` пустой, а не придуманный;
- один анализ за раз: второй поверх идущего не ставится (двойные токены за один
  и тот же ответ);
- размышления модели отключены — как у перевода, иначе рассуждающая модель
  тратит на них весь бюджет ответа и возвращает обрезанный JSON.

Режимы: «состояние и пробелы» (по умолчанию), только состояние, только пробелы.
Env: `NJ676_ANALYSIS_MODEL` (по умолчанию `NJ676_MODEL`), `NJ676_ANALYSIS_TOKENS`
(4000).

## Шлюз: семь инструментов вместо сотен

| Инструмент | Зачем |
|---|---|
| `hub_ready {limit?, sort?, ignore?}` | «что можно вызвать прямо сейчас» — без обязательного запроса |
| `hub_search_tools {query?, limit?, only_ready?, sort?, ignore?}` | найти инструменты под задачу: сервисы N2J и серверы каталога MCP (`sort`: `latency` / `reliability`) |
| `hub_describe_tool {tool, server?}` | полная JSON Schema и готовый пример вызова; работает и для сервисов N2J |
| `hub_call_tool {tool, arguments}` | вызвать сервис N2J; для удалённого сервера — `{server, tool, arguments}`; `dry_run` — план без исполнения |
| `hub_feedback {call_id, rating}` | отзыв строго по `call_id` реального вызова |
| `hub_status {}` | что доступно этому ключу, готовые серверы с сигнатурами, активные фильтры, размеры каталога |
| `hub_configure {no_auth_only?, no_install?, categories?, transport?, latency_max?, ignore?, reset?}` | «у меня нет ключей — ищи только без авторизации», темы как предпочтение, скрыть серверы, которые у вас падают |

Пример:

```json
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"hub_search_tools","arguments":{"query":"проверить компанию по ИНН"}}}
```

Клиент протокола свой (`Service_Nj676_McpClient`): `initialize` →
`notifications/initialized` → `tools/list` / `tools/call`, с `Mcp-Session-Id`,
`MCP-Protocol-Version` и разбором SSE-ответов. Наивный POST без сессии ломается
на большинстве современных серверов.

Если агент помнит имя инструмента (`get_weather`), но не slug сервера, шлюз
сам найдёт сервер по кэшу `tools` — это путь для слабых моделей.

Транспорт ведёт себя как Streamable HTTP: `DELETE /mcphub/mcp` → 204 (клиент
закрывает сессию), в ответе есть `MCP-Protocol-Version` и `Mcp-Session-Id`
(метка подключения, обратно её не требуем), `initialize` объявляет
`tools.listChanged = true`, а GET с `Accept: text/event-stream` отдаёт
`notifications/tools/list_changed` только если реально менялся ответ
`tools/list` (семь корневых инструментов шлюза). Каталог на это не влияет —
иначе нотификация приходила почти на каждое подключение, и клиент делал
лишний `tools/list` зря. В остальное время в потоке честный SSE-комментарий:
`tools/list не менялся`.
Эндпоинт не ставит браузерных cookie: ответ идёт с `Access-Control-Allow-Origin: *`,
и сессионная кука сайта (`HttpOnly/Secure/SameSite`) агенту не нужна — личность
это ключ в заголовке или IP анонима. Анонимные лимиты раздельные — чтение и
вызовы, час и минута; отказ приходит как 429 с `Retry-After` и кодом
`RATE_LIMITED`. **Оба бюджета объявлены заранее** в каждом ответе
(`X-RateLimit-Call-Limit-Hour`, `X-RateLimit-Call-Limit-Minute`,
`X-RateLimit-Read-Limit-Hour`, `X-RateLimit-Read-Limit-Minute`,
`…-Remaining-…`) и в `hub_status.budgets` — до того, как агент в них упрётся;
старые `X-RateLimit-Limit/Remaining/Budget` остались совместимостью.

Безопасность: проксируются только HTTPS-адреса **из опубликованных карточек**
после проверки DNS (приватные, loopback и metadata-адреса отклоняются),
редиректы не выполняются, ответ ограничен 512 КБ и 20 секундами. Локальные
stdio-серверы на сервере не запускаются — агент получает конфигурацию для
своего клиента. Анонимный доступ (`NJ676_ANON=1`, по умолчанию включён)
работает только для каталога и серверов без ключей, с **раздельными**
бюджетами: чтение 600/час (burst 60/мин), вызовы 60/час (burst 12/мин),
`NJ676_ANON_*`; инструменты N2J требуют ключ.

Экономия контекста агента: в выдаче поиска нет полных JSON Schema чужих
инструментов — только сигнатура (`send_email(to*, subject)`), обязательные
аргументы и флаг «изменяет данные». Полная схема — по запросу через
`hub_describe_tool`. Объяснение «почему здесь» приходит только при
`explain: true`.

## Схема — закон: проверка аргументов

`additionalProperties: false` в схеме не декорация. Перед работой шлюз
проверяет аргументы по объявленной схеме:

| Что | Ответ |
|---|---|
| лишнее поле (`nonsense_arg`) | `INVALID_ARGUMENT`, `field`, `allowed_arguments` |
| неверный тип (`limit: "много"`) | `INVALID_ARGUMENT`, `field`, `expected` |
| значение вне `enum` (`sort: "похожие"`) | `INVALID_ARGUMENT`, список допустимых |
| число вне диапазона (`limit: 9` при схеме 1…8) | `INVALID_ARGUMENT`, `field`, `expected` с границами схемы |

Тихая подрезка чисел отменена 24.10.2026: `limit: 9` молча становился 8,
`limit: 0` — 1, и агент читал это как «схема разрешает 9». Схема — контракт:
не сошлось — `INVALID_ARGUMENT` с диапазоном.

Ошибки удалённых серверов нормализуются тем же словарём: `code`, `hint`,
`retryable`, `upstream_message` (`AUTH_REQUIRED`, `INVALID_ARGUMENT`,
`UPSTREAM_TIMEOUT`, `RATE_LIMITED`, `UPSTREAM_ERROR`). Сырой текст апстрима
(«Input validation error… request UTDWN-4TNNH») остаётся в ответе ниже
разделителя — он нужен человеку, а не агенту.

## Русский каталог: перевод рядом с оригиналом

Сайт русскоязычный, а каталог приходит из GitHub и официального реестра на
английском. Поэтому у карточки два слоя текста:

| Поле | Чей текст | Кто использует |
|---|---|---|
| `name`, `description` | автор проекта (английский) | шлюз, агент, поиск по оригиналу |
| `name_ru`, `description_ru` | модель или редакция | витрина, сортировка «по алфавиту», поиск |
| `ru_source` | `llm` или `manual` | защита ручного перевода от перезаписи |

Правила:

- **переводит воркер** (канал `nj676.translate`), не сайт: у сайта нет модели,
  и HTTP-запрос не должен ждать перевода;
- воркер забирает порцию карточек без перевода
  (`GET /mcphub/api/translate-candidates`), просит у модели `name_ru` и
  `description_ru` и отдаёт результат обратно (`POST /mcphub/api/translate-item`);
- перевод **не затирает оригинал** и не затирает ручной текст редакции
  (`ru_source = manual`); пустой перевод никогда не подменяет уже сохранённый;
- витрина показывает `display_name` / `display_description` (= перевод, а если
  его нет — оригинал) и рядом честно пишет оригинальное имя автора; на карточке
  сервера оригинальное описание раскрывается в `<details>`;
- кнопка **«Перевести всё»** в `/mcphub/admin?tab=quality#translate` ставит
  **цепочку независимых задач** (40 карточек на задачу, до 40 задач за клик):
  одна упавшая задача видна в мониторе, остальные доезжают, а следующая
  продолжает с того места, где стало пусто. Рядом — «Порция 20» для добора
  по чуть-чуть;
- раз в сутки небольшую порцию ставит тик (`NJ676_AUTO_TRANSLATE=0`
  выключает);
- прогон **докладывает итог** на `POST /mcphub/api/translate-finish`
  (переведено, пропущено, сколько осталось, ошибки модели/сайта) — админка
  показывает его строкой «Последний прогон перевода». Без этого «переведено 5
  из 1037» ничего не объясняет;
- пачка, на которой модель ошиблась, повторяется и делится пополам: плохой
  ответ стоит одной карточки, а не прогона;
- карточку берёт **одна** задача: при выдаче она помечается (`ru_claimed_at`,
  миграция 013), клейм снимается после сохранения перевода или когда воркер
  докладывает пропуск. Без этого десятки одновременных задач получали один и
  тот же список и переводили каталог по кругу, сжигая токены;
- **клейм принадлежит задаче** (`ru_claimed_job`, миграция 015). 24.10.2026
  перевод встал: задача взяла 25 карточек, перевела 8 и закончилась по бюджету
  времени, а клейм жил ещё час — сайт показывал «25 в работе», свободных не
  было, обе кнопки выключены, модель простаивала. Теперь сайт знает, какие
  задачи канала живы, и отпускает клеймы закончившихся сразу (клеймы без
  номера задачи — по времени). Кнопка **«Разблокировать»** в блоке перевода
  снимает все метки и сразу ставит новую задачу;
- воркер берёт карточки **окнами по две пачки**, а не весь лимит разом, и всё,
  что взял и не успел (время, таймаут, падение), возвращает в очередь сразу.
  Контрольный запрос «сколько осталось» идёт с `claim=0` и карточку не забирает;
- прогон, который реально перевёл хоть что-то, **сам ставит продолжение**, если
  остались карточки и живых задач нет (не больше трёх продолжений в час) —
  каталог не ждёт суточного тика.

## Смысловой поиск: «задача → нужный сервер»

Каталог ищет не только по словам. Карточки (имя, описание, категории, имена и
описания инструментов) индексируются **векторами** платформенного
эмбеддинг-сервера — того же, что `EMBEDDING_API_URL` / `EMBEDDING_MODEL`
(по умолчанию `text-embedding-qwen3-embedding-0.6b`, 1024 измерения).

Зачем: лексический поиск честно находит слово и честно ошибается смыслом.
В тесте 24.10.2026 на «отправить письмо» первым выходил набор иконок — в его
инструментах встречалось «email». Вектор ставит почтовый сервер выше набора
иконок, а объяснение «почему здесь» больше не приписывает серверу чужие слова.

Как устроено:

- векторы хранит **nj115_semantic** (правило платформы: своих таблиц с
  эмбеддингами модули не заводят), коллекция `nj676_mcphub`, сущность
  `server`, `id` = slug; источник для покрытия и «Догнать» описан в
  `application/config/nj115.php`;
- текст карточки для вектора — `name`, `description`, `name_ru`,
  `description_ru`, категории и пары «имя описание» инструментов; та же
  формула описана SQL-источником в `application/config/nj115.php`, менять их
  нужно вместе;
- индексация идёт **через очередь nj120**: раз в сутки её ставит тик
  (`/mcphub/api/tick`), вручную — кнопка «Проиндексировать новые карточки» в
  блоке «Смысловой поиск» (`/mcphub/admin?tab=quality#semantic`) с отчётом «поставлено /
  без изменений / ошибка»; воркер считает векторы и пишет их в базу. Рядом под
  раскрывашкой — «Пересобрать индекс целиком» (`force`): пересчитывает всё,
  даже неизменившееся; нужен после смены модели эмбеддингов;
- индекс идёт **страницами по всему каталогу** и сравнивает хеши текста:
  неизменившиеся карточки не тратят эмбеддинг-сервер, а карточки из хвоста не
  остаются без вектора навсегда (раньше отбирались только первые N по дате);
- поиск сначала спрашивает смысл, затем слова; итоговая релевантность —
  максимум из двух. **Порогов два, по одному на шкалу**: слово в описании
  (`LEXICAL_FLOOR = 0.33`, то есть 2 совпадения из 6) и смысл
  (`SEMANTIC_FLOOR = 0.2` — нижняя граница шкалы: содержательные отсечки у
  смысла свои, см. таблицу ниже);
- у смысла **три отсечки** (`Service_Nj676_Semantic::select()` — чистая
  функция, её проверяет стенд без базы и без эмбеддинг-сервера):

  | Отсечка | По умолчанию | Что значит |
  |---|---|---|
  | `max_distance()` | `0.62` (`NJ676_SEMANTIC_MAX_DISTANCE`) | дальше — «другая тема», в выдачу не берём |
  | `confident_distance()` | `0.55` (`NJ676_SEMANTIC_CONFIDENT`) | если даже лучший вектор дальше — **по смыслу ничего нет**, поиск остаётся лексическим |
  | `spread()` | `0.07` (`NJ676_SEMANTIC_SPREAD`) | держим только тех, кто не дальше лучшего на этот зазор |

  Раньше порог был один и щедрый (0.75), а относительная отсечка резала мусор
  только внутри мусора: любой запрос набирал 40 «похожих», и `zzzqqq
  gibberish` возвращал 40 серверов с `funasr` в топе. Теперь мусорный запрос
  даёт **честный ноль** и объяснение «переформулируйте»;
- пустая выдача — это ответ, а не сбой: шлюз пишет «по запросу «…» ничего не
  нашлось» и (если смысл молчал) причину. Подставлять случайные серверы
  запрещено: `next` в неверный инструмент стоит агенту вызова. Что решила
  семантика (лучшая дистанция, сколько отсеклось) видно в
  `structuredContent.semantic_check`;
- после порогов режется **хвост по относительному скору** (`SCORE_CUTOFF =
  0.6`): остаётся всё, что набрало ≥ 60 % от лучшего результата. Абсолютный
  порог отвечает «это про задачу?», относительный — «это так же про задачу,
  как лучшее?». При явной сортировке (`latency`/`reliability`) хвост не
  режется: порядок задал агент;
- готовность в скор **не входит**: `score = 0.75·релевантность + 0.10·надёжность
  + 0.10·свежесть + 0.05·популярность`, а «можно вызвать» — только тайбрейкер
  при равной уместности. Иначе готовый `temporal-mcp` вылезал первым на
  «распознать речь», хотя тема не его;
- **перевод и вектор связаны**: текст вектора включает `name_ru` /
  `description_ru`, поэтому карточка, проиндексированная ДО перевода, отвечает
  на русский запрос английским текстом — так «иконки» не находили
  `dashboard-icons`, хотя «логотипы» находили. Теперь воркер, сохранив перевод,
  ставит переиндексацию этих карточек сразу (`Semantic::index_slugs()`), а не
  ждёт суточного догона. Если модель эмбеддингов различает «документ» и
  «запрос», включается инструкция: `NJ676_SEMANTIC_INSTRUCT` (по умолчанию
  пусто — выключено);
- **без `EMBEDDING_API_URL` ничего не ломается**: `Service_Nj676_Semantic`
  молча возвращает пусто, поиск работает по словам и синонимам RU↔EN. Если
  эмбеддинг-сервер упал в момент запроса, ответ тоже деградирует до слов, а не
  отдаёт 500;
- **одна правда о готовности**: витрина, `hub_ready`, `hub_status` и
  `hub_search_tools {only_ready:true}` считают по `McpHub::readiness()`, а
  кандидатов отбирает один общий SQL-предикат `McpHub::_ready_condition()`;
  список, счётчики и причина сбоя — из одного `McpHub::ready_overview()`.
  До 24.10.2026 витрина считала `health_status='operational'` (8), а шлюз — с
  живым вызовом и ключом из окружения (10), и разница читалась как вранье.
  Если расчёт упал, это видно: `hub_status.ready_error`, плитка на витрине и
  `WARNING` в журнале, а не молчаливый ноль;
- **отказ «нужен ключ» запоминается**: живой вызов с `AUTH_REQUIRED` ставит
  `auth_required_at`, и сервер уходит из `hub_ready` и «Отвечают прямо
  сейчас» на 30 дней (`NJ676_AUTH_WINDOW_DAYS`); успешный вызов отметку
  снимает. Отметку ставит **одна точка** — `Gateway::error()` при
  `code = AUTH_REQUIRED` и известном slug, — иначе семь разных веток забывают
  её по очереди: именно так `temporal-mcp` остался в «Отвечают прямо сейчас»
  после вызова, вернувшего отказ. Английские формулировки («OAuth authorization
  required», «authentication needed») теперь тоже распознаются как
  `AUTH_REQUIRED`, а не как `UPSTREAM_ERROR`;
- «Отвечают прямо сейчас» на витрине берётся из того же `readiness()`, что
  `hub_ready`, а не из отдельного SQL: три способа считать готовность давали
  три разных числа;
- ошибка внутри шлюза наружу не выходит текстом: `Database_Exception` и любые
  непойманные исключения отдаются как `INTERNAL` с `request_id`, подробности —
  в журнале. 24.10.2026 клиент получал сырой Postgres («столбец
  "auth_required_at" не существует») и фрагмент SQL с именами колонок. Если
  расчёт готовности упал, `hub_status` отвечает `degraded: true`;
- бюджеты видны и в тексте `hub_status`, и в заголовках; имена заголовков —
  одно место (`Gateway::budget_headers()`), поэтому текст не может обещать
  `X-RateLimit-Call-*`, пока клиент видит `X-RateLimit-Limit`;
- состояние видно в `hub_status` («Поиск: смысл + слова»), в
  `GET /mcphub/api/selfcheck` (шаг «Семантический поиск») и в админке.

Порог и веса — в `Service_Nj676_Semantic::relevance()` и
`Service_Nj676_Gateway::match_detail()`: имя сервера весит больше описания,
описание — больше имён инструментов (иначе набор иконок с иконкой конверта
обгоняет почтовый сервер).

## Совместимость клиентов

Шлюз следует спецификации MCP и проверен на строгой валидации (OpenCode
v2.1.4 — он отклоняет `tools/list` целиком при одной ошибке схемы, поэтому
одно кривое поле делает невидимыми все инструменты):

- `properties` в схеме — **объект**, даже если аргументов нет (`{}`, а не `[]`).
  PHP кодирует пустой массив как `[]`, поэтому схемы прогоняются через
  `Service_Nj676_McpHub::schemas_as_objects()` и в ответе шлюза, и в
  `api/tools`, и в `api/search`. То же исправлено в `/mcp` (nj160);
- `initialize` отвечает эхом на запрошенную версию протокола (знакомые —
  `2025-06-18`, `2025-03-26`, `2024-11-05`), сервер stateless и не требует
  `Mcp-Session-Id`;
- ошибки инструмента приходят как `result.isError` с текстом, а не как
  `error` JSON-RPC: агент читает причину и исправляет вызов сам.

Пример конфигурации OpenCode (`~/.config/opencode/opencode.json`):

```jsonc
"mcp": {
  "servers": {
    "mcphub": {
      "type": "remote",
      "url": "https://n2j.ru/mcphub/mcp",
      "headers": { "Authorization": "Bearer {env:N2J_MCP_KEY}" }
    }
  }
}
```

Без ключа работают `hub_search_tools`, `hub_configure`, `hub_status` и вызовы
серверов каталога, которым не нужна авторизация.

## Карточка и доверие

- **Состояние** — живая проверка (`Работает`, `Сбоит`, `Недоступен`) или честное
  «не проверен». Ручная отметка модератора отображается отдельно.
- **Доверие 0–100** — звёзды, свежесть коммитов, лицензия, архивность,
  статический разбор схем (MCP Guard, модуль `nj674`).
- **Конфигурация** — только закреплённые версии пакетов; переменные окружения —
  плейсхолдеры `SET_LOCALLY`. Значения ключей каталог не хранит.

Тот же тик ставит и **проверку живости** (`nj676.probe`, не чаще
`NJ676_PROBE_EVERY_SEC`, по умолчанию 6 ч): воркер делает `initialize` +
`tools/list` и возвращает статус, задержку и схемы.

Вручную — вкладка **«Карточки»** (`?tab=cards`), блок «Проверка карточек»,
кнопка **«Проверить удалённые»** (`#probe`). Рядом видно очередь: сколько
удалённых серверов, сколько ни разу не проверялись, сколько старше
`NJ676_STALE_DAYS`. Одна кнопка берёт 24, 48 или 60 серверов — сначала ни разу
не проверенные, потом самые давние (по `health_checked_at`). На вкладке
«Сборка» та же кнопка упомянута ссылкой: искать её там, где её нет, — обычное
дело. На сервере с тысячей карточек один прогон по 60 — это ~17 нажатий;
автоматический путь — тик раз в 6 часов, он берёт ту же очередь.

Порция идёт одной задачей с таймаутом 15 минут: 60 серверов × таймаут пробы
8 с — верхняя граница 8 минут, задача не должна умирать на середине.

Автодобор по таймеру: `curl -fsS -X POST -H "X-Worker-Token: $TOKEN" https://n2j.ru/mcphub/api/tick`
(нужен и `NJ676_AUTO_DISCOVER=1`). Расписание в планировщике платформы не
заводится намеренно — триггеры расписаний принадлежат чужому модулю.

Воркер (`workers/.env`): `NJ676_API_BASE` (или общий `NJ120_API_BASE`),
`NJ676_SITE_TOKEN` (или `WORKER_SITE_TOKEN`), `NJ676_GITHUB_TOKEN`,
`NJ676_MODEL`, `NJ676_MIN_STARS`, `NJ676_README_CAP`, `NJ676_LLM_BATCH`,
`NJ676_PROBE`, `NJ676_DDG`, `NJ676_REGISTRY_MAX` — все описаны в
`workers/.env.example`. Каналы: `nj676.discover` (поиск и карточки),
`nj676.registry` (импорт реестра), `nj676.probe` (живая проверка удалённых),
`nj676.audit` (полевой ИИ-агент исследователь открытых MCP-серверов, поиск «алмазов» с безопасным пробным `tools/call`, оценками `utility_score`/`safety_score` и отчётом в `nj_676_audits`),
`nj676.analysis` (ИИ-анализ каталога, см. раздел выше), `nj676.translate`
(русские названия и описания; `NJ676_TRANSLATE_LIMIT` —
карточек за прогон, `NJ676_TRANSLATE_BATCH` — в одном запросе к модели).

**Проверка после деплоя без клиента** — одна ссылка: `GET /mcphub/api/selfcheck`.
Сайт сам прогоняет шлюз изнутри: схема инструментов → `hub_status` → поиск →
живой `tools/list` удалённого сервера → настоящий вызов `calculate`
(2^10 + sqrt(144) должен дать 1036) → бесплатный вызов погодного сервера.
С `?http=1` добавляется реальный POST на собственный эндпоинт (проверка сети и
веб-сервера, не только кода). Ответ — JSON по шагам с временем; 200, если всё
зелёное, иначе 503. Ручка ограничена `NJ676_SELFCHECK_LIMIT` (12 в час на IP):
каждый прогон дергает два чужих сервера.

Та же проверка есть кнопкой «Проверить шлюз» на `/mcphub`.

**Проверка из терминала** — скрипт, который разговаривает с эндпоинтом как
агент: initialize (+`Mcp-Session-Id`, без `Set-Cookie`) → tools/list →
hub_status → поиск (`why` не приходит без `explain`) → уведомление 202 →
ошибка разбора 400 → батч 400 → GET без SSE 405 → GET-поток SSE → DELETE 204:

```bash
bash .tools/mcphub_smoke.sh                        # https://n2j.ru
bash .tools/mcphub_smoke.sh http://127.0.0.1:8080  # локальный стенд
MCPHUB_TOKEN=... bash .tools/mcphub_smoke.sh       # с ключом
```

Статус удалённого сервера ставится по правилу «двух ударов»: одна неудача —
`degraded` (сервер остаётся в выдаче), две подряд — `offline`, любой успех
сбрасывает счётчик `probe_failures`. Иначе случайный DNS-таймаут на воркере
выключал бы живой сервер из каталога.

Проверка шлюза без интернета — локальный стенд MCP:
`python3 .tools/nj676_mcp_stub.py 8765` и `NJ676_ALLOW_LOCAL_PROBE=1`
(в песочнице внешние MCP недостижимы, стенд отвечает по настоящему протоколу).

Таблицы: `nj_676_servers`, `nj_676_runs` (журнал, чистка 180 дней),
`nj_676_agent_profiles`. Стенд: `.tools/nj676_mcphub_stand.php`
(запуск через `.tools/phpwasm_stand.mjs`), тесты воркера:
`cd workers && python3 -m pytest tests/test_nj676_mcphub.py -q`.

## Границы

Это каталог и шлюз к **уже существующим** серверам, а не песочница их запуска.
Контейнерная проверка stdio-серверов (Docker/gVisor), uptime-история и биллинг —
следующие этапы. Статический разбор MCP Guard не доказывает безопасность кода:
подключение запускает сторонний пакет на компьютере пользователя.
