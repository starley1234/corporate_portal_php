# prx400_specflow — Оцифровка спецификаций

## Что делает
Скан PDF спецификации/BOM → детерминированный разбор таблицы по семантическому
шаблону → математический аудит → fuzzy-матчинг с НСИ → верификация оператором →
JSON/CSV для ERP. LLM не используется: разбор воспроизводим и бесплатен.

## Ключевые решения
- **Хранение — фасад `Storage` (prx212)**: артефакт загружается БЕЗ
  пользователя (`Storage::put(..., 'prx400', NULL, ...)`) — owned-методы
  read_owned/delete_owned определены только для «файлов без пользователя»;
  владелец записи — `prx_400_specs.owner_id`. Ранние user-загрузки читает
  fallback `Storage::bytes`, удаляет владелец файла (лог prx400_diag).
  Загрузка: `Storage::put(..., 'prx400', ...)`
  при загрузке, в БД — маркер `prx212:<file_id>`, чтение — `read_owned`/
  `metadata`. Файл переживает выкатку релиза и не зависит от каталога кода.
  Легаси-записи с путями ФС (до перехода) читает `resolve_pdf` с
  самолечением: относительный путь / абсолютный «как есть» / перепривязка
  по структуре `<storage>/<id>/spec-*.pdf` к текущему корню хранилища.
- **Шаблоны — JSON** в `config/templates/*.json`: якоря детекции, синонимы
  колонок, правила пропуска/итогов/разделов, проверки математики. Новый формат
  документа = новый файл, код не меняется. Шаблоны едут в payload задачи.
- **Разбор — в воркере** (`workers/prx_workers/handlers/prx400_specflow/`):
  чистые функции `parse.detect_template/parse/run_math_checks` — тестируются
  напрямую (golden-корпус в `workers/tests/handlers/prx400_specflow/`).
- **Матчинг и статусы — в PHP** (`Service_Prx400_Match`): воркер отдаёт строки,
  PHP сопоставляет со справочником и расставляет цвета (ok/review/new/error).
  Справочник `prx_400_catalog` — локальный MVP; внешний MDM (endpoint в
  конфиге шаблона) — плановое расширение.
- **Математика — на воркере** (qty*price==sum, Σ==итого, непрерывность №,
  дробные штучные) — флаги едут в `flags` строк, отчёт в `prx_400_specs.math`.
- **Верификация HITL**: карточка — цвета строк, «похожие: код…» подтверждают
  код НСИ одним кликом (set_manual_match), «Завершить проверку» → done.

## Права
`prx400.view` (страницы/файл/экспорт), `prx400.run` (загрузка, верификация,
запуск). Deny by default; ключи в `application/config/acl.php`.

## Внешние контракты
- Канал очереди `specflow.parse` (владелец — этот модуль, манифест `worker`).
- Воркер: `GET /prx400_specflow/worker/<id>/file`, `POST .../result`
  (X-Worker-Token; PHP-сторона — `Controller_Prx400_Worker`).
- Scope API-хаба: `prx400.export` (JSON проверенной спецификации).

## Не делать
- Не складывать текст документа в БД (только sha256 и позиции).
- Не переносить разбор в LLM — сначала исчерпать детерминированные правила.
- SQL prx_400_* — только в `Model_Prx400_*` (стража архитектуры).

## Уроки итераций file_unavailable/no_rows/vision (standing — для агента)

Разбор диалога с владельцем: 11 его вмешательств на ~15 правок. Обобщённые
правила, нарушать которые нельзя:

1. **Эталон-диффинг прежде диагноза.** Корень поломки ищется сравнением с
   РАБОТАЮЩИМ модулем (prx397/prx399/prx390/prx212), а не правкой симптомов.
   Примеры пойманных так корней: URL воркера несёт job_id (prx397: всё по
   `WHERE job_id =`, а не по spec_id); хранение — фасад Storage; owned-методы
   prx212 требуют артефакт БЕЗ пользователя (`_owned_private_file: user_id IS NULL`).
2. **Контракт владельца читать до использования.** AGENTS.md модуля-владельца
   + его гвард-код. Не изобретать семантику («кто действует»).
3. **Диагностика с первого дня.** prx400_diag stage=… на каждой развилке
   (паттерн prx390_diag); лог-маркеры заодно доказывают, что новый код доехал
   до прода (нет `stage=worker_file` — деплой не доехал).
4. **Пустой результат ≠ успех.** Приёмник (`result()`) обязан переводить 0
   строк в failed; семантику валидируют ОБЕ стороны (устойчивость к старому
   воркеру).
5. **Сайт и воркер обновляются порознь.** Изменён workers/ → рестарт воркера
   обязателен (писать ПЕРВОЙ строкой в отчёте о деплое); «ошибка не ушла» →
   сначала проверить версию кода по лог-маркерам, потом искать новый баг.
6. **Финальный аудит многошаговых правок.** После python-replace серий:
   сигнатура+тело каждого затронутого метода (потерянный параметр = 500 в
   проде), сканер undefined-переменных, смоук ПУТИ УСПЕХА (вьюха на живых
   строках — первый успех и упал на JSONB-строке).
7. **JSONB из PDO — строка.** Нормализация (json_decode) на уровне модели
   (Row::for_spec), не вьюхи; экспорт и карточка читают одно место.
8. **Молчаливые дефолты запрещены.** Выбор пользователя (parse_mode)
   хранится на сущности и виден в UI; если параметр нельзя исполнить —
   громкая ошибка, а не тихий downgrade в ocr.
9. **Ремонт — на странице ошибки.** Перезаливка/повтор живут на карточке,
   а не «на странице списка».
10. **Один источник правды статуса.** Индикатор UI (file_ok) = тот же путь
    чтения, что у потребителя (воркер); иначе UI врёт при сломанном чтении.
