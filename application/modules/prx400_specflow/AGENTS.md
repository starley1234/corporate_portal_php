## Что делает
Скан PDF спецификации/BOM → разбор таблицы по семантическому шаблону (ocr —
детерминированно; vision/ocr_vision — мультимодальная LLM по страницам) →
математический аудит → матчинг с НСИ (обозначение → память решений → fuzzy) →
верификация оператором (HITL) → JSON/CSV/XLSX и закупочная ведомость для ERP.
Спецификация — один или несколько PDF (листы), строки — дерево BOM
(`parent_id`, `pos_path` «1.2.3», `level`), у строки файл и страница. Продукт
API-first: всё, что умеет оператор в UI, доступно ключу prx150 (scope review). Каналы входа: UI (сессия + CSRF через Prx_PostGuard),
внешнее API prx150 (ключ + scope), воркер (X-Worker-Token + номер попытки).

## Слои (канон prx397)
- `Controller_Prx400_Ui|Api|Worker` — только HTTP: метод, размер тела, перевод
  `Prx400_Error` в flash/HTTP-статус/JSON. Никакого SQL и бизнес-правил.
- `Service_Prx400_Specs` — жизненный цикл для UI и API (submit/launch/reupload,
  чтение, правки оператора); `Service_Prx400_Pipeline` — протокол воркера
  (lease, приём результата) и обслуживание `maintain()` (prx400:purge).
- `Policy_Prx400_Spec` — единственное место прав: владелец — подписанный ID
  (UI `-user_id`, API-ключ `+key_id`); UI с prx400.view видит всё, ключ — своё.
- `Model_Prx400_*` — весь SQL prx_400_*; JSONB/boolean приводятся в моделях.
- `Service_Prx400_Rows` — HITL-операции над строками для UI и API (verify,
  code, edit, add, delete, split, bulk_verify, listing с фильтрами); правки
  только в review/done, каждая — в `prx_400_edits` (с `row_label`: удалённая
  строка остаётся в журнале).
- `Service_Prx400_Matcher` (партия строк: prime → assess, память
  `prx_400_aliases`), `Service_Prx400_Catalog` + `Prx400_Catalog_Provider`
  (`Local` — prx_400_catalog, `Http` — внешний НСИ, только чтение).
- `Service_Prx400_Notify` (итог разбора: outbox webhook в транзакции + шина
  `prx400.spec.<status>` после COMMIT), `Service_Prx400_Hooks` (подписка
  ключа, HMAC, доставка с повторами, SSRF-страж).
- `Service_Prx400_Match` (матчинг, `row_status`), `Service_Prx400_Checks`
  (построчные флаги), `Service_Prx400_Limits` (единственное чтение конфига),
  `Service_Prx400_Templates`, `Service_Prx400_Export` (+ `Prx400_Xlsx`, без
  ZipArchive) — чистая логика.
- `Prx400_Messages` — тексты кодов для UI; сервис и API оперируют кодами.

## Ключевые решения
- **Хранение — `Storage` (prx212)**: PDF — артефакт модуля без пользователя
  (`Storage::save(..., 'prx400', NULL, ...)`), ссылка — `file_id`, проверка —
  `file_sha256`. Ранние user-загрузки читает fallback `Storage::bytes`
  (WARNING в журнал). `file_id` NULL → на карточке перезаливка.
- **Идемпотентность** приёма — `Prx_Idempotency` (scope `prx400.extract`,
  владелец — подписанный ID; хеш = sha256 файла | режим | шаблон).
- **GET не пишет.** Статус в работе для показа выводит `Specs::effective()`
  из очереди; записывает сверку только `Pipeline::maintain()`.
- **Ошибки — машинные коды** из `Specs::FAILED_CODES`; произвольный текст
  очереди становится `job_failed`. Воркер сообщает терминальный код ОДИН раз
  (`handler.handle`, `{error_code}`); протокольные ошибки не сообщаются.
- **Lease**: воркер шлёт `X-PRX-Worker-Attempt`; PHP сверяет канал, статус
  processing и attempts, а запись — под блокировкой по job_id. Перезапуск/
  удаление отменяют задачу — её результат получает 409 lease_lost.
- **Шаблоны — JSON** (`config/templates/*.json` + пользовательские в БД):
  якоря, `columns.<key>.match`, правила пропуска/итогов/разделов, проверки.
  Библиотека едет в payload задачи (`templates`, `template_id`, `parse_mode`).
- **Импорт НСИ — всё или ничего**: `Service_Prx400_CatalogImport` не обрезает
  значения молча (обрезанный код — чужой код), строка с ошибкой отменяет файл;
  чтение CSV/XLSX — платформенный `Prx_Spreadsheet` (без php-zip), upsert —
  `Model_Prx400_Catalog::upsert_many` под advisory-блокировкой.
- **Матчинг и статусы — в PHP**: воркер отдаёт строки; большой справочник
  предотбирает pg_trgm (`PRX400_MATCH_FULL_SCAN_MAX`), матчинг идёт ДО
  транзакции записи. Порядок: код из обозначения (1.0) → память решений
  оператора (`via: memory`) → нечёткий. Ручной код запоминается (`remember`),
  отзывается на странице «Сопоставления».
- **НСИ — через провайдера.** Код позиции — её идентичность в любом источнике;
  внешний (`PRX400_CATALOG_PROVIDER=http`) только читается, запись → 409
  `catalog_readonly`, сбой → 503 `catalog_unavailable` (не «все строки new»).
- **Несколько PDF — одна спецификация**: `prx_400_spec_files` (file_no 1..N),
  воркер берёт `worker/<job>/file/<n>`, продолжения без шапки — шаблоном
  первого файла, лист без таблицы пропускается (`file_<n>_<код>`).
- **Дерево BOM строит PHP** (`Pipeline::link_tree`): родитель — по префиксу
  `pos_path` в том же файле, иначе по явному уровню (колонка `level`), иначе
  корень. Закупочная ведомость (`Export::aggregate`) не закупает сборки;
  `per_parent` умножает на количество сборок выше.
- **Повторный разбор не теряет работу**: `merge_decisions` переносит
  подтверждения/ручные коды по ключу (наименование|обозначение|кол-во|ед.),
  ручные строки сохраняет, потерянные — `verified_rows_lost`.
- **Webhook — outbox**: событие пишется в транзакции смены статуса,
  доставляет `prx400:hooks` (расписание, каждую минуту); тело — только ссылка.

## Права
`prx400.view` (страницы/файл/экспорт), `prx400.run` (загрузка, запуск,
правки, справочник, шаблоны). Deny by default; ключи в `application/config/acl.php`.
API — scope `prx400.extract` (загрузка, чтение, webhook) и `prx400.review`
(правки строк, подтверждение, повтор, удаление) — манифест `api_scopes`.

## Внешние контракты
- Канал очереди `specflow.parse` (манифест `worker`), приоритет 40.
- Воркер: `GET /prx400_specflow/worker/<job_id>/file/<n>` (без `<n>` — файл 1,
  старые воркеры), `POST .../result` (тело ≤ `PRX400_MAX_RESULT_BYTES`; строки
  с `pos_path`/`level`/`page`/`file_no` или `{error_code}`). Payload задачи —
  `files: [{file_no, sha256, name}]`.
- API: `/api/v1/spec-extractions(/<id>(/rows|export|files|verify-bulk|relaunch|finish))`,
  `/webhook`, `/api/v1/spec-catalog` — полный список в докблоке `Controller_Prx400_Api`.
- Внешний НСИ: `GET {url}/search?q=&limit=` → `{items}`, `GET {url}/items/<code>`.
- Расписание: `prx400:hooks` (доставка webhook). Качество: `prx400:eval
  [--days=30]` (бой, по журналу); парсер — корпус
  `workers/tests/handlers/prx400_specflow/eval/` + `evaluate.py` (гейт в pytest).
- Расписание: `bin/console prx400:purge` (манифест `schedule`, исполняет
  `portal:maintain`): сверка с очередью, автоповтор после падения воркера
  (`recover`, причина — только `Service_Prx120_JobQueue::stop_reason`, тексты
  ошибок prx120 здесь не разбирать), срок хранения, осиротевшие файлы.

## Уроки итераций file_unavailable/no_rows/vision (standing — для агента)

Разбор диалога с владельцем: 11 его вмешательств на ~15 правок. Обобщённые
правила, нарушать которые нельзя:

1. **Эталон-диффинг прежде диагноза.** Корень поломки ищется сравнением с
   РАБОТАЮЩИМ модулем (prx397/prx399/prx390/prx212), а не правкой симптомов.
   Примеры пойманных так корней: URL воркера несёт job_id (prx397: всё по
   `WHERE job_id =`, а не по spec_id); хранение — фасад Storage; owned-методы
   prx212 требуют артефакт БЕЗ пользователя (`_owned_private_file: user_id IS NULL`).
2. **Контракт владельца читать до использования.** AGENTS.md модуля-владельца
   + его гвард-код. Не изобретать семантику («кто действует»).
3. **Диагностика с первого дня.** `prx400 spec=… stage=…` на каждой развилке
   (паттерн prx390_diag); лог-маркеры заодно доказывают, что новый код доехал
   до прода (нет `stage=worker_file` — деплой не доехал).
4. **Пустой результат ≠ успех.** Приёмник (`store_result()`) обязан переводить 0
   строк в failed; семантику валидируют ОБЕ стороны (устойчивость к старому
   воркеру).
5. **Сайт и воркер обновляются порознь.** Изменён workers/ → рестарт воркера
   обязателен (писать ПЕРВОЙ строкой в отчёте о деплое); «ошибка не ушла» →
   сначала проверить версию кода по лог-маркерам, потом искать новый баг.
6. **Финальный аудит многошаговых правок.** После python-replace серий:
   сигнатура+тело каждого затронутого метода (потерянный параметр = 500 в
   проде), сканер undefined-переменных, смоук ПУТИ УСПЕХА (вьюха на живых
   строках — первый успех и упал на JSONB-строке).
7. **JSONB из PDO — строка.** Нормализация (json_decode) на уровне модели
   (Row::for_spec), не вьюхи; экспорт и карточка читают одно место.
8. **Молчаливые дефолты запрещены.** Выбор пользователя (parse_mode)
   хранится на сущности и виден в UI; если параметр нельзя исполнить —
   громкая ошибка, а не тихий downgrade в ocr.
9. **Ремонт — на странице ошибки.** Перезаливка/повтор живут на карточке,
   а не «на странице списка».
10. **Один источник правды статуса.** Индикатор UI (file_ok) = тот же путь
    чтения, что у потребителя (воркер); иначе UI врёт при сломанном чтении.
11. **Корпус — до «улучшений» парсера.** Первый же прогон eval (5 документов)
    нашёл три боевых дефекта, которых не видели юнит-тесты: универсальный
    шаблон обходил узкий по сырому числу якорей (теперь — доля), выгрузка SAP
    не детектилась, пустая ячейка сдвигала колонки (выравнивание по шапке).
    Новый тип документа, на котором ошиблись, — сначала в корпус.
12. **Model не зовёт Service** (portal_check Д8): нормализацию запроса
    (написания марок) строит сервис и передаёт в модель готовыми словами.
13. **Счётчики API — в словаре фильтров.** `counts` ключами `?filter=`
    (all/disputed/…), иначе клиенту нечем связать вкладку и число.
14. **`updated_at` — время результата, не активности.** Правки строк его не
    трогают (это `processed_timestamp` выгрузки); всё, что решает «запись
    жива» (срок хранения), смотрит и в `prx_400_edits`. Удаление по условию —
    одним `DELETE … WHERE <условие>`, а не «выбрал → удалил».
15. **Форма входа — на границе.** `(string)` от массива в Kohana = 500;
    `Prx400_Input::scalars` в `Api::input()`/`guard_query()` и `Ui::before()`.
16. **Цикл доставки ловит исключение на элемент**, иначе один битый элемент
    останавливает пачку и крутится в аренде без счёта попыток.
