# prx399_docmerge — слияние договоров и допсоглашений

Образцово-показательный модуль: демонстрирует КАЖДЫЙ слой платформы в канонном
исполнении. Читается как учебник — от миграции до воркера; следующий модуль
пиши по этому файлу, как по чек-листу.

## Идея (0 фраз на маркетинг)

Пакет = базовый договор (PDF) + цепочка ДС (PDF). Пайплайн:

    [PDF: договор + ДС] → OCR/текстовый слой → AST (без LLM)
                        → дельты ДС (LLM, изолированно по каждому ДС)
                        → ДЕТЕРМИНИРОВАННАЯ сборка (PHP, без LLM)
                        → риск-аудит (LLM, Map-Reduce по темам)
                        → редакция + diff + матрица рисков + паспорт сделки

Ключевой принцип: **модель предлагает, код распоряжается**. Текст документа
собирается строковыми операциями по инструкциям (`replace/add/annul` + якорь),
поэтому «галлюцинация» физически не может попасть в итоговую редакцию;
повторный build на тех же входных байт-в-байт совпадает.

## Границы (нарушать нельзя)

- Таблицы только `prx_399_*` (владелец — модуль); чужих JOIN нет — перекрёстное
  чтение только доверенными методами, как `headers_for_processing` (prx391).
- UI — `prx399.view` (просмотр) и `prx399.run` (действия); ключи объявлены в
  `application/config/acl.php`, lint следит за использованием.
- API воркера не знает про сессии: `X-Worker-Token`
  (`PRX399_SITE_TOKEN → WORKER_SITE_TOKEN → WORKER_API_TOKEN`), пустой токен
  закрывает API. Worker-результат валидируется СТРОГО (схема опов/рисков) —
  «модель ошиблась» = отклонённая дельта, а не тихий мусор в БД.
- Промпт дельты не получает весь договор: только карточку сделки
  (Contract Scratchpad, 200–300 токенов) и текст ДС — изолированный анализ.

## Состояния и идемпотентность

- контракт: `draft → parsing → auditing → audited`; `failed` — честная остановка
  (сборка НЕ делается «из того, что есть» — частично собранный договор опаснее).
- файл: `queued → working → parsed | failed`; повторный `delta_result` того же
  файла перезаписывает данные (idempotent delivery).
- сборка под `pg_advisory_xact_lock(399, contract_id)` — два параллельных
  результата ДС не дают двух сборок; последний закрывший файл ставит аудит.
- перестановка ДС (`move_ds`) возможна только в `draft/failed` — ординалы
  образуют хронологию применения.

## Diff-семантика узлов (doc_tree)

`node.status`: `base` — исходный; `added` — новый пункт из ДС (номер = первый
свободный ребёнок родителя, БЕЗ модели); `changed` — текст заменён (прежний
сохранён в `node.history`); `annulled` — исключён вместе с поддеревом (текст в
history, живой текст пуст → ссылка на такой пункт станет «битой»: это фича).

## Битые ссылки — гибридная валидация

Ссылки (`п. 4.2`, `раздел 2`, `статья 5`) находит РЕГУЛЯРКА в PHP
(`Service_Prx399_Merge::_validate_links`) и независимый дубль-контур в воркере
(`ast_text.references`) — без расхода модели. Битая ссылка = риск
`source='static', severity=high`. Смысловые противоречия — работа LLM-аудита
(Map по тематическим чанкам `chunks.py`, Reduce: дедуп + паспорт сделки).

## Урок платформы: никаких BOOLEAN-колонок

PDO/pgsql отдаёт BOOLEAN строкой `'t'/'f'`, `(int) 't' === 0` — инцидент prx102
26.11.2026. В prx399 статусные колонки — VARCHAR, булевых нет вообще; если
когда-нибудь понадобится булево — читать только через предикат
(`Model_Prx102_User::is_active`, `Service_Prx597_Base::_truthy`).

## Проверки

- `make check` — manifest_check (манифест), acl_lint (ключи), portal_check
  (каналы `doc.merge.delta`/`doc.merge.audit` в whitelist + reconcile),
  route_registry, php_lint.
- `PYTHONPATH=workers python3 -m pytest workers/tests/handlers/prx399_docmerge/`
  — 22 теста: парс AST, схема дельт (зеркало PHP-валидации), тематические чанки,
  sync лимитов с workers/.env.example, e2e с фейк-LLM (без сети и БД).
- Лимиты: PHP (`prx399_docmerge.php`) ↔ воркер (`limits.py`) ↔
  `workers/.env.example` — три места, один контракт, тест держит их вместе.
