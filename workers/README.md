# Python-воркеры N2J

Асинхронные исполнители фоновых задач платформы: LLM, эмбеддинги, файлы и всё
долгое. Очередь — таблица `nj_120_jobs` в PostgreSQL (модуль `nj120_jobs`).

> **Агентам:** новый канал = новый файл в `n2j_workers/handlers/` +
> строка в `handlers/__init__.py`. Правила написания — `docs/WORKERS.md` (корень).

## Запуск

```bash
cd workers
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env          # настроить DSN/эндпоинты
python -m n2j_workers                     # все каналы
WORKER_CHANNELS=echo python -m n2j_workers
```

> `.env` в git не хранится (секреты). `bin/setup.sh` создаёт его из шаблона
> автоматически и вписывает `WORKER_SITE_TOKEN` = `WORKER_API_TOKEN` сайта;
> если файл пропал — просто запустите `bash bin/setup.sh` ещё раз.
> Персональные `NJxxx_*_SITE_TOKEN` перекрывают общий `WORKER_SITE_TOKEN`.

Docker (из корня репозитория): `docker compose --profile workers up -d`.

## Самопроверка очереди

1. С монолита поставить задачу:
   ```php
   // bin/console eval не существует — проверьте через любой контроллер/тась:
   Service_Nj120_JobQueue::push('echo', ['hello' => 'world']);
   ```
2. Воркер подхватит и вернёт результат в `nj_120_jobs.result`:
   ```sql
   SELECT id, channel, status, result FROM nj_120_jobs ORDER BY id DESC LIMIT 5;
   ```

## Структура

| Файл | Назначение |
|---|---|
| `__main__.py` | точка входа (`python -m n2j_workers`) |
| `config.py` | конфиг из окружения / `.env` |
| `queue.py` | клиент очереди: `PgQueue` (asyncpg, LISTEN/NOTIFY) или `HttpQueue` (токен) |
| `base.py` | цикл воркера: claim → handler → complete/fail, heartbeat, таймауты |
| `llm.py` | клиенты LLM-шлюза и **отдельного эмбеддинг-сервера** |
| `logs/` | плоский ротируемый лог `n2j-worker.log` (в git не хранится; см. «Логи») |
| `handlers/` | каналы: `echo`, `embeddings.index`, `llm.summarize`, `review_reply` («Отзыв 2 Ответ», LangChain), `job_search` («Работа 2 Оффер», ddgs+LangChain) + ваши |

## Логи: что прислать при разборе

Воркер пишет в два места: в stderr (в бою его ведёт systemd → `journalctl -u n2j-worker`)
и в **один простой файл** в корне воркеров:

```
workers/logs/n2j-worker.log      # текущий лог (видно глазами, режется grep)
workers/logs/n2j-worker.log.1    # архивы: .1 … .5, по 5 МБ каждый
```

Что в нём есть: старт воркера и состав каналов, начало/конец каждой задачи,
падения и таймауты задач, сбои модели, доставка результата (`доставлено=true/false`)
и ответы сайта целиком — например `site: POST /label/api/worker_result -> HTTP 500:
приёмка результата упала: Database_Exception: …` или `HTTP 403: Неверный токен воркера`.

Это файл для владельца: при инциденте достаточно прислать его целиком — он
покрывает и причину на стороне воркера, и то, что ответил сайт.

Настройки (`workers/.env`, все необязательные):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `WORKER_LOG_ENABLED` | `1` | `0` — только stderr (как было раньше) |
| `WORKER_LOG_FILE` | `logs/n2j-worker.log` | путь к файлу |
| `WORKER_LOG_LEVEL` | `INFO` | `DEBUG`…`ERROR` |
| `WORKER_LOG_MAX_MB` | `5` | размер файла до ротации |
| `WORKER_LOG_BACKUPS` | `5` | сколько архивов хранить |
| `WORKER_LOG_QUIET` | `httpx` | чьи INFO/DEBUG не писать вообще (логгеры через запятую; пусто — писать всё) |
| `WORKER_LOG_SKIP` | `/nj120/api/claim` | подстроки сообщений, которые не пишем (через запятую; WARNING и выше проходят всегда) |
| `WORKER_IDLE_MAX_SEC` | `10` | потолок затихания опроса очереди при простое: пауза удваивается от `WORKER_POLL_INTERVAL` до этого значения и сбрасывается на первой задаче. Это же значение — задержка старта задачи в http-режиме (в pg-режиме будит LISTEN/NOTIFY) |

Почему про шум отдельная строка. `httpx` пишет INFO на **каждый** HTTP-запрос,
а воркер постоянно опрашивает очередь — файл лога заполнялся строками вида
`INFO httpx: HTTP Request: POST https://…/nj120/api/claim "HTTP/1.1 200 OK"`
(≈720 строк в час на один простой воркер) быстрее, чем полезными событиями.
Теперь: INFO `httpx` не пишется вовсе (`WORKER_LOG_QUIET`), сам эндпоинт
`/nj120/api/claim` можно исключить точечно (`WORKER_LOG_SKIP`) — это полезно,
если вы хотите видеть запросы httpx, но не рутину опроса, — а при простое
очереди пауза опроса растёт до `WORKER_IDLE_MAX_SEC`. Ошибки опроса (уровень
WARNING и выше) проходят через фильтр всегда: «claim вернул 500» — не шум.

`/nj120/api/claim` — это и есть «дай задачу»: воркер спрашивает очередь, пока
в ней пусто. Больше запросов нет, пока нет задач; во время работы тот же путь
только у `complete`/`fail`/`progress`/`heartbeat`.

Если процессов воркера несколько, у каждого должен быть свой файл
(`WORKER_LOG_FILE=/var/log/n2j/worker-1.log`): ротация в Python считается по
размеру и два процесса в один файл писать не должны.

Парная сторона — лог сайта `application/logs/n2j-site.log` (класс
`Log_Plain`): одна строка на событие, там же приёмка результатов прогонов.
Сверяя два лога, видно, чей это был отказ — воркера, сайта или модели.

```bash
tail -f workers/logs/n2j-worker.log
grep -E "HTTP 4|HTTP 5|упал|не принял" workers/logs/n2j-worker.log
```

## Если задача «висит» (пульс есть, движения нет)

Воркер закрывает зависания четырьмя независимыми слоями — снизу вверх:

| Слой | Что делает | Настройка (по умолчанию) |
|---|---|---|
| Парсинг в потоке | `webread.to_markdown()` — async-обёртка (`asyncio.to_thread`); синхронный разбор HTML прямо в event loop запрещён: он морозит пульс и таймауты ВСЕХ задач воркера | лимит разбора `WEBREAD_PARSE_LIMIT_BYTES` (1 МБ), `WEBREAD_MAX_PAGE_BYTES` (3 МБ) |
| Сторожевой поток | Раз в 5 с снимает задачи, вышедшие за `timeout_sec + запас`, и синхронно пишет `failed` в очередь — работает, даже когда цикл заморожен | `N2J_JOB_HARD_GRACE` (180 с), `N2J_HARD_WATCHDOG_SEC` (5 с) |
| Диагностика лага | Если цикл стоял дольше 5 с, в журнал пишется «Event loop был занят N с» + какие задачи держали слот | `N2J_LOOP_LAG_WARN` (5 с) |
| Остановка процесса | SIGTERM (рестарт, обновление сайта) — ждём текущие задачи не дольше grace-секунд, остальным ставим **понятный финал** («воркер остановлен — запустите заново»), а не оставляем строку `processing` | `N2J_STOP_GRACE_SEC` (60 с, меньше systemd `TimeoutStopSec`) |
| Перезапуск процесса | Если цикл молчит дольше 15 минут при активных задачах — задачи закрываются, процесс выходит (`os._exit(9)`), systemd поднимает воркер заново | `N2J_LOOP_STALL_EXIT` (900 с, `0` = выключить) |

Сироты прошлого запуска (процесс убили — OOM, деплой) закрываются на старте:
`Nj120\JobQueue::release_mine()` через `POST /nj120/api/release_mine` (HTTP-режим)
или одноимённым SQL в `PgQueue.release_own_orphans()`. Задача с оставшимися
попытками возвращается в очередь сразу, с исчерпанными — честно проваливается
(иначе был бы вечный цикл «упал → вернул → снова упал»).

Долгие этапы ИИ идут под тикером (`n2j_workers/llmwatch.py`): пока модель
думает, в статус-ряд уходит «модель думает N с (лимит M с)…», а по исчерпании
лимита вызов снимается и задача закрывается понятной причиной. Тот же приём —
в сборке обзоров GitHub (nj593) и в потоке заказчиков (nj606, лимит
`NJ606_LEADS_LLM_TIMEOUT`, по умолчанию 420 с). Молчащий этап ИИ — самый частый
вид «зависло»: снаружи не отличить работу модели от мёртвой задачи.

Так же устроен `semantic.index` (запись векторов, модуль nj115): этапы
«Проверяю коллекцию» → «Считаю векторы N текстов» (под тикером, лимит
`NJ115_EMBED_TIMEOUT`, 180 с) → «Записываю векторы i/N» → «Готово: N векторов».
Соединение с базой на время внешнего вызова эмбеддинг-сервера НЕ держится
(иначе пул обработчиков выедается и «висит» уже соседняя задача), ожидание
свободного соединения ограничено 20 с, а недоступный сервер даёт внятную
ошибку вместо тишины. Массовый наполнитель базы знаний (nj560) ставит одну
задачу на 32 документа, а не по задаче на каждый.

Правила «пульс есть, работы нет» на СТОРОНЕ САЙТА (видит и гасит сам):

| Правило | Порог | Настройка |
|---|---|---|
| Пульса нет | `N2J_SILENT_STOP_SEC` — ровно он, без «или timeout_sec/4» | 240 с |
| Пульс есть, прогресс не обновлялся | `Nj120\JobQueue::auto_stop_stalled()` | `N2J_STALLED_PROGRESS_SEC` (600 с) |

Оба порога заданы в одном месте (`JobQueue::silent_stop_sec()` /
`stalled_progress_sec()`) и используются модулями (nj602/nj605/nj606) при
поллинге статус-ряда — раньше в каждом месте было своё «240», а множитель
`timeout_sec/4` отодвигал остановку на 15-25 минут для длинных каналов.

Отмена со стороны сайта (кнопка «Прервать» в модуле, авто-стоп молчащего воркера,
перехват задачи другим воркером) тоже приходит через heartbeat: два отказа подряд →
`_cancel_lost_job()` отменяет asyncio-задачу, и воркер освобождает слот, ничего не
записывая в очередь (статус там уже проставлен сайтом).

Что смотреть, когда владелец говорит «зависло»:

```bash
journalctl -u n2j-worker -n 200 | grep -E "Сторож задач|был занят|заморожен|прошлого запуска"
```

## Отдельный сервер воркеров

Воркеру не нужен доступ к БД: `WORKER_QUEUE_MODE=http`, `NJ120_API_URL` и
`WORKER_API_TOKEN` — и он работает через HTTP-API монолита. Миграции на
сервере воркеров не выполняются никогда.

## Требования

Python ≥ 3.11 — заявленная версия пакета (`pyproject.toml`), зависимости —
`requirements.txt`. Общий цикл и обработчики Solid3D используют
`asyncio.wait_for`, без вызова `asyncio.timeout` (этого API нет в Python 3.10).
Регрессия `tests/test_nj669_timeout.py` проверяет именно отсутствие этого API,
дедлайны, отмену и учёт ресурсов; это не полная сертификация пакета на Python 3.10.


### Диагностика отказа приёмной Solid3D

`NJ669_API_BASE=https://n2j.ru/solid3d/w` задаёт модульную базу;
`NJ120_API_BASE=https://n2j.ru` — общий корень, без `/solid3d/w`.
В `context` запрос уходит на `/solid3d/w/context`, не на базовый `/solid3d/w`.
Общий `site.py` включает в ошибки HTTP фактический URL без userinfo/query/fragment;
HTML-страницу 404 не копирует в ошибку. Это помогает отличить удвоенный путь
от отсутствующего маршрута/устаревшего PHP-кода сайта. Токены не присылать.
Сценарий `tests/test_nj669_http.py` проверяет конечные адреса, JSON, multipart,
диагностику 404 и скрытие секретных частей URL. Контракт старых собственных
`*_API_BASE` не меняется: они по-прежнему перекрывают общий адрес полностью.
